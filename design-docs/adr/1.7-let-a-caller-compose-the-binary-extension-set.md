# Let a caller compose the binary extension set

- **Status:** accepted
- **Date:** 2026-10-13
- **Initiative:** `01-kartta-fs-port`

The extensions that settle a file as binary without the file being read are a set a caller composes, not a fixed
list. `BinaryExtensions` is built from the named built-in `BinaryGroup`s and the caller's own extensions, combined with
`union` and `difference`, and it travels on `BuildOptions`. The default is every built-in group.

A public crate meets two kinds of project the fixed list cannot serve. One has asset formats the list does not know —
a studio's packed archives, an engine's compiled meshes. The other disputes what the list holds: one entry, such as
`svg` for a project that wants its vector art searchable, or a whole group, such as one studio's engine formats in a
tree that has none of them. `difference` serves the second kind: removing one extension and removing a whole group are
the same operation.

The set belongs to the index, not to a query. The index caches each file's classification on the first ask, a verdict
settled by the name included, so one set per index is what keeps that cache answering by one policy.

## Refused and absent are different things

An entry that no extension of any file name can equal is refused by name: an empty one, one holding a dot past its
first character (only the last extension of a name is compared, so `tar.gz` would never match — `gz` already does),
and one holding `/` or a NUL. An extension that is merely absent from a tree is accepted silently. Most of the built-in
set is absent from any one tree, so treating absence as a mistake would make the defaults unusable.

Silence hides one real mistake: a misspelled extension in a caller's own set classifies nothing and says nothing.
`Index::binary_extension_counts` reports how many files each extension settled, from the names alone, so a count of
zero on an extension the caller added is where a misspelling shows.

## What it costs

`BuildOptions` is no longer `Copy`, because the set owns the caller's extensions. A set compares and hashes by its
members rather than by how it was composed, so two configurations that differ only in how their sets were built compare
equal — which is what a cache keyed on a configuration needs.

## Considered Options

- **A fixed list** — the shape the crate started with. It serves neither a project with formats the list lacks nor one
  that disputes an entry.
- **A pair of constructors: extend the built-in list, or replace it** — answers "add my formats" and "own the whole
  list", and cannot say "remove this one". Removing `svg` would mean replacing the list, restating every built-in
  extension by hand and then missing every one a later version adds. An extend or replace mode at a serialization
  boundary maps onto the chosen shape: extend is the built-in set `union` the caller's, replace is the caller's alone.
- **The set as an argument of each query** — two sets over one index would leave the per-entry cache answering by
  whichever set asked first.
- **Refusing an extension no file carries** — the built-in set would then fail on almost every tree.

Revisit if a caller needs a classification rule richer than a name's last extension, such as a compound suffix or a
path prefix.
