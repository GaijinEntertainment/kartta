# Bind a Python bare call by the scope that binds its name

- **Date:** 2026-10-16
- **Governs:** `crates/kartta-lang-python/src/walk.rs` (`Frame`, `Binding`, `close`, `scope_frame`,
  `drop_builtin_calls`), `crates/kartta-lang-python/src/runtime.rs` (`BUILTINS`)
- **Pinned by:** `crates/kartta-lang-python/tests/extract.rs` (the `local_calls` module and
  `a_bare_call_of_a_builtin_*`), `crates/kartta-languages/tests/engine.rs`
  (`a_python_call_of_a_builtin_binds_a_namesake_only_where_its_file_imports_it`)

Python binds a name for the whole of the scope that binds it, and the graph's cascade
([ADR 3.172](/design-docs/adr/3.172-bare-call-binding.md)) binds a
recorded call by its name alone. The Python walk
([ADR 3.12](/design-docs/adr/3.12-python-qualified-names.md)) decides each bare call by Python's own scoping
before the graph sees it: a call of a definition its scope holds becomes a local call, and a call of a value, or of a
builtin no scope binds, records nothing. The walk keeps no order of execution, so where a scope binds a name two ways
it picks by kind, not by line.

## Decision

- **When a call is decided.** A bare call is decided when the walk leaves a scope, because a name binds for the whole of
  that scope: first the scope that makes the call, then each function around it, a class body skipped, as the
  interpreter resolves a free name. A call made in a class body sees the names that body binds, and a function nested in
  it does not. The first iterable of a comprehension, and a class's bases, are looked up in the scope around them.
- **What binds a name.** A nested `def` or `class` binds its name to itself. A parameter, an assignment, a `for`, `with`
  or `except` target, a `case` capture, a comprehension's or a lambda's variable and an assignment expression bind the
  name to a value; an assignment expression in a comprehension binds it in the scope around the comprehension. An import
  binds it to the import. A `global` declaration sends the name to the module, and a `nonlocal` one past the scope that
  declares it.
- **Two bindings in one scope.** Where one scope binds a name more than one way, an import or a `global` declaration
  wins, then a `nonlocal` one, then a definition, then a value: of `def f` and `f = wrap(f)`, the definition is the
  target, and of an import and an assignment of `None` in an `except`, the import. Of two definitions of a name in one
  scope, the later is the target, as the later `def` rebinds the name.
- **Local calls.** Where the scope that decides a call binds its name to a definition, and that scope is a function or
  lies inside one, the call is a local call to that definition, made by the call's own caller: a class inside a function
  makes the local calls of its body. A definition in a class body at module level is no local, and a call of it there is
  recorded as a call.
- **Calls of values.** Where a function, a class body or a comprehension that decides a call binds its name to a value,
  the call records nothing, as a computed callee, `handlers[0]()`, does, so a walk over callees does not count it among
  the calls it could not resolve.
- **Calls for the graph.** A call whose name no scope around it binds, or binds to an import or the module, is recorded
  as a call for the graph to resolve across files: a call from a function of a name assigned at module level is
  recorded. A bare call at module level, outside every function and class, is recorded whatever the module binds its
  name to.
- **Builtins.** A bare call of a name of Python 3's `builtins` module, its functions, types and exceptions and the ones
  `site` adds, that no scope around it binds and the module binds nowhere, by a definition, an import or an assignment,
  records nothing, wherever it is made: `list(items)` reaches the builtin. The walk does not infer the names a wildcard
  import binds, so the call records nothing even where the wildcard's module defines the builtin's name.

## Why

- The graph knows no Python scope, and a bare call of a nested definition bound by its name alone takes a namesake: of
  the 1,471 local calls on the 1,215 Python files of the game-engine tree, 78 bound a function of the same name in
  another file that way (2026-10-17, #58).
- A parameter, `chunk_fn(source, tags)`, or a name a function assigns holds a value that no symbol of the graph is, so
  binding its call by name binds a function that only shares the name: 52 of the 786 such calls on that tree had bound
  a definition, each through a parameter or an assigned name, `cls(...)` in a class method among them (2026-10-17, #58).
- A definition is what a scope that binds a name both ways means: each of the 8 such calls on that tree reaches the
  definition, made after a `def` that follows an unrelated assignment or after an `if` whose other branch assigns it
  (2026-10-17, #58). An import wins because it reaches its module whenever it succeeds.
- Python looks a name its scopes and its module do not bind up in `builtins`, so such a call of a builtin's name never
  reaches a function of another file, and the graph's one-callable tier bound it to any namesake: all 455 pairs that
  the rule unbinds on the game-engine tree, each a `list()` bound to a web route handler, were false (2026-10-24, #463).

## Consequences

- The walk keeps the names each open scope binds until it closes, about 2% of extracting Python on one thread. Accepted.
- A call made before an assignment of the same name in its scope, or after a `def` the scope later rebinds, takes the
  stronger binding rather than the one in force at the call. Accepted.
- A builtin's call counts among no function's unresolved callees: 21,876 of the 112,351 Python call sites on the
  game-engine tree. A builtin's name that a module rebinds through a wildcard import or `globals()` loses its calls.
  Accepted.

## Rejected

- **Binding a nested definition by its name anywhere in its file** — a call in one function would bind a definition of
  the same name nested in another: on the game-engine tree, 26 nested definitions that share a name with one nested in
  an earlier function of the same file would lose their callers to it.
- **Keeping a builtin's call in a file with a wildcard import** — keeps 52 of the 455 false pairs on the game-engine
  tree, and none of the 20 files' wildcard modules binds the name (2026-10-24, #463).
- **Recording no bare call of any name the module binds nowhere** — outside a file with a wildcard import, such a call
  of a name that is no builtin can only raise `NameError`, but of the 167 pairs such calls reach in another file on
  the game-engine tree, 166 sit in a file whose wildcard import may bind the name, and the rule would unbind 1
  elsewhere (2026-10-24, #603).
- **A list of builtins in the language's conventions for the graph's tiers to hold back** — the graph sees no
  assignment and no import inside a function, which the walk already reads, and adds a convention for one language.

## Revisit if

A real tree shows the stronger binding of a scope wrong at the call often enough to need an order of execution. Each
of the 8 calls the game-engine tree holds of a name bound both ways reached the definition.
