# Return the memory a build freed to the system

- **Date:** 2026-10-17
- **Governs:** `crates/kartta-fs/src/index.rs` (`release_freed_memory`), `crates/kartta/src/engine.rs`
  (`release_freed_memory`), `kartta_fs::Index::build`, `kartta_fs::Index::refresh`, `kartta_fs::Index::refresh_paths`,
  `kartta::Engine::build`

A build allocates far more than it keeps, and glibc keeps what a thread frees in that thread's arena, so a build left
its whole peak resident. On Linux with glibc the library ends each build with `malloc_trim(0)` and changes nothing else
about the allocator; a scoped refresh does not trim, and off glibc, musl included, nothing runs.

## Decision

- **Where it trims.** On Linux with glibc, `kartta_fs::Index::build` and `Index::build_with` call `malloc_trim(0)` once
  the index is built, and `Index::refresh` once the index it replaced is dropped. `kartta::Engine::build` trims once
  its graphs hold every extraction, so an engine build trims twice.
- **What a trim reaches.** It returns the free pages of every arena in the process, the caller's own included, and holds
  each arena's lock while it trims that arena.
- **What it does not trim.** `Index::refresh_paths` does not trim, unless it walks the whole tree as `Index::refresh`.
  Off Linux with glibc the trim compiles to nothing.
- **Nothing else.** The library crates set no global allocator and call no `mallopt`. The C ABI's archive sets none
  either, as [ADR 4.31](/design-docs/adr/4.31-c-abi-allocator.md) states.
- **Extractions.** [ADR 1.67](/design-docs/adr/1.67-extraction-memory.md) states how an engine build holds its
  extractions.

## Why

- glibc hands pages back to the system only from the top of a heap: a cold engine build of the C++ game-engine tree in
  a glibc container limited to 4 CPUs left 1,654–1,818 MB resident without a trim and 612–621 MB with both trims
  (2026-10-17).
- The index build's trim lowers the engine build's peak: resolution inserts each batch into the graphs on the calling
  thread, whose arena cannot reuse the pages the walk's threads freed into theirs, so without it the graphs grow on top
  of the walk's freed pages.
- Which allocator a process runs, how many arenas glibc makes and where its thresholds sit are choices for the whole
  process, so they belong to the program that links these crates. A trim at the end of a build undoes none of them: it
  returns the free pages the arenas hold at that moment.
- A scoped refresh frees one copy of the index's per-entry arrays, which its next call allocates again, and a series of
  them does not grow: over 2,000 one-file refreshes and 50 whole ones of the game-engine tree, the heap grew
  1.5–1.6 MiB by the first whole refresh and 0.1–0.4 MiB over the 49 after it (2026-10-21, #163).
- musl hands freed memory back without a trim, so the consumer that ships, Kensai's static musl binaries over the C ABI,
  needs none.

## Consequences

- The trims cost time, and a thread of the process that allocates from an arena waits while that arena is trimmed: both
  trims of an engine build took 35–60 ms on the game-engine tree, about 0.2% of the build. Accepted.
- A glibc consumer that runs `Index::refresh_paths` gets no trim from it. Accepted: a series of scoped refreshes ended
  3–21 MiB below where its build left it on Linux.

## Rejected

- **Trim only after the engine build** — the same memory resident afterwards, and the peak of a build without a trim.
- **Trim only after the index build** — the lower peak, but the extractions' decodes stay resident: 0.87–0.95 GB on the
  game-engine tree.
- **Set the allocator up: a global allocator, or `mallopt` for fewer arenas or a lower trim threshold** — each is a
  choice for the whole process made inside a library, and a consumer that made its own would find it overridden.
- **`malloc_zone_pressure_relief` on macOS** — released nothing after either tree's build.
- **Lower the build's live peak instead** — the gap between the resident peak and the live heap is pages the allocator
  keeps, not data the build holds, and with both trims the resident peak is the walk's.
- **Trim after each scoped refresh** — a series of refreshes does not grow, so it has nothing to return. Not built.

## Revisit if

A consumer's resident memory grows across scoped refreshes. High confidence: a series of 2,000 did not grow on macOS,
glibc or musl, through the Rust API or the C ABI.
