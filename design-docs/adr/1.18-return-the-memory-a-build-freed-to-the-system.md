# Return the memory a build freed to the system

- **Status:** accepted
- **Date:** 2026-10-17
- **Revised:** 2026-10-18
- **Initiative:** `01-kartta-fs-port`

The engine's consumers run it on Linux under glibc: one calls it from Go through cgo, in containers with a 4-CPU quota,
so Rust allocates through the system's `malloc`. A build allocates far more than it keeps. Profiled on macOS, an engine
build of the C++ game-engine tree allocated 10.0 GB in all and held 622 MB once done, and its live heap peaked at
658 MB, late in resolution; the Go monorepo allocated 5.6 GB, held 293 MB and peaked at 375 MB. glibc keeps what a
thread frees in that thread's arena and hands pages back to the system only from the top of a heap, so a cold engine
build of the game-engine tree in such a container left 1.65–1.82 GB resident, all of its peak, and one of the monorepo
0.74–0.78 GB.

**A build ends with `malloc_trim(0)` on Linux with glibc.** `kartta_fs::Index::build` and `Index::build_with` trim
once the index is built, `Index::refresh` once the index it replaced is dropped, and `kartta::Engine::build` once its
graphs hold every extraction. An engine build therefore trims twice, and the first trim lowers its peak: resolution
inserts each batch into the graphs on the calling thread, whose arena cannot reuse the pages the walk's threads freed
into theirs, so without that trim the graphs grow on top of the walk's freed pages. The trim returns the free pages of
every arena in the process, the caller's own included, and holds each arena's lock while it trims that arena.

**The library trims after its own work and changes nothing else about the allocator.** Which allocator a process runs
on, how many arenas glibc makes and where its thresholds sit are choices for the whole process, so they belong to the
program that links these crates: none of them sets a global allocator or calls `mallopt`. A trim at the end of a build
undoes nothing the process chose: it returns whatever free pages the arenas hold at that moment, and the process takes
pages from the system again only as it allocates.

`Index::refresh_paths` does not trim, unless it walks the whole tree as `Index::refresh`. A scoped refresh walks only
the parts it names, and what it frees is one copy of the index's per-entry arrays, which its next call allocates again.

## What it costs

Measured on Linux in a container limited to 4 CPUs (aarch64, glibc 2.41), cold engine builds of all sixteen languages
without a content cache, interleaved rounds. Resident memory is `VmRSS`, the peak `VmHWM`, after the build:

| | game-engine tree (182,714 entries) | | Go monorepo (70,011 entries) | |
| --- | --- | --- | --- | --- |
| | peak | resident | peak | resident |
| no trim | 1,654–1,818 MB | 1,654–1,818 MB | 739–789 MB | 739–781 MB |
| a trim after the engine build | 1,602–1,910 MB | 629–643 MB | 701–789 MB | 357–364 MB |
| a trim after the index build | 1,484–1,530 MB | 867–952 MB | 591–616 MB | 584–616 MB |
| both | 1,206–1,494 MB | 612–621 MB | 608–610 MB | 354–365 MB |

The index build's trim took 22–46 ms on the game-engine tree and 10–13 ms on the monorepo, and the engine build's trim
after it 13–15 ms and 10–12 ms; alone, the engine build's took 32–39 ms and 18–24 ms. Against `main`, four further
interleaved rounds of each, on a host loaded by a concurrent profile, put the game-engine tree at 630–650 MB resident
after the build against 1,341–1,794 MB, its peak at 1,468–1,628 MB against 1,529–1,794 MB and its build at 38.4–42.1 s
against 39.9–41.9 s; the monorepo at 355–360 MB against 721–769 MB, its peak at 562–621 MB against 721–769 MB and its
build at 11.4–17.7 s against 11.0–14.5 s. A depth-3 callers query after the build left the game-engine tree at
630–651 MB and the monorepo at 381–386 MB, against 1,341–1,794 MB and 741–790 MB, and took 9.9–13.9 ms against
11.0–11.8 ms and 153–162 ms against 166–190 ms in the first rounds. An index build alone of the game-engine tree,
without a visitor or a content index, held 10 MB against 23 MB, and 10–12 MB against 36 MB after a refresh, which
took 585–651 ms against 604–666 ms.

## Revised 2026-10-18: an extraction is held at its exact size

**The walk's threads encode into buffers they reuse, and the build holds an exact-size copy of each encoding.** An
encoding grew in a fresh vector by doubling and was shrunk to fit, and the build holds every encoding until resolution;
under glibc that left freed memory resident in the walk threads' arenas beside the held encodings, and it set about a
quarter of the game-engine tree's resident peak. The buffers number at most the walk's threads, each as large as the
largest encoding it wrote, and they are freed with the visitor, before resolution.

The figures above counted the Rust heap alone. tree-sitter allocates its parse trees through the C library's `malloc`,
which a profiler of the Rust allocator does not see. Routed through that allocator, a build of the game-engine tree
on macOS allocated 41.9 GB in 350 million blocks, 30.4 GB in 284 million of them parse trees, and its live heap peaked
at 1,154 MB, 797 MB of it parse trees, against the 658 MB the Rust heap alone reaches. Of the Rust heap's 9.6 GB, the
file reads took 1.5 GB in 140,000 blocks, the encodings grown in place 1.2 GB in 950,000, building the extractions'
symbols and calls 0.8 GB, the resolvers' path joins 0.6 GB in 5 million and the graphs' name arenas 0.5 GB in 165.

The resident peak follows the largest files. Sampled every 100 ms on Linux, the resident set rose by 435 MB while a
30 MB C source of numeric tables was parsed, by 218 MB for a 6.8 MB C++ header and by 141 MB for a 4.8 MB one, and it
stayed there until the trim after the walk. That C source alone holds a 586 MB parse tree.

### What it costs

Measured as above, against `main`, interleaved, in five sessions on a shared host; sixteen builds of each:

| | game-engine tree | | | Go monorepo | | |
| --- | --- | --- | --- | --- | --- | --- |
| | peak | resident | build | peak | resident | build |
| `main` | 1,206–1,783 MB | 606–642 MB | 27.4–33.1 s | 563–619 MB | 354–364 MB | 11.6–13.1 s |
| exact-size encodings | 1,059–1,400 MB | 620–669 MB | 27.7–32.6 s | 552–629 MB | 357–370 MB | 12.2–13.1 s |

The game-engine tree's peak fell from a median of 1,480 MB to 1,087 MB, eleven of its sixteen builds within
1,059–1,129 MB, and it mostly comes 18–21 s into the build, while the C source above is parsed, where `main` peaked at
the end of the walk, 28.6–30.8 s in. Its build took a median 31.1 s against 31.2 s, and it stays resident 9 MB higher
after the build at the medians, 635 MB against 626 MB. The monorepo has no file large enough to matter: its peak, a
median 596 MB against 605 MB, and its build did not move beyond the spread, and it stays resident 8 MB higher.

On macOS, six interleaved builds of each on a host loaded to about 20, the change is within the spread: the
game-engine tree peaked at a footprint of 1,148–1,484 MB against 1,092–1,397 MB and built in 11.7–14.5 s against
12.7–14.6 s, the monorepo at 712–835 MB against 618–765 MB in 3.3–3.8 s either way. The Rust heap peaks and ends where
it did, at 658 MB and 622 MB on the game-engine tree and 375 MB and 293 MB on the monorepo, and the build allocates
0.8 GB and 0.6 GB less of it, in 0.8 million and 0.4 million fewer blocks.

### Considered Options

- **Measure the encoding before writing it, and reserve its exact size** — a counting pass of the codec in
  `kartta-lang`: 1,086–1,199 MB, three rounds, the same peak as the copy, with each build about a second slower than
  `main`, and a change to a published crate's codec for what the engine does alone.
- **Reuse each thread's read buffer, keeping buffers of 1 MiB or less** — 1,472–1,684 MB, three rounds: no change.
- **Pack the encodings into shared 1 MiB blocks** — 1,074–1,428 MB, six rounds, no lower than the copy and more code.
- **Trim after or before extracting each file of 1 MiB or more** — alone 1,029–1,366 MB, nine rounds; with the
  exact-size copy 972–1,206 MB, six rounds, a median 3% under the copy's, for a trim per large file on glibc alone.
- **Trim after each resolution batch** — the monorepo at 541–602 MB against 552–616 MB: no change.
- **Resolve batches while the walk runs** — resolution reads the finished index, the positions it inserts in, path
  order and the repository the resolvers ask, so it cannot start before the walk ends.
- **Reuse the parsers and their trees** — each language keeps one parser per thread already, and a tree is one file's.

The game-engine tree's peak is now its largest parse tree, live memory that neither a trim nor the layout of the build's
own allocations reaches. Revisit when such a file has to be bounded, which changes what the graph holds of it and is a
decision of its own.

## Considered Options

- **Trim only after the engine build** — the same memory resident afterwards, and the peak of a build without a trim.
- **Trim only after the index build** — the lower peak, and the extractions' decodes left resident: 0.87–0.95 GB on the
  game-engine tree.
- **Set the allocator up instead: a global allocator, or `mallopt` for fewer arenas or a lower trim threshold** — each
  is a choice for the whole process, made inside a library the process links, and a consumer that made its own would
  find it overridden.
- **`malloc_zone_pressure_relief` on macOS** — released nothing after either tree's build: the footprint stayed at
  1,127–1,262 MB on the game-engine tree and 712–776 MB on the monorepo, as without it.
- **Lower the build's live peak** — the live heap peaks 36 MB above what the game-engine tree's build keeps and 82 MB
  above the monorepo's, so nothing the build holds longer than it needs reaches the 548–970 MB between the game-engine
  tree's resident peak with both trims and its live peak: that gap is pages the allocator keeps, not data the build
  holds. With both trims the game-engine tree reached its resident peak by the end of the index build in each of three
  rounds, and the monorepo within 7 MB of it, so the peak is the walk's.
- **Encode each extraction into a scratch buffer each thread keeps, and hold an exact-size copy** — a prototype brought
  the game-engine tree's peak to 959–1,590 MB against 1,403–1,689 MB and the monorepo's to 565–605 MB against
  603–614 MB, three rounds each, and left 30–50 MB and 8–19 MB more resident after the build, in the buffers the threads
  keep. Left for a change of its own, which can drop the buffers with the build.

Revisit when a consumer's resident memory grows across scoped refreshes.
