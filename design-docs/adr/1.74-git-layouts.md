# Hold a nested worktree of the indexed repository empty, and leave every other git layout to the ignore rules

- **Date:** 2026-11-25
- **Governs:** `crates/kartta-fs/src/worktree.rs`, `crates/kartta-fs/src/policy.rs` (`Indexing::enter`,
  `Indexing::rules_in`), `crates/kartta-fs/src/index/scoped.rs` (`Rewalk::rules_above`), `Index::pruned_worktrees`,
  `crates/kartta-mcp/src/render.rs` (`pruned_worktrees=`), `crates/kartta-ffi/src/wire/build.rs` (`pruned_worktrees`)
- **Pinned by:** `crates/kartta-fs/tests/worktrees.rs`, `crates/kartta-mcp/tests/stdio.rs`
  (`the_index_counts_the_worktrees_of_its_repository_it_holds_empty`), `crates/kartta-ffi/tests/dispatch.rs`
  (`a_build_and_stats_name_the_worktrees_the_index_holds_empty_and_a_refresh_drops_a_removed_one`)

kartta knows a checkout by the entry name `.git`, and agent tools put linked worktrees of the repository they work on
inside it. The ignore rules alone decide what the index holds, with one special case: a linked worktree of the indexed
repository inside the root is held as an empty directory and counted, known by the two files git writes for it. A bare
container, a nested clone and a git directory under another name get no handling of their own, at the costs below.

## Decision

- **The rule.** Everything inside the root that no ignore rule hides is indexed: a nested repository, a submodule and a
  clone under their own rules, since a `.git` below the root resets the inherited rules
  ([ADR 1.19](/design-docs/adr/1.19-pruned-names.md) prunes the `.git` itself).
- **The special case.** While ignore rules apply, a directory below the root whose `.git` is a gitfile,
  `gitdir: <path>`, naming a git directory that holds a `commondir`, is held as an empty entry when that `commondir`
  comes to the common git directory of the root's own `.git`. The root's common git directory is its `.git` directory or
  the git directory its gitfile names, or the directory that one's `commondir` names. A gitfile's path resolves against
  the directory that holds it, a `commondir`'s against its git directory, and the two compare canonical.
- **Everywhere the index walks.** A build, a whole refresh, a named refresh and a follow apply it: a part below such a
  directory is walked as gone. `Index::pruned_worktrees` names each such directory, the MCP index answer counts
  them in `pruned_worktrees=`, absent when zero, and the wire's `build` and `stats` answers list them in
  `pruned_worktrees`, absent when none.
- **What it reads.** The gitfile and the `commondir` of each directory below the root that holds a `.git`, in process.
  No git subprocess runs, no git configuration is read, and no directory is taken for a git directory by its shape.
- **Without ignore rules.** At `IgnoreSources::None` no worktree is held empty.

## Why

- The maintainer, on nested worktrees: "Nested work trees, especially the ones that are not excluded are very dangerous
  because we can just explode in terms of memory and the parsing time. So the nested work trees should be handled. All
  other situations are handled as stated." On a directory shaped like a git directory: "we should not try to Duck type
  the folder in case the folder is git directory. The git itself does know that" (#145).
- Three nested worktrees in the Go monorepo's working tree held 88,861 of the 118,402 files its index took in
  (2026-11-25).
- The two files are not the git configuration [ADR 1.53](/design-docs/adr/1.53-machine-local-ignore-files.md) refuses
  to parse: `gitrepository-layout(5)` defines the gitfile as "a plain text file `.git` ... containing
  `gitdir: <path>`" and `commondir` as a path that, "If the specified path is relative, it is relative to `$GIT_DIR`"
  (git v2.56.1 `Documentation/gitrepository-layout.adoc:24-26`, `:268-273`). git reads each whole, strips the line
  ends and joins a relative path, with no configuration (`setup.c:975`, `:1005-1060`, `:321-345`).
- `git worktree add` writes a `commondir` of `../..` into every linked worktree's git directory
  (`builtin/worktree.c:540-544`; `Documentation/git-worktree.adoc:375-378`), and a submodule's git directory holds
  none, so a submodule stays a repository of its own.

## Consequences

- Each directory below the root that holds a `.git` costs a read of it, and a gitfile a read of its `commondir` and a
  canonical path; the root's `.git` is read once a build and once a refresh call. A build of the macOS data volume,
  8.9 million entries, took 36.8 s against 36.6 s and peaked at 872 against 868 MB, inside the spread of each
  (2026-11-25). Accepted.
- A git directory under another name is indexed unless an ignore rule hides it: a `git init --separate-git-dir` inside
  the tree indexed its 27 files (2026-11-25). Accepted (#147).
- A bare container whose root `.git` gitfile names its bare repository holds each worktree inside it empty, as linked
  worktrees of the root's repository: the index held the bare repository's 39 files and no source file. Without that
  gitfile it held both worktrees and the bare repository, 47 files (2026-11-25). Accepted (#145).
- A nested clone of the root's repository is indexed, every file a second time: 4 of 8 files (2026-11-25). Accepted.
- A root inside a repository has no `.git` of its own, so a worktree inside it is indexed: 4 of 6 files (2026-11-25).
  Accepted.
- On Linux the worktree's own directory keeps its watch, one a worktree; nothing below it is watched. Accepted.

## Rejected

- **Take a directory for a git directory by its shape (`HEAD`, `objects`, `refs`)** — the maintainer rejected it
  (#147).
- **Ask `git` about each nested checkout** — a subprocess on the walk's path, which #146 forbids.
- **Drop the worktree's directory from the index** — the walk records a directory in its parent before it lists it, so
  dropping it takes a change to `kartta-walk`'s `Policy`; the empty entry keeps its watch, which sees its `.git` change.
- **Give a bare container, a nested clone or a submodule's worktree handling of its own** — the maintainer decided each
  stays with the ignore rules (#145).

## Revisit if

Agent tools put their checkouts in the tree as something other than linked worktrees, or a bare container proves a
common root. Medium confidence: every nested checkout #146 measured was a linked worktree.
