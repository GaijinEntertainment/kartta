# Re-encode only the blocks a change lands in

- **Date:** 2026-10-15
- **Governs:** `crates/kartta-fs/src/index/splice.rs` (`spliced_paths`, `copy_blocks`, `encode_run`),
  `crates/kartta-fs/src/index.rs` (`Block`, `block_of`, `starts_block`)
- **Pinned by:** `crates/kartta-fs/src/index.rs` (`blocks_of_any_length_read_back_and_answer_lookups_and_listings`),
  `crates/kartta-fs/src/index/splice.rs` (`a_run_that_grows_past_a_block_is_laid_again_in_blocks_of_128_from_its_start`,
  `a_range_replaced_across_blocks_reads_back_as_the_new_tree`)

The front-coded path store of [ADR 1.9](/design-docs/adr/1.9-path-storage.md) is spliced in place when a scoped refresh
([ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md)) adds or removes entries. Each block records its own
first position, so a block holds any number of entries up to 128 and a splice re-encodes only the blocks a change lands
in, at the price of a binary search to find a position's block.

## Decision

- **Blocks of up to 128.** A block holds up to 128 entries; a build lays one at every 128th entry, as
  [ADR 1.9](/design-docs/adr/1.9-path-storage.md) states.
- **A splice re-encodes what a change lands in.** An added or removed entry moves every later position, and with it
  anything keyed by position, but no other block's bytes. A splice copies each untouched block's bytes whole, and lays
  the blocks a change lands in again from their first entry, in blocks of 128 with at most one shorter block at the end
  of each run it re-encodes.
- **Finding a block.** Reading a position finds its block by a binary search over the blocks' first positions.
- **Where a block starts.** An entry starts a block exactly when its offset is 0, because every stored suffix is at
  least one byte: the next path in tree order is never a prefix of the one before it.

## Why

With a block at every 128th entry, one inserted entry moves every later block's boundary, so the store is re-encoded
whole: 0.3 s on 5.3M entries, where a one-entry splice of blocks of any length takes 1.8–3.2 ms on 5.5M entries (data
volume, 2026-10-15, #22).

## Consequences

None measured: against blocks fixed at 128 on the data volume, a sweep of lookups took a median 187 ms against 198 ms,
an in-order read of every path 59 ms against 61.5 ms, and builds were unchanged (2026-10-15).

## Rejected

- **Blocks fixed at 128 entries, with changes merged in by re-encoding the store** — no position stored per block and a
  division in place of the search, but every change pays a pass over every stored byte.

## Revisit if

Reads by position become the cost that matters and the per-block search shows in their profile. High confidence: the
measured reads did not slow.
