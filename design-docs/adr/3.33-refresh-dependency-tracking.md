# Follow a tree through the questions each file's resolution asked

- **Date:** 2026-10-18
- **Governs:** `crates/kartta/src/following.rs`, `crates/kartta/src/repository.rs` (`Query`, `asked`,
  `reached_by_presence`, `asked_while`), `crates/kartta/src/resolving.rs`, `kartta::Engine::refresh`,
  `kartta::Engine::refresh_paths`, `kartta::EngineRefresh`, `kartta_lang::Resolver`
- **Pinned by:** `crates/kartta-languages/tests/refresh.rs`
  (`an_engine_refreshed_after_edits_answers_as_a_build_of_the_edited_tree`,
  `a_refresh_of_an_unchanged_tree_reads_and_resolves_nothing`,
  `an_engine_refreshed_again_and_again_follows_every_change`,
  `a_path_outside_the_tree_fails_a_refresh_that_would_walk_the_whole_tree`)

The index refreshes in place and the graph keeps its files apart, so a file read again goes back into its graph by
itself, but what a resolver makes of a file depends on other files: an include finds a header that was added, a Go
package gains a file. An engine built with stamps keeps, for each file, the questions its resolution asked of the tree,
and resolves again from a second read the files whose questions a change answers differently; an engine without stamps
keeps nothing and builds every graph again.

## Decision

- **What a followed engine keeps.** An engine built with `BuildOptions::stamps` keeps, for each file its graphs hold,
  the questions its resolution put to the repository. A question is one of five kinds, `contains` and `read` of a path,
  `files_in_dir` of a directory, `files_named` of a name, and `files_ignoring_case` of an ASCII-lowered path, and is
  filed under a 32-bit key hashed from its kind and that text. A file keeps its keys once each, sorted;
  [ADR 3.81](/design-docs/adr/3.81-refresh-reached-files.md) states how they are stored and searched. The same switch
  that stamps the index ([ADR 1.40](/design-docs/adr/1.40-unchanged-file-detection.md)) turns this on, so the consumer
  that never refreshes pays for neither.
- **What a change reaches.** A regular file the refresh added or removed, as `kartta_fs::RefreshOutcome::added` and
  `removed` list them, claimed by a language or not, such as a README in a Go package or an extensionless header,
  reaches the five keys of its path: `contains` and `read` of the path, `files_in_dir` of its directory, `files_named`
  of its name and `files_ignoring_case` of its lowered path. A file the refresh read again reaches the `read` key of its
  path. Each followed file whose keys hold a reached key is read again from disk, extracted and resolved; two questions
  that share a key only resolve one file more. A family's own configuration is followed apart:
  [ADR 3.82](/design-docs/adr/3.82-followed-resolver-rebuilds.md).
- **The contract this rests on.** It is stated on `kartta_lang::Resolver`: `resolve` asks the repository on the thread
  that called it, asks again for each file what it needs, and reads no file's content. The engine attributes a
  question to the file whose resolution asked it on the asking thread, so a resolver that asks from another thread, or
  answers one file from what it asked for another, leaves a change to that answer unseen.
- **Without stamps.** The engine keeps nothing. `Engine::refresh` walks the whole tree, reads every file again, and
  builds every graph again from what it read; `Engine::refresh_paths` is then `Engine::refresh`, and still fails a path
  the index cannot spell with `BuildError::Misspelled` ([ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md)).
- **What a refresh reports.** `EngineRefresh` gives, beside the index's own outcome: `extracted`, the files read new or
  changed; `resolved_again`, the files carried over and resolved again; `dropped`, the files the graphs no longer hold,
  `None` when every graph was rebuilt; `reconfigured`, the families whose configuration changed what they resolve;
  `rebuilt`, whether every graph was built again; and `widened`. Past a number of parts that grows with the tree,
  `Engine::refresh_paths` refreshes the whole tree and says so in `widened`:
  [ADR 3.80](/design-docs/adr/3.80-named-refresh-widening.md). The tables the resolvers find files in are kept between
  refreshes: [ADR 3.83](/design-docs/adr/3.83-refresh-file-tables.md).

## Why

- The files a change reaches are few: over 5,000 commits of the Go monorepo, a commit's adds and deletes reach 77 files
  at p99 and 0 at the median (2026-10-18, #79), about 80 ms of CPU to read, extract and resolve again.
- The keys are small beside what they replace: 2.34M keys, 8.9 MiB, on the C++ game-engine tree of 182,714 entries,
  where the raw extractions a resolution could start again from take 300.6 MiB (2026-10-18, #79).
- The build drops each raw extraction once it is resolved, so what a resolver made of a file can only be started again
  from the file.
- A refresh can see only what a resolver asks through the repository, which is why the contract binds every language.

## Consequences

- A followed engine holds its keys and, per held file, its path, its language and a map slot: about 27 MB on the
  game-engine tree against 622 MB of heap after a build (2026-10-18); accepted.
- Listing the regular files added and removed costs a whole index refresh one pass over the paths before and after
  it: 145 ms to 151 ms on the game-engine tree; accepted.
- A refresh without stamps holds the old graphs while it builds the new ones: the resident set rose by 300 MB on the Go
  monorepo; accepted, since that consumer chose not to follow.
- A resolver that breaks the contract answers stale after a refresh, silently; accepted, stated on the trait.

## Rejected

- **Keep every file's raw extraction to resolve it again without a read** — 300.6 MiB on the game-engine tree, half the
  heap of a built engine, to save reading the 77 files a commit reaches at p99.
- **Resolve every file of a family again on any add or remove** — needs no keys, but either keeps every raw extraction
  or reads at the cost of a build, for a change that reaches 0 to 4 files at the median.
- **A resolver that resolves only a file's directives** — a few bytes a file and no read, at a change to the contract
  of every language crate and a graph that replaces part of a file.
- **Read the reached files through the content cache** — the index would have to hash and look up bytes it did not read
  during the walk; the files a commit reaches are few enough that extracting them is cheaper.

## Revisit if

The files a change reaches grow from tens to a large share of the tree, so that reading them again costs more than
holding the raw extractions would; high confidence on the measured history.
