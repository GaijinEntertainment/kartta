# Search definitions by the words of their names and paths

- **Status:** accepted
- **Date:** 2026-10-17
- **Initiative:** `03-code-graph`

An agent that knows what a symbol does but not its exact name asks for it by a word: `config loader`, `HTTPServer`,
`parse request`. `definitions` answers a name as written; a search has to rank every definition that holds a word of
the query, in a graph kept a file at a time (ADR 3.5) that a refresh changes one file at a time, on trees of millions of
definitions.

**Each file keeps the hashes of its words, gathered by the first search that reads it.** A file's words are those of
the qualified names and names of its definitions and of the last three segments of its path, kept as a sorted set of
32-bit hashes, with the count of words its definitions hold for the length normalization. A search reads every file's
set in parallel, splits the names only of the files that may hold a word it asks for, and counts each word exactly
there, so a hash collision only adds a file it then finds holds nothing. Nothing outside a file's slot is shared, so a
removal or a replacement drops the slot and touches nothing else. The set is built the first time a search for a word
reads the file, so building the graph spends nothing on search: a consumer that never searches never pays for it, a
query with no word builds no set, and the first search for a word splits every name of the graph once across the pool,
27.4 to 29.9 ms on the C++ game-engine tree and 36.1 to 38.9 ms on a Go monorepo, against a median of 5.5 to 5.8 ms
and of 5.0 to 5.3 ms for the searches after it.

**A word is split as a reader splits it.** A name splits at every character that is not a letter or a digit, between a
lowercase letter or a digit and the capital after it, and before the last capital of a run that a lowercase letter
follows, so `parseHTTPRequest` holds `parse`, `http` and `request`; words are lowercased by Unicode, a letter outside
ASCII stays in its word, and the extension is cut from the file's name alone, so a directory `v1.2` keeps both words.
Path stems split the same way as names, so `httpServer/config_loader.go` holds `config` and `loader`. The reference
search splits a capital run into single letters, which on the Go monorepo leaves 349,108 of 1,364,186 symbols (25.6%)
and on the C++ tree 103,763 of 1,193,586 (8.7%) unfindable by their acronym, and leaves path stems unsplit, which no
split query word can then meet: 38,327 of 43,356 C++ files (88%) and 20,258 of 39,771 Go files (51%).

**A definition ranks by BM25 over the words it shares with the query, weighed toward the definitions that name the
query.** BM25 takes k1 1.2 and b 0.75 over the words a definition holds: those of its qualified name, those of its own
name once more, and those of its file's path. The score is multiplied by the share of the query's words it holds among
those some definition holds, doubled when the search looks for two or more words and the definition's qualified name
holds all of them in query order with no word between, capped at 500, halved for generated code and cut by a quarter
for vendored code, both read from `SymbolFlags`; a definition whose name is the query as written scores 1000 more, so
it leads every other hit and the lead survives a merge of the hits of several language families by score. Equal scores
rank by path and line.

**When the words match fewer definitions than the limit, a fill-up adds those whose name or qualified name spells the
query.** The query, its whitespace dropped and lowercased, must be a subsequence of the lowercased characters of the
name, or else of the qualified name, so `authent` reaches `Authenticate` and `pcf` reaches `parseConfigFile`; a hit
scores the share of its name's characters the query spells, or of its qualified name's when only that spells the
query, 0 to 1, demoted as a word match is, is marked `fuzzy`, and ranks among the word matches by that score; at an
equal score a word match ranks first, and then path and line decide. A density over the qualified name alone ranks a
Python definition by the length of its module path: on the C++ tree, a camel-word query's mean reciprocal rank rose
from 0.234 to 0.310 when the density moved to the name.

**The answer counts what it left out.** `total` counts every definition a word or the exact name matched before the
limit, `named` those of them a name matched rather than only a path, `unmatched_words` lists the words the search
looked for that no definition holds, `dropped_words` counts the distinct words past the eighth, which the search does
not look for, and `fuzzy_total` counts the fill-up's own matches when it ran and is absent when it did not; with a
limit of 0 the answer holds no hit and the fill-up does not run, and every other count is that of any other limit.

## Measured

Quality is measured against the reference search on its own query sets, 209 per tree, built from real symbols: 40 exact
names, 30 partial words, 30 two-word camel fragments, 29 qualified fragments, 30 path words, 30 two-word queries of a
name word and a path word, and 20 misses. For every query built from a symbol, the rank of that symbol in each answer;
hits of one score rank at the middle of their tie group, and a hit in a nested worktree copy of the tree counts as the
same hit as the one it copies, since the Go monorepo holds a second copy of most of itself. Mean reciprocal rank per
category, the reference search first:

| category  | C++ tree      | Go monorepo   |
| --------- | ------------- | ------------- |
| exact     | 0.505 → 0.519 | 0.519 → 0.552 |
| partial   | 0.060 → 0.103 | 0.133 → 0.162 |
| camel     | 0.188 → 0.310 | 0.312 → 0.306 |
| qualified | 0.689 → 0.707 | 0.488 → 0.639 |
| path      | 0.000 → 0.010 | 0.003 → 0.017 |
| two-word  | 0.060 → 0.063 | 0.132 → 0.169 |
| all       | 0.262 → 0.295 | 0.277 → 0.319 |

Every miss stays a miss on both sides. The one category below the reference, camel on the Go monorepo, holds 21
vendored symbols of 30: vendored code ranks after repository code of near relevance here, and in the reference search
only under a root `vendor/`; over the 9 repository symbols of that category the difference is two queries ranked one
place lower, each among hits that all hold the query's words. Over repository symbols alone, recall at 10 is 0.464
against 0.443 on the C++ tree and 0.615 against 0.538 on the Go monorepo.

Each ranking choice was measured by turning it off, the mean reciprocal rank of all queries on the C++ tree and on the
Go monorepo against 0.295 and 0.319: without the phrase lead 0.290 and 0.311, camel queries falling to 0.293 and 0.282;
without the share of the query's words held 0.293 and 0.318; with the name counted once 0.295 and 0.312, camel queries
at 0.300 and 0.281; vendored code halved rather than cut by a quarter 0.293 and 0.319.

Cost against the graph without search, four interleaved rounds at a load of 8 to 11, on the C++ tree of 146,752 files
(1,193,586 C++ symbols) and the Go monorepo of 44,443 files (39,771 Go): inserting the files takes 778–791 ms against
792–809 ms and 504–521 ms against 505–531 ms, the build 3.75–3.82 s against 3.75–3.91 s and 1.70–1.83 s against
1.71–1.82 s, the peak footprint 749–759 MB against 744–753 MB and 491–493 MB against 491–495 MB, and the heap after the
build holds 634.1 MB against 626.6 MB and 296.9 MB against 294.5 MB for the empty slot each file keeps its words in.
After every query set ran, the heap holds 640.5 MB and 301.9 MB, 2.2% and 2.5% over the graph. Over three runs of the
query sets, a query answers at p50 2.6–2.9 and 3.4–3.5 ms, at p99 19.3–19.6 and 17.7–26.6 ms, at worst 27.4–29.9 and
36.1–38.9 ms, the first search of a graph; the reference search answers at p50 0.5 and 0.9 ms from its stored index,
at p99 101 and 121 ms and at worst 113 and 128 ms, its fill-up scanning every symbol on one thread. The broadest query
of each set, 276,749 and 293,976 matches, holds at most 17.8 and 24.2 MB of heap while it runs, over six runs.
Reading the sets of every Go file for a word none of them holds takes 0.13 ms at the median, so a query spends its time
on splitting the names of the files that hold its words, on ranking and on the fill-up, not on the scan.

## Considered Options

- **An index of every definition under every word, with per-definition lengths** — p99 4.5–7.5 ms, and 171 MB on the Go
  monorepo and 178 MB on the C++ tree, 125 to 150 bytes per definition, where the word sets hold 5.1 and 6.5 MB once
  searched; a removal walks the posting list of every word the file holds, up to 0.8 ms at p99.
- **An index of distinct names under their words, the names reaching definitions through `by_name`** — 56 and 68 MB,
  and a removal that retains over long shared lists, up to 23 ms.
- **No index, splitting every name for every query** — 0.3 MB, and about 0.4 CPU-seconds per query.
- **Word sets built at insert, the words interned in the graph's strings** — the same answers, and the insert phase,
  which runs on one thread, 250 to 280 ms longer on the C++ tree and 200 to 240 ms on the Go monorepo, about a tenth
  of the build; hashing instead of interning still left 160 to 230 ms.
- **Only definitions whose own name holds a query word are matched** — 29 to 58% fewer matches and p99 up to a quarter
  lower, at the price of 5 to 22% of the top-10 hits changing against the full match; `named` counts the same split
  without losing the path matches.

Revisit when a family's first search, which splits every name of the graph once, outgrows the latency a query is
allowed, or when a refresh replaces files often enough that re-splitting the replaced files' names on the next search
costs more than keeping their sets current at insert.
