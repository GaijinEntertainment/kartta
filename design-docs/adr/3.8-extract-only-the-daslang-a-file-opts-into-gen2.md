# Extract only the daslang a file opts into gen2, and find modules by file name

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-23
- **Initiative:** `03-code-graph`

Daslang has two syntaxes. The only tree-sitter grammar, `tree-sitter-daslang`, reads the second generation, which a file
selects with a top-level `options gen2`; the compiler reads that one option to choose its parser. The first generation
is indentation-delimited and has no tree-sitter grammar. Its tree from the second-generation grammar is errors, and a
walk over it gives symbols that no source declares.

**A file that does not opt into gen2 extracts to nothing.** The option is read from the parse tree, as a top-level
`options_declaration` that names `gen2`. A comment or a string that spells `options gen2` is no such node, and a byte
order mark or a header lower in the file does not hide one. An explicit `options gen2 = false` wins over any opt-in in
the same file, because a first-generation file extracted costs wrong symbols and a second-generation file dropped costs
only its absence. On the tree this was built against, 3,629 of 8,794 `.das` files extract to nothing, and the gap
follows project lines: one game is almost all second-generation, two others are all or almost all first-generation,
and 633 of the engine's 2,773 files are first-generation.

**A `require` names a file by its module name.** The compiler binds `require x` to the module that declares
`module x`, wherever its module path puts it; the module path is a compiler input that no repository holds. On the same
tree, 1,290 of 1,293 `module` clauses name their own file stem, so the repository's file names are the module index and
no pass over every file builds one. The resolver tries, in order, and stops at the first that names a file:

- a specifier that starts with `./` or `../`, relative to the importer;
- for a dotted or slashed specifier, its dots read as slashes, under each directory of the importer from the nearest to
  the root, then as the one path anywhere that ends with it at a directory boundary, then as the one file named for its
  last component — a dotted specifier is a path through the module namespace, which need not follow the directories;
- for a bare name, the one file named for it.

A specifier that two files could satisfy names neither. Every match is case-sensitive, as the compiler's is: a specifier
that matches a file only without case names a native module, which the compiler binds by its registered name and never
through a file. 18,620 of 25,976 directives on the tree resolve. The rest name the compiler's builtin modules, native
bindings and generated stubs, which no `.das` file provides, and no include is the correct answer for them. Each of
them is an import instead, kept as written, so the dependency stays visible.

**An `include` takes its file name as the compiler's lexer does**: the run of non-blank characters after the keyword,
so a quoted name keeps its quotes and names no file.

**A block's calls belong to the `def` that runs them.** A block applied in place — the argument of a call, a `new` or a
pipe, `query() <| $(eid) { ... }` — runs in its enclosing `def`, so its calls are that `def`'s. A block or a local
function stored in a name runs when the value is called, so its calls belong to no symbol, and the graph drops them
rather than give them to the `def` that only defines the block. A block applied to a field, `obj.handler { ... }`, is
recorded as a call of `handler` on `obj`, though no call node of the grammar covers it.

**A construction names its type only where the syntax spells one.** `T(...)` and `new T(...)` call `T`. `default<T>`,
a `new` over a container or a make-expression, and a macro splice in call position name no symbol and record nothing.

**Revised 2026-10-23: code a macro takes as data is no call of the `def` around it, and the names it spells are
uses.** `quote(foo(1 + 2, "bar"))` made `foo` a callee of the `def` that holds it, though `quote` builds the tree of the
call and nothing runs: `foo` need not exist, and the name bound a namesake or counted as ambiguous. The same holds for
each macro whose compiler class reads an argument as syntax, found in dagor's daScript tree
(`prog/1stPartyLibs/daScript`):

- `quote(e)` is the builtin `ExprQuote`, registered at `src/builtin/module_builtin_ast_annotations_1.cpp:338`;
  inference types it `Expression?` and visits no argument (`src/ast/ast_infer_type.cpp:1582`, `ExprQuote::visit` at
  `src/ast/ast.cpp:1383`, `canVisitQuoteSubexpression` false at `include/daScript/ast/ast_visitor.h:39`).
- `qmatch(e, pattern)`, `qmatch_block(e) { pattern }` and `qmatch_function(f) { pattern }` (`daslib/ast_match.das:1882`,
  `1921`, `1971`) visit argument 0 alone, so the matched expression runs and the pattern does not; a capture such as
  `$e(x)` reads only the variable's name (`tag.subexpr as ExprVar`, `:821`, `:999`).
- `qmacro`, `qmacro_block`, `qmacro_block_to_array`, `qmacro_expr` and `qmacro_type` (`daslib/templates_boost.das:1216`
  to `1242`) visit no argument, "like quote" (`:1189`); `qmacro_function` and `qmacro_variable` (`:1317`, `:1322`) visit
  the name alone, `qmacro_method` (`:1366`) the name and the class. A splice, `$e`, `$i`, `$v`, `$b`, `$a`, `$t`, `$c`
  or `$f`, is the exception: `QRulesVisitor.visitExprTag` (`:912`) copies its expression into the block that runs where
  the macro expands.

Not read as data: `match` (`daslib/match.das:642`) visits its arguments, and its patterns mix guards that run with
shapes; the `_sql_*` macros (`daslib/sql_linq.das:5080`) take a SQL dialect; `qmacro_template_function` and
`qmacro_template_class` (`:1494`, `:1537`) take `@@F` and `type<T>`, which name what exists; and
`data |> qmatch(pattern)`, which passes the data first, has no use on the tree.

The walk records no call in the data of those macros, a block after the call counting as its last argument. What the
data names, `f(...)`, `mod::f(...)`, `T(field = ...)`, `new T()` and `@@f`, is a use of the name instead: the code
compiled from a `qmacro` calls it, a `quote` holds it, and a `qmatch` pattern matches it, so a name the graph left
unrecorded would let `dead_code` list a function that only generated code calls, `qm_extract` or `to_sql_literal`, as
unused. `_::f`, the compiler's name for the scope that compiles the code, binds as a bare `f`. A member call records
nothing in data, its receiver there being a variable's name and no type. A `qmacro` splice keeps its calls as the
enclosing `def`'s, as does the matched expression of a `qmatch`.

On the game-engine tree the walk records 1,392 fewer calls of 356,313 and 1,372 more uses, 1,490 to 2,862, in 73 of
8,794 daslang files; the other 146,682 claimed files of all languages extract to the same bytes. The calls left out sit
in `qmacro` 464, `qmacro_expr` 271, `qmacro_block` 197, `qmacro_function` 143, `qmatch_block` 103, `qmatch` 100,
`qmacro_block_to_array` 60, `qmatch_function` 45, `quote` 7 and `qmacro_method` 2; the two macros the report named hold
107. The edge dump loses 286 of 75,902 caller-callee pairs and gains or moves none (119 at confidence 80, 93 at 70, 67
at 60, 3 at 50, 4 at 30), and the calls left ambiguous between several definitions fall from 86,500 to 85,983. 314 use
edges bind (1,030 to 1,344), 186 at 80 and 128 at 70. By hand, 30 of 30 removed pairs (seed 203) and 30 of 30 removed
calls (seed 251) sit in data; all 42 calls the splices keep run in the macro; 29 of 30 added use edges (seed 7) name the
function the code emits, the 30th a namesake macro function, `match.match_copy`, for a function the code generates.
`dead_code` reports 2,338 to 2,347 daslang definitions and none fewer; the 9 are written `coverage::f`, `decs::f` or
`sql_boost::f`, or name a module the writing file does not require. Of the 21,117 calls of the parity plan on the tree
28 differ, all daslang: `find_callers` 9, `find_references` 5, `impact_of_change` 4, `find_callees` 3, `impact_of_edit`
3, `find_unused` 1 and the index counts 3.

Other readings, measured. Leaving the calls keeps all 1,392. Dropping them and recording nothing lists 98 more
definitions as unused, 2,436, 78 of them defined in the file of the macro that emits calls to them; recording the uses
with `_::f` kept as a qualifier, 2,374. Reading every argument as data, the splices too, loses 42 calls that run;
reading `qmatch`'s argument 0 as data changes nothing on this tree and would drop a call that runs. The two named macros
alone leave 1,285 of the 1,392 in place. A plain `@@f` sits in no data on the tree, the form there being `@@$c(...)`,
so keeping and skipping it extract the same; it stays a use, as the code compiled from it takes the address.

Extraction runs 0.2% to 0.4% more instructions on the tree's 65 MB of daslang (three pairs, one thread). The index
build on dagor at 4 threads, six and eight rounds alternating under a load of 9 to 12, shows no gap its spread does not
cover: warm 4.46 to 5.43 s against 4.47 to 5.84, peak 851 to 872 MiB against 864 to 905; cold 27.2 to 37.7 s against
27.1 to 33.3, peak 1,068 to 1,178 MiB against 1,154 to 1,198.

## Considered Options

- **A first-generation grammar** — covers the files gated out, but means porting the compiler's bison grammar and an
  off-side external scanner, and owning a grammar with no upstream.
- **The compiler's own AST dump** — exact for both generations, but puts a C++ build and a process boundary into an
  engine that has neither.
- **A module index from every file's `module` clause** — exact where a clause differs from its file stem, which is 3
  clauses of 1,293, at the price of a pass over every file before any resolves.
- **Case-insensitive matching** — adds edges to files that the compiler never loads for the specifier.
- **The first of several candidates** — adds an edge that is wrong as often as the candidates are many.

Revisit when first-generation files appear in reviews as often as second-generation ones.
