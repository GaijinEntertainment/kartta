# Build the content index from sorted runs merged in place

- **Date:** 2026-10-14
- **Governs:** `crates/kartta-fs/src/content_index/build.rs`, `crates/kartta-fs/src/trigram.rs` (`Trigrams`),
  `crates/kartta-fs/src/policy.rs` (the reading lock)
- **Pinned by:** `crates/kartta-fs/src/content_index.rs` (`many_small_runs_merge_into_the_index_one_run_builds`),
  `crates/kartta-fs/src/trigram.rs` (`a_cleared_extractor_starts_the_next_file_afresh`)

The walk's reading threads hand each text file's trigrams to the build in no fixed order, and the finished lists must be
ascending and laid out end to end. The build collects runs in id order, spills them sorted, and merges them straight
into place, holding about one index's size of spill on the way.

## Decision

- **A seen-bitmap per thread.** A file's distinct trigrams are found with a 2 MiB seen-bitmap per reading thread,
  pooled for the build and zeroed lazily, so only the pages a file's trigrams touch are resident.
- **Runs in id order.** Ids are handed out and a file's trigrams appended to the run under one lock, so a run's pairs
  arrive in id order, and a stable radix sort on the trigram leaves every list ascending.
- **Spilled as lists.** A run of 2^20 pairs is spilled as the same lists over the run's own ids, which makes the spill
  about the size of the finished index.
- **Merged in place.** The merge first sums each trigram's length from the run headers alone, so every list's final
  size and offset is known before a byte is written. It then merges the 256 first-byte partitions in parallel, each
  writing its lists straight into place.
- **Pooled buffers.** Reading buffers, run buffers and seen-bitmaps are pooled for the build.

## Why

- Filling fresh allocations under the id lock, and the allocator's retention of freed ones, cost a first prototype a
  2.9 GB footprint for 0.5 GB of live data (game-engine checkout, 2026-10-15, #20).
- Lists sized before the merge land in place, so the output never grows and the partitions need no coordination.

## Consequences

- The shared lock costs about 0.3 s of thread time on the game-engine checkout and nothing on the wall. Accepted.
- The spill takes about the finished index's size again while the build runs. Accepted.

## Rejected

- **Spill runs as varint deltas** — 169–178 MiB of spill against 112–122 MiB as lists, in a format the merge then has
  to tell apart from the final one.
- **One run buffer per thread, ids interleaved** — no shared lock, and lists that arrive unordered across runs, so the
  merge has to sort each one.
- **A single-threaded heap merge** — 0.62 s on the checkout against 0.06–0.12 s for the partitioned one, and an output
  that has to grow rather than land in place.
- **A sparse set of seen trigrams** — sized to a file's trigrams rather than up to 2 MiB per thread, and a hash on every
  byte of every text file the build reads.

## Revisit if

The id lock shows on a build's wall time, which a build with many more reading threads could cause. High confidence on
the measured trees: it costs thread time only.
