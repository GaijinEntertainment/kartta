# Name Rust items by their module chain and resolve modules by Cargo's layout

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-22
- **Initiative:** `03-code-graph`

A Rust file names what it declares through inline modules, `impl` blocks and paths, and it reaches other files only
through `mod` declarations, whose targets Cargo's layout decides; a `use` names a module path, not a file. ADR 3.1
makes Rust a language of its own; this decides how `kartta-lang-rust` qualifies what it extracts, which receiver a call
names, and which files a `mod` pulls in.

**An item is qualified by the chain of its inline modules and its type.** An item of `mod a { mod b { ... } }` is
`a::b::Worker`, so two modules of one file keep their same-named items apart; a member of a `trait`, or of an `impl`
whose target names a type, is owned by that type and qualified under it, `a::b::Worker::run`, and a field or a variant
under its struct or enum. A member of an `impl` for a tuple, `dyn` or function type has no owner, because no single
name spells the type. A
`macro_rules!` keeps its bare name, because it is in scope textually rather than by path. A file's own module is named
by its path, which the extraction from the bytes does not see, so no qualified name carries it. An item that a function
body declares inside an `impl` is qualified under the type but is no member of it, because no receiver reaches it.

**An impl's owner is the type its path names in the file, or the path as written.** `impl super::W` inside `mod inner`
of `mod a` names `a::W` when the file declares `a::W`; otherwise its members keep `super::W` as written, because the
file does not tell where the path leads. A path through `crate::`, a leading `::` or a `super::` past the file's root
leaves the file's module tree and keeps its spelling too. The owner settles after the walk, once every declaration of
the file is known, and what the walk recorded under the impl — its members, the items nested in them, its `self`
receivers and its trait pair — follows it; settling one impl renames nothing of another. `impl Trait for Type` adds
`Trait` to the parents of the type the file declares under that path, or else under that name, which a type that a
`use` brings into an inline module spells; the first such type of the file takes it. A pair whose path names no
declaration of the file, `impl Trait for other::Foo` or `crate::Foo`, is dropped rather than matched by its last
segment, which could give the trait to an unrelated local `Foo`; so is a pair whose type another file declares.

**A call names its receiver only where the syntax spells it.** `self.m()` and `Self::f()` name the owner of the `impl`
or `trait` around them. A scoped call names the type or module that its path names in the file, `a::Worker::run()`
naming `a::Worker` and `super::W::new()` in `a::inner` naming `a::W`, and otherwise the last segment of the path,
`Graph::build()` naming `Graph`. No receiver resolves through a `use`, which would need the files the path leads to
(revised below). A path whose last segment is `self`, `super` or `crate` names a module and records no receiver, and a
member call on anything but a name records the empty receiver, as ADR 3.2 decides for Go. A macro invocation is a call
of the macro.

**A call of an item that a function body declares is a local call.** No other file can reach such an item, so a call
inside its block binds it in the extraction rather than by name in the graph. The item is in scope in its whole block,
a `macro_rules!` only after its definition and also inside an inline module, and an item of an `extern` block in the
block around it. The innermost item of the name binds; a `use` of the name in a block, or a `let` binding of it in the
same function, shadows it and leaves the call unbound. A path call binds an item of a module of the block that its path
names, through `self::` and `super::` too.

**A bodiless `mod` includes a file, and Cargo's layout decides which.** A `#[path]` override is relative to the
declaring file's directory, or inside an inline module to that module's directory. Otherwise a crate root, or a file
named `lib.rs`, `main.rs` or `mod.rs` wherever it sits, keeps its submodules beside it, any other file in the directory
named for its stem, and each inline module around the declaration adds a directory of its name: `mod inner { mod
child; }` in `src/lib.rs` pulls in `src/inner/child.rs`. A directory that holds a `Cargo.toml` is a package, and its
crate roots are those of Cargo's conventional layout: `src/lib.rs`, `src/main.rs`, `build.rs`, and each target under
`src/bin/`, `examples/`, `tests/` and `benches/`, as a file or as a directory with a `main.rs`. A top-level `fn main` in
a crate root other than the library is the entry point, in each of its `cfg` alternatives. The resolver finds the
packages once, from the `Cargo.toml` files of the repository, and reads none of them (revised below), so a target that
a manifest places off the layout is no crate root and no entry. Its file name still keeps its modules beside it when it
is a `lib.rs` or a `main.rs`, because that is what such a file is on real trees: in a registry of 447 crates, every
`lib.rs` off the layout is a library that `[lib] path` places, such as the `bindings/rust/lib.rs` of each tree-sitter
grammar, and no `mod lib;` or `mod main;` pulls in a file of either name, though the resolver includes one when a
declaration does. `use` and `extern crate` add no import (revised below for a `use` into another crate of the
repository).

**Test and generated code is marked by attributes, paths and banners.** An item gated by `#[test]`, `#[bench]` or a
`cfg` that holds only under `test` is test code with everything in it; the `cfg` predicate is evaluated over the
configurations of its other atoms, one truth per distinct atom, so `cfg(all(test, not(miri)))` gates, while
`cfg(any(test, feature = "x"))`, `cfg(not(test))` and the never-true `cfg(any())` do not. The check tries every
assignment of the atoms the predicate repeats and leaves an atom written once unknown, which decides it exactly however
many atoms it has; past 12 repeated atoms the rest stay unknown too, which can miss a gate that holds through the
repetition of a thirteenth, and can mark as test code an item whose predicate never holds, which no build compiles. A
file below a `tests` directory outside `src`, counted from the repository root or from any package around the file, is
integration-test code. A test-gated `mod`, or any `mod` of a test file, makes the file it pulls in a test include,
because that file is extracted on its own and cannot see the gate. A `*.gen.rs` or `*_generated.rs` file, or one with a
`@generated` or `DO NOT EDIT` marker in its leading comments outside a backtick span, is generated code. A `#[path]`
value is read as written, without decoding escapes, which none of the 1,601 `#[path]` attributes in the registry
writes.

**The fingerprint covers the walk and the grammar**, as ADR 3.4 settles for TypeScript.

**Revised 2026-10-22: a path into another crate of the repository imports the module file it names.** No receiver
resolved through a `use`, and a file-level `use` was recorded nowhere, so a call into another crate of a workspace bound
only by its name: on this repository `kartta_lang::tree::text` had no caller and 198 calls of `text` counted as
ambiguous. Three parts change:

- **The walk keeps the paths that may start at another crate.** Each name a `use` binds, an alias by its alias and
  `self` in a list by the module the list is under, is kept with the path it reaches, and so is the receiver of each
  path call, `kartta_walk::walk::run()` for `walk`, its first segment read through the file's `use` of that name. A
  path whose first segment is capitalised, or is `crate`, `self`, `super`, `std`, `core` or `alloc`, keeps nothing,
  and so do a glob and `as _`. A name the file declares at its top level keeps nothing, and a name bound to two
  paths anywhere in the file keeps neither: a `use` inside a block binds for the whole file. Of the 10,947 names a
  single-path `use` binds to another crate in a cargo registry of 488 crates, 33 are bound to two paths only by such
  `use`s, most of them `cfg` alternatives with no one answer, as getrandom's `rdrand_step`.
- **The resolver reads each `Cargo.toml` for its library.** Its name is the `[lib] name`, else the `[package] name`
  with `-` read as `_`, and its root the `[lib] path`, else `src/lib.rs`, read from the `key = "value"` lines Cargo
  writes, which every package manifest of the trees below uses; a value spread over lines or kept in an inline table is
  not read. A path starts at the library its first segment names: the caller's own package's, else that of the package
  sharing the most leading directories with the caller's. Two as near bind nothing, as the versions of one crate side
  by side in a registry are, 88 crates of this one. Each segment after it names `NAME.rs` or `NAME/mod.rs` by the layout
  above, asked of the tree as the file resolves, and the path imports the file of the module it ends at, or of the
  module that holds the item, named in lower case, it ends at. A longer rest, or a capitalised item, a type whose member
  the path names, imports nothing. Neither does a module that a `#[path]` places, since the resolver reads no file the
  path leads through: 486 public modules of the registry are placed so, 460 of them linux-raw-sys's alternatives of a
  few modules per architecture, with no one answer, and a call through one binds by name as it did.
- **A call of the name, or through it, binds what that file exports at its top level** (ADR 3.7, revised the same day).

  this repository's 26 take 0.5 ms. Resolving every Rust file on one thread takes 0.082 s against 0.067 s; 4,573 of
  the 47,718 paths kept bind a file, and the rest name a crate outside the tree, as `serde::` does, or one the
  registry holds twice.
- **The build:** in one process, five warm builds of the registry took at best 0.565 and 0.598 s against 0.552 and
  0.587 s, about 2%, and peaked at a footprint of 349.0 to 358.0 MB against 342.4 to 352.9 MB, the kept paths that the
  raw extractions of 8,831 files hold until those files resolve. Eight alternating rounds of the MCP server took 4.15
  to 7.47 s against 3.80 to 6.66 s cold and 0.98 to 1.15 s against 0.95 to 1.15 s warm, at peaks of 475 to 655 MiB
  against 494 to 735 MiB cold and 317 to 356 MiB against 337 to 356 MiB warm. On the snapshot, six rounds took 2.67 to

  map it derived instead of the manifests' bytes, so a version bump would resolve nothing again, as ADR 3.33 leaves to
  revisit; that waits for a consumer that follows a large Rust tree.

## What it costs

On a Cargo registry of 16,978 Rust files, the extraction yields 1.37 million symbols, 925,727 calls and 13,048 `mod`
declarations, of which 12,991 include a file, 206 of them through the directories of inline modules; one thread on
macOS extracts them in 15.3 s. Against crate roots told by file names alone, the packages add 355 includes — the `mod
common;` of integration tests, which keep their shared code in `tests/common/mod.rs` — and 104 entry points of build
scripts, benchmarks and tests without the default harness. They lose 6 entry points in a fuzzing directory whose
`Cargo.toml` the published package left out. Finding the packages costs one string per `Cargo.toml` of the repository,
once per build.

## Considered Options

- **Crate roots by file names alone** — no package lookup, but a crate root such as `tests/it.rs` or `build.rs` looks
  for its submodules under its own stem, where none is, and a build script's `fn main` reads as dead code.
- **Reading every `Cargo.toml`** — finds the targets that `[lib]`, `[[bin]]` and the `auto*` keys place off the layout,
  at the cost of a TOML parser and a read of every manifest when the resolver is built.
- **Matching a scoped impl target by its last segment** — keeps the pair of `impl Trait for crate::Foo` in a crate
  root, but in the same registry it gives `From` to the own `Error` of a file that writes `impl From<Error> for
  io::Error`, and a trait implemented for `std::fs::DirEntry` to a local `DirEntry`.
- **Resolving receivers through `use`** — `use crate::m::Worker; Worker::run()` would name `m::Worker`, but only by
  reading the files the path leads to, which one file's extraction does not have.
- **Qualifying by the file's module path** — the module path depends on the path and on the `mod` tree of the crate, so
  the extraction from the bytes could not carry it and every name would change with a file's location.

Revisit when a consumer needs targets placed off Cargo's layout, or receivers named through `use`.
