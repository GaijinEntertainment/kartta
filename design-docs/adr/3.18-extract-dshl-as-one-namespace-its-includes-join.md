# Extract DSHL as one namespace that its includes join

- **Status:** accepted
- **Date:** 2026-10-16
- **Initiative:** `03-code-graph`

`kartta-lang-dshl` extracts DSHL, the shader language of the Dagor Engine, through `tree-sitter-dshl` 1.0.0. No
extractor for the language existed to follow, so the model below comes from the grammar, the language reference and the
shader compiler's source. Each count is taken on the public Dagor Engine shader tree: 1,134 `.dshl` files, 7.3 MB, of
which 6 carry a parse error. One thread extracts the whole tree in 130 ms.

**A compilation has one namespace, so a declaration is qualified by its own name.** The compiler reads a shader file and
its includes, each included once, as one script: a global variable, an interval, a block or a macro that an included
file declares is visible by its bare name, and DSHL has no package or module. Each name of a `shader` is a class, a
`block` an interface, a `macro` a macro, and a render pass, a render pass group and a framebuffer layout each a class. A
variable or a sampler at file scope is a variable, a global that the engine sets by name; inside a declaration it is a
field of that declaration, and a `local` variable is a temporary and no symbol. A preshader binding,
`tex@smp2d = frame_tex`, is a field, a `bool` a constant, and an `interval` an enum whose ranges are its variants,
`quality.high`. The members of a shader with several names take the first name as their owner, because a symbol has one
owner. Every symbol is exported: once a file is included, nothing in it is private to it. The tree gives 1,217 classes,
29 interfaces, 2,495 macros, 6,057 variables, 8,563 fields, 128 constants, 696 enums and 1,687 variants.

**A `supports` names a parent, and a macro invocation is the only call.** `supports` lists the blocks that a shader or a
block runs inside, so each block it names is a parent of the declaration around it, of every name of a shader with
several, the way a type implements an interface, and a use of that block. A macro invocation, in a body or in a
condition, is a call that the declaration around it makes. The conventions let a call reach only a macro: no variable,
constant or field, and no member of the caller's owner. The tree records 7,451 calls; the 23 at file scope have no
caller, and the graph drops them.

**A use is a name in a position that reads a declaration.** The grammar spells a sampler state, a render state, a
channel mask, an intrinsic, a hardware feature and a macro argument as identifiers, the same as a variable. A table of
parent node and field therefore admits only the positions that read something the script declares: the operands of a
condition or an expression, an `assume`, a `##if`, `##bool` or `##declare` directive, a preshader value, an initial
value, a `shader ==` condition and a `pass` statement. The right side of a comparison, the range in `quality == high`
or the `NULL` in `tex != NULL`, is not a use: the graph binds no use to an enum variant, and `NULL` declares nothing.
That excludes 3,614 names that would bind to nothing. 15,905 uses remain, and the graph drops the 357 of them at file
scope.

**An include resolves to the nearest file whose path ends in its spelling.** The compiler looks an include up under each
include path of the build configuration that compiles the file, in order, then relative to its working directory, and
never relative to the including file. An HLSL `#include` in a code block goes through the same lookup. Which
configuration compiles a file is a fact of the build, not of the repository: a library shader is compiled by each game
that lists it, each with its own include paths. The resolver takes the files whose path ends in the spelling at a
directory boundary, and of several the one that shares the most leading directories with the including file. A game's
configuration puts its own shader directory first, as `samples/testGI` puts `./source`, and the copy there is the one
nearest the game's files. Two candidates equally near resolve to neither and stay an import, because a guess binds a
game's shader to another game's globals. A spelling that climbs, `../common.dshl`, is joined to the including file's
directory, and the 3 such includes in the tree resolve that way. Of the 3,145 DSHL includes, 2,298 name the only file of
their spelling, 286 resolve by nearness and 561 stay imports. 464 of those imports name one of four files that each game
keeps its own copy of: `shader_global.dshl`, held 7 times, 267; `gbuffer.dshl` 118; `sky_shader_global.dshl` 65;
`sq_clouds_shadow.dshl` 14. A library file that includes one of them is compiled against each copy in turn, so no single
edge is correct.

**HLSL is opaque text.** The grammar keeps the body of an `hlsl { }` block as text, and parses only the DSHL `##`
directives in it. No HLSL function, structure or `#define` is a symbol and no HLSL call is recorded: that needs an HLSL
grammar over the text ranges, which is a language of its own. A line scan of the text reads each `#include "x"` and
`#include <x>`, and these resolve as DSHL includes do. The tree holds 1,322 of them; the measured checkout holds no HLSL
files, so their resolution is not measured.

**Only `.dshl` is claimed.** Every DSHL source in the tree ends in `.dshl`, no `.dshl.inl` occurs, and the 20 `.sh`
files in the shader directories are compile scripts, not shader source.

**Two needs of DSHL fall outside the contract.**

- A call or a use at file scope has no holder, and the graph drops it: 23 calls and 357 uses in the tree.
- A use binds only to a symbol of its own file, its package or a dot-imported package. DSHL has no package, so a read of
  a global that an included file declares binds to nothing, though the includes say where it is. Binding it needs a
  tier that follows includes; a package for each directory would bind a game's shader to the copy of
  `shader_global.dshl` that another game holds.

## Considered Options

- **Resolve an include only where one file has its spelling** — no edge is a guess, but the 286 includes that nearness
  resolves to the including game's own copy stay imports.
- **Read the build configurations** — the `.blk` files name the include paths, but a configuration includes other
  configurations and is chosen for each platform, and it still does not say which game's configuration compiles a
  library file. The resolver would become a model of the build system.
- **Record an edge to every candidate** — an include of `shader_global.dshl` would claim seven files, and the contract
  has no way to mark edges as alternatives.
- **Parse HLSL with a second grammar** — it is a separate language over the text ranges, and out of the scope of this
  crate.

Revisit when the contract gains a tier that binds a use through includes, or when the build configuration becomes an
input of the graph.
