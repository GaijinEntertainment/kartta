# Give a daslang call to the code that runs it

- **Date:** 2026-10-16
- **Governs:** `crates/kartta-lang-daslang/src/walk.rs` (`anonymous_scope`, `block_call`, `constructor`, `new_call`,
  `data_macro`, `data_arguments`, `data_block`, `splice`)
- **Pinned by:** `crates/kartta-lang-daslang/tests/extract.rs` (`an_applied_block_keeps_its_calls_in_the_enclosing_def`,
  `a_stored_block_keeps_its_calls_out_of_the_enclosing_def`, `a_macro_splice_in_call_position_records_no_call`,
  `quoted_code_records_a_call_as_a_use_of_its_name_and_no_call`,
  `a_qmatch_pattern_records_no_call_but_the_matched_expression_runs`,
  `a_qmacro_records_the_calls_of_its_splices_and_none_of_the_rest`)

A daslang `def` writes code that runs elsewhere: a block stored for later, and code a macro takes as data and compiles
where it expands. A call is credited to the `def` only where the `def` runs it, so a `def` is not listed as the caller
of what it merely defines or quotes, and a call in stored or quoted code has no caller in the graph.

## Decision

- **Blocks.** A block applied in place, as the argument of a call, a `new` or a pipe (`query() <| $(eid) { ... }`),
  runs in its enclosing `def`, so its calls are that `def`'s. A block or a local function stored in a name runs when
  the value is called, so its calls belong to no symbol, and the graph drops them. A block applied to a field,
  `obj.handler { ... }` or `obj.handler <| ${ ... }`, is a call of `handler` on `obj`, though no call node of the
  grammar covers it; a data pipe, `obj.field |> f()`, calls nothing through the field.
- **Constructions.** `T(...)` and `new T(...)` are calls of `T`. `default<T>`, a `new` over a container or a
  make-expression, and a macro splice in call position name no symbol and record nothing.
- **Code a macro takes as data.** The walk records no call in these arguments:
  - every argument of `quote`, `qmacro`, `qmacro_block`, `qmacro_block_to_array`, `qmacro_expr` and `qmacro_type`;
  - the arguments after the first of `qmacro_function`, `qmacro_variable`, `qmatch`, `qmatch_block` and
    `qmatch_function`, and after the first two of `qmacro_method`, so a `qmatch`'s matched expression runs and its
    pattern does not;
  - a block after the call, `macro(args) <| data` or `macro(args) { data }`, which counts as its last argument.

  Inside a `qmacro*` argument a splice, `$e`, `$i`, `$v`, `$b`, `$a`, `$t`, `$c` or `$f`, runs where the macro
  expands, so its expression's calls are the enclosing `def`'s; what follows the expression, such as the arguments of
  `$c(name)(...)`, is data again. A `qmatch` capture such as `$e(x)` reads only a name, and its pattern stays data.
- **Names in data.** What data calls, constructs or takes the address of is a use of the name, as the daslang rule of
  [ADR 3.66](/design-docs/adr/3.66-uncalled-name-reads.md) states. A member call in data records nothing.
- **Which macros read data.** A macro is read as data only where its callee is a bare identifier:
  `shell::quote(path)` is an ordinary call. `match`, the `_sql_*` macros, `qmacro_template_function` and
  `qmacro_template_class` are ordinary calls, and so is `data |> qmatch(pattern)`, which passes the data first.

## Why

- A block stored in a name runs when the value is called, not where it is written, and giving its calls to the `def`
  that only defines it would list that `def` as their caller.
- Each macro's compiler class decides what is data, in dagor's daScript tree (`prog/1stPartyLibs/daScript`): `quote`
  is the builtin `ExprQuote`, which type inference visits no argument of; `qmatch*` (`daslib/ast_match.das`) visit
  argument 0 alone; the `qmacro*` family (`daslib/templates_boost.das`) visits no argument or only the name and the
  class, and `QRulesVisitor.visitExprTag` copies a splice's expression into the block that runs where the macro
  expands.
- `match` visits its arguments and mixes guards that run with shapes; the `_sql_*` macros take a SQL dialect; the
  `qmacro_template_*` macros take `@@F` and `type<T>`, which name what exists.
- A call in data named a function that need not exist, so it bound a namesake or counted as ambiguous: 1,392 such calls
  of 356,313 on the game-engine tree (2026-10-23, #251).
- The code compiled from data calls the names it spells, so a name the graph left unrecorded would let `dead_code` list
  a function that only generated code calls, `qm_extract` or `to_sql_literal`, as unused.

## Consequences

- A member call in data, whose receiver there is a variable's name and no type, reaches nothing: about 40 records on
  the game-engine tree, and no method becomes unused for it. Accepted.
- `data |> qmatch(pattern)` reads its pattern as code; no use on the tree. Accepted.

## Rejected

- **Leave the calls in data** — keeps the 1,392 calls that bind namesakes or count as ambiguous.
- **Drop the calls in data and record nothing** — lists 98 more daslang definitions as unused on that tree, 78 of them
  defined in the file of the macro that emits calls to them.
- **Keep `_::f` as a qualifier** — leaves 36 more definitions unused where reading it as a bare `f` leaves 9; `_` is
  the compiler's name for the scope that compiles the code.
- **Read every argument as data, the splices too** — loses the 42 calls the splices hold, each of which runs.
- **Read a `qmatch`'s argument 0 as data** — drops a call that runs.
- **Only `quote` and `qmatch`** — leaves 1,285 of the 1,392 calls in place; the `qmacro` family holds the rest.

## Revisit if

The daScript macro library adds a macro whose compiler class reads an argument as syntax. Held with high confidence for
the macros listed: each was read from its source.
