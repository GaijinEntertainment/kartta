An engine of a large tree peaks past a gigabyte, and an agent's session asks about one repository. The server holds
one engine: a new `index_repo` cancels a build under way, and its own build waits until no query holds the engine it
replaces, so the process never holds two. An `index_repo` that names no readable directory, or repeats the request the
held index answers, keeps that index. Work a request no longer needs stops when the client cancels it.

## Decision

- **One repository.** The process indexes one repository at a time, and indexing another replaces it.
- **At launch.** A root given as the argument, or as `KARTTA_ROOT` when there is none, starts the build before any call.
  Until it ends, `index_stats` answers `status="building"` with the seconds so far, and every other query answers a
  tool error saying so. A launch build that ends without an index writes why on stderr.
- **The root.** An `index_repo` whose root is not an absolute path, or names no directory the server can read, is a tool
  error before the slot changes, so the index held stays. A launch root may be relative: the operator's shell sets the
  directory it resolves in.
- **A repeat.** An `index_repo` of the request being built, the same root, languages and `index_ignored`, waits for it.
  A repeat of the request the held index was built from answers that index: at once while it follows its tree, after a
  whole refresh while its watch is off, and rebuilt only when a refresh that panicked broke it.
- **A rebuild.** Any other `index_repo` cancels a build under way, and cancels a refresh of the engine it replaces. The
  new build starts once the cancelled build has ended and every query holding the replaced engine has answered.
- **No index.** `index_stats` answers an `<index>` envelope in every state the slot can hold: `status="empty"` before
  any build, `status="building"` during one, `status="failed"` with the root and the error after one that failed.
- **Cancel.** A request the client cancels with `notifications/cancelled` cancels its `grep`'s token
  ([ADR 1.70](/design-docs/adr/1.70-content-search-batches.md)), which each file checks before it is opened,
  so a cancelled search ends with the files already being read. The answer of a cancelled request is never sent.

## Why

- Two engines at once double a rebuild's peak memory, to answer about a tree the caller asked to replace (#74).
- A build at launch starts before the agent's first call, where `index_repo` starts it only when the agent asks.
- A mistyped root replaced the held index with a failure, so every later query answered that failure (#1033).
- A followed index already holds what a rebuild of the same request would build. On the Go monorepo snapshot at 4
  threads a repeat rebuilt in 6.2 to 6.7 s, every other tool answering an error meanwhile, where the held index answers
  in 8 ms, and in under 0.2 s after a whole refresh (2026-11-03).
- A search nobody waits for holds the index's threads: a grep of the macOS data volume takes about 12 s, which a
  cancelled request spent in full before the cancel reached the search (2026-10-19).

## Consequences

- An agent moving between repositories rebuilds each time. Accepted.
- A query that arrives during a rebuild answers an error until the build ends. Accepted.
- A repeat of a followed index answers before the watch delivers an edit made just before it, as any query does.
  Accepted.
- Each `index_repo` opens its root once before the slot changes. Accepted.

## Rejected

- **Keep the replaced engine serving while a rebuild runs** — doubles a rebuild's peak memory, to serve answers about a
  tree the caller asked to replace.
- **Resolve a relative `index_repo` root against the server's directory** — indexes a tree the agent cannot see and did
  not name.
- **A `force` parameter on `index_repo`** — schema text every session pays for, where `refresh` already brings an index
  up to its tree.

## Revisit if

Agents work across several repositories in one session often enough that rebuilds cost more than a second engine's
memory.
