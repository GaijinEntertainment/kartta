# Answer where a refresh walked and where its kept entries went

- **Date:** 2026-10-21
- **Governs:** `crates/kartta-fs/src/index.rs` (`RefreshOutcome::walked_over`, `RefreshOutcome::kept_positions`,
  `RefreshOutcome::position_after`, `RefreshOutcome::walked_positions`), `crates/kartta-fs/src/index/changed.rs`
- **Pinned by:** `crates/kartta-fs/tests/refresh.rs` (`a_refresh_walked_over_the_paths_inside_its_parts_and_no_other`,
  `a_refresh_says_where_each_entry_it_kept_sits_now_and_what_its_parts_hold`,
  `an_entry_that_changed_kind_in_place_is_not_kept`, `a_refresh_that_only_read_files_again_kept_every_position`)

A consumer that keeps something per file or per index position, as an engine that follows its tree does
([ADR 3.33](/design-docs/adr/3.33-refresh-dependency-tracking.md)), must learn after a refresh which of its data the
refresh reached. `RefreshOutcome` answers both by a binary search of what the refresh already holds, the walked parts
and the runs its splice replaced, at 32 bytes a run.

## Decision

- **Walked over.** `RefreshOutcome::walked_over` says whether a refresh walked again the part that holds a path spelled
  as `Index::entries` spells one. The parts in `RefreshOutcome::walked` are kept in the index's tree order, none below
  another, so the one part that can hold a path is the last at or before it in that order, which a binary search finds.
- **Kept positions.** `RefreshOutcome::kept_positions` answers whether every position holds after the refresh the entry
  it held before, with the same path and kind: true of a refresh that only read files again, false of one that added,
  removed or retyped an entry.
- **Where an entry went.** `RefreshOutcome::position_after` maps a position from before the refresh to after it, by a
  binary search of the runs the splice replaced; it answers `None` inside a part walked again and past the entries the
  index held before.
- **What the parts hold now.** `RefreshOutcome::walked_positions` gives the positions the replaced runs hold after the
  refresh, in rising order, one run for parts that lay side by side, empty for parts that hold nothing now.
- **Taken from the splice.** The splice already compares each run before and after it to list the files added and
  removed, so it notes each run and whether an entry came, went or changed kind as it goes, 32 bytes a run.

## Why

- A test of every path against every part costs the two counts multiplied: the engine's test of the files its
  resolvers read took up to 1.05 s of a refresh at its limit on 2.92M entries, where the binary search took at most
  12.6 ms (2026-10-21, #158).
- A splice shifts every position after a part whose count of entries changed, so without the map a consumer could only
  build its per-position data again from every entry: building the table of files by name took 222.7 ms of a 305.9 ms
  one-file refresh on 2.92M entries (2026-10-21, #312).

## Consequences

- An entry inside a walked part has no position from before; a consumer reads those positions again (accepted).

## Rejected

- **Test each path against every part walked** — costs the paths times the parts, up to 1.05 s at the limit on 2.92M
  entries.
- **Rebuild per-position data from every entry after each refresh** — a pass over every entry on every refresh, most of
  a one-file call.

## Revisit if

A consumer needs to know which entries inside a walked part kept their position. Medium confidence: the engine reads
every walked part again.
