# Reach the engine through one JSON call over a small C ABI

- **Status:** accepted
- **Date:** 2026-10-18
- **Revised:** 2026-10-21
- **Initiative:** `04-consumer-surfaces`

Go and Node consumers reach the engine across a C boundary. `kartta-ffi` is that boundary: a static library exporting
five functions, every method a name and a JSON object of params, every answer JSON. One dispatch serves every binding
and every test, so a method is a match arm and never a new export, and a binding translates JSON and decides nothing.
serde lives in this crate alone; the library crates carry no wire derives.

## The ABI

`crates/kartta-ffi/include/kartta.h` is hand-written and committed: `kartta_abi_version`, `kartta_open`, `kartta_call`,
`kartta_string_free`, `kartta_free`. cbindgen is MPL-2.0, which `deny.toml` does not allow, and the surface is five
functions. The Go binding's cgo build compiles the header and links every function it declares, in CI on Linux and
macOS, so a header that drifts from the library fails there.

- **`kartta_open`** takes `{"root": <path>}` and answers a handle, or null with the structured error
  `{"code", "message"}` written to an out-parameter: never a bare null for a caller that asks for the reason.
- **`kartta_call`** takes a NUL-terminated method name and the params' bytes, and answers `{"ok": <answer>}` or
  `{"err": {"code", "message"}}`, never a null string.
- **Ownership:** arguments are borrowed for the call; every returned string is the caller's, freed once.
- **`kartta_abi_version`** returns 1, which the header's `KARTTA_ABI_VERSION` must equal; the Go binding checks it at
  open. It changes only when a binding built against an older header would misuse the library. The `version` method
  lists the methods and languages a library answers.
- **Panics:** every entry point runs under `catch_unwind`. `kartta_open` and `kartta_call` answer the code `internal`
  and the handle stays usable; the frees, which answer nothing, drop a panic. That holds only for a library built with
  unwinding panics.
- **Crate types:** `staticlib`, which cgo links, as Kensai's static musl binaries need, and `rlib`, which a Rust shell
  such as a napi-rs addon builds on. No `cdylib`: neither consumer loads one, each crate type is a full link per build,
  and a shared library beside the archive would make `-lkartta_ffi` link dynamically on macOS.

## The wire

kartta's own JSON, keeping the method names Kensai already calls where the meaning holds, with no compatibility layer
for the shapes it reads today; Kensai migrates once.

- **Lifecycle:** `build`, `cancel`, `stats`, `version`, `resolution`.
- **Graph:** `callers`, `callees`, `call_path`, `references`, `definitions`, `sources`, `search`, `implementations`,
  `dead_code`, `outline`, `dependents`, `analyze_segment`, `analyze_change`.
- **Files:** `list`, `glob`, `fuzzy`, `grep`.
- **Answers carry what they left out.** Every capped or bounded answer is an object with the engine's counts:
  `total`, `truncated`, `turned_away`, `unexpanded`, `below_confidence`, `passed_over`, `unresolved`, grep's
  `unsearched` and its account of every candidate, a listing's `excluded` and `unlisted`. A bare array for search,
  implementations, dead code or dependents would have nowhere to put them.
- **A graph query names no graph by default:** it answers one match per graph the name selects a symbol in; `lang`
  names one graph by a language or its family. A file query answers the graph that claims the file and whether it holds
  it.
- **Params refuse unknown fields,** one type per method, because a silently ignored option is worse than an error;
  answers may gain fields. A bound left out or 0 takes the method's default: callers 3 calls deep, callees 1, a walk
  500 symbols, a call path 8 deep and 20,000 symbols, 500 references, 10 definitions, 20 search hits, 100 implementors,
  dependents 3 deep and 100 files, 100 dead definitions, a listing 1 level and 1,000 entries, 50 fuzzy matches, and
  grep 100 matching lines, 1,024 bytes a line and 4 MiB a file. Only the caps a caller can lift take 0 as none: a
  listing's depth and entries, glob's and grep's matches, dependents' files, and the lines and line bytes of a source.
- **Dropped:** `paths` (150 MB of JSON on three million entries, and no consumer calls it), `len` (folded into
  `stats` as `entries`), `grep_index/build` (the content index is a `build` option, made in the same walk), and
  `validate_globs` (a bad glob answers `invalid_glob` from the call that takes it).
- **Golden files** under `crates/kartta-ffi/tests/golden`, one method each, pin a request on a fixture tree and its
  answer. A Rust test replays them through the dispatch and the Go binding's test through cgo. For a method with a
  typed call, the Go test decodes the request into its typed params and encodes the typed answer back, so a Go type
  that drops a field the wire sends fails it; the other methods replay as raw JSON through `Call`. Both match every
  value exactly but a `score`, which agrees when it is within a relative 1e-12 of the pinned one, as the Node
  binding's test does (ADR 4.3). The Rust test parses the files with serde_json's `float_roundtrip`, so a file it
  blesses pins the score the engine answered on the blessing OS to the last bit, and the comparison still takes any
  score within the tolerance. Revised 2026-10-21: both matched scores exactly too, so a golden passed only on an OS
  whose libm rounds as the blessing one did. `search`'s scores pass through `ln_1p` in `inverse_frequency`, and Apple's
  libm and glibc 2.41 round its result one ulp apart for 76 of the 820 pairs of 1 to 40 definitions and 1 to as many
  holders; the fixture with `Circle`'s constructor defined in `circle.cpp` scored 3.5799073758139874 on macOS and
  3.579907375813988 on Linux. 1e-12 holds thousands of ulps of a score and less than a change of one in its twelfth
  significant digit.

### Error codes

| Code | Meaning |
| --- | --- |
| `invalid_request` | A null handle or method, null params with a length, bytes not UTF-8, or params not JSON |
| `invalid_params` | JSON that is not the method's params: an array or scalar, an unknown field or language, a wrong type |
| `unknown_method` | No method of that name; the message lists the methods |
| `invalid_root` | `open` could not read the root's metadata, or the root is not a directory |
| `not_built` | The method needs a build and none has finished, or the last failed or was cancelled |
| `building` | The method needs a build and one is in flight |
| `build_failed` | The build stopped on a failure that leaves no index |
| `build_cancelled` | A cancel stopped the build |
| `invalid_glob`, `invalid_pattern` | A glob or a content pattern does not compile |
| `not_found`, `not_a_directory` | `list` names a path the index does not hold, or one that is not a directory |
| `internal` | The engine panicked, or an answer could not be encoded |

## Lifecycle and concurrency

- **`open` names the tree; `build` walks it once** and builds the index, the optional content index and every graph
  (ADR 3.6), replacing what an earlier build made. It drops the old engine before walking, so a handle never holds two;
  a query already running keeps the engine it asked until it returns.
- **Queries run concurrently** with each other and with `cancel`, each reading the engine through a shared reference.
  **Builds run one at a time.** A build empties the slot when its turn comes, so while it runs a query answers
  `building`; while it still waits its turn, queries answer from the engine the last build left.
- **A fresh cancel per build.** A build enters the library under a token of its own, registered before it waits its
  turn, and the caller names it with an id it uses once. `cancel` with that id trips it, running or waiting; an id
  that has not entered yet is remembered, so a context that fires before its build reaches the library
  still stops it, and a cancel that comes after its build finished stops a later build that reuses the id; `cancel`
  with no id stops every build in flight. A cancel with no id while no build is in flight never stops a later build,
  as one token per handle would. A build whose token was tripped answers `build_cancelled` even when its walk had
  finished, so a cancel that reported `stopped` always wins. A query that finds no engine looks again under the lock a
  build publishes under, so a build finishing beside it never reads as `not_built`.
- **At most 1,024 ids are remembered,** the latest, and as many for greps. A new id past them forgets the oldest,
  which then stops nothing, and `cancel` still answers `stopped` false. A cancel comes ahead of its call while the call
  is on its way to the library: a build between naming its id and entering, and a Node query also while it waits for
  one of libuv's pool threads. A binding's close that lands on a burst of builds, each on a thread of its own, finds
  many of them on their way: over bursts of 50 to 2,000 builds of `/usr/share`, 30 of each size, each followed by a
  cancel per id as a close sends them, at most 156 cancels came ahead of their build in one burst. Under a bound of 64,
  41 of the 3,000 builds in bursts of 100 and 110 of the 6,000 in bursts of 200 ran uncancelled; under 1,024, every
  build a cancel came ahead of stopped. A close that lands while more than 1,024 builds are on their way leaves all
  but the latest 1,024 running. A remembered id takes 8 bytes, 8 KiB at most, and a build or a grep with an id scans
  the remembered ids once as it enters: 0.6 ns when one is remembered and 240 ns when 1,024 are and its id is not among
  them, on an M5 Max. Revised 2026-10-19: the ids had no bound, so a consumer that cancels after its calls finish grew
  the list for the life of the handle, and every call with an id scanned all of it.
- **A grep is cancelled the same way.** It is the one query long enough to need it — about 12 s over a data volume —
  so it takes an `id` as a build does, under a registry of its own: `cancel` names a build with `build` and a grep
  with `grep`, the two ids never stop each other's calls, and `cancel` naming neither stops every build and every grep
  in flight. A cancelled grep answers what it covered, `cancelled` set and the rest counted `unsearched` (ADR 1.11).
  A cancel that lands after the search opened its last file still reports `stopped`, and the grep answers whole with
  `cancelled` false: the answer's own `cancelled` says whether the cancel turned a file away, and unlike a build's, a
  finished search is worth keeping. Revised 2026-10-19: the answer carried `cancelled` from the first, but nothing could
  set it.
- **A cancelled or failed build leaves no index,** the file index included: a cancelled walk holds whichever entries
  its threads reached, so there is nothing worth keeping, and the consumer's own deadline is what cancels. Kensai's
  rule that file tools outlive a failed graph build does not survive the fused build.

## The Go binding

`bindings/go`, module `github.com/GaijinEntertainment/kartta/bindings/go`, `go 1.27.2`, no dependencies.

- **`wire`** holds the params, answers and error codes with no cgo, so code that only handles answers builds and tests
  without the library, the split Kensai's tools rely on. A `wire.Code` is an error, and a `*wire.Error` unwraps to its
  code, so `errors.Is(err, wire.NotBuilt)` matches.
- **`kartta`** links `libkartta_ffi.a` statically through cgo, from the same checkout: the header is read from
  `crates/kartta-ffi/include`, the archive's directory comes from `CGO_LDFLAGS`. A `Kartta` is safe for concurrent use:
  calls share a read lock, `Close` cancels the builds in flight and takes the write lock. `Build(ctx, …)` gives its
  build an id and trips it once `ctx` is done; the error then matches both `wire.BuildCancelled` and the context's
  cause. A `runtime.AddCleanup` frees a handle nobody closed.
- **Typed calls cover the methods Kensai calls,** each answering its `wire` type, a graph query's as a
  `wire.Matches[T]` with one part per graph. `callees`, `dead_code` and `resolution`, which it does not call, go
  through `Call`, with the wire types or raw JSON.

## The allocator

The library crates stay allocator-neutral (ADR 1.18); `kartta-ffi`'s archive is a final artifact and could set one.
Kensai ships static musl, so the choice was measured under musl: cold engine builds of the game-engine tree, all
sixteen languages, no cache, `threads` 4, in an Alpine container (musl 1.2, aarch64) limited to 4 CPUs, the tree
mounted from the macOS host, variants interleaved, two rounds each on a host shared with other builds:

| | build | peak | resident after the build |
| --- | --- | --- | --- |
| musl's malloc | 99.0–100.3 s | 688–691 MB | 666–673 MB |
| mimalloc 3.3 | 89.2–89.3 s | 1,000–1,010 MB | 778–1,010 MB |
| mimalloc, purge delay 0 and a forced collect after the build | 88.4–91.6 s | 738–757 MB | 661–681 MB |

**The library sets no global allocator: musl's malloc stays.** mimalloc builds about 10% faster, and tuned to purge at
once and collect after the build it ends where musl does, but it peaks 50–70 MB higher, and it brings two crates and a
C build into the archive for it. Untuned, it peaks 45% higher and keeps up to half again as much resident. musl hands
freed memory back without a trim: it peaks below what glibc reached with both trims in ADR 1.18, 1,059–1,400 MB, and
ends where glibc did after them. The build times are not comparable to ADR 1.18's: under this session's load and mount,
neither allocator came near its 27–33 s, and no glibc build ran beside them.

Revisit when build time matters more to a consumer than its peak, or when a glibc build of the same session shows the
musl build's time is the allocator's.

**Revised 2026-10-19: a name's methods take a path prefix, and an answer lists what it passed over.** `callers`,
`callees`, `references` and `implementations` take `path_prefix`, and `call_path` takes `from_path_prefix` and
`to_path_prefix`, which keep the symbols a name selects to the files under them (ADR 3.35). A `callers`, `callees`,
`references` or `implementations` answer that passed symbols over carries `candidates`, at most five, each a
`symbol` and the `count` the query ranks by; a `call_path` match carries them per end, as `candidates.from` and
`candidates.to`. The key is absent when nothing was passed over, so every other answer keeps its bytes; the Go and
TypeScript wire types carry both.

**Revised 2026-10-19: a `callers` match lists its file-scope callers.** A walk over callers carries `file_scope`: each
file whose top level calls or uses the root's name and sees the root, as a `file` and the `confidence` of how it sees
it, in path order (ADR 3.23). `below_confidence` also counts the files the floor drops. A file-scope caller has no line,
because the graph keeps only the names a top level spells. The key is absent when no file's top level names the root,
so a `callees` answer and every other `callers` answer keep their bytes; the Go and TypeScript wire types carry it.

**Revised 2026-10-20: `glob` and `fuzzy` take an exclusion.** Each takes `exclude`, globs in the query dialect that
remove a matched path and everything beneath a matched directory before the limit is spent, as `list` and `grep` take
one (ADR 1.4). A `glob` answer carries `excluded`, the matches the exclusion removed before the answer ended; the key is
absent when it is 0, so an answer without one keeps its bytes. The field is optional, so a request written before it
reads as it did and breaks no caller, Kensai's included; the Go and TypeScript wire types carry both.

**Revised 2026-10-20: a `fuzzy` answer counts its matches.** It carries `matched`, how many paths matched every term
of the query, those past the limit included, beside `truncated`, which still says only whether the limit cut the answer
(ADR 1.5). The ranking counts what it scores, so the field costs no pass of its own. A query with terms always carries
it, 0 included, and an empty query never does: the index does not count one (ADR 1.5), and an absent key never reads
as no match. A new field in an answer is additive, since params refuse unknown fields and answers may gain them: no
caller breaks, Kensai's included. The Go and TypeScript wire types carry it, and the golden request asks a query its
limit cuts, so it pins `matched` past the answer.

**Revised 2026-10-20: the callers, segment and change answers count the ambiguous calls.** A `callers` match, a
segment's symbol and a changed symbol carry `ambiguous`: the calls of the symbol's name that bound no definition because
several definitions of the name may be meant, which the MCP answers count as `ambiguous=` (ADR 4.1). Any of them may
call the symbol, and none is among the match's `reached`, the symbol's `callers` and `blast`, or the seed's
`caller_count` and `reach`, so a consumer that reads an empty caller list as dead code learns that calls may reach the
symbol. The engine counts them for these answers already, so the field costs no work. The key is absent when the count
is 0, as `glob`'s `excluded` is, so an answer without such calls keeps its bytes, and a `callees` answer never carries
it. The field is additive under the rule above: no caller breaks, Kensai's included. The Go and TypeScript wire types
carry it. The fixture's two Go methods of one name, one of them called on a value whose type the graph does not follow,
pin it in the callers, segment and change goldens.

**Revised 2026-10-20: a symbol method reads a name with the other owner separator.**
- **The defect:** the methods selected by a name's separators as written, while Rust and C++ qualify a member with `::`
  and Go, Python and TypeScript with `.`. A consumer that asked for `Index.refresh_paths` in Rust got no match and no
  hint, where the MCP tools read the same name as `Index::refresh_paths` (ADR 4.1).
- **The shape:**
  - `callers`, `callees`, `references`, `implementations`, `definitions` and `sources` read a qualified name that
    selects no definition of the kinds the method takes, in the graphs it asks and under its path prefix, with each `.`
    as `::`, or else each `::` as `.`, the first reading that selects one. The answer carries the reading as
    `read_as`, beside `matches`. `call_path` reads each end on its own, into `from_read_as` and `to_read_as`.
  - The keys sit beside `matches`, not in each part: one reading is chosen across the graphs asked, so every part
    answers for it. A reading the method then answers nothing for, as a suffix several definitions end with, or a
    `call_path` whose other end selects nothing, still names what was read, over an empty `matches`.
  - A name that selects as written is never read another way, and its answer carries no key and keeps its bytes. The
    keys are additive under the rule above: no caller breaks, Kensai's included.
  - The reading is the engine's own, `kartta::ask_reading`, which the MCP tools call too, so the two surfaces read a
    name one way.
  - The Go `wire.Matches` and the TypeScript `Matches` carry all three keys, as the type every graph query answers, so a
    typed call keeps its signature. The definitions golden asks `Circle.area` for C++'s `Circle::area`, and the
    call_path golden `main::main` and `main::helper` for Go's `main.main` and `main.helper`, so both bindings' types
    are held to the keys; every other golden asks in its language's own spelling and pins their absence.
- **No alternatives on the wire.** The MCP answers a name neither spelling selects with up to 5 close alternatives, a
  search of each graph by the name. The engine holds no such list when a wire miss answers: it costs that search, which
  `search` already answers for the same name, ranked and counted. An empty `matches` with no reading says the name
  selects nothing in either spelling, so a consumer that wants the alternatives asks `search` and pays for them only
  then.
- **Measured with the C ABI wire harness against `main`,** on the C++ game-engine tree and the Go monorepo snapshot:
  - Its plan asks each sampled name in its language's own spelling, and all 1,671 and 1,074 answers are identical.
  - Each sampled qualified name was then asked of the seven methods in the other spelling, 93 names on the C++ tree and
    58 on the snapshot. `main` answered every one of them empty. The branch answered all 554 and 345 calls the own
    spelling answers exactly as it does, plus the reading. The rest are empty in both spellings, the implementors of a
    name that is no type among them: 91 and 57 carry no reading, and 6 and 4 `call_path` calls between two graphs
    name their ends' readings over an empty `matches`.
- **Cost:** a name answered as written runs the queries it ran before and allocates what it did, one list of the parts.
  Per-call medians, 1,000 calls each in 3 rounds of `main` and the branch in alternation, at load 12–50:
  - as written, `callers` 17.0–17.5 µs against 16.6–17.8 µs on the C++ tree and 29.8–30.5 µs against 30.0–30.4 µs on
    the snapshot; `definitions` 1.8 µs against 1.7–1.8 µs and 0.8–0.9 µs against 0.9 µs;
  - in the other spelling, the branch answers in the own spelling's time and 2 µs more, `callers` 18.7–19.5 µs and
    32.0–32.3 µs, where `main` answered nothing in 1.3 µs and 1.0 µs;
  - in neither spelling, a definition lookup per graph and spelling: `callers` 2.3–2.4 µs against 1.2 µs, and 1.9 µs
    against 1.0 µs;
  - the alternatives the wire does not list: a `search` of the same name answers in 22.9–31.6 ms on the C++ tree and

  The build runs none of it.

Considered:
- **The reading in each part:** a reading the method answers nothing for would leave no part to carry it, and the same
  string would repeat in every graph's part.
- **A type of its own for the `call_path` answer in the bindings:** the Go `CallPath` call answers a
  `wire.Matches[wire.CallPath]`, and a new type would break every caller that names it.

**Revised 2026-10-20: a `references` part says when a type's uses as a type go unrecorded.**
- **The defect:** Rust, C and C++, TypeScript and JavaScript, PHP, Ruby, daslang and Puppet record no use of a type
  where code names it as one, such as a declaration, a signature, a generic argument or an import: their conventions
  state `TypeUses::Nowhere` (ADR 3.1). Such a type named only so answered no site and a `total` of 0, which a consumer
  such as Kensai reads as an unused type, while `find_references` names the language that records none (ADR 4.1).
- **The shape:**
  - A part whose `symbol` is a type, by `kartta::is_type_kind`, and whose graph's conventions state
    `TypeUses::Nowhere` carries `type_uses_unrecorded`, true: its `sites` hold only the calls that name the type and,
    where the language records them, its reads as a value. The key is absent otherwise, so the part of a type whose
    language records some or every use of one, as Go, Python, DSHL and Quirrel do, and of every symbol that is no type
    keeps its bytes. The key is additive under the rule above: no caller breaks, Kensai's included.
  - A flag on the part, because what a consumer acts on is whether that part's `sites` can stand for every use of the
    type. It reads the answer it holds and needs no list of kartta's languages, which would fall behind them.
  - A language that records some uses of a type, as Python records an annotation inside a body, carries no key: its
    sites hold the uses it records, and `find_references` answers such a type as before as well.
  - `kartta::is_type_kind` is the graph's own test of a type, which the MCP tools read too in place of a copy of their
    own, so both surfaces tell a type the same way. Their answers are unchanged: the parity harness answered all 21,096
    calls on the C++ game-engine tree and all 24,238 on the Go monorepo snapshot as `main` did.
  - The Go and TypeScript wire types carry the key. The C++ fixture gains a constructor of `Circle` and a call of it,
    and the references golden asks `Circle`: a class with a call site, the constructor passed over as a candidate, and
    the key.
- **Measured with the C ABI wire harness against `main`** on the C++ game-engine tree and the Go monorepo snapshot:
  only `references` answers differ, each by the key alone, 18 of 328 and 40 of 212. The other 1,654 and 1,035 answers
  are identical.

  | tree | language | answers with the key |
  | --- | --- | --- |
  | C++ game-engine tree | C and C++ | 14 |
  | C++ game-engine tree | TypeScript and JavaScript | 4 |
  | Go monorepo snapshot | C and C++ | 26 |
  | Go monorepo snapshot | Rust | 10 |
  | Go monorepo snapshot | TypeScript and JavaScript | 10 |

  Six snapshot answers carry it in two graphs, a C header's `typedef` and the Rust struct of the same name. The type
  parts in the other languages are unchanged: 4 in DSHL and 2 in Python on the C++ tree, 4 in Go and 4 in Python on the

- **Precision:** all 27 distinct types the key marks are true. In 24 the tree names the type where its language
  records no use: a field's, a parameter's or a return type, a pointer, a cast, a template or generic argument, an
  annotation, an import, a union of types or an `impl`. The other 3 are C struct tags that only the `typedef` aliasing
  them names, and code names the alias.
- **Cost:** per part, a read of the conventions the graph holds and a match on the symbol's kind, with no allocation;
  an answer grows by the key's 28 bytes only where it is set. The harness's `references` calls, timed one by one in
  10 rounds per run, `main` and the branch in alternation, 7 pairs on the C++ tree in both orders and 3 on the
  snapshot, at load 15–41: per-call medians 4.6–5.9 µs against 4.6–5.5 µs, and 2.5–3.2 µs against 2.5–2.7 µs. In the

Considered:
- **The conventions' label on every type's part,** `type_uses` as `nowhere`, `partial` or `every`: the part of every
  Go and Python type gains a key, and a consumer has to learn what each label leaves out to act on the one value that
  changes how it reads the sites.
- **The conventions per graph in `stats`:** a consumer joins them to each part by its graph and has to know that they
  bear on a type's sites alone.
- **A note in words, as the MCP answer carries:** the wire answers facts a program reads, and ADR 4.1 words them for an
  agent.

## Considered Options

- **A drop-in for the ABI Kensai calls today** — its three-step open, grep-index build and graph build cannot map onto
  one fused walk without walking twice, the cost ADR 3.6 removed, and its bare arrays have nowhere to put a count.
- **Typed C structs, or a schema'd binary format** — every answer a C layout marshalled in Go and again in JS, and
  every new count an ABI break; answers are kilobytes, where JSON costs nothing next to the query.
- **A cancel token per handle** — one stray cancel stops every later build.
- **A bound on remembered cancel ids that refuses a new one** — once stale ids fill it, no cancel that comes ahead of
  its call is remembered again. Telling a stale id from an early one would mean remembering the ids of finished calls,
  a second list every call writes to.
- **A ring for the remembered ids** — it forgets the oldest of 1,024 in 2.5 ns where the list takes 66 ns, but scans
  one or two remembered ids 0.3–0.4 ns slower, and the scan runs on every call with an id while the forgetting runs
  only on a cancel past the bound.
- **Keep the old engine until the new one is built** — two engines at the build's peak.
- **A `cdylib` beside the archive** — no consumer loads one, and it changes what `-lkartta_ffi` links on macOS.
