# Keep the graph a file at a time

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-17
- **Initiative:** `03-code-graph`

kartta's index refreshes in place (ADRs 1.15, 1.16, 1.17), and the code graph must follow it: a file edited, added or
removed has to change what the graph answers without the graph being built again. A graph that numbers its definitions
densely, in path order, cannot do that cheaply: inserting one file shifts the number of every definition after it, so
an update renumbers that suffix and rewrites every edge and index entry that names a definition in it — for a file
early in path order, close to what building the graph again costs.

**A graph holds one language family's files, each in a slot.** `kartta_graph::Graph::insert` takes one file's
`Extraction` and puts its definitions in a slot, replacing whatever the graph held for that path; `Graph::remove`
empties the slot, and the next insertion takes it. A definition is addressed by its file's slot and its place in the
file, so one file going in or out renumbers nothing else: the name index loses the removed file's entries and gains the
new file's, and no other entry moves.

**Names are interned once per graph.** Every name, qualified name, owner and signature is stored once in one byte arena
and named by a 4-byte handle, which a definition stores in place of its strings. A string is never removed, so a graph
refreshed many times keeps the names of files it no longer holds; compacting the arena is left for when a refresh can
count how much of it nothing references.

**Answers borrow from the graph and say what they cut.** `Graph::outline` answers what a file defines, ordered by line,
and tells a file with no definitions, an empty outline, from one the graph does not hold, `None`.
`Graph::definitions` answers where a bare or qualified name is defined, nearest to the asking file first, then outside
test code, then by path and line, cut to a limit that its `total` reports.

**Revised 2026-10-17: a file's test flag also follows from the files that include it.** An extraction names the files
it pulls in as test-only modules, `test_includes`, where the included file is extracted on its own and cannot see the
gate, as the file of a Rust `#[cfg(test)] mod tests;` cannot (ADR 3.11). A file is test code, with every definition in
it, when every file that includes it lists it so or is such a test module itself, so the modules a test module declares
are test code too; a production file that includes it keeps it production code. Every answer and every query that
reads the flag reads it so: the ranking of definitions, dead code's `test` exclusion (ADR 3.23), the hotspots of an
analysis (ADR 3.22) and the names a directory package offers a call (ADR 3.7). The flag of a file depends on other
files, so the graph does not store it: it keeps the includers of each test include beside its includers, works out the
set of test modules the first time a query asks after an insert or a removal, and forgets the set on the next one. A
graph with no test include pays one emptiness check per definition read. On a Cargo registry of 16,978 Rust files this
marks 1,791 more definitions in 184 files as test code, 72 of those files modules that a test module declares, and the
whole-graph dead-code answer counts 61,930 test definitions against 60,139 and 74,551 dead against 74,698, in
1,004–1,903 ms against 996–1,889 ms at a load of 20 to 32, within its spread. The C++ game-engine tree holds no Rust
and the Go monorepo no test-gated `mod` with a file, so neither answer changes there.

How calls and references resolve is not decided here. Resolving every call when a file goes in ties each edge to
definitions in other files, which a change elsewhere can invalidate; resolving a name's calls when a query asks for it
keeps a file's data its own. Both are to be measured before the call graph is built.

## Considered Options

- **Dense ids in path order, with edges in compressed rows** — compact and fast to query, and rebuilt whole on any
  change.
- **Owned strings in each definition** — no interner to maintain, and every repeated name stored again.

Revisit when a refresh's leftover strings are measurable against the arena, or when the per-name lists of the name index
are a measurable share of a graph's memory.
