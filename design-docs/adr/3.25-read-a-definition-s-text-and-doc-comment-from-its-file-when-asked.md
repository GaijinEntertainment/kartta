# Read a definition's text and doc comment from its file when asked

- **Status:** accepted
- **Date:** 2026-10-17
- **Revised:** 2026-10-19
- **Initiative:** `03-code-graph`

An agent that looks a definition up wants to read it — its lines and the comment that documents it — without a second
call that reads the file and counts lines. The graph holds where each definition starts and ends and keeps no file text
(ADR 3.5), and the comment above a definition is no part of what an extraction records: only the language knows which
lines above a definition document it, in which comment forms, and which attributes, decorators or template headers the
declaration carries there.

**The text is read from the file when asked.** `Engine::sources` answers each definition it is given with its text, in
the order given: it reads each file once for all the definitions in it, as a stream that stops at the last line one of
them answers, its end or the line the caller's line cap stops it at, and splits the lines without their endings, a byte
sequence that is not UTF-8 reading as U+FFFD. The engine holds the index's root and the language of each path, which
the graph does not, so the query is the engine's. The lines are those the build found the definition on, so a file
edited since answers its new text there; `Source::resized` says whether the file's size differs from the size the build
read, which the index keeps for every file it read, at no cost. An edit that keeps the size goes unseen. A file that
cannot be opened or read answers its error, the message naming the file, for each of its definitions.

**Each language states its doc comments, and the query reads them above the definition.**
`Language::doc_comments` answers a `DocComments`: the line comments, the block comments and the carried lines of the
language, none by default. `DocComments::first_line` takes the run of lines directly above the definition that start,
after their leading whitespace, with one of them; a blank line ends the run. A line that ends with a block comment's
closing token, a line comment after it aside, closes a comment that counts whole up to the nearest line above that
starts with the opening token and leaves a comment open at its end, whatever the lines between hold. A line between
them that ends another comment means the token closes none: the closer of a comment opened after code on an earlier
line, `int x; /* counts the` and `rows */`, reaches no comment above the code. An opening token in the middle of a line
opens nothing the scan takes, because comment text holds it as often as code does, `src/*.c` and `http://*` among it.
A block comment whose closer can end code too, Lua's `]]` and Ruby's `=end`, closes only on a line of its own.

| Language | Line comments | Block comments | Carried lines |
| --- | --- | --- | --- |
| Go, TypeScript, TSX, JavaScript, daslang, DSHL | `//` | `/* */` | |
| C++ | `//` | `/* */` | `template ` and `template<` |
| Rust | `//` | `/* */` | `#[`, an attribute |
| PHP, Quirrel | `//`, `#` | `/* */` | |
| Python, Bash | `#` | | |
| Puppet | `#` | `/* */` | |
| Ruby | `#` | `=begin` to `=end` | |
| Lua | `--` | `--[[ ]]` and its levels to `--[===[ ]===]` | |

A Python definition's lines start at its first decorator, a TypeScript or JavaScript one's too since the revision
below, and a daslang definition's at its annotation, as their extractions record them, so none carries anything; a
Python docstring is inside the body and comes with it. A carried `@` would be wrong for TypeScript anyway:
`@Input() a: T;` is a field of its own, which a carried `@` would read as a decorator of the field below it. Carrying
`@` took in the decorators of 12 classes on the two trees and as many wrong lines: the decorated fields above 10
fields, and the decorators around 2 values that a decorator's argument defines. BLK states nothing: it extracts no
definition.

**Revised 2026-10-19: a TypeScript or JavaScript declaration starts at its first decorator.** tree-sitter keeps a class
member's decorators, and those written before `export`, beside the declaration rather than inside it, so a decorated
method or exported class started below its decorators: its doc comment above them was not found and its text left them
out. The extraction now starts a declaration at the first decorator of the run directly before it. On the two trees 42
classes start higher, each on a decorator line, which the source confirms for all 42; none has a doc comment above its
decorators there, so their text gains the decorators alone. The reference starts these declarations below their
decorators, as kartta did.

**The caps are the caller's.** `SourceOptions::max_lines` bounds the lines of an answer, the doc comment's included;
a definition longer than the cap keeps its head, and a doc comment too long to leave room loses its own head, so the
text always holds the definition's first line. `SourceOptions::max_line_bytes` cuts a longer line on a character
boundary, keeping its start, and `Source::cut_lines` names each cut line and the bytes it lost. Neither is set by
default, as the content search sets no bound its caller did not ask for and cuts a line only at the caller's limit
(ADR 1.10). What a cap left out is in the answer: `Source::doc_line` is where the doc comment and the lines the
declaration carries start, a carried line with no comment above it included, `Source::first_line` where the text does
and `Source::lines` how many lines it holds, so the definition's lines past them are the ones cut.

## Measured

On the C++ game-engine tree (43,356 C++ files, 1.50M definitions) and the Go monorepo (39,771 Go files, 1.46M
definitions), against the reference engine's answers on the same day's trees, with the caps it applies, 400 lines and
1,024 bytes a line.

**Every doc start.** Counted once for each file and line a definition starts on, so that definitions sharing a line
count once, every definition both engines hold on the Go monorepo starts its doc where the reference engine's does:
1,359,085 Go definitions, 399,428 of them with a doc comment, and the TypeScript and JavaScript, Rust, C++, Bash,
Python, Lua, Ruby and PHP ones, 83,477 more. On the C++ tree so do all 75,098 daslang,
103,298 Quirrel, 24,628 Python, 22,823 TypeScript and JavaScript, 3,351 Go, 286 Bash, 139 Lua and 16 PHP definitions,
and all but 34 of the 1,173,029 C++ ones, 192,392 of which have a doc comment. In 33 of the 34 a comment opened after
code on an earlier line, `ogg_uint32_t keyframe_frequency_force; /* also used for decode init to`, closes on the line
above the definition, and the reference walks past the code to an older comment, `/* encode only */`, reading it as
the definition's doc; in the other, a comment opens at `/*v4sf __builtin_ia32_addps` and holds a second opener 17 lines
down, and the reference starts the comment at the second. Each answer here reads the comment where C does. The
definitions only one engine holds are the 11 C++ declarations folded into their definitions and the Bash variables of
ADR 3.24, and the 31,582 lines that DSHL's 35,083 definitions start on, a language the reference does not read.

**The sampled text.** For 40 names of every family that holds definitions, every other one asked from the file it was
sampled from, and up to 5 names a family defines across 400 lines or more, with the reference engine's own 100
definition queries per tree beside them: every definition both answers list, 1,035 on the C++ tree and 1,140 on the Go
monorepo, has the same text, first line and cut, those the line cap and the byte cap cut among them. A definition only
one answer lists is a namesake ranked past the fifth, by the definitions query's own ranking.

**What it costs.** Nothing at the build: the build reads no doc and keeps nothing new, and its time and heap are those
of `main`, three warm rounds interleaved, 3.16–3.45 s against 3.14–3.43 s on the C++ tree and 1.32–1.35 s against
1.33–1.43 s on the Go monorepo, with 643,095,067 B of heap after the build against 643,095,069 B and 298,492,960 B
against 298,492,962 B, the peaks within 50 KB. The process footprint on the Go monorepo was 505–510 MB against 487–498
MB in all three rounds with the same heap, which no allocation of this change explains. A call answering up to 5
definitions takes 84–114 µs at the median and 0.76–1.9 ms at the 99th percentile on the C++ tree, 136–144 µs and
0.58–1.1 ms on the Go monorepo, under a load of 12 to 20; the reference engine's answers took 97 µs and 816 µs, 128 µs
and 485 µs, under a load of 6 to 11. The doc scan alone takes 2–13 ns at the median for a definition and 0.8–1.4 µs at
the 99th percentile.

## Considered Options

- **Record each definition's doc start in its extraction at the build** — measured as a prototype that scanned each
  file's lines once at extraction and kept 4 bytes a definition: 5.99 MB more heap after the build on the C++ tree and
  5.83 MB on the Go monorepo, about 0.9% and 2.0%, with the build's time within the noise of cold and warm runs, to
  save the scan's 0.8–1.4 µs at the 99th percentile of each definition answered, which reads its file anyway.
- **Keep the text of the files in the graph** — every answer without a read, at the cost of every claimed file's text
  held in memory beside the 643 MB of heap the whole engine holds after building the C++ tree, for a query few calls
  make.
- **Detect any edit since the build by a hash of the file** — a hash kept per file and computed on every read the build
  makes, which the walk computes today only for a build that shares a content cache, against a size check that is free.
- **Fixed caps, 400 lines and 1,024 bytes a line** — what an MCP tool renders, and a cut the engine would impose on
  every other consumer; the caps travel with the call instead.
- **Carry TypeScript decorators** — measured above: as many wrong starts as right ones on the two trees.

Revisit when a consumer asks for text often enough that reading the file costs more than keeping it, or when a
language's extraction records comments, so its doc lines can come from the tree instead of the line scan.
