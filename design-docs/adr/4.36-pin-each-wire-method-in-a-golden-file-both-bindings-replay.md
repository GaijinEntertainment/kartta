# Pin each wire method in a golden file both bindings replay

- **Status:** accepted
- **Date:** 2026-10-18
- **Updated:** 2026-10-21
- **Initiative:** `04-consumer-surfaces`
- **Governs:** `crates/kartta-ffi/tests/golden/`, `crates/kartta-ffi/tests/fixture/`,
  `crates/kartta-ffi/tests/golden.rs`, `bindings/go/kartta/golden_test.go`
- **Pinned by:** `crates/kartta-ffi/tests/golden.rs`, `bindings/go/kartta/golden_test.go`,
  `bindings/node/test/golden.test.ts`

The wire of ADR 4.2 is one contract that Rust, Go and Node each hold. Each method's contract is a golden file, a request
on a fixture tree and the answer it must get, which every binding's test replays, so a binding type that drops a field
fails; the comparison is exact but for a search score, which agrees within a relative 1e-12.

## Decision

- Every method has a file under `crates/kartta-ffi/tests/golden`, named after it, holding `method`, `params` and
  `answer` on the fixture tree under `crates/kartta-ffi/tests/fixture`. A method whose keys only a second request
  reaches has a second file named after the method and what it pins, as `references-unmatched.json`.
- The Rust test replays them through the dispatch on one handle, `build.json` first and the rest in file-name order, so
  the goldens after the refreshes pin that a refresh of the unchanged fixture changes no answer, and fails unless every
  method `version` lists has a golden. `KARTTA_FFI_BLESS=1` writes the answers the dispatch gives now in place of the
  pinned ones.
- The Go test replays them through cgo in the same order. For a method with a typed call it decodes the request into
  its typed params, refusing unknown fields, and encodes the typed answer back, so a Go type that drops a field the wire
  sends fails; the other methods replay as raw JSON through `Call`. It fails when a typed call has no golden. The Node
  binding's test does the same (ADR 4.3).
- Every value must match exactly, except a value under a `score` key, which agrees when it is within a relative 1e-12
  of the pinned one. The Rust test parses the files with serde_json's `float_roundtrip`, so a file it blesses pins the
  score the engine answered on the blessing OS to the last bit.

## Why

- `search`'s scores pass through `ln_1p` in `inverse_frequency`, and Apple's libm and glibc 2.41 round it one ulp apart
  for 76 of the 820 pairs sampled, so an exact score passed only on an OS whose libm rounds as the blessing one did
  (2026-10-21).
- 1e-12 holds thousands of ulps of a score and less than a change in its twelfth significant digit, and is exact for any
  integer score below 1e12, such as fuzzy's.

## Consequences

A score that moves by less than a relative 1e-12 passes unnoticed: accepted.

## Rejected

- **Scores matched exactly** — a golden blessed on macOS failed on Linux.
- **A tolerance on every number** — a count or a line that differs is a real change, and must fail.

## Revisit if

A score other than through `ln_1p` comes to differ between platforms by more than 1e-12. High confidence: the
difference measured is one ulp.
