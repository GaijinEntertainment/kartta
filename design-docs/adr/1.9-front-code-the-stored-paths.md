# Front-code the stored paths

- **Status:** accepted
- **Date:** 2026-10-14
- **Revised:** 2026-10-15
- **Initiative:** `01-kartta-fs-port`

An index holds every path its build found, and on a tree of millions of entries the paths are most of its memory. Index
order is depth-first, so each path shares most of its bytes with the path before it. **The index stores each path past
the prefix it shares with the previous path, and the first entry of each block, a restart, stores its whole path.** A
build lays a block at every 128th entry. Per entry the index keeps a byte of shared length and a `u16` offset counted
from its block's start; each block keeps the `u32` position of its first entry and the `u32` start of its bytes. A
value too wide for its byte or its `u16`, about one entry in ten thousand on a real tree, sits in a side table kept in
position order and searched by position.

Apart from the restarts, no path exists whole in the index, so an answer cannot borrow one. Queries answer positions,
and `Index::paths` rebuilds each path into one buffer it reuses: reading positions in rising order copies the few bytes
each entry stores, and any other order rebuilds the path from its block's restart. `Entry` owns its path. The scorer
takes candidates one at a time with their positions through `kartta_fuzz::Ranking`, because a reused buffer lends one
candidate at a time; `Matcher::rank` and `Matcher::merge` stay for a caller that holds every candidate at once.

**How a path is laid out, read and found.** The build walks the tree depth-first twice, once to size the stored bytes
exactly and once to write them. Each pass builds every path into one reused buffer, and the shared length falls out of
the same pass: the entry visited before shares at least the parent's path with the next, so the shared length is the
parent's length plus how far the old and the new tail agree. The shared length is floored to a character
boundary, so every stored suffix is valid UTF-8 on its own. Slicing the stored bytes therefore skips the boundary check,
which would read every byte of the buffer on a sweep that only needs where each entry's bytes lie. A reader up to four
positions behind the one asked for steps forward through them, copying each one's stored bytes; further behind, or
ahead, it rebuilds the asked path outright, walking back to the last entry that stores each part of its prefix, so every
byte of the path is copied once and each entry back to the restart costs one load. A lookup by path is a binary search
over the restarts, whose whole paths are stored, then a forward scan of one block that compares stored bytes without
rebuilding a path: an entry that shares more with its predecessor than the last entry passed shares with the path
differs from the path at the same byte and in the same direction, so it is passed without a look at its bytes. The
comparison finds the first differing byte eight bytes at a time, because compared paths share long prefixes and a byte
at a time made a lookup four times slower. The binary search holds because depth-first order with name-sorted siblings
is itself sorted by that comparison, bytewise with `/` below every other byte, which ties it to the bytewise name order
`kartta-walk` sorts siblings in. A listing finds where a directory's subtree ends without rebuilding a path either: the
entry right after the directory settles an empty or a leaf directory outright, and otherwise a binary search over the
restarts finds the block the subtree ends in, inside which an entry following one beneath the directory is beneath it
too exactly when it shares at least `dir/` with it.

The trade is speed for memory. It is taken because every call stays under 500 ms on the largest tree measured, and below
that bound memory and the amount of code outrank speed. Each layout was built, tuned and measured on
`/System/Volumes/Data` at 4.4M entries, three rounds each, all of them answering identically:

| | whole paths, `usize` offsets | whole paths, `u32` offsets | the walk's tree | front-coded, `u32` + `u16` | front-coded, narrowed |
|---|---|---|---|---|---|
| resident after build | 611–616 MB | 589–595 MB | 202–203 MB | 142–145 MB | 130–133 MB |
| fuzzy `e`, no limit | 179–183 ms | 178–182 ms | 327–333 ms | 395–414 ms | 427–442 ms |
| list the root | 20–21 ms | 20–21 ms | 96–98 ms | 58–59 ms | 68–69 ms |
| read every path | 5.3–5.8 ms | 6.0–6.1 ms | 51–57 ms | 33–34 ms | 40–42 ms |

Resident memory is the footprint after the build with macOS's large-allocation cache off. With the cache on, it keeps
the walk's freed tree and adds about 400 MB to every layout. A lookup by path stays under 1 µs in every layout, and the
build's peak belongs to the walk, which no storage layout changes.

Measured again beside whole paths on one tree of 4.45M entries under a heavier load, the narrowed layout held 130–131 MB
against 617–619 MB and peaked at 577–586 MB against 1,049–1,058 MB, while its heaviest call, the unbounded fuzzy
ranking for `e`, took 458–470 ms against 180–186 ms. That call is the one that leaves the least room under 500 ms.

**A block holds up to 128 entries, so a change re-encodes only the blocks it lands in.** An added or removed entry
moves every later position, and with it anything keyed by position, but no other block's bytes: a splice copies each
untouched block's bytes whole, and lays the blocks a change lands in again from their first entry, in blocks of 128 with
at most one shorter block at the end of each run it re-encodes. With a block at every 128th entry, one inserted entry
moved every later block's boundary and the store had to be re-encoded whole, 0.3s on 5.3M entries; with blocks of any
length a one-entry splice of the store takes 1.8–3.2 ms on 5.5M entries. Reading a position finds its block by a binary
search over the blocks' first positions instead of a division, and an entry starts a block exactly when its offset is
0, because every stored suffix is at least one byte. Measured on the data volume against blocks fixed at 128, a sweep of
lookups took a median 187 ms against 198 ms and an in-order read of every path 59 ms against 61.5 ms; builds were
unchanged.

## Considered Options

- **Whole paths with an offset per entry** — the fastest reads, at four to five times the memory.
- **The walk's tree kept, with a parent link per entry** — a path rebuilt by climbing its parents. About 70 MB more than
  the narrowed front-coding, and the slowest listing.
- **Lengths stored inline before each entry's bytes, as varints** — the least memory, but a read decodes forward from
  its restart, and the unbounded fuzzy ranking passed 500 ms.
- **A `u8` stored length per entry in place of the `u16` offset**, summed across the block on a random read — 4 MB less
  at 4.4M entries, but the unbounded fuzzy ranking reached 473 ms, and keeping in-order reads fast needs a running start
  in the reader.
- **A restart every 64 or 256 entries** — 64 stores 0.9 B more per entry; 256 saves 0.4 B per entry and brings the
  unbounded fuzzy ranking near the bound.
- **Blocks fixed at 128 entries, with changes merged in by re-encoding the store** — no position per block, but every
  change pays a pass over every stored byte.

Revisit if a call nears 500 ms on a larger tree. The restart interval is the knob: a shorter one buys speed back at a
known cost per entry.
