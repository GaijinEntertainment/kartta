# Follow a tree through its change notifications

- **Status:** accepted
- **Date:** 2026-10-15
- **Revised:** 2026-10-21
- **Initiative:** `01-kartta-fs-port`

ADR 1.16 lets a consumer refresh the paths that changed. A consumer that keeps an index current while the tree is
edited needs those paths from somewhere, and the operating system already knows them: inotify on Linux, `FSEvents` on
macOS, `ReadDirectoryChangesW` on Windows. The first consumer builds once and never looks again, so following a tree
must cost nothing to a consumer that does not.

**A `Watcher`, behind the `watch` feature, hands over what changed; the loop that refreshes is the caller's.**
`Index::build_watched` and `Index::refresh_watched` start one on the root before their walk and hand it back beside
the outcome, `Watcher::drain` hands over what changed while the walk ran, and `Watcher::wait(timeout)` blocks until the
tree changes, gathers what follows until the tree has been quiet for 20 ms, or for 500 ms at most so a steady writer
cannot hold the refresh off, and returns the root-relative paths for `Index::refresh_paths_watched`, which refreshes
them under the watcher. Each read a wait makes takes one bounded helping of notifications, so a stream that never stops
still lets the batch close on time. The index holds no thread, no lock and no reference to a watcher, and without the
feature none of it is built. When changes are dropped before they reach the caller, the batch names the whole tree, so
the refresh that follows walks it all, unless `FSEvents` names a directory below the root for them, which the batch
then names for the refresh to walk with everything below it. A change made before the watcher starts is not reported,
but `FSEvents` and `ReadDirectoryChangesW` can still deliver one made moments before. Refreshing the path it names
changes nothing when the index already holds that change, as for one the walk read after it was made, and takes the
change in when it does not.

**Linux is watched through inotify directly, one watch for each directory the walk keeps.** The walk watches each
directory as its visit keeps it, before the walk lists it, so starting costs a watch call each and no second walk, and
none of the directories the ignore rules hide or that `.git` holds is in the starting watch set: on `~/wrk` the index
holds 94,001 of the 150,237 directories on disk. A change made in a directory after its listing raises a notification,
one made before is in the listing, and a directory made after its parent was listed raises one in the parent's watch.
A directory the walk cannot read is not watched, since the walk cannot list it either and the build reports it. The
mask asks for no access event, so the reads of a refresh raise none. A directory made later is watched by the walk of
the refresh that takes it in, `Index::refresh_paths_watched`, which watches each directory it keeps before it lists it
as the build's walk does, so the ignore rules read for that refresh decide what is watched, and what was made in the
directory before its watch went on is in its listing; a directory a later edit hides loses its watches, and those of
every directory below it, to the refresh that drops it from the index. A watch the user's
`fs.inotify.max_user_watches` cannot cover leaves the walk to finish and hands back `WatchError::Limit` in place of the
watcher, beside the outcome of the refresh that met the directory, or at the next wait when that refresh failed of its
own, naming how many directories were watched and how many were wanted: past that point changes inside the directory
would go unseen, so the watcher no longer covers the tree. Reading happens inside `wait`, on the caller's thread, and
the kernel's own queue bounds what waits between two of them. A watch follows its directory wherever it moves, so the
watches below a directory moved away are dropped as the move is read. When that queue overflowed, the move of a
directory went with the rest, and its watches would go on naming its changes by the path it had, so a caller answers a
batch that names the whole tree with `Index::refresh_watched` and its new watcher, not with a refresh under the old one.

**macOS and Windows go through notify 9.0.0-rc.6.** Both systems watch a whole tree from one root, so there is no
watch set to choose and nothing to gain over the crate. 8.2.0, the latest release, ignores the byte count a Windows
completion reports, so an overflowed buffer loses its changes with no sign; the 9.0 candidate reports it as a rescan,
which the watcher turns into a lost batch. Notifications wait for the caller in a queue of 65,536, past which the batch
is lost, as an overflowed inotify queue is. On macOS, `FSEvents` names a change on the data volume by its firmlinked
path, `/Users/...` rather than `/System/Volumes/Data/Users/...`, and a stream on the data-volume spelling of a root
hears nothing at all; the watcher resolves the root through `/usr/share/firmlinks` and watches each firmlink below a
root that holds several, skipping those the machine does not have.

**kartta-fs 1.0 ships on the candidate while notify 9.0.0 is unreleased.** On 2026-10-20 crates.io holds 9.0.0-rc.6
as notify's newest version and 8.2.0 as its newest release. A requirement on a candidate is a caret one: a downstream
build that resolves afresh takes every later candidate, and 9.0.0 and each 9.x release once published, whatever this
repository's lock holds. A later version that changes what the watcher calls fails that build, one that changes what a
rescan means changes the watcher's answers, and nothing here sees either first. The requirement therefore names the
newest candidate, so the lock CI tests holds what a fresh downstream build takes. rc.6 keeps every public item of rc.5.
On Windows it changes only `unwatch`, which the watcher never calls: a completion that reports no bytes, or
`ERROR_NOTIFY_ENUM_DIR`, is still a rescan that names no path, and so still a lost batch. On macOS it fixes a hang when
a stream is stopped before its run loop starts, which the watcher risks with each firmlink it adds after the first and
when it is dropped; the run loop now wakes every 0.5 s to check. It also delivers the recovery notice `FSEvents` raises
at an ancestor of the watched paths, which rc.5 dropped, and the watcher loses the batch for it, as the revision below
says. Move to 9.0.0 once crates.io publishes it, and to a later candidate before then, since a downstream build takes
either unasked: raise the requirement and the lock, check in the changelog that a Windows completion with no bytes is
still a rescan that names no path and that an `FSEvents` rescan still names the directory the system names, and run the
watch tests, on Windows through CI.

**Revised 2026-10-20: a rescan of the root or above it loses the batch.** A rescan is notify's report that events were
lost, and it names the directory to scan again, with everything below it, when the system names one; Windows never
does, so its rescan was a lost batch already. `FSEvents` names the common directory of the changes it coalesced, which
may lie below the root, at it or above it, and raises a notice of events the kernel or the client dropped at every
watched path, asking for a scan of each, so one such notice names the root or a directory above it. The watcher
handed over only the paths inside the tree, so a rescan above the root came back as an empty batch and the changes it
stood for went unseen until another change named their paths. A rescan of the root, or of a directory outside the
tree, loses the batch, and the refresh that follows walks the whole tree; one below the root names its directory, which
`Index::refresh_paths` walks again with everything below it. A data-volume root watched through its firmlinks loses the
whole tree for a directory above one firmlink alone, such as `/usr` above `/usr/local`, though only that firmlink's part
was dropped: naming the part would take a second name for a path outside the tree, for a notice the system raises only
when it falls behind. An event that is no rescan costs nothing more, and a rescan's path takes the comparison with the
watched paths that `wait` makes for every path it hands over. No answer of a build or a refresh changes. No kernel drop
could be forced to raise the notice, so the decision is tested on notify events made by hand.

**Revised 2026-10-20: the watcher starts before the walk it follows.** `Watcher::new(&index)` started over a built
index, so it missed every change made while the build walked, and a caller that wanted them walked the whole tree once
more and called `Watcher::cover`, which watched the directories that refresh added and named them to refresh again: a
second pass over the tree at every start, 46.6–51.2 s on the data volume (ADR 1.16). Both are gone; the watched build
and refresh start the watcher first, and the first drain takes in what the walk could not see. On macOS and Windows the
stream covers the whole tree from its start, so the walk tells it nothing. `FSEvents` reported a write 11.9 ms after it
at the median, 12.9 ms at the 99th percentile and 13.1 ms at most, under load averages of 15 to 20, so a drain there
waits up to 50 ms for the system to report a change, where inotify has queued it as the call that made it returned;
Windows takes the same 50 ms unmeasured, since notify hands its reports over from a thread of its own. On Linux the
walk adds each watch from its visit, which keeps a directory before the walk lists it, so no directory is listed
unwatched. The paths of those watches are appended to one buffer that the caller's thread makes the map from: a map
filled on the walk threads left its paths in their glibc arenas among the pages the walk freed, 132–135 MiB resident
after the build against 64 MiB. A queue that overflows during the walk loses the batch the first drain hands over, as
one during a wait does; on macOS that is the watcher's own queue of 65,536. How many notifications `FSEvents` raises for
a burst of writes depends on the machine: 40,000 new files overflowed the queue on one Mac and not on a CI runner, so
the overflow is tested on notify events made by hand while a build walks. `Watcher::new` also failed the whole watch
for a directory the index held but the user could not read; the walk skips it, as it cannot list it either.

**Revised 2026-10-20: a drain reads every change queued at its call before it closes.** A drain reads one 64 KiB buffer
a poll, 2,048 of the notifications that writes to a short name raise, and closed at 500 ms as a wait does, handing over
what it had read as complete. A queue deeper than one drain reads in that time left the rest unread, the overflow marker
with it, and the server published an index without them. A Docker VM's `fs.inotify.max_queued_events` of 1,048,576
allows such a queue, where a distribution's 16,384 is read in eight polls. In a debug build in a Linux container a flood
of 1,048,577 writes queued 33,554,448 bytes, which a drain read in 301–329 ms; beside 40 busy loops 14 of 16 drains
stopped at 500 ms having read 247,808–645,120 of the 1,048,577 notifications, with the overflow marker unread.

A drain now takes the bytes inotify holds, through `FIONREAD`, before it reads, and does not close at 500 ms until its
reads have covered them. inotify queues a change as the call that made it returns and hands its events over in order, so
those bytes hold every change made before the drain, one dropped as the overflow marker among them. Once they are read
the drain closes as a wait does, so a steady writer still cannot hold it open, and a drain that cannot take the count,
or whose reads end before they cover it, loses the batch. The count walks the kernel's queue: a drain of a quiet tree
took a median of 0.29 µs with it against 0.12–0.17 µs without, and the count of 1,000,000 queued notifications took
36–44 ms. A deep queue then costs the drain the time its reads take, and every notification read holds its path until
the batch closes, 64 MiB more at the peak for 1,000,000.

On macOS and Windows a poll takes all 65,536 notifications the watcher's queue holds, so no drain closes with one made
before it still queued there. What a drain there cannot show is that the system has reported every change made before
the call: one reported more than 50 ms after the drain began comes with a later wait, and notify neither flushes an
`FSEvents` stream nor hands over the event ids that would show how far the stream has come. Over 20 bursts of 1,000 new
files on macOS at load averages of 11 to 13, each drain named the burst's directory and every file within 21–41 ms, and
no later wait named any of them.

**Revised 2026-10-21: a drain is bounded without counting the queue.** `FIONREAD` counts an inotify queue by walking it
under the lock that every writer into the watched tree takes to queue an event, so the count a drain took first held
each of those writers for the whole walk. On the copies of a game tree, 1,828,130 entries in a Linux container, a write
loop beside a drain of 1,000,000 queued notifications stalled 29.4–33.2 ms writing to one watched file and 31.3–34.3 ms
writing to two, over 4 rounds alternating the build before this revision with this one at container load averages of 2
to 6 and host ones of 10 to 34; the count alone took 27.5–35.2 ms, and the writer waited all of it.

A drain no longer counts. inotify's read hands over every queued event that fits its buffer, so a read that leaves room
for the longest event, a header and a name as long as `PATH_MAX`, found the queue empty, with every change queued before
it read. The queue holds no more than the `fs.inotify.max_queued_events` an instance took as it started, and the
overflow marker, so a drain that has read that many events has read every change queued at its call. A drain reads on
past 500 ms until one of the two holds, so a steady writer still cannot hold it open, and where the limit cannot be
read it reads until a read finds the queue empty. One whose poll a signal interrupts before then loses the batch. The
longest write beside a drain took 16.5–115.8 µs to one file and 22.5 µs–1.63 ms to two, overlapping the
19.6 µs–1.45 ms of the same writes with no drain. Drains of 1,000 files took a median of 432 ms against 471 ms and of
1,000,000 files 330 ms against 353 ms, peaking 113 MiB and 47 MiB above where they began on both, a quiet drain
0.17 µs against 0.29 µs, and 100 new files 24.1 ms against 23.8 ms.

Beside 1, 2, 4 or 8 writers, each alternating between two files of its own from 50 ms before a drain of 1,000,000
queued notifications until it returned, every drain of 2 rounds closed, at 507.2–510.0 ms against 534.5–542.6 ms on
`main`; each overflowed the queue and handed over the whole tree. inotify's lock let the writes through at 0.76–1.42
million a second whatever the number of writers.

## What it costs

Measured on macOS and in a Linux container, through the public API:

| tree | entries | start | resident | write to refreshed | 1,000 files into a new directory |
| --- | --- | --- | --- | --- | --- |
| game-engine checkout, macOS | 182,714 | 1.4 ms | +3.2 MiB | median 41 ms, max 44 ms | 1 batch, all indexed |
| `~/wrk`, macOS | 468,552 | 1.3 ms | +3.1 MiB | — | — |
| data volume, macOS | 6,999,792 | 6.2 ms | +4.0 MiB | — | — |
| copies of a game tree, Linux | 1,828,130 | +0.17–1.07 s of the build, 111,001 watches | +10–13 MiB | median 35 ms, max 43 ms | 1 batch naming the directory, all indexed |

Write to refreshed is a file written into a watched directory until the index answers for it, over 20 files; most of
it is the 20 ms the batch waits for quiet. A refresh whose paths are neither indexed nor on disk, which is what most
batches of build output in ignored directories come to, makes no pass over the index: 100 such paths took 1.0–1.1 ms
on the data volume against 6.5–6.8 ms before.

Measured with probes on the same Linux tree, notify 8.2.0 started in 1.57s, raised 110,913 events from its own setup
walk and 1,690,730 from one read of every file, which took 2.91s against 1.43–1.48s under a watcher that asks for no
access event; at a distribution's default `max_queued_events` of 16,384 that read overflows. notify 9.0.0-rc.5 with
access events masked started in 0.59–0.66s at +44 MiB, against 0.15s at +12 MiB for the watches taken from the index.

Measured through the same build of this crate on macOS, alternating notify 9.0.0-rc.6 with rc.5 under load averages of
4 to 26, the first start in a process took 2.3–6.1 ms against 2.7–3.8 ms on the game-engine checkout over 4 processes
each, and 20–42 ms against 20–48 ms on the data volume, then 6.2 million entries, over 6; one more round, run while the
volume was being written across, took 163 ms against 58 ms. That start added 1.5–2.9 MiB resident against 1.3–3.0 MiB,
most of it the system frameworks loading. A write to refreshed, 20 files into a tree of 1,000 in each of 3 rounds, took
a median of 36–41 ms against 38–40 ms. Linux builds no notify, so its row does not move.

## Considered Options

- **notify 8.2.0 everywhere** — the access events on Linux and the silent loss on Windows.
- **notify 9.0.0-rc.5 everywhere** — on Linux it walks the tree again at start and watches every directory, ignored
  and `.git` ones included, at four times the start and memory.
- **notify 8.2.0 on Windows alone** — back to the silent loss of an overflowed buffer, the one thing the candidate was
  taken for, with two major versions of one crate to keep.
- **An exact `=9.0.0-rc.6` requirement** — holds a downstream build to the tested candidate, but Cargo keeps one version
  of a crate per compatible range, so a consumer that requires any other notify 9, 9.0.0 included, fails to resolve,
  and no consumer takes a notify fix without a release of this crate.
- **Own `FSEvents` and `ReadDirectoryChangesW` backends** — the same system calls the crate makes, as unsafe code to
  keep, for no measured difference. Leaving the candidate does not tip it: a later notify that breaks the build or
  changes what a rescan means costs a release of this crate, and the Windows backend would be more code only CI runs.
- **One `FSEvents` stream on `/`, which covers every firmlink and the data volume's own spelling** — through notify
  alone it started in a median of 2.2 ms, 1.6–4.0 ms, at 1.2 MiB more resident, against 4.6 ms and 1.8 MiB for one
  `update_paths` call over the same 24 rounds, with the first event 11.7 ms after its write. It needs a path for the
  stream beside the paths the events are named by, and the stream then covers every path outside the tree too: none
  changed in those rounds, but a rescan `FSEvents` names there loses the batch, to save 2.4 ms and 0.6 MiB once a start.
- **A watcher inside the index, on a thread of its own** — every consumer would pay for a thread and a lock around the
  index, the first one included.
- **Watch each directory from the walk's `enter`, after its listing** — a change made between the listing and the
  watch raised nothing, so each directory would need a stat after its watch went on and a listing again when it moved:
  0.41–0.43 s with that stat, at 137–141 MiB resident with its paths still kept on the walk threads, and the listing
  again still to write.
- **Watch from the index after the build, and stat every entry against the build's start** — 0.48 s, the watches
  0.16 s and the stats 0.09 s, at 64–65 MiB resident, but a stat finds a changed entry, not one made in a directory:
  each changed directory would need a listing compared with the index and a watch for every directory made in it, more
  code than the walk's own watch and still a second pass over every entry.
- **fanotify's filesystem-wide marks** — one mark for the filesystem in place of a watch a directory, but it needs
  `CAP_SYS_ADMIN`, which a consumer may not have; not prototyped.
- **Close a drain at 500 ms and lose the batch when the count is still unread** — every drain stays as short as a
  wait, but a queue it cannot read in that time costs a whole refresh under a new watcher, 0.60–0.83 s on the copies of
  the game tree at rest and 2.8 s beside 40 busy loops. There 1 of 6 such drains lost its batch after 711 ms, where
  reading on took at most 920 ms and lost none.
- **Count only when a drain reaches 500 ms before a read comes back short** — most drains take no count, but those
  that run longest still hold every writer for a walk of what is left, where the queue's limit bounds them without one,
  and the count stays a third state in every drain.
- **Read until a read finds the queue empty, with no bound** — nothing to read as the watcher starts, and no drain
  beside 1 to 8 writers was held open, since inotify's lock let their writes through at 0.8–1.4 million a second
  whatever their number, fewer than a drain reads; but nothing would close a drain whose writers outpaced its reads,
  which the queue's limit does for one read of `/proc` at the start.
- **Read the ignore rules in the watcher as it reads each creation, and follow a directory again when its `.gitignore`
  changes** — no call beside `Index::refresh_paths`, and the same 116 watches over the build and installs above, but the
  watcher keeps a second reader of the rules, reads those above each new directory once more than the refresh does, and
  lists again on the caller's thread every directory below a `.gitignore` that changed. Prototyped on the copies of the
  game tree: a root `.gitignore` edit took 1.61–3.18 s to its refreshed index, median 2.00 s, against 0.30–0.84 s, and a
  thousand new directories 39–53 ms, median 45 ms, against 32–45 ms.
- **Keep watching each directory as its creation is read, and drop what the refresh did not keep** — a directory the
  rules hid at the start and a `.gitignore` edit shows is still never watched, and a tree like `target/` holds its
  watches until the refresh that names it; not prototyped, since it leaves the defect it is for.
- **Re-point a moved directory's watches from the walk of the refresh that keeps it** — no watch dropped and added
  again for a move inside the tree, but a directory moved where no refresh keeps it, under an ignored directory or out
  of the tree, keeps its watches and goes on naming its changes by the path it had.
- **A map from each path to its watch, so a refresh skips the watch call of a directory already watched** — saves the
  median 28 ms of a whole refresh under the watcher, which stays under half a second, for a second copy of every watched
  path; not prototyped.
- **Hand the watcher each directory the walk's rules hide, and release the watches at and below those** — needs no word
  from the index, but the walk meets a directory ignored from the start, such as `target/`, each time it walks the part
  that holds it, so the pass over the watches runs where nothing was watched: 19.6 ms against 7.1 ms on `main` for the
  copy whose `prog` directories were ignored from the start, in the table above.
- **Mark each watch the walk asks for again, and release the watches in the walked parts it did not ask for** — needs
  no word from the index either, but passes over the watches at every refresh under the watcher, 12.8 ms against 6.6 ms
  for one file, and takes a lock for each directory the walk keeps.
- **Read the queue between releases, so their notices cannot overflow it** — the changes read would wait in the
  watcher for the next wait, a second place a batch is gathered from, for a hide of more directories than a
  distribution's 16,384 notices; not prototyped.
- **De-duplicate the paths as they are read** — a flood of writes to a few files holds a path a file, not one a write,
  but a batch of distinct paths pays a probe of a table a notification and holds the table beside the paths: 492–2,200
  ms against 408–568 ms for 1,000,000 of them, in the table of the revision that sizes each path at its length.

Revisit when a consumer watches a tree whose directories outrun `fs.inotify.max_user_watches`, where fanotify's
filesystem-wide marks need privileges a consumer may not have, and when the walk threads' queue on the watch calls
costs a build more than a whole refresh did: one inotify instance a walk thread would take that queue apart. Revisit
the drain too when a consumer raises `fs.inotify.max_queued_events` far past a million: a drain holds a path for every
notification it reads that names one, however few files they name, 97 MiB for a million on the copies of a game tree.
