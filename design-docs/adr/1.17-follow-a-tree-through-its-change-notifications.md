# Follow a tree through its change notifications

- **Status:** accepted
- **Date:** 2026-10-15
- **Revised:** 2026-10-18
- **Initiative:** `01-kartta-fs-port`

ADR 1.16 lets a consumer refresh the paths that changed. A consumer that keeps an index current while the tree is
edited needs those paths from somewhere, and the operating system already knows them: inotify on Linux, `FSEvents` on
macOS, `ReadDirectoryChangesW` on Windows. The first consumer builds once and never looks again, so following a tree
must cost nothing to a consumer that does not.

**A `Watcher`, behind the `watch` feature, hands over what changed; the loop that refreshes is the caller's.**
`Watcher::new(&index)` starts following the index's root, and `Watcher::wait(timeout)` blocks until the tree changes,
gathers what follows until the tree has been quiet for 20 ms, or for 500 ms at most so a steady writer cannot hold the
refresh off, and returns the root-relative paths for `Index::refresh_paths`. Each read a wait makes takes one bounded
helping of notifications, so a stream that never stops still lets the batch close on time; the bound covers gathering,
and on Linux a wait that reads of a large directory tree made since the start also watches each of its directories.
The index holds no thread, no lock and no reference to a watcher, and without the feature none of it is built. When
changes are dropped before they reach the caller, `Changes::lost` says so and the batch names the whole tree, so the
refresh that follows walks it all. A change made before the watcher starts is not reported, but `FSEvents` and
`ReadDirectoryChangesW` can still deliver one made moments before. Refreshing the path it names changes nothing when
the index already holds that change, as for one made before the build, and takes the change in when it does not.

**Linux is watched through inotify directly, one watch for each directory the index holds.** The index already lists
its directories, so starting costs a watch call each and no second walk, and none of the directories the ignore rules
hide or that `.git` holds is in the starting watch set: on `~/wrk` the index holds 94,001 of the 150,237 directories on
disk. The mask asks for no access event, so the reads of a refresh raise none. A directory made later is watched as its
creation is read, together with every directory already inside it but `.git`, at a watch call and a listing each,
whether the rules hide it or not, before the refresh that names it walks it, so what was made in it before its watch
went on is found by that walk. A watch the user's `fs.inotify.max_user_watches` cannot cover fails `Watcher::new`, or
the `wait` that met the directory, with `WatchError::Limit`, naming how many directories were watched and how many were
wanted: past that point changes inside the directory would go unseen, so the watcher no longer covers the tree. Reading
happens inside `wait`, on the caller's thread, and the kernel's own queue bounds what waits between two of them.

**`Watcher::cover` watches the directories a refresh after the start added.** A caller that builds and then watches
refreshes once more for what changed in between, and on Linux a directory that refresh took in was never watched, so
every change inside it went unseen until a refresh of the whole tree. `cover(&index)` makes a watch call for each
directory the index holds; inotify hands back the descriptor of a directory already watched, so a new one marks a
directory to follow, with every directory inside it, and to name for `Index::refresh_paths`, since a change made in it
before its watch went on raised no event. A limit met on the way fails it with `WatchError::Limit`. On macOS and
Windows it returns nothing. On the game-engine checkout in a Linux container, bind-mounted, 11,086 directories, it
took 6.2–7.9 ms, about half of what `Watcher::new` took on the same run, 10.4–16 ms, and allocated nothing.

**macOS and Windows go through notify 9.0.0-rc.5.** Both systems watch a whole tree from one root, so there is no
watch set to choose and nothing to gain over the crate. 8.2.0, the latest release, ignores the byte count a Windows
completion reports, so an overflowed buffer loses its changes with no sign; the 9.0 candidate reports it as a rescan,
which the watcher turns into a lost batch. Notifications wait for the caller in a queue of 65,536, past which the batch
is lost, as an overflowed inotify queue is. On macOS, `FSEvents` names a change on the data volume by its firmlinked
path, `/Users/...` rather than `/System/Volumes/Data/Users/...`, and a stream on the data-volume spelling of a root
hears nothing at all; the watcher resolves the root through `/usr/share/firmlinks` and watches each firmlink below a
root that holds several, skipping those the machine does not have.

## What it costs

Measured on macOS and in a Linux container, through the public API:

| tree | entries | start | resident | write to refreshed | 1,000 files into a new directory |
| --- | --- | --- | --- | --- | --- |
| game-engine checkout, macOS | 182,714 | 2 ms | +0.4 MiB | median 41 ms, max 44 ms | 1 batch, all indexed |
| `~/wrk`, macOS | 595,134 | 2 ms | +0.3 MiB | — | — |
| data volume, macOS | 5,511,099 | 21 ms | +0.5 MiB | — | — |
| copies of a game tree, Linux | 1,828,280 | 133 ms, 111,061 watches | +13.4 MiB | median 35 ms, max 43 ms | 1 batch naming the directory, all indexed |

Write to refreshed is a file written into a watched directory until the index answers for it, over 20 files; most of
it is the 20 ms the batch waits for quiet. A refresh whose paths are neither indexed nor on disk, which is what most
batches of build output in ignored directories come to, makes no pass over the index: 100 such paths took 1.0–1.1 ms
on the data volume against 6.5–6.8 ms before.

Measured with probes on the same Linux tree, notify 8.2.0 started in 1.57s, raised 110,913 events from its own setup
walk and 1,690,730 from one read of every file, which took 2.91s against 1.43–1.48s under a watcher that asks for no
access event; at a distribution's default `max_queued_events` of 16,384 that read overflows. notify 9.0.0-rc.5 with
access events masked started in 0.59–0.66s at +44 MiB, against 0.15s at +12 MiB for the watches taken from the index.

## Considered Options

- **notify 8.2.0 everywhere** — the access events on Linux and the silent loss on Windows.
- **notify 9.0.0-rc.5 everywhere** — on Linux it walks the tree again at start and watches every directory, ignored
  and `.git` ones included, at four times the start and memory.
- **Own `FSEvents` and `ReadDirectoryChangesW` backends** — the same system calls the crate makes, as unsafe code to
  keep, for no measured difference.
- **A watcher inside the index, on a thread of its own** — every consumer would pay for a thread and a lock around the
  index, the first one included.
- **A set of the watched paths for `cover` to look each directory up in** — 2.3–2.9 ms on the same tree, at 0.27 MiB
  more at its peak and the code to build the set, to save 4 ms beside the whole refresh every cover follows,
  0.23–0.24 s there.

Revisit when notify 9.0 is released, which replaces the candidate, and when a consumer watches a tree whose directories
outrun `fs.inotify.max_user_watches`, where fanotify's filesystem-wide marks need privileges a consumer may not have.
