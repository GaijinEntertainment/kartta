# Model git's ignore rules, not git's index

- **Status:** accepted
- **Date:** 2026-08-24
- **Updated:** 2026-08-24
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/policy.rs`, `crates/kartta-fs/src/rules.rs`

git keeps tracking a file once a rule added later would hide it, and that answer lives in git's index, not in the tree.
`kartta-fs` applies git's ignore rules alone, so a directory without a repository indexes the same way, and it leaves
a tracked-but-ignored file out.

## Decision

- A build applies git's ignore rules to the tree on disk and never reads git's index, so a file git tracks but a rule
  hides is not indexed.
- `git check-ignore --no-index` is the command whose answer agrees with `kartta-fs`'s index; `git ls-files` is the one
  that does not.

## Why

- Re-including tracked files means reading `$GIT_DIR/index`, which needs a real git repository and a second large
  dependency tree, for a case that arises only when a rule is added after a file.

## Consequences

- A tracked file a later rule hides is missing from the index, which looks like a bug to a reader who compares with
  `git ls-files`; accepted.

## Rejected

- **Read `$GIT_DIR/index` so tracked-but-ignored files are indexed** — needs a real git repository, which forecloses
  indexing a plain directory, for a case created by adding a rule after a file.

## Revisit if

Indexing a repository whose rules were added after its files turns out common rather than incidental. Medium
confidence: it has not been counted across repositories.
