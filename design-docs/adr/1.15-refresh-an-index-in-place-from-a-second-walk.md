# Refresh an index in place from a second walk

- **Status:** accepted
- **Date:** 2026-10-15
- **Revised:** 2026-10-15
- **Initiative:** `01-kartta-fs-port`

An index answers for a tree that goes on changing, and consumers live with that in one of three ways. The first consumer
builds once and never looks again, so building must stay exactly as cheap as it was. A second asks for an up-to-date
index when it needs one, and a third would follow the filesystem's notifications as they come. Measured on git
history, a commit changes 2–3 files at the median and 10–12 at the 90th percentile, and a day of work on a
171,722-file checkout changes 1,165 files at the median — under 1% of its files. A refresh therefore spends most of
its time finding what changed, not reading it.

**A refresh walks the whole tree again and replaces the index in place.** `Index::refresh` applies the rules the index
was built with — root, ignore sources, binary extensions, content index storage, stamps, threads — and leaves the index
what a build would make now. It takes `&mut self` and keeps the old index whole until the new one is done, so the two
are held at once, and a refresh that returns an error, a cancelled one included, leaves the index answering as it did;
errors collected from its walk do not stop it replacing the index. Since it walks everything, it re-encodes the
paths from the walk the way a build does, rather than applying a list of changes to the old index: the build's encoder
costs about 60 ns an entry, 0.3s on 5.3M entries, beside a walk that takes 2–49s on the same trees. An answer borrows
the index that gave it — `Capped` and `FuzzyMatch` too since this change — so none can be held across a refresh.

**Ids a refresh hands out follow every id handed out before.** A consumer keeps data per `ContentId`, so an id names one
file for the life of an index: each read gets the next id, and `RefreshOutcome::retired` lists the ids that no longer
name a file, every file read again and every file gone. The id map holds a position for each id from the oldest it may
still answer for, and a retired id maps to nothing. A refresh that returns an error, or that a panicking visitor
unwinds, may have handed its visitor ids already, so the readers count the ids they hand out, the index keeps its next
id apart from its map and raises it by that count even then, and the next refresh that completes lists those ids as
retired. Ids never return to use, so an index runs out after about four billion reads in all, and a
refresh that would need an id past the last returns `BuildError::ContentIdsExhausted` instead of reusing one. That is
about a thousand refreshes without stamps of the data volume measured below, each reading its 4.1M files again; with
stamps a refresh reads only what changed.

**Stamps are asked for, and taken from the stat the read already makes.** With `BuildOptions::stamps`, a build keeps,
for each file it reads, the time the file last changed — eight bytes a file, from the `fstat` of the opened file, so a
build pays no stat it did not make before and a build that asks for none keeps nothing. On unix the time is the inode
change time, which no write can set back: `cp -p`, `rsync -t` and `tar x` set a modification time back on a same-size
edit, and a stamp of it would carry the edit over unread. Elsewhere the stamp is the modification time
(`Metadata::modified`), so there such an edit is carried over unread. A time within two seconds before the walk began
is not trusted, because a coarse clock can give a later write the same time. A refresh stats each file the index read
and carries one whose size and time match over unread: it keeps its id, what the index knew of it and its posting
lists, and the visitor is not handed it again unless it wants it now and was never handed it — the stamp's top bit
records that. A `.gitignore` is carried the same way; its rules are read anew either way.

**What a refresh carries stays in its segment; what it reads goes into a new one.** The content index is a list of
segments, each over its own range of ids, and a search reads every segment, skipping ids the map says are gone. A
refresh that carries a text file and reads anything adds a segment with its own 768 KiB bucket table and leaves the old
lists of what it read again behind. Past eight segments the refresh merges the ones after the first into one, and once
more than a quarter of the files the segments hold lists for are gone it merges all of them into one. A refresh that
carries no text file, as every refresh without stamps, writes a single segment as a build does. The merge writes
through the build's own partitioned writer, with each trigram's live ids drawn from the old segments instead of the
build's spilled runs. Ids keep their numbers through it, so the merged lists still span the ids that are gone.

**Revised 2026-10-15: past eight segments, the first stays out of the merge.** The first segment is the one the build or
the last merge of everything wrote, so it holds most of the files, and each refresh since added one that holds what that
refresh read. Merging them all every eighth refresh that reads text cost about what the build's merge does, every time:
a call of ADR 1.16 naming 100 files took 1,073 ms on `~/wrk`'s 1 GiB content index when it merged, against 23–36 ms
when it did not. Merging only the segments after the first bounds the merge by what refreshes read since: the same call
took 51.6 ms, and on the game-engine checkout 18.9 ms against 13.3–16.2 ms, where merging everything had taken 135 ms.
The merged segment counts as files the live ids in its range whose entries are text and not left unindexed, which is
exactly the files it holds lists for. The first segment keeps the lists of the files read again since until more than a
quarter of what the segments hold is gone.

## What it costs

Measured on macOS, mapped content index:

| tree | entries / files indexed | build | refresh, nothing changed | refresh after changes |
| --- | --- | --- | --- | --- |
| game-engine checkout | 182,714 / 168,885 | 2.80–3.91s | 0.22–0.30s | 172 files 0.25–0.30s; 34,367 0.67–0.75s; 85,831 and a merge 1.70–1.77s |
| `~/wrk` | 629,922 / 518,977 | 29.6s | 2.29–2.31s | — |
| data volume | 5,531,904 / 4,111,924 | 555s | 187–212s, the volume changing 4,244–116,029 files between walks | — |

Without stamps a refresh costs a build: 2.84–3.01s on the checkout. A refresh that finds nothing to read costs a walk
and one stat per file the index read — on macOS a stat per file doubles a walk, on Linux it adds about a third. The
data volume is the outlier: it includes an SMB share and an NFS mount, and its stats are network round trips. After
half the checkout's files were read again and merged, the content index held 128.8 MiB against a fresh build's
116.6 MiB, its lists sized for every id handed out rather than for the files that remain. Builds are unchanged against
`main`: an inert build of `~/wrk` took 1.32–1.43s against 1.33–1.57s, a content-index build of the checkout 2.75–2.78s
against 2.76–3.62s and one of `~/wrk`, down to 594,872 entries by then, 25.0–28.8s against 25.3–29.5s, at equal
footprint. The writer merges each of its 256 partitions from that partition's own input inside the task that writes
it, and drops the input when the task ends: held until the last partition was written, the inputs raised a build of the
checkout with the index in memory from 348–349 MB to 380–385 MB, and merges built for every partition before the first
write raised a mapped `~/wrk` build by 15 MB.

## Considered Options

- **Apply a list of changes to the index instead of re-encoding it** — the streaming rebuild costs the same 55–65 ns
  an entry whatever the batch size, so beside a refresh's own walk it saves nothing. It pays where a change arrives
  without a walk, which is what following the filesystem's notifications needs: with variable-length blocks of paths a
  one-entry splice takes 1–3 ms on 5.3M entries against 0.3s for a rebuild, at 0.2% more path bytes. That layout landed
  with the notifications, as ADR 1.9's revision, and ADR 1.16 splices with it.
- **Keep the old index answering while the new one replaces it** — what an atomic swap would need, and two indexes held
  for as long as any query holds the old one. Nothing a consumer was shown needs the old answers once it has asked for a
  refresh.
- **Stamp every file during the walk** — the walk takes the file type from the directory listing and stats no file, and
  a stat per file costs 40–105% of a walk on macOS; an inert build would pay it for nothing.
- **Stamp the modification time** — the time a tool keeps across a same-size edit.
- **Renumber the ids when merging** — smaller lists after churn and no limit on an index's reads, but every consumer's
  per-id data would have to follow.
- **Rebuild the content index from scratch on each refresh** — reads every text file again: 98 GB on the data volume.

Revisit when the refresh walk on macOS takes its stamps from `getattrlistbulk`, which returned them at +20% of a walk
against +105% for a stat per file; when a tree's retired ids leave its merged lists, or its id map at 12 bytes an id
from the oldest carried one, sized far past the files that remain; or when a consumer refreshes often enough to near the
last id.
