# Refresh an index in place from a second walk

- **Status:** accepted
- **Date:** 2026-10-15
- **Updated:** 2026-10-15
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/index.rs` (`Index::refresh`, `RefreshOutcome`),
  `crates/kartta-fs/src/index/refresh.rs`, `BuildError::ContentIdsExhausted`
- **Pinned by:** `crates/kartta-fs/tests/refresh.rs`, `crates/kartta-fs/src/index.rs`
  (`a_refresh_that_needs_an_id_past_the_last_fails_and_leaves_the_index_answering`)

An index answers for a tree that keeps changing, and a consumer that asks for an up-to-date index now and then needs one
without a new build. `Index::refresh` walks the whole tree again under the build's rules and replaces the index in
place, numbering what it reads past every id handed out before. It pays a walk per call and holds two indexes while it
runs.

## Decision

- **Whole walk, in place.** `Index::refresh` walks the whole tree again and makes the index what a build would make now,
  under the rules it was built with: its root, ignore sources, binary extensions, content index storage, stamps and
  threads. It re-encodes the paths from the walk as a build does; it applies no list of changes to the old index.
- **Old index whole until the new one is done.** The call takes `&mut self` and keeps the old index whole until the new
  one is finished, so the two are held at once while it runs. A refresh that returns an error, a cancelled one included,
  leaves the index answering as it did. A refresh that returns `RefreshOutcome` has replaced the index, even when
  `RefreshOutcome::errors` lists what its walk could not read.
- **Answers borrow the index.** Every answer borrows the index that gave it, `Capped` and `FuzzyMatch` included, so none
  is held across a refresh.
- **Ids follow every id handed out.** A consumer keeps data per `ContentId`, so an id names one file for the life of an
  index. Each file a refresh reads gets the next id. `RefreshOutcome::retired` lists the ids the index stopped answering
  for: every file read again and every file gone. The id map holds a position for each id from the oldest one the index
  may still answer for, and a retired id maps to nothing.
- **Stopped refreshes count.** A refresh that returns an error, or that a panicking visitor unwinds, may have handed its
  visitor ids already. The readers count the ids they hand out, the index raises its next id by that count even then,
  and the next refresh that completes lists those ids as retired.
- **No id returns to use.** An index runs out after about four billion reads in all, and a refresh that would need an
  id past the last returns `BuildError::ContentIdsExhausted` and leaves the index answering.
- **What a refresh may carry over unread** follows
  [ADR 1.40](./1.40-carry-an-unchanged-file-over-by-its-size-and-change-time.md); **where the content index keeps what
  it reads** follows
  [ADR 1.41](./1.41-index-what-a-refresh-reads-in-a-segment-of-its-own.md). ADR 1.16 refreshes the parts a caller
  names, widened as it states, up to a whole `Index::refresh`.

## Why

- A refresh spends most of its time finding what changed, not reading it: a day of work changed 1,165 of the 171,722
  files of a checkout at the median, under 1% (its git history, 2026-10-15).
- Re-encoding is cheap beside the walk a refresh makes anyway: the build's encoder costs about 60 ns an entry, 0.3 s on
  5.3M entries, where the walk takes 2–49 s on the same trees (2026-10-15).
- Nothing a consumer was shown needs the old answers once it has asked for a refresh, so the index need not keep
  answering from the old state while the new one is built.
- Ids that are never reused let a consumer keep per-id data across refreshes and drop exactly what `retired` names.

## Consequences

- A refresh holds the old and the new index at once while it runs (accepted).
- An index that never refreshes pays nothing: a build is as cheap as before (accepted).
- Ids run out: about a thousand refreshes of the data volume's 4.1M files without stamps, each reading every file again;
  with stamps a refresh reads only what changed (accepted).

## Rejected

- **Apply a list of changes to the index instead of re-encoding it** — costs the same 55–65 ns an entry whatever the
  batch size, so beside a refresh's own walk it saves nothing; ADR 1.16 splices where a change arrives without a walk.
- **Keep the old index answering while the new one replaces it** — an atomic swap holds two indexes for as long as any
  query holds the old one, for answers no consumer needs once it asked for a refresh.
- **Renumber the ids when merging** — smaller lists after churn and no limit on an index's reads, but every consumer's
  per-id data would have to follow.

## Revisit if

A consumer refreshes often enough to near the last id, or retired ids leave the id map, 12 bytes an id from the oldest
carried one, sized far past the files that remain. Medium confidence: no consumer measured refreshes at that rate.
