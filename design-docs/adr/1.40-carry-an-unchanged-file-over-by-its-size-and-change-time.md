# Carry an unchanged file over by its size and change time

- **Status:** accepted
- **Date:** 2026-10-15
- **Updated:** 2026-10-15
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/stamp.rs`, `crates/kartta-fs/src/index/refresh.rs` (`Previous::carry`),
  `BuildOptions::stamps`, `kartta_walk::WalkOptions::listed_stats`
- **Pinned by:** `crates/kartta-fs/tests/refresh.rs` (`a_stamped_refresh_reads_again_only_the_files_that_changed`,
  `a_file_written_just_before_the_build_is_read_again_by_a_stamped_refresh`,
  `a_stamped_refresh_hands_the_visitor_a_file_it_was_never_handed`,
  `a_stamped_refresh_reads_a_same_size_edit_whose_modification_time_was_set_back`,
  `a_stamped_refresh_of_an_unchanged_tree_reads_nothing_and_retires_nothing`)

A refresh of ADR 1.15 that reads every file again costs a build. A build that asks for stamps keeps each read file's
change time from the stat its read already makes, and a refresh carries over unread a file whose size and time still
match. On macOS the refresh takes those from the directory listing; elsewhere it stats each file it read.

## Decision

- **Asked for.** With `BuildOptions::stamps`, a build keeps eight bytes for each file it reads: the time the file last
  changed, from the `fstat` of the opened file. A build pays no stat it did not make before, and a build that asks for
  no stamps keeps nothing.
- **Which time.** On unix the stamp is the inode change time. Elsewhere it is the modification time
  (`Metadata::modified`).
- **Untrusted times.** A time within two seconds before the walk began is not trusted, and the file is read again.
- **Carrying.** A refresh compares each file the index read with its stamp. A file whose size and time match is
  carried over unread: it keeps its `ContentId`, what the index knew of it and its posting lists. The visitor is not
  handed it again, unless the visitor wants it now and was never handed it; the stamp's top bit records the hand-over.
  A `.gitignore` is carried the same way, and its rules are read anew either way.
- **Where the comparison comes from.** A walk that may carry files over, a whole refresh or the walks of
  `Index::refresh_paths`, asks `kartta-walk` for `WalkOptions::listed_stats`. macOS returns each regular file's length
  and inode change time with its name through `getattrlistbulk`, and the refresh compares those instead of statting the
  file. A directory the kernel cannot list with them is listed by name, and its files are stat'd. Linux and Windows
  stat each file the index read, since no other listing carries a change time. A build lists by name, since it stats
  nothing it does not read.

## Why

- A same-size edit made through `cp -p`, `rsync -t` or `tar x` sets the modification time back, and a stamp of it would
  carry the edit over unread. No write sets an inode change time back.
- A filesystem whose clock ticks coarsely can give a write that lands after the read the time the read saw.
- On macOS a stat per file more than doubled a refresh's walk; with the listing a walk that takes every regular file's
  stat over the data volume's 6.95M entries took 74–82 s against 214–262 s by lstat (2026-10-15).

## Consequences

- Without stamps a refresh reads everything again and costs a build (accepted).
- Off unix, a same-size edit whose modification time a tool set back is carried over unread (accepted).
- The listing creates no vnode, where an lstat creates one and costs about four times as much for a file whose vnode
  the kernel does not hold. So a part small enough for the vnode cache, refreshed again and again, stats cheaper by
  lstat once its vnodes are cached; a tree past the cache keeps no vnodes from one walk to the next (accepted).

## Rejected

- **Stamp every file during the walk** — the walk takes the file type from the listing and stats no file; a stat per
  file costs 40–105% of a walk on macOS, which an inert build would pay for nothing.
- **Stamp the modification time** — the time a tool keeps across a same-size edit.
- **Stat each file through `fstatat` on its directory's descriptor** — took 5.79–5.84 s on `~/wrk` against 4.86–5.01 s
  for an lstat by path (2026-10-15).
- **List every walk in bulk** — the listing costs more than `read_dir` when no stat is wanted, 3.08–3.20 s with names
  alone against 2.17–2.23 s on `~/wrk` (2026-10-15), so a build keeps `read_dir`.

## Revisit if

A consumer refreshes one part of a tree small enough for the kernel's vnode cache, about 263,168 vnodes on the machine
measured, so often that an lstat per file would cost it less than the listing. High confidence for the trees this engine
targets: a tree past the cache keeps no vnodes between walks.
