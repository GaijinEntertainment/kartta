# Let the caller bound the index's threads

- **Status:** accepted
- **Date:** 2026-10-14
- **Initiative:** `01-kartta-fs-port`

An index does its work in parallel — the walk that builds it, the reads a content visitor asks for, and the content and
fuzzy searches after — and the machine it runs on is not always the machine it is told about. A container runtime that
misreports its CPU quota hands the process the host's core count, and a default sized by that oversubscribes the quota
the process actually has.

**`BuildOptions::threads` bounds all of it.** A named count gets the index a pool of exactly that size, built once with
the index and kept for its lifetime, and every parallel step of the index runs on it — the walk, its reads, and every
search after. One pool rather than one per call is what makes the count a bound: two searches running together divide
those threads instead of each starting as many again. `Index::threads` reports the count the index runs on.

**Unnamed, the index takes every core.** It runs on the ambient rayon pool, which is sized to the machine's reported
cores unless the process configured it otherwise. The caller that knows better names a count; the one that does not is
not slowed down by a guess at what else the machine runs.

## Considered Options

- **Three quarters of the reported cores by default** — leaves room for whatever else the machine runs, and is wrong
  in both directions: it idles a quarter of a machine dedicated to the index, and it still oversubscribes a container
  whose runtime misreports the quota, which only an explicit count fixes.
- **A worker count per call** — each step bounded on its own terms. Concurrent calls then add their counts together,
  so no one number bounds what the index does at once.
- **Leave pools to the caller, through `ThreadPool::install`** — no option at all, and every caller has to know that
  each of the index's methods is parallel and wrap each one; the walk already took a thread count, so the build would
  have been bounded and the searches not.
- **Always own a pool, of the reported cores when unnamed** — the same answer as the ambient pool for the default, plus
  a second pool's threads beside the one a rayon-using process already has.

Revisit if searches and builds need different bounds — a long build beside interactive searches — in which case the
second count is named on the search, not inferred.
