# Qualify Python by the module its path names

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-19
- **Initiative:** `03-code-graph`

A Python file declares no package: its module is its path, `pkg/service.py` being `pkg.service`, and an import names a
module by a dotted path that the interpreter looks up on `sys.path`, which no file of the repository states. ADR 3.1
makes Python a language of its own; this decides how `kartta-lang-python` qualifies what it extracts and which files an
import includes.

**The resolver qualifies every symbol by the module its path names.** The path with `/` turned to `.` and the `.py` or
`.pyi` extension dropped, in any case as the language claims it, is the module, and every qualified name starts with
it: `pkg.service.Service.greet`. A package's `pkg/__init__.py` is the module `pkg`, as the interpreter names it, and a
root `__init__.py` names no module. The extraction from the bytes keeps the names local, `Service.greet`, because a
cache shares it between every file with the same content, and two such files at two paths are two modules. A `.pyi`
stub names the module of the source it describes, so a stub and its source define the same names. An owner is the chain
of classes alone, `Service` or `A.Worker`, which a receiver spells; the graph joins the chain at `.`.

**A symbol is what another module can name.** A function, a method and a class are symbols; a function or a class nested
in a function is qualified by the module alone, a nested class keeping its own methods under its name, is no member of a
class around that function, and is local to the function's body, so a call of its name from another module or function
never reaches it, and a call of its name inside that body is a local call to it. A variable is a symbol only when it is
assigned to a bare name at module level: `a = b = 1` defines `a`, and `a, b = 1, 2` defines nothing. In a class body,
only an annotated attribute, `name: str = ""`, is a field, because the annotation is what declares the fields of a
dataclass or a pydantic model and an unannotated attribute is commonly state. A decorated definition starts at its first
decorator, which a reader takes as part of it. A name that starts with `_` is not exported.

**A call names its target only where the syntax spells it.** A bare call records its name, and a member call its
attribute with the receiver: the name when the object is a name, as in `self.greet()`, and the empty receiver for
anything else, `items[0].close()` or `make().run()`, as ADR 3.2 decides for Go. A call belongs to the function around
it: a call in a class body belongs to the function around the class, or to the module when the class is at its top
level, and one made before the file's first definition is a call from file scope too (ADR 3.23). A call in a
default argument, `def f(x=make()):`, belongs to `f`, and its name is looked up in the scope of `f`, though Python
evaluates it in the scope around the definition; the pattern is rare enough to accept the wrong scope. A bare call
never reaches a method of the caller's class, because Python reaches one only through `self` or `cls`.

**Revised 2026-10-17: a bare call of a definition local to a function is a local call, found as Python's scoping
finds the name.** A name binds for the whole of the scope that binds it, so a call is decided when the walk leaves a
scope: the scope that makes the call first, then each function around it, a class body skipped, as the interpreter
resolves a free name; a call made in a class body sees the names that body binds, and a function nested in it does
not; the first iterable of a comprehension is looked up in the scope around the comprehension, where Python evaluates
it. A nested `def` or `class` binds its name to itself. A parameter, an assignment, a `for`, `with` or `except` target,
a `case` capture, a comprehension's or a lambda's variable, an assignment expression and an import bind the name to
something else and hide a definition around them; a `global` declaration sends the name to the module, and a
`nonlocal` one past the scope that declares it. Where one scope binds a name both ways, `def f` and `f = wrap(f)`, the
definition is the target: the walk keeps no order of execution, and each of the 8 such calls on the game-engine tree
reaches the definition, one made after a `def` that follows an unrelated assignment of the name, or one after an `if`
whose other branch assigns it. Of two definitions of a name in one scope, the later is the target, as the later `def`
rebinds the name: the 6 such calls on that tree follow an `if` that defines the name in both branches. A name that no
function around the call binds is recorded as a call, for the graph to resolve across files. A definition in a class
body at module level is no local, and a call of it there is recorded as a call. On the 1,215 Python files of the
game-engine tree, 1,471 calls become local calls: 1,393 that bound nothing before, and 78 that bound a function of the
same name in another file. The walk keeps the names that each open scope binds until it closes, which adds about 2% to
extracting those files on one thread, 950 ms against 930 ms.

**Revised 2026-10-17: a bare call of a value that a function around the call binds records nothing.** A parameter,
`f(source, tags)`, or a name a function assigns holds a value that no symbol of the graph is, and the graph's
cascade binds a recorded call by its name alone, so it would bind a function that only shares the name. The call records
nothing, as a computed callee, `handlers[0]()`, does and as ADR 3.2 decides for Go, so a walk over callees does not
count it among the calls it could not resolve: it names no target, inside the graph or outside. On the game-engine tree
this drops 786 calls: 734 that bound nothing, and 52 that bound a definition, 26 of them at 60, 11 at 70, 4 at 80 and
11 at 50, each a call through a parameter or a name its function assigns, `cls(...)` in a class method among them. The
monorepo's Python changes by no call. A name assigned at module level is a variable symbol, and a call of it from a
function is recorded. An import in the scope that assigns the name wins over the value, as a definition does, and the
call is recorded: the one such call on the game-engine tree follows a `try` whose `except` assigns `None` to the
imported name, and it reaches the import whenever the import succeeds.

**Revised 2026-10-18: a name a class body assigns and an attribute a method gives its instance are fields.** With
annotated attributes alone, most of a class's data had no symbol: a class declares it where `__init__` assigns
`self.size = size`, so a read or a write of it, which ADR 3.34 records, had nothing to bind to, and "who sets this
attribute" had no answer. A class body's assignment to a bare name is a field of the class, the first name of a chain
alone as at module level. An attribute a method assigns on its
first parameter, whatever its name, is a field too, and so is one a function or a lambda nested in the method assigns on
that name; a static method has no such parameter, and a nested parameter, or a binding of the name in the method or a
scope inside it before the assignment, `nonlocal` aside, hides the receiver. Each such attribute is declared once, at
its first assignment, after the members of the class body, so a method, a property or an annotated attribute of the
name keeps its symbol, and the members of two classes of one name local to two functions are apart. An augmented
assignment declares nothing: it reads the attribute first, which a class body, a base or a plain assignment declares.
On the 1,215 Python files of the game-engine tree the fields grow from 721 to 4,571. A call through such an
attribute, `self.items.append(1)`, stays a member call that binds nothing, but its miss now counts as a name the graph
does not admit as a callee rather than an undefined one: 4,170 calls of that tree.

**An import includes the files of the repository it names, and one that names none is recorded as written.** An `import`
or `from ... import` that includes a file is an include alone, as a C++ or TypeScript directive that resolves is, and a
`from __future__ import` or a module found nowhere, as one of the standard library is, is an import. A module is the
file `a/b.py` or the package `a/b/__init__.py`, and failing both its stub, `a/b.pyi` or `a/b/__init__.pyi`, which a
repository that ships only the types of a module holds; the probe takes the first of `a/b.py`, `a/b/__init__.py`,
`a/b.pyi` and `a/b/__init__.pyi` that exists, and the stub probe adds 3.7 ms to resolving the 1,149 Python files of a
game-engine tree, which hold no stub. An absolute module is probed from the repository root, then from each directory
around the importing file, nearest first, which finds a module under a `src` layout; with `app/db.py` and
`src/app/db.py` both present, `import app.db` from under `src/` takes the root one, a heuristic and not the
interpreter's search path. A relative module climbs one directory for each leading dot after the first and names nothing
above the root. A from-import also includes each name that is a submodule, which only a package can hold, so no name
below a plain module file is probed. A module found nowhere may be a namespace package, a directory without an
`__init__.py`: its names are probed under the same anchors, and the first anchor that holds one of them is the package,
so a portion under a later anchor is not merged. On the 1,149 Python files of a game-engine tree this adds 101 includes
and 2.9 ms to resolving them all. A name that is a symbol of the module includes nothing. `import a.b.c` includes the
module `a.b.c` alone, `a/b/c.py` or `a/b/c/__init__.py`, not the `__init__.py` files of `a` and `a.b` that the
interpreter runs on the way. A `__future__` import is a compiler directive and is never probed.

**A file is test, generated or entry code by Python's conventions.** A `test_*`, `*_test` or `conftest` file, or one
below a `test` or `tests` directory, is test code, and every symbol in it is, fixtures and helpers included; the rule is
a heuristic after pytest's naming conventions, and it does not read which files a pytest configuration collects. A
`*_pb2` or `*_pb2_grpc` file is protobuf output, and a `@generated` or `DO NOT EDIT` marker in the header — the comments
and a triple-quoted module docstring before the first statement, a plain, raw or unicode string, never a bytes or
formatted one, which an escaped quote does not close — marks other generated code, but only outside a backtick span,
where documentation of the convention quotes it. A free `def main` directly at module level is the entry point a script
runs under `if __name__ == "__main__":`. A method whose name opens and ends with `__` is an entry point too, as is a
method that `property` or `cached_property` decorates or that an accessor of the property of its name decorates,
`@size.setter` over `def size`: the interpreter calls a special method, `__init__`, `__enter__` or `__eq__`, for an
object it makes, a statement or an operator, and a property for an attribute read, and no call spells their names, so a
dead-code query would report each one. The spelling is a heuristic: Python reserves it for the special methods, yet
nothing stops a class from defining `__custom__`, which the interpreter never calls. A free function is never one.

**The fingerprint covers the walk and the grammar**, as ADR 3.4 settles for TypeScript.

## What it costs

On the Python trees this was built against, 1,480 files yield 31,846 symbols, 166,710 calls and 9,443 import
statements, which give 2,514 includes of files of the repository. On the 1,149 Python files of the game-engine tree,
7,515 statements give 2,096 includes and 5,694 imports. One thread on macOS extracts 1,216 of the files in 0.90 s.
Qualifying by the module costs one string per symbol in the resolver, which no cache shares.

## Considered Options

- **Qualifying in the extraction** — the module would depend on the path, and a cache could not share the extraction
  of two files with the same content.
- **Reading `sys.path` from the repository's configuration** — `pyproject.toml`, `setup.cfg` and a `src` layout each
  spell the import roots differently, and the probe from the root and the directories around a file reads none of
  them.
- **Every assignment as a variable** — tuple targets and class state would add symbols that nothing imports by name.
- **Including the `__init__.py` of every package on an import's path** — an edge per level for code the import only
  runs, not code it names.
- **Binding a nested definition by its name anywhere in its file** — the graph knows no Python scope, so a call in one
  function would bind a definition of the same name nested in another: on the game-engine tree, 26 nested definitions
  that share a name with one nested in an earlier function of the same file would lose their callers to it.

Revisit when an import root that the probe misses, or a root-first match that is wrong, shows up on a real tree.
