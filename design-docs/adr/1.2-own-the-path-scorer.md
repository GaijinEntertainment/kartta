# Own the path scorer

- **Status:** accepted
- **Date:** 2026-08-11
- **Initiative:** `01-kartta-fs-port`

Path search ranks candidates for a language model rather than for a human scrolling a picker, so the ranking decides
which files the model reads first and how many it must ask for. Two maintained Rust matchers cover the general case —
`nucleo-matcher` 0.3.1, the fzf-style matcher behind helix, and `frizbee` 0.12.0, a SIMD Smith-Waterman matcher used by
several pickers — and both were measured against the behaviours this crate has to guarantee before any code was
written. Neither ranks a filename hit above a directory hit: for the query `main` over `["main/lib.rs", "src/main.rs"]`
nucleo scores the two identically at 109, and frizbee prefers the directory match, 76 against 68. nucleo further ties
an exact basename against a directory of the same name (`cargo` over `["src/cargo/mod.rs", "Cargo.toml"]`, 134 each),
and frizbee under its default case handling ties a camelCase hump against a flat match (`fb` over
`["foobar.rs", "fooBar.rs"]`, 38 each). A model asking for `main` and being handed a directory first is the single most
common failure mode of repository path search, and it is the one behaviour a path-aware scorer exists to prevent.

The gap is structural rather than a matter of tuning. Both crates award boundary bonuses uniformly per delimiter —
nucleo through `Config::delimiter_chars`, frizbee through `Scoring::delimiter_bonus` — and neither exposes a
per-position hook, so a bonus that applies only inside the last path segment cannot be expressed through their
configuration, and their scoring internals are private, so it cannot be added by anything short of a fork. It can be
recovered outside the matcher by scoring the full path and the basename separately and combining the two, at twice the
matcher calls and with a weighting that would have to be re-tuned against no ground truth. Owning the scorer instead
puts the basename bonus inside the alignment recurrence where it costs nothing, and makes the whole model configurable
— the boundary classes, the gap penalties, the separator sets that decide what a segment is, and a prefix boost — with
the shipped default as the one tested point in that space and property tests carrying the invariants that must hold
across the rest of it. That configurability is also what keeps the exact-match guarantee honest: the score that beats
every alignment is derived from the active weights rather than declared as a constant, so no configuration can
invert it.

The concession is throughput, and it is real. Over 473k synthetic repository paths, a scalar prototype of this scoring
model answers a six-character query matching 108k of them in about 62ms where nucleo takes 19ms and frizbee 8ms; on a
query matching nothing the same comparison is 17ms against 4ms and 1ms. It does not bind here, because the consumer is
a tool call answering a language model, where tens of milliseconds sit inside the round trip — it would bind
immediately for an interactive picker, and this crate has no such consumer. Part of the gap is ours to close without a
dependency: an isolated byte-level prefilter over the same corpus costs 7ms against the prototype's 17ms. The
remaining reasons are secondary but point the same way. frizbee carries roughly 600 lines of unsafe SIMD across four
backends into a crate that is exported through a Go binding and a Node addon, and scores in `u16`, which panics on a
pattern longer than 10922 characters where a saturating `i32` model degrades instead; nucleo is MPL-2.0, which turns a
technical choice into a licence-policy decision. Because the comparison is settled it does not live in the crate — the
scorer is not documented, benchmarked or tested against another matcher, and its own benchmark measures only its own
regressions. This record is the evidence that the alternatives were measured rather than dismissed.

## Considered Options

- **Adopt `nucleo-matcher` as it stands** — ties both ranking cases that matter most, and its MPL-2.0 licence adds a
  policy decision to a technical one.
- **Adopt `frizbee` as it stands** — fastest by a wide margin and dependency-free, but inverts the basename case and
  brings a large unsafe SIMD surface into a crate exported over two foreign-function boundaries.
- **Adopt either and recover the basename preference around it** — two matcher calls per candidate and a weighting with
  nothing to tune it against; the option to revisit if throughput ever starts to bind.
- **Fork one and add a per-position bonus** — the scoring internals are private in both, so this is a fork to maintain,
  not a dependency to track.
- **Hide a matcher behind a trait so the engine stays swappable** — one implementation behind an interface is
  indirection, not abstraction; borrowed `&str` in and out already makes a later swap a non-breaking change.
- **A generic string-distance crate** — no alignment model and no path awareness; the most-downloaded candidate last
  released in 2020.

Revisit if an interactive consumer appears and tens of milliseconds begin to bind, if either matcher grows a
per-position or per-segment scoring hook, or if the property tests prove too weak to keep the configurable space
honest.
