# Make the ignore source set explicit

- **Status:** accepted
- **Date:** 2026-08-24
- **Updated:** 2026-08-24
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/build.rs`, `kartta_fs::IgnoreSources`, `kartta_fs::BuildOptions::ignore_sources`
- **Pinned by:** `crates/kartta-fs/tests/index.rs` (`ignore_sources_order_from_none_upwards`,
  `ignore_sources_none_indexes_everything_except_the_git_directory`)

Git reads ignore rules from four places, and only the `.gitignore` files live in the tree. A build names the sources it
honours as a level of `IgnoreSources`, and the default stops at the tree, so the same tree indexes the same on every
machine that agrees on filename case; a caller that wants git's machine-local rules has to ask for them.

## Decision

- The ignore sources a build honours are `BuildOptions::ignore_sources`, an `IgnoreSources` level rather than a flag.
- `IgnoreSources` is ordered and `#[non_exhaustive]`, and its levels nest: no rules, the in-tree `.gitignore` files,
  then the repository-local file, then the machine-global ones. `sources >= IgnoreSources::InTree` reads as "at least
  the in-tree rules apply".
- The default is `InTree`, the reproducible level. The guarantee is over the tree on disk, never over a commit: a build
  reads the working tree and not git's index, so two checkouts of one commit differ wherever their untracked, unignored
  content does. It holds across machines that agree on filename case: a control file spelled `.GITIGNORE` governs its
  subtree on a case-insensitive filesystem and is an ordinary file on unix, as it is for git.
- Only the implemented levels are spelled, `None` and `InTree`. A level that silently does nothing is worse than none,
  and a non-exhaustive enum gains the others without breaking a caller.
- A cache keyed on an index covers the active source set and a content hash of every source outside the tree, as the
  type's docs state, or an index built under one rule set is served under another.
- How the machine-local levels find their files is
  [ADR 1.53](/design-docs/adr/1.53-machine-local-ignore-files.md). That git's rules are modelled and not
  git's index is [ADR 1.54](/design-docs/adr/1.54-tracked-ignored-files.md). What the MCP server's index answer says
  about the applied rules is [ADR 1.52](/design-docs/adr/1.52-applied-ignore-files.md).

## Why

- `$GIT_DIR/info/exclude`, `core.excludesFile` and its XDG fallback `~/.config/git/ignore` are machine-local, so an
  index that honours them is machine-dependent: the same tree indexes to different file sets on a laptop and in CI, and
  nothing downstream can tell.
- The seam is real: across the repositories measured, the file set matched `git check-ignore --no-index` in every one,
  and the one that diverged from `git ls-files` diverged at a line of that clone's `info/exclude` (#4).
- A ladder, because the sources nest, and because the property worth reading off the type is where reproducibility
  ends, not which file is which.

## Consequences

- A cache over an index has to hash the files outside the tree once the machine-local levels exist; nothing else
  catches an index served under the wrong rule set. Accepted.

## Rejected

- **A `respect_gitignore` boolean** — answers "are rules on" and cannot answer "which rules", the question that decides
  whether two machines agree.
- **Three booleans, one per source** — expresses combinations that do not occur, global rules without in-tree ones, and
  hides where reproducibility ends.
- **Honour every source by default, as git does** — right for a command a human runs in their own checkout, wrong for an
  index a cache is keyed on and a model reads through. Machine-dependence is asked for.

## Revisit if

A consumer needs full git fidelity by default. Medium confidence: no consumer has asked for it.
