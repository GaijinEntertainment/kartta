# Build the graph inside the index's walk

- **Status:** accepted
- **Date:** 2026-10-16
- **Updated:** 2026-10-18
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta/src/extracting.rs` (`Extracting`, `claimant`), `crates/kartta/src/resolving.rs`
  (`Resolving::graphs`, `Resolving::insert_all`), `kartta::Engine::build`
- **Pinned by:** `crates/kartta/tests/engine.rs` (`a_second_build_takes_each_extraction_from_the_shared_cache`,
  `an_extraction_the_cache_holds_malformed_is_extracted_again_from_the_file`,
  `a_build_cancelled_after_its_walk_stops_before_it_resolves`, `a_tree_of_more_files_than_one_batch_resolves_whole`)

The code graph needs every source file's whole content, and a pass over the tree after the index's walk would read
each file a second time. The engine extracts each file in the walk's own read and holds every extraction encoded until
the walk is done, then resolves them in batches, at the price of one decode per file.

## Decision

**The engine extracts each file in the walk's own read.** `kartta::Engine::build` builds the index with a
`ContentVisitor` that wants every file one of its languages claims. The first language that claims a file takes it, and
extracts it on the walk's thread from the bytes the walk read. With a content cache, the extraction is taken from the
cache, or computed and given to it ([ADR 2.2](/design-docs/adr/2.2-build-cache-lookup.md)), under
the namespace `graph/` followed by the language's name, whose fingerprint is the language's
([ADR 3.120](/design-docs/adr/3.120-language-fingerprints.md)) followed by
`kartta_lang::FINGERPRINT`. The encoding is code of `kartta-lang`, which that identity digests, so a change to its
layout names a new namespace with no codec identity of its own.

**Extractions wait encoded.** A resolver asks the repository about any file, so no extraction is resolved before the
walk is done, and the build holds every one until then. It holds each in the encoded form the cache stores, which a
cache hit hands over as it is and a miss produces anyway to cache it, and decodes each when it resolves it. An encoding
that does not decode, as a cache entry in a form this build cannot read, is extracted again from a second read of the
file, and that read failing is collected as `BuildError::Read`.

**Resolution runs in batches on the index's threads.** Once the walk is done, the extractions are put in path order and
resolved a batch at a time on `Index::on_threads`, and each batch goes into its family's graph in path order before the
next is resolved, so at most one batch is held resolved;
[ADR 3.124](/design-docs/adr/3.124-resolution-batch-size.md) sets the batch at 1,024 files. A family's
resolver is built only when a file of the family was read
([ADR 3.122](/design-docs/adr/3.122-language-family-resolvers.md)). A cancel token
stops the build before the first batch and between batches, as it stops the walk; a build whose last batch is resolving
completes. On Linux with glibc the build ends with the trim
[ADR 1.18](/design-docs/adr/1.18-freed-build-memory.md) describes.

## Why

- The walk already reads every wanted file once (ADR 1.12); a second walk reads it again after the filesystem's caches
  of the tree have moved on, on review hosts that run several builds at once over nearly identical trees under a tight
  memory limit.
- Holding the extractions encoded rather than decoded peaked at 1.16 GB of footprint against 2.90 GB on a Go monorepo
  of 119,888 Go files and 4.12M definitions, macOS, 18 cores, no cache (2026-10-16): about 1.75 GB saved for one decode
  per file.

## Consequences

- One decode per file: about 10% more CPU time on that monorepo; accepted.

## Rejected

- **A second walk for the graph** — keeps the index and the graph apart, and reads every source file twice.
- **Holding extractions decoded** — no decode per file, and 2.5 times the peak footprint on that monorepo.
- **Resolving inside the walk** — no extraction held at all, and impossible: a resolver asks the repository about files
  the walk has not reached yet.

## Revisit if

Decoding grows well past the tenth of a build's CPU it took, or the hosts kartta builds on stop being bound by memory,
so that holding extractions decoded would pay. Medium confidence: the decode was measured on one tree.
