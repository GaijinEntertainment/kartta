# Count what a graph holds and how its calls bind when asked

- **Status:** accepted
- **Date:** 2026-10-17
- **Revised:** 2026-10-18
- **Initiative:** `03-code-graph`

An agent that gets an empty answer cannot tell a language that parsed nothing from code that defines nothing, nor a
call into a library from a call the cascade could not place; a language port cannot tell how much of a tree its
extraction lets the cascade bind. Both need counts: what each graph holds, what the build made of each language's
files, and how the call sites bind. The graph resolves calls only when a query asks and stores no edge (ADR 3.7), so an
engine that resolves every site at its build gets the second half free, and this one does not.

**What a graph holds is counted when asked.** `Graph::stats` reads every file and definition the graph holds and counts
its files, those with no definition, its definitions in all and by kind, the calls written by name and the local calls
inside definitions, the uses, and the includes. The graph already keeps the count of its files and definitions; the
rest takes 5.8 ms for the 1.50M definitions of a C++ game-engine tree and 5.0 ms for the 1.46M of a Go monorepo, for
every family at once, which a counter kept on every insert and removal would save at a cost to each of them. A call or
a use made outside every definition is no site: the graph keeps only the name it spells, and no count holds it.

**What the build made of each language's files is counted as the build meets them.** `Engine::stats` answers each
family's `Stats` beside, for each language, the files it was the first to claim among those the ignore rules kept, the
claimed files the walk read as text, those of them the content cache answered, and those its family's graph holds. The
walk's content visitor counts the claims, the reads and the cache answers on atomics, one triple per language, and the
build counts what it inserts. A count taken afterwards would rescan every index entry, 24.5 ms for the 182,714 entries
of the C++ tree, and could not see the cache at all. A claimed file the walk did not read is binary, by extension or
content, or is listed among the build's errors as unreadable; a read file the graph does not hold had its extraction
cached in a form the build could not decode and could not be read again.

**How the calls bind is resolved on request.** `Graph::resolution(limit)` resolves every call and local call inside a
definition through the cascade the call queries take, and answers the sites bound at each confidence, the surest
first, the caller and callee pairs they make, a declaration counting as the definition it links to, and the sites that
bound nothing by reason, listing the first `limit` of them in path order with what each spells and from where, and
counting the rest. The cascade names why it stops without a binding:

- `ExternalImport` — the receiver names an import of a module outside the repository.
- `NotExported` — the receiver names an import of a directory whose code outside its tests exports no callable of the
  name. Go is the only language that binds a directory, and on the Go monorepo all 44 such sites are external test
  packages calling helpers that an `export_test.go` defines.
- `Undefined` — no definition the graph holds has the name as the call writes it: a builtin, or code outside the graph.
- `NotAdmitted` — definitions of the name exist and the call can bind none: a field, a value where calls bind no value,
  a local of another body, or a member of an owner the call does not reach.
- `Ambiguous` — several definitions may be meant and neither scope nor nearness picks one.

`through_a_receiver` counts, of the undefined and the not-admitted sites, those made through a receiver that names no
import: mostly calls of a library type's method on a value. The files are split into four runs per thread of the pool
the query is called on, each resolved with a memo of its own, and rayon's ordered reduce keeps the listed sites the
first in path order. A limit of 0 answers the counts alone and skips the path sort. `Engine::resolution` runs each
family's resolution on the index's threads, one family after another.

**What the reference engine reports and kartta does not.** Its stats carry the call edges of each graph and in all;
here the edge count is `Resolution::edges`, because counting edges is resolving every site, and `Stats::calls` counts
the sites without that cost. Its `workers` is `Index::threads`. Its retained bytes estimate the heap from the sizes of
its structures; kartta's footprint is measured from the process, and no consumer reads the estimate beyond checking it
is not zero. Its cache counters are those of the store a build opens; the engine reports how many extractions the cache
answered for each language, and the store's own counters stay inside the index until a consumer needs them.

**Revised 2026-10-18: the uses are counted by how they touch their target as well.** Beside every use, `Graph::stats`
counts the reads, the writes and the updates apart (ADR 3.34), from marks each stored use already carries.

## Measured

On the C++ game-engine tree (43,356 C++ files among 182,714 index entries) and the Go monorepo (39,771 Go files, 20,290
of them in one nested worktree), with a warm extraction cache, on an 18-core machine at a load of 5 to 6, three rounds
interleaved with `main`:

| | `main` build | this build | `Engine::stats` | `Engine::resolution` | resolution of the largest family |
| --- | --- | --- | --- | --- | --- |
| C++ tree | 3.23–3.89 s | 3.20–3.22 s | 5.8 ms | 0.40 s | C++, 2.74M sites: 0.28–0.41 s |
| Go monorepo | 1.40–1.63 s | 1.31–1.34 s | 5.0 ms | 0.13 s | Go, 1.95M sites: 0.14–0.16 s |

The build's peak footprint stays within the noise of `main`'s, 466–495 MB against 484–497 MB on the Go monorepo built
by one harness at each commit; the engine keeps 32 bytes per language. Resolving the Go graph on 18 threads holds 18
memos at once and raises the process peak to 591 MB, 80 MB above the build's; on the C++ tree it stays within 25 MB of
the build's peak.

Against the reference engine's stats and diagnostics on the same day's trees, the files, files with no definition,
definitions and kinds of every language match, but for:

- The 3 `dx12_cache.blk` files on the C++ tree are binary, so the walk does not read them, where the reference holds
  them as empty files.
- 11 C++ definitions in 9 vendored files are declarations a definition in the same file implements, which kartta folds
  into it while the reference keeps both, the two spelling an empty parameter list differently, `(void)` against `()`,
  or one adding `override final`.
- Bash holds 113 and 376 more variables, and 5 and 4 fewer files with no definition, because a variable that a
  top-level `if` or loop assigns is a symbol (ADR 3.13).
- DSHL, a language the reference does not read: 1,817 files and 35,083 definitions on the C++ tree.

Engine-wide resolution, the reference's reasons mapped to kartta's: its `no-candidate` is undefined, not-admitted and
not-exported together, its `likely-external` is external-import and through-a-receiver together:

The C++ tree's sites differ by the 12,959 DSHL sites and by 786 Python calls through a value, which the Python
extraction does not record as calls (ADR 3.12). Comparing every caller and callee pair, by qualified name, explains
the rest:

- C++: 812,000 of 825,638 reference pairs match. 13,472 of the 13,638 the reference alone holds come from member calls
  on a value other than `this`, which the extraction records with an empty receiver so that no owner's member of the
  name is guessed (ADR 3.3); the reference binds them at 70 to 85, `A2dExporter::convert` calling a free `reset`
  through `x.reset()` among them. Of the 854 kartta alone holds, 694 bind such a member call to the one member of the
  name in the caller's directory or its parent at 50 or 30, where the reference binds each of their 983 sites to
  another member of the name: 427 at 70 through an include, 334 at 80 to the caller's own class, 206 at 85 to a type
  the operand's name spells, `list->size()` to `list::size` (ADR 3.3), and 16 to members it reaches at two of those
  tiers or more. 86 bind a call through `this` to a member of the caller's own class, protobuf's accessors among them.
- Go: 681,559 of 726,920 reference pairs match. 42,112 of the 45,361 the reference alone holds come from calls through
  a value the caller declares (ADR 3.2); of the 41,302 that kartta leaves ambiguous, the reference binds 17,807 at 15,
  12,026 at 70 and the rest at 80 to 95, `abi.Frame.String` calling one of thousands of `String` methods through a
  value among them. 2,062 are calls whose receiver names an owner, which kartta binds to the owner nearest the caller
  and the reference to a namesake in another package, as `admin.Project.Validate` calling `project.Project.validate`;
  702 are calls into nested modules the root module never builds, which kartta resolves as outside the repository (ADR
  3.2). Of the 4,266 kartta alone holds, 2,121 bind a receiver that names an owner and 1,227 an import. 44,938 shared
  pairs bind at 85 where the reference binds at 80 or 75, because a receiver that names an owner binds before any scope
  tier (ADR 3.7), which is most of the 109,840 sites the histogram gains at 85 and the 113,699 it loses at 80.
- TypeScript and JavaScript: on the C++ tree, 1,236 of the 1,319 pairs kartta alone holds, counted as the pairs above
  are, once for each two definitions a call joins, bind a member call at 15 to a free function far from the caller,
  `line.trim()` to the `trim` of an emscripten bundle. Counted once for each two qualified names, the method of ADR
  3.7's revision, the TypeScript and JavaScript pairs kartta alone holds are 1,151 before that revision and 70 after it.
  The reference leaves out of that step only what lies under `vendor/` at the root or under `node_modules/`, so more
  namesakes stay in it and it finds no one callable. On the Go monorepo, 306 of the 332 follow a re-export chain at 65.
- Python on the C++ tree, 707 pairs only the reference holds and 584 only kartta, from the scope and qualification
  rules of ADR 3.12. Rust on the Go monorepo, 114 pairs only kartta holds, each a call through a type path such as
  `CancelToken::new`. Quirrel differs by 4 pairs and Go on the C++ tree by 6, each a call through a value.

A C++ member call on a value that nearness binds is a guess on both sides: kartta takes the one member of the name near
the caller, the reference a member that an include, the caller's class or the operand's name suggests, and ADR 3.3
found the caller's class right for 5 of 20 sampled calls. The guess kartta alone made at 15, a member call bound to a
free function anywhere in the tree, is gone since ADR 3.7's revision of 2026-10-17, which also takes a member alone for
a Go member call at every tier; the counts above predate that revision.

## Considered Options

- **Resolve every site at the build and keep the counts** — diagnostics free at query time, and ADR 3.7's trade: every
  build pays a resolution few consumers ask for, and a graph that takes an insert holds counts no longer true.
- **Keep the graph's counts on every insert and removal** — saves 5 ms a call at a cost to each of millions of
  inserts, and a counter per kind kept beside the definitions.
- **Count each language's files from the index when asked** — no work during the walk, 24.5 ms a call on the C++ tree,
  and no count of what the cache answered.
- **One memo for the whole resolution, on one thread** — one memo's memory instead of 18, and 18 times the time.
- **Fold the reasons into the reference's three** — `NotExported` and `NotAdmitted` would hide inside `no-candidate`,
  though one points at test code a package exposes and the other at a definition the call cannot reach, each a
  different fix for a language port.

Revisit when a consumer asks for the edge count often enough that 0.4 s a call matters.
