# Count what a graph holds and how its calls bind when asked

- **Status:** accepted
- **Date:** 2026-10-17
- **Updated:** 2026-10-18
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta-graph/src/stats.rs`, `crates/kartta-graph/src/resolution.rs`, `Graph::stats`,
  `Graph::resolution`, `crates/kartta/src/stats.rs`, `crates/kartta/src/extracting.rs`, `Engine::stats`,
  `Engine::resolution`
- **Pinned by:** `crates/kartta-graph/tests/graph/stats.rs`, `crates/kartta-graph/tests/graph/resolution.rs`,
  `crates/kartta/tests/engine.rs` (`the_stats_count_the_files_each_language_claimed_read_took_from_the_cache_and_holds`)

An agent that gets an empty answer cannot tell a language that parsed nothing from code that defines nothing, and a
language port cannot tell how much of a tree the cascade binds. The engine counts what each graph holds when asked,
what the build made of each language's files as the build meets them, and how the calls bind only on request, because
the graph stores no edge (ADR 3.7) and counting edges means resolving every site.

## Decision

**What a graph holds.** `Graph::stats` reads every file and definition the graph holds when asked, and counts its
files, those with no definition, its definitions in all and by kind, the calls written by name and the local calls
inside definitions, the uses inside definitions, and the files they include. It counts the uses that read, write and
update their target apart (ADR 3.34), from the mark each stored use carries. A call or a use made at file scope is no
site: the graph keeps only the name it spells
([ADR 3.112](./3.112-keep-the-names-a-file-s-top-level-calls-and-uses.md)), and no count holds it. `Stats` holds no
edge count.

**What the build made of each language's files.** `Engine::stats` answers each family's `Stats` beside, for each
language, the files it was the first to claim among those the ignore rules kept (`claimed`), the claimed files the walk
read as text (`read`), those of them the content cache answered (`cached`), and those its family's graph holds
(`held`). The walk's content visitor counts the claims, the reads and the cache answers on atomics, one triple per
language, and the build counts what it inserts; a refresh that follows the tree adjusts each count for the files it
reads, adds or drops. A claimed file the walk did not read is binary, by extension or content, or is listed among the
build's errors as unreadable; a read file the graph does not hold had its extraction cached in a form the build could
not decode, and could not be read again.

**How the calls bind.** `Graph::resolution(limit)` resolves every call and local call inside a definition through the
cascade the call queries take (ADR 3.7), and answers:

- `sites`, and the sites bound at each confidence, the surest first;
- `edges`, the caller and callee pairs they make, each once, a declaration counting as the definition it links to;
- the sites that bound nothing by reason, and `through_a_receiver`: of the undefined and the not-admitted sites, those
  made through a receiver, mostly calls of a library type's method on a value;
- the first `limit` unbound sites in path order, a file's calls by name before its local calls, each with its caller,
  line, callee and receiver as written, and `unlisted`, the rest. A limit of 0 answers the counts alone and skips the
  path sort.

The cascade names why it stops without a binding:

- `ExternalImport` — the receiver names an import of a module outside the repository.
- `NotExported` — the receiver names an import of a directory whose code outside its tests exports no callable of the
  name.
- `Undefined` — no definition the graph holds has the name as the call writes it: a builtin, or code outside the graph.
- `NotAdmitted` — definitions of the name exist and the call can bind none: a field, a value where calls bind no value,
  a local of another body, a member of an owner the call does not reach, or for a call from outside test code a test
  definition that is the one callable of the name
  ([ADR 3.46](./3.46-bind-no-test-definition-by-name-for-a-call-from-outside-test-code.md)).
- `Ambiguous` — several definitions may be meant and neither scope nor nearness picks one, or nearness picks a test
  definition for a call from outside test code.

The files are split into four runs per thread of the pool the query is called on, each resolved with a memo of its
own, and rayon's ordered reduce keeps the listed sites the first in path order. `Engine::resolution` runs each family's
resolution on the index's threads, one family after another.

## Why

- Counting what a graph holds reads its files once: 5.8 ms for the 1.50M definitions of the C++ game-engine tree
  (2026-10-17).
- The walk already meets every claimed file, and only the walk sees which reads the cache answered.
- A resolution of every site costs what resolving the graph costs, 0.40 s for the whole C++ game-engine tree
  (2026-10-17, #60), which a consumer asks for when porting a language, not on every call.
- Each reason points at a different fix for a language port: `NotExported` at test code a package exposes, 44 sites of
  the Go monorepo, all external test packages calling helpers an `export_test.go` defines (2026-10-17, #60);
  `NotAdmitted` at a definition the call cannot reach.

## Consequences

- An edge count costs a whole resolution. Accepted.
- A resolution on 18 threads holds 18 memos at once: it raised the Go monorepo's process peak 80 MB above the build's
  (2026-10-17). Accepted.
- The engine keeps four counts per language for the life of the index. Accepted.

## Rejected

- **Resolve every site at the build and keep the counts** — ADR 3.7's trade: every build pays a resolution few
  consumers ask for, and a graph that takes an insert holds counts no longer true.
- **Keep the graph's counts on every insert and removal** — saves about 5 ms a call at a cost to each of millions of
  inserts, and a counter per kind kept beside the definitions.
- **Count each language's files from the index when asked** — 24.5 ms a call for the 182,714 entries of the C++
  game-engine tree (2026-10-17), and no count of what the cache answered.
- **One memo for the whole resolution, on one thread** — one memo's memory instead of 18, at 18 times the time.
- **An estimate of retained bytes from the sizes of the structures** — the footprint is measured from the process, and
  no consumer reads an estimate beyond checking it is not zero.
- **The cache store's own counters in the stats** — the engine reports what the cache answered for each language; the
  store's counters stay inside the index until a consumer needs them.
- **A worker count in the stats** — `Index::threads` answers it.
- **Three reasons: no candidate, likely external, external import** — `NotExported` and `NotAdmitted` would hide inside
  no candidate, though each points at a different fix.

## Revisit if

A consumer asks for the edge count often enough that a whole resolution, 0.4 s on the C++ game-engine tree, matters on
each call. High confidence: only `index_stats` with `coverage` asks (ADR 4.23).
