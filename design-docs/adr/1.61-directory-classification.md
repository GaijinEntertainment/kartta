# Classify a large directory's entries in parallel

- **Date:** 2026-10-14
- **Governs:** `crates/kartta-walk/src/walk.rs` (`PARALLEL_CLASSIFY`, `CLASSIFY_RUN`, `Walker::classify`,
  `Walker::classify_in_parallel`)
- **Pinned by:** `crates/kartta-walk/tests/walk.rs`
  (`a_directory_large_enough_to_classify_in_parallel_walks_to_the_same_tree_and_spreads`)

The index's policy decides an entry by a name check in a build that reads nothing and by a file read in one that reads
([ADR 1.12](/design-docs/adr/1.12-build-content-reads.md)), so a flat directory classified one entry at a time read on
one thread while the rest of the pool waited. A directory of 64 entries or more has its entries decided in parallel, in
bounded runs, at the price of `visit` calls that run at once and in any order.

## Decision

- **Parallel from 64 entries.** A directory of 64 entries or more has its entries decided in parallel and recorded in
  listing order, so the tree is identical either way. A smaller directory is decided in order on the thread that walks
  it.
- **Runs of 4096.** The entries are decided in runs of 4096, each recorded before the next starts. A run that a
  cancellation stopped ends the directory.
- **One path buffer.** Each entry's path is built in one buffer per directory, or per parallel piece, that already holds
  the directory's prefix, so classifying allocates no path per entry.
- **Any order of `visit` calls.** A `Policy`'s `visit` calls for one directory may run at once and in any order: the
  tree does not depend on that order, and a value a policy derives from call order does.

## Why

- A reading build on a 182,714-entry checkout took 2.30 s with parallel classification against 2.69 s without, over
  eight interleaved rounds, and its build that reads nothing stayed at 0.21 s either way (macOS, 2026-10-14, #19).
- Below 64 entries the fork costs more than the work it spreads.
- Runs bound the decisions waiting to be recorded to one run, however large the directory.

## Consequences

- A policy must not depend on the order of `visit` calls within a directory. Accepted: the index hands out content ids
  in call order, which is why [ADR 1.12](/design-docs/adr/1.12-build-content-reads.md) maps each id to a position after
  the build.

## Rejected

- **Classify one entry at a time, as the walk did** — no change to the walk, and a large flat directory reads on one
  thread: 2.69 s against 2.30 s on the checkout.
- **Decide a whole directory at once** — the decisions waiting to be recorded grow with the directory.

## Revisit if

The policy's `visit` stops doing I/O for every consumer, so the fork spreads only name checks. High confidence while a
reading build exists.
