# Follow the tree over the wire only when a build asks

- **Date:** 2026-10-22
- **Governs:** `crates/kartta-ffi/src/built.rs` (`Shared::build_watched`, `Followed for Shared`),
  `crates/kartta-ffi/src/handle.rs` (`Kartta::build`, `Drop for Kartta`), `crates/kartta-ffi/src/wire/build.rs`
  (`WatchView`, `BuildParams::options`), `bindings/go/kartta.go` (cgo flags), `bindings/go/wire/build.go`
  (`BuildOptions.Stamps`)
- **Pinned by:** `crates/kartta-ffi/src/handle.rs` tests, `crates/kartta-ffi/tests/dispatch.rs`,
  `bindings/go/kartta_test.go`, `bindings/go/zero_test.go` (`Test_FalseStamps`)

A wire consumer that cannot tell what changed, an agent's host or an editor, can by itself only refresh the whole tree
on a schedule ([ADR 4.32](/design-docs/adr/4.32-wire-refresh.md)) or answer from an engine older than the tree. A build
of [ADR 4.2](/design-docs/adr/4.2-c-abi-wire.md) that asks to `watch` leaves the engine following its tree, as the MCP
server's does ([ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md)), and a build that does not ask follows nothing, so
only a consumer that wants the follow pays its thread, its watcher and its stamps.

## Decision

- **`build` takes `watch`.** It is false by default. The build starts a watcher before it walks, takes in what the
  watcher holds before it answers, and leaves `kartta::Follower` refreshing the engine from each change the operating
  system reports, on a thread of the library's own, `kartta-watch`, under the write lock a `refresh` takes, so a query
  waits for it as for any refresh. A change macOS or Windows reports more than 50 ms after that drain began is taken in
  after the build answers ([ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md)).
- **`watch` keeps stamps.** `stamps` left out takes `watch`'s value. `watch` with `stamps` false answers
  `invalid_params`, naming both, while the wire reads the build's params: it asks the engine's
  `Engine::check_watched`, the rule `Engine::build_watched` holds
  ([ADR 4.43](/design-docs/adr/4.43-follow-policy-placement.md)), and holds no copy of the condition. The refused
  build changes nothing, as every refused params does, so the handle keeps answering from the engine it held. Go's
  `wire.BuildOptions.Stamps` is a `*bool`, so a Go caller's false reaches the engine as a Node caller's does.
- **The `watch` answer.** `build`, `stats` and `refresh` answer `watch`: `following`, whether a watcher still refreshes
  the engine; `reason`, why the watch a build asked for is off, the reasons
  [ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md) lists, absent while it follows and when the build asked for
  none; and `restarts`, the watchers the follow started over a whole refresh, absent at 0. A build that asked for no
  watch answers `{"following": false}`. `following` false is a consumer's cue to `refresh`.
- **Its own token.** The follow runs under a token of the engine's, which `cancel` never reaches, so a cancel naming no
  call ([ADR 4.30](/design-docs/adr/4.30-wire-cancellation.md)) leaves the watch following. A build trips the token of
  the engine it replaces before it empties the slot, under the refreshes' lock as it cancels them, and dropping the
  handle trips it too, so `kartta_free`, Go's `Close` and Node's `close` end the watch. A refresh of the follow's under
  way stops before its walk ends. The thread holds the engine through a `Weak`, upgraded for one refresh at a time, and
  ends at its next wake, a second at most, letting its watcher go.
- **Lock order.** The locks are taken in one order: the refreshes' registry, then the builds', then the slot, then the
  engine's own, which the watch thread takes alone.
- **Linking.** `kartta-ffi` enables `kartta`'s `watch` feature, so the archive carries the watcher. The Go binding links
  CoreServices and CoreFoundation on macOS, which FSEvents needs; the Node addon links them itself
  ([ADR 4.3](/design-docs/adr/4.3-node-addon.md)).
- **The bindings.** The bindings carry it as Go's `wire.BuildOptions.Watch`, `wire.Watch`, `Stats.Watch` and
  `Refresh.Watch`, and TypeScript's `watch` in `BuildParams`, `Watch`, `Stats.watch` and `Refresh.watch`.
- **The goldens.** The goldens ask for `stamps`, not `watch`, so they answer `{"following": false}`: a watched golden's
  `restarts` would vary, since FSEvents can report a tree's own making after a watch began. Tests pin a watched build
  in the dispatch and in both bindings.

## Why

- A watched edit reached `definitions` in about 47 ms on the C++ game-engine tree, where a scheduled whole refresh took
  339-443 ms there and seconds on larger trees (2026-10-22, #154).
- A build that asks for no watch runs what it ran, and a following engine holds no memory past the stamps'.

## Consequences

- On a volume other processes write, the watch takes in every change it reports: 10 s without edits took up to 1.85 s
  of CPU on the macOS data volume (2026-10-22), where an unwatched engine takes none. Accepted: the consumer asked.
- A rebuild does not wait for the old watch thread to end, so on Linux its new watcher can meet the old one's inotify
  watches for up to a second; a tree that needs more than half the limit can build with the watch off, its `reason`
  saying so: accepted.

## Rejected

- **Watch on by default, as the MCP server** — a wire consumer such as Kensai builds a tree for one job and does not
  edit it; a watch costs a thread, a watcher, on Linux an inotify watch a directory, and the stamps it needs.
- **The follow under `cancel`** — a consumer that cancels what is in flight on a deadline would lose its watch, with no
  way to start it again but a build.
- **A build or a close that waits for the watch thread to end** — a wait of up to a second for a thread that holds
  nothing but its watcher once the engine is let go.
- **The wire's own refusal of `watch` without stamps, before the build drops the engine** — a second copy of a rule
  the engine holds, and one a binding's types can keep a caller from: a Go `bool` under `omitempty` never sends a
  false (#1043).
- **The wire answering the refusal `Engine::build_watched` returns** — it comes after the build's turn dropped the
  engine the handle held ([ADR 4.45](/design-docs/adr/4.45-wire-build-lifecycle.md)), so a mistake in one option
  would cost the caller its index (#1043).
- **Stamps kept whatever an explicit false says** — the caller's false would be ignored without a word (#1043).

## Revisit if

A wire consumer edits the trees it builds, so a watch would pay for itself by default. High confidence: Kensai's builds
serve one job each.

## History

- 2026-11-06 — `watch` keeps stamps: the wire's own refusal of an explicit false moved into the engine, which the wire
  asks before the build drops its engine, so the rule lives once, and Go's `Stamps` became a `*bool` so a Go caller
  reaches it (#1043)
