# Announce every cap

- **Date:** 2026-08-24
- **Governs:** `crates/kartta-fs/src/glob.rs` (`Capped::truncated`, `Capped::matched`, `Capped::excluded`),
  `crates/kartta-fs/src/list.rs` (`Listing::truncated`), `crates/kartta-fs/src/fuzzy.rs` (`FuzzyMatches::truncated`),
  `Index::entries`
- **Pinned by:** `crates/kartta-fs/tests/index.rs` (`glob_honours_a_limit_by_taking_the_first_paths_in_index_order`,
  `glob_matching_exactly_the_limit_is_not_truncated`, `glob_without_a_limit_is_never_truncated`,
  `a_glob_limit_stays_exact_under_an_exclusion`, `a_cut_glob_counts_every_match_and_exclusion_past_its_limit`,
  `a_limit_cuts_the_listing_and_says_so`,
  `a_directory_holding_exactly_the_limit_is_not_truncated`,
  `a_ranked_answer_is_truncated_only_when_the_limit_turned_a_match_away`),
  `crates/kartta-fs/src/glob.rs::chunks_counted_apart_count_as_one_chunk_does`

Three path queries of the file index take a cap, a glob, a ranking and a listing, and a content search decides as a
listing does. Each answer carries a `truncated` flag. A listing keeps it exact by looking for one entry past the cap,
and a glob by counting every match past it on the index's threads. A ranking's count of matches settles it for a query
with terms at no cost, and an empty query probes one candidate past the limit in each run. On a ranking the flag is set
on most capped calls.

## Decision

- **The test.** Every capped answer says whether its cap turned an item away, so no caller works it out, and carries
  the count the engine holds without another pass: a ranking's matches
  ([ADR 1.56](/design-docs/adr/1.56-ranking-match-count.md)) and a listing's entries under its directory
  ([ADR 1.8](/design-docs/adr/1.8-listing-counts.md)). A glob carries its count of matches too, the one count here
  that takes a pass of its own.
- **A ranking.** `Index::fuzzy` answers `truncated` beside its count of matches
  ([ADR 1.56](/design-docs/adr/1.56-ranking-match-count.md)). A query with terms compares the count with the answer. An
  empty query, which answers in index order and which the count leaves out, stops on the first path past the limit.
- **Index order.** Index order explains nothing. `Index::glob` returns a `Capped` and `Index::list` a `Listing`, and
  each carries `truncated`: whether the limit turned an item away.
- **A glob's count.** `Capped::matched` counts every path the filter selects outside the exclusion, those past the
  limit included. Past the first match the limit turns away, the glob counts the rest of the index in runs on the
  index's threads, what the exclusion removed there included, and `truncated` compares the count with the answer.
- **An actual rejection.** `truncated` is set by an actual rejection, never inferred from the answer holding as many
  items as the limit. Under a limit of *n* a listing looks for the *n*+1th entry and reports whether it was there, and a
  glob counts its matches, so an answer holding exactly the limit is complete and says `false`.
- **Exclusion before the limit.** An exclusion removes paths before the limit sees them
  ([ADR 1.55](/design-docs/adr/1.55-path-query-exclusion.md)), so the limit is spent on what the exclusion leaves, and
  the probe and the count see only the paths it leaves: `truncated` stays exact under an exclusion.
- **What an exclusion removed.** A listing's count of what its exclusion removed ends where the answer ends
  ([ADR 1.8](/design-docs/adr/1.8-listing-counts.md)). A glob's covers the whole index, as its count of matches does
  ([ADR 1.55](/design-docs/adr/1.55-path-query-exclusion.md)).
- **No capped iterator.** A capped answer is materialized, and one in index order carries the flag. An iterator takes no
  cap: `Index::entries` yields every entry.
- **Content search.** A content search decides as a listing does, because matches within a file arrive in file order;
  [ADR 1.11](/design-docs/adr/1.11-content-search-limits.md) states how it keeps `truncated` exact.

## Why

- The engine answers as a library: its caller sets each bound per call and decides what to show, and whether a bound
  turned an item away is a fact only the engine holds without running the query again unbounded (#1044). That a
  ranking's order explains its cut is a matter of presentation, which a consumer owns: `kartta-mcp` prints the count
  instead.
- A ranked answer with no flag left the wire asking one ranked item past its limit to answer `truncated`, a rule no
  other surface held, and an empty query's index order explains no cut.
- Ten paths in depth-first order look exactly like the first ten of two hundred, and a listing of twenty entries
  asserts that the directory holds twenty. Without a flag the caller has a wrong answer and nothing to detect it with.
- The walk dropped its entry cap because a cut tree could not be told apart from a whole one and its surviving subset
  depended on thread scheduling. `Index::entries` is depth-first and deterministic, so a cap takes a defined prefix,
  and the flag makes the cut visible.
- Inferring the flag from a full answer gets it wrong in the case a caller most needs it right: an answer that holds
  exactly the limit.
- An iterator ends when the caller stops pulling, so nothing can set a flag and there is nowhere to put one; a capped
  iterator would bring back the unannounced cut.
- For a listing, counting what a bound removed past the end of the answer is the work the cap exists to avoid.
- A glob answers matches, and a caller handed its first 200 could not tell them from 200 of millions without asking
  again unbounded (#1347). In runs on 8 threads, a glob of `**` capped at 200 counted the 8.6M matches of the data
  volume's 9.6M entries in 132-142 ms, and in 149-151 ms excluding `**/node_modules` with the 107,747 paths it removed
  (2026-11-27).

## Consequences

- Each capped listing matches one entry past its limit, and each run of a capped empty query offers one path past it.
  Accepted.
- A cut glob matches every path past its limit on the index's threads, up to 151 ms on the data volume. Accepted.
- The C ABI wire answers a glob's `truncated` and `excluded` and not its count of matches, though a cut glob through
  it pays for the count (#1351).
- A glob the limit does not cut walks the whole index on one thread: 218-221 ms for one that matches nothing on the
  data volume (#1352).
- A capped ranking sets the flag whenever the index holds more matches than the caller asked for, the ordinary case, so
  a caller learns more from `matched`. Accepted.

## Rejected

- **A ranked answer with no flag, its order standing for one** — an empty query's order explains nothing, and the wire
  answered the flag anyway.
- **Report it nowhere** — a capped listing then reads as a small directory; a symmetrical answer is a wrong one.
- **Return the count of what the cap cut instead of a flag** — counting what a depth bound, a collapse and an exclusion
  would still let through past the cap means visiting it, the work a listing's binary-search skip avoids. The index's
  own total under a listed directory costs no such scan and stands beside the flag
  ([ADR 1.8](/design-docs/adr/1.8-listing-counts.md)).
- **Count a glob's matches past the cap on one thread** — 574-613 ms for `**` on the data volume's 9.7M entries
  (2026-11-27), past the 500 ms a call may take.
- **Count a glob's exclusions only up to the cut, beside a count of matches past it** — the two lines of one answer
  then cover different parts of the tree (#1347).
- **Leave the caller to ask for one more than it wants** — the caller reimplements the flag with an off-by-one at each
  call site, where the query does it once.
- **Return an iterator from the capped queries** — the caller then cannot tell exhausting the matches from stopping on
  its own count.

## Revisit if

A caller needs the count of what a listing's cap cut, which arrives as its own named number and never by widening
`truncated`; or a glob's count past its cap runs past 500 ms on a tree a caller indexes. High confidence: every count
past the answer's end costs a scan, and the data volume is the largest tree measured.

## History

- 2026-11-27 — A glob's count, What an exclusion removed: a cut glob said only that more paths matched, so a caller
  asked again unbounded and counted them, and its count of exclusions then had to cover the same tree (#1347)
- 2026-11-02 — A ranking: a ranked answer carried no flag, so the wire worked one out from one more ranked item, and an
  empty query's cut had no account (#1044)
- 2026-10-20 — Exclusion before the limit: a glob or a ranking took no exclusion, so its callers dropped paths after
  the cap and answered a short list with a wrong `truncated` (#152)
- 2026-10-19 — Content search: `truncated` depended on whether the batch that filled the limit held a further match,
  so a content index flipped it (#111)
- 2026-10-14 — Content search: a content search's matches arrive in file order, as a listing's entries arrive in index
  order (#19)
- 2026-10-13 — Index order: a listing reports what it left out, and the index's own total under the listed directory
  costs no scan (#15)
