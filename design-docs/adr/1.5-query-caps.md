# Announce a cap unless the order already explains it

- **Date:** 2026-08-24
- **Governs:** `crates/kartta-fs/src/glob.rs` (`Capped::truncated`), `crates/kartta-fs/src/list.rs`
  (`Listing::truncated`), `crates/kartta-fs/src/fuzzy.rs` (`FuzzyMatches`), `Index::entries`
- **Pinned by:** `crates/kartta-fs/tests/index.rs` (`glob_honours_a_limit_by_taking_the_first_paths_in_index_order`,
  `glob_matching_exactly_the_limit_is_not_truncated`, `glob_without_a_limit_is_never_truncated`,
  `a_glob_limit_stays_exact_under_an_exclusion`, `a_limit_cuts_the_listing_and_says_so`,
  `a_directory_holding_exactly_the_limit_is_not_truncated`)

Three queries of the file index take a cap: a glob, a ranking and a listing. An answer whose own order explains what a
cap left out says nothing more; an answer in index order carries a `truncated` flag, kept exact by looking for one item
past the cap. The flag costs one more item per capped query, and a ranked answer carries none.

## Decision

- **The test.** A capped answer announces the cap unless the answer's own order explains what is missing. Each surface
  is judged by one question: can a caller tell from the order alone that something is missing?
- **A ranking.** A ranking explains its cut, so `Index::fuzzy` carries no `truncated`. Its count of matches is a named
  number beside the ranking ([ADR 1.56](/design-docs/adr/1.56-ranking-match-count.md)).
- **Index order.** Index order explains nothing. `Index::glob` returns a `Capped` and `Index::list` a `Listing`, and
  each carries `truncated`: whether the limit turned an item away.
- **An actual rejection.** `truncated` is set by an actual rejection, never inferred from the answer holding as many
  items as the limit. Under a limit of *n* the query looks for the *n*+1th item and reports whether it was there, so an
  answer holding exactly the limit is complete and says `false`.
- **Exclusion before the limit.** An exclusion removes paths before the limit sees them
  ([ADR 1.55](/design-docs/adr/1.55-path-query-exclusion.md)), so the limit is spent on what the exclusion leaves, and
  the probe looks for the *n*+1th path it leaves: `truncated` stays exact under an exclusion.
- **Counts end with the answer.** A count of what an exclusion removed ends where the answer ends, for a glob
  ([ADR 1.55](/design-docs/adr/1.55-path-query-exclusion.md)) and for a listing
  ([ADR 1.8](/design-docs/adr/1.8-listing-counts.md)).
- **No capped iterator.** A capped answer is materialized, and one in index order carries the flag. An iterator takes no
  cap: `Index::entries` yields every entry.
- **Content search.** A content search decides as a listing does, because matches within a file arrive in file order;
  [ADR 1.11](/design-docs/adr/1.11-content-search-limits.md) states how it keeps `truncated` exact.

## Why

- "The ten best matches for `main`" is answered in full by ten paths: the order says the rest scored lower. A flag
  there would be set on nearly every call with a cap, which is how a flag stops being read.
- Ten paths in depth-first order look exactly like the first ten of two hundred, and a listing of twenty entries
  asserts that the directory holds twenty. Without a flag the caller has a wrong answer and nothing to detect it with.
- The walk dropped its entry cap because a cut tree could not be told apart from a whole one and its surviving subset
  depended on thread scheduling. `Index::entries` is depth-first and deterministic, so a cap takes a defined prefix,
  and the flag makes the cut visible.
- Inferring the flag from a full answer gets it wrong in the case a caller most needs it right: an answer that holds
  exactly the limit.
- An iterator ends when the caller stops pulling, so nothing can set a flag and there is nowhere to put one; a capped
  iterator would bring back the unannounced cut.
- Counting what a bound removed past the end of the answer is the work the cap exists to avoid.

## Consequences

Each capped glob and listing matches one item past its limit. Accepted.

## Rejected

- **Report truncation on every capped surface** — on the ranked query the flag is set whenever the index holds more
  matches than the caller asked for, which is the ordinary case, so it trains the caller to ignore it.
- **Report it nowhere** — a capped listing then reads as a small directory; a symmetrical answer is a wrong one.
- **Return the count of what the cap cut instead of a flag** — counting what a depth bound, a collapse and an exclusion
  would still let through past the cap means visiting it, the work a listing's binary-search skip avoids. The index's
  own total under a listed directory costs no such scan and stands beside the flag
  ([ADR 1.8](/design-docs/adr/1.8-listing-counts.md)).
- **Leave the caller to ask for one more than it wants** — the caller reimplements the flag with an off-by-one at each
  call site, where the query does it once.
- **Return an iterator from the capped queries** — the caller then cannot tell exhausting the matches from stopping on
  its own count.

## Revisit if

A caller needs the count of what a cap cut on an index-order surface, which arrives as its own named number and never
by widening `truncated`. High confidence: on an index-order surface every count past the answer's end costs a scan.

## History

- 2026-10-20 — Exclusion before the limit: a glob or a ranking took no exclusion, so its callers dropped paths after
  the cap and answered a short list with a wrong `truncated` (#152)
- 2026-10-19 — Content search: `truncated` depended on whether the batch that filled the limit held a further match,
  so a content index flipped it (#111)
- 2026-10-14 — Content search: a content search's matches arrive in file order, as a listing's entries arrive in index
  order (#19)
- 2026-10-13 — Index order: a listing reports what it left out, and the index's own total under the listed directory
  costs no scan (#15)
