# Follow a tree through its change notifications

- **Date:** 2026-10-15
- **Governs:** `crates/kartta-fs/src/watch.rs`, `crates/kartta-fs/src/watch/`, `crates/kartta/src/follow.rs`,
  `kartta_fs::Watcher`, `kartta_fs::WatchError`, `Index::build_watched`, `Index::refresh_watched`,
  `Index::refresh_paths_watched`
- **Pinned by:** `crates/kartta-fs/tests/watch.rs`, the tests of `crates/kartta-fs/src/watch.rs` and
  `crates/kartta-fs/src/watch/notified.rs`

A consumer that keeps an index current needs the paths that changed for
[ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md)'s refresh, and the operating system already knows
them. A `Watcher` hands them over in batches for a loop the caller runs, so an index nobody follows pays nothing; the
trade is that every consumer that follows runs that loop itself.

## Decision

- **The caller's loop.** `Watcher` is built only with kartta-fs's `watch` feature. The index holds no thread, no lock
  and no reference to a watcher. `Index::build_watched` and `Index::refresh_watched` start a watcher on the root before
  their walk and return it beside the outcome; a watcher that cannot start, or cannot watch a directory it should, does
  not stop the walk, and the second value is the `WatchError` that says why. `Watcher::drain` hands over every change
  made before the call, those made while the walk ran included. `Watcher::wait(timeout)` blocks until the tree changes,
  then gathers until the tree has been quiet for 20 ms, or for 500 ms at most, so a steady writer cannot hold the
  refresh off; each poll takes one bounded helping, so a stream that never stops still lets a batch close. Reading
  happens inside `wait` and `drain`, on the caller's thread. The caller takes a batch in with
  `Index::refresh_paths_watched`, which refreshes the paths under the watcher.
- **What a drain waits for.** A drain waits for the system to report a change 0 ms on Linux, where inotify queues a
  change as the call that made it returns, and up to 50 ms on macOS and Windows; a change those systems report later
  comes with a later wait. Once a change is there, a drain gathers as a wait does, but a Linux drain does not close
  before it has read every change queued at its call ([ADR 1.21](/design-docs/adr/1.21-linux-drain-bound.md)).
- **What a batch names.** A batch is a sorted list of root-relative, forward-slash paths, each once, named as the system
  reported them. A notification for the root's own path names nothing, since the index holds no entry for it and a
  change of an entry inside the root is reported for that entry, so a `touch` of the root alone hands over a batch of no
  paths, and the watch goes on. [`Watcher::wait`](/crates/kartta-fs/src/watch.rs) states what a path outside the tree, a
  name that is not valid UTF-8, and a name a refresh refuses by its spelling come to: a name that holds a `\` or starts
  with a drive is named by the directory that holds it, and directly below the root it makes the batch the whole tree,
  so the refusal of [ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md) never stops a follow.
  [ADR 1.26](/design-docs/adr/1.26-batch-path-memory.md) states what a batch holds while it is gathered.
- **A lost batch.** The batch is the empty path alone, the whole tree, whenever the watcher cannot name what changed:
  when a batch was closed before its reads covered what was queued, and when the system dropped changes, as
  [`Watcher::wait`](/crates/kartta-fs/src/watch.rs) lists them, more notifications than the macOS and Windows queue
  holds ([ADR 1.25](/design-docs/adr/1.25-notification-queue.md)) included. A rescan of a directory below the root names
  that directory, which `Index::refresh_paths` walks again with everything below it. An overflow during the walk loses
  the first drain's batch. A caller answers a lost batch by dropping the watcher, then calling `Index::refresh_watched`
  and following with the watcher it returns, never by refreshing under the old watcher. A root that went is told apart
  from a lost batch, as [ADR 1.73](/design-docs/adr/1.73-watched-root-loss.md) states.
- **The follow.** `kartta::Follower` answers a lost batch, `WatchError::Stopped` and `WatchError::Limit` that way, a new
  watcher over a refresh of the whole tree; the reason names what asked for it, such as
  `the notifications dropped changes`. A restart that fails, and any other `WatchError`, such as `Start` or
  `Unsupported`, end the follow with the reason in `Watch::off`; [ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md)
  states the rest of its policy.
- **Changes before the start.** A change made before the start is not reported, but `FSEvents` and
  `ReadDirectoryChangesW` can deliver one made moments before. Refreshing its path changes nothing when the index holds
  the change already, and takes it in when it does not.
- **The backends.** Linux is watched through inotify directly, one watch for each directory a walk keeps
  ([ADR 1.20](/design-docs/adr/1.20-linux-directory-watches.md)). macOS and Windows are watched through notify, one
  recursive stream from the root, beside a watch of the root's parent alone on Windows, which covers the whole tree,
  ignored and pruned parts included, so the walk tells it nothing, no watch is released, and a refresh under the watcher
  is `Index::refresh_paths`. A write inside an ignored or pruned part is still handed over, and its refresh changes
  nothing ([ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md) states what such a call costs).
  [ADR 1.23](/design-docs/adr/1.23-notify-version.md) pins notify's version, and
  [ADR 1.24](/design-docs/adr/1.24-macos-firmlink-watch.md) names the macOS paths.

## Why

- The first consumer builds once and never looks again, so following has to cost nothing to a consumer that does not.
- A watcher started before the walk holds every change the walk could not see, so the first drain replaces a second walk
  of the whole tree: a start that refreshed the tree after the build took 46.6–51.2 s on the data volume (2026-10-20).
- `FSEvents` reported a write 13.1 ms after it at most on a loaded machine (2026-10-20), which the 50 ms drain covers
  once a stream is live.
- The empty path is the one answer to a batch the watcher cannot name: a whole refresh under a new watcher, the only
  answer that also forgets a Linux directory moved while its notice was dropped.
- `FSEvents` keeps every flag the root's path has had on each later notification for it, and a `touch` of the root or
  the creation of a tree just made raises one; a batch that named the root lost the tree to a `touch`.

## Consequences

- Each consumer that follows runs the loop, or uses `kartta::Follower`
  ([ADR 4.43](/design-docs/adr/4.43-follow-policy-placement.md)). Accepted.
- A write reaches a refreshed index in a median of 35–41 ms, most of it the 20 ms the batch waits for quiet. Accepted.
- A change of a name directly below the root that holds a `\` or starts with a drive restarts the watch over a whole
  refresh; a home directory held no such name, nor any name with a `\` (2026-11-03). Accepted.
- A data-volume root watched through its firmlinks loses the whole tree for a rescan above one firmlink, such as `/usr`
  above `/usr/local`, though only that firmlink's part was dropped: naming the part would take a second name for a path
  outside the tree, for a notice the system raises only when it falls behind. Accepted.
- On macOS a change reported more than 50 ms after a drain began reaches the index only with a later wait: notify
  neither flushes an `FSEvents` stream nor hands over the event ids that would show how far it has come. Accepted.
- A stream sends its history before it goes live, so a change made in its first 150 ms was reported up to 323 ms after
  it, none lost (2026-11-02, [ADR 1.23](/design-docs/adr/1.23-notify-version.md)), and on a walk that short it reaches
  the index with the wait after the drain. Waiting it out would hold every macOS drain of a short walk for those
  300 ms, with no sign when to stop, for a change that arrives anyway. Accepted.

## Rejected

- **A watcher inside the index, on a thread of its own** — every consumer would pay for a thread and a lock around the
  index, the first one included.
- **Start the watcher over the built index, then refresh the whole tree** — a second pass over the tree at every start.
- **Watch from the index after the build, and stat every entry against the build's start** — a stat finds a changed
  entry, not one made in a directory, so each changed directory would need a listing and a watch for each directory made
  in it, still a second pass over every entry.
- **notify 9.0.0-rc.5 on Linux too** — it walks the tree again at start and watches every directory, ignored and `.git`
  ones included: 0.59–0.66 s at +44 MiB against 0.15 s at +12 MiB on 1.8 million entries (2026-10-15).
- **Refresh the root's own entries for a notification of the root** — a listing of the root and a pass over its entries
  for each such notification, for nothing the batch's own paths missed.

## Revisit if

A consumer that cannot run a loop of its own needs to follow a tree. High confidence: the MCP server and the C ABI
follow through `kartta::Follower`, and Kensai never watches.
