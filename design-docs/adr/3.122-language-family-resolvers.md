# Resolve a language family through the resolver its first language builds

- **Date:** 2026-10-22
- **Governs:** `crates/kartta/src/resolving.rs` (`Resolving::resolvers`), `crates/kartta/src/engine.rs` (`families`),
  `kartta_lang::Language::family`, `kartta_lang::Language::resolver`
- **Pinned by:** `crates/kartta/tests/engine.rs` (`a_family_resolves_through_one_resolver_its_first_language_builds`,
  `a_family_whose_first_language_claims_no_file_resolves_the_files_of_the_others`)

The languages of one family resolve against each other in one graph
([ADR 3.1](/design-docs/adr/3.1-language-plugin-contract.md)), and TypeScript, TSX and JavaScript each read every
`tsconfig.json` and `package.json` of the tree to build a resolver of their own. The engine builds one resolver per
family, from its first language, and every file of the family resolves through it, so a language that joins a family
must resolve that family's files as its first language does.

## Decision

- **Interchangeable resolvers.** The languages of one family build interchangeable resolvers. The engine asks only the
  first of a family's languages, in the order `Engine::build` was given them, for the resolver every file of the family
  resolves through, and asks it once per build. The same first language gives the family's graph its conventions.
- **Built for a family that was read.** The first language builds it even when it claims no file the build read, as
  `typescript` does in a tree of only `.tsx` files. A family no file of which the build read builds none.
- **Languages outside kartta.** A language kartta does not ship still plugs in without a change to kartta: one that
  names a family of its own is that family's first language, and one that joins a family states that it resolves that
  family's files as the family's first language does.
- **Followed families.** A followed engine keeps one resolver and one configuration for the family, and names the
  family when that configuration changed what it resolves
  ([ADR 3.82](/design-docs/adr/3.82-followed-resolver-rebuilds.md)).

## Why

- A family read its configuration once per language: the three jsts languages each read every `tsconfig.json` and
  `package.json`, and a family's one resolver reads them once ([ADR 3.4](/design-docs/adr/3.4-jsts-extraction.md),
  #167).
- The rule that picks the family graph's conventions already names the first language, so the resolver follows the
  same rule and no new method is needed.

## Consequences

- A second language of a family that resolves differently from the first is resolved as the first resolves, silently;
  accepted, since the contract asks the family's languages to build interchangeable resolvers.

## Rejected

- **A resolver for each language of a family, over a repository that reads each file once for all of them** — saves
  the reads, but still holds and compares a configuration for each language of the family, and needs a cache shared
  across their resolvers.
- **A resolver asked of the family through a method of its own** — every language crate implements one more method,
  where the first of a family's languages already decides the family's conventions.

## Revisit if

A family's languages need different resolutions of the same import, so that one resolver cannot serve them all. High
confidence it does not happen: the jsts family's three languages resolve alike.
