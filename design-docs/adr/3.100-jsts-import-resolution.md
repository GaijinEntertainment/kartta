# Resolve a TypeScript or JavaScript import as the compiler and bundlers do

- **Date:** 2026-10-16
- **Governs:** `crates/kartta-lang-jsts/src/resolve.rs`, `crates/kartta-lang-jsts/src/modules.rs`,
  `crates/kartta-lang-jsts/src/tsconfig.rs`, `crates/kartta-lang-jsts/src/package_json.rs`,
  `crates/kartta-lang-jsts/src/config.rs`, `crates/kartta-lang-jsts/src/walk/exports.rs` (`push_directive`)
- **Pinned by:** `crates/kartta-lang-jsts/src/tests/resolution.rs`, `crates/kartta-languages/tests/engine.rs`
  (`a_javascript_root_relative_import_binds_through_the_file_a_jsconfig_roots_it_at`)

A TypeScript or JavaScript specifier names a file through rules the compiler and the bundlers take from the
repository's `tsconfig.json`, `jsconfig.json` and `package.json` files. The `jsts` family's resolver
([ADR 3.4](/design-docs/adr/3.4-jsts-extraction.md)) reads those files and resolves as they do, and leaves out the
configuration that only a bundler or a web server states, save the alias Vue CLI sets unasked.

## Decision

Each probe, option and order below is stated in full in [`modules.rs`](/crates/kartta-lang-jsts/src/modules.rs)
and the config readers beside it.

- **What the resolver reads.** The family builds one resolver
  ([ADR 3.122](/design-docs/adr/3.122-language-family-resolvers.md)). It reads every `tsconfig.json`,
  `jsconfig.json` and `package.json` outside `node_modules` and `vendor` directories when it is built, and a
  `tsconfig*.json` or `jsconfig*.json` only when one of those extends or references it. A file of another name that a
  config extends is not read. It keeps only what it derived, which a refresh compares
  ([ADR 3.82](/design-docs/adr/3.82-followed-resolver-rebuilds.md)).
- **Relative specifiers.** A specifier that starts with `./` or `../` probes the path as written, with each script
  extension, and as a directory with an `index` file of each; on a miss, an ESM `./m.js` probes again as the
  TypeScript source it stands for. Every probe below takes the same steps.
- **`#` specifiers.** A `#` specifier takes the `imports` of the nearest `package.json` above the importing file,
  which stops the lookup whether it declares any or not.
- **Configured paths.** Any other specifier first takes the `paths` of the nearest config above the importing file, a
  `tsconfig.json` or else a `jsconfig.json`, which governs alone, one that yields no `paths` included. A root-relative
  specifier takes `paths` alone: `"/*": ["./*"]` in `public/jsconfig.json` reads `/scripts/m.js` as
  `public/scripts/m.js`. Another specifier that no `paths` pattern resolves takes the config's explicit `baseUrl`,
  unless `paths` declares `*`: `helpers/fetch` under `"baseUrl": "src"` names `src/helpers/fetch.ts`. One `extends`
  hop applies, and a config with neither option takes those of the configs it references in its own directory. A
  `package.json` that depends on `@vue/cli-service` governs as a config whose one alias reads `@/` as its own `src/`,
  below a config of its directory.
- **Repository packages.** Where those `paths` resolve nothing, or there are none, a specifier that names a package of
  the repository takes its `exports`, and failing `exports`, the bare name takes the package's `module`, then its
  `main`, then its directory, and a subpath the file under the package's directory. A bare import of a package whose
  `exports` omits `.` therefore falls through to `main`, where Node rejects it.
- **Which package.** Of the packages whose names prefix the specifier, the longest name wins, then the package
  nearest the importing file; two equally near resolve to neither.
- **Queries.** A specifier with a `?query`, as Vite writes them, resolves without the query only after it misses as
  written.
- **Includes and imports.** A resolved import, a `require` or a dynamic `import()` of a string, a type-only one
  included, is an include of its file; one that names no file of the repository is kept as an import as written. What
  the names of such an import bind is [ADR 3.186](/design-docs/adr/3.186-jsts-package-bindings.md).
- **Re-exports.** A re-export names the file its specifier resolves to by the same rules, or none, and resolves
  together with the import of its statement.

## Why

- The compiler and the bundlers already define where a specifier leads, and the repository's own configuration is what
  they read. Vendored configs belong to third-party packages, and a checkout can hold thousands.
- The compiler resolves a non-relative specifier against an explicit `baseUrl` before it looks for a package, and a
  project that sets one imports its own files that way: on dagor, 43 TypeScript call pairs bind or rise to the include
  tier through it (2026-10-24, #518).
- The TypeScript language service looks for a `jsconfig.json` after a `tsconfig.json` in each directory, and applies
  `paths`, not `baseUrl`, to a root-relative specifier. SillyTavern's `public/jsconfig.json` roots all 27 such import
  lines at the `public/` its server serves: 26 call pairs rise to the include tier and 12 bind, each right (2026-10-24,
  #424).
- Vue CLI aliases `@` to `src` in every project it builds, and a project with no `tsconfig.json` imports its own files
  through it: 4 imports on the Go monorepo snapshot, each naming a file of the repository (2026-10-24, #519).
- A repository finds files by their exact name, and a `tsconfig*.json` variant takes part only as the target of a
  config that names it.
- An include edge is worth more than strictness: `main` is the module most bundler setups load. A monorepo of
  independent frontends can declare one package name twice, and a missing edge is better than one no bundler would
  make.
- A re-export resolved with its statement costs no second resolution, and the resolver knows the extensions and
  aliases a graph-side match would guess at.

## Consequences

- Each re-export that names a file costs a copy of its path: 118,642 of 166,762 on a monorepo checkout of 374,827
  files (2026-10-16, #30). Accepted.
- A root-relative specifier that no config's `paths` roots stays an import as written and goes on to the name tiers,
  though the server's code, `express.static('public')`, may root it. Accepted.
- A `jsconfig.json` include lets a member call on a call's result, or on a local one initializes, bind the included
  file's member of its name: 7 of the 20 pairs it adds on SillyTavern, `$('#x').hide()` among them (2026-10-24, #592).
- A specifier under a `baseUrl` that names no file of the repository probes the `baseUrl` once more before the
  packages. Accepted.
- An include the `baseUrl` resolves lets a bare call of a name a local declares, `const { setError } =
  useContext(AppContext)`, bind the included file's namesake: 13 pairs on dagor, none right, and 3 functions that a
  React context hands out read as unused (2026-10-24, #543).

## Rejected

- **The graph matching re-exports to includes** — by stem, path segment or an appended `.ts`, it could not see an ESM
  `.js` specifier, an alias, an `index.tsx` barrel or a package, and the graph would keep a language's extension rules
  against [ADR 3.1](/design-docs/adr/3.1-language-plugin-contract.md).
- **Resolving each re-export on its own** — one more resolution per re-exported name, where a statement re-exporting
  many names resolves the same specifier once.
- **A `baseUrl` probe kept apart from `paths`** — answers as the `*` pattern does, with one more field on every
  config.
- **Leaving a Vue CLI project's `@/` a package import** — its member calls bind outside the repository, and with
  #422 its bare calls do too.
- **Reading every `tsconfig*.json` up front** — reads variants that take part only through a config that names them.
- **Node's strict `exports`** — drops the include edge of a package whose `main` is what its bundler loads.
- **Rooting a root-relative specifier at the nearest `index.html`, a `public/` beside the `package.json`, or the
  nearest ancestor holding the file** — each binds SillyTavern's pairs as its `jsconfig.json` does and no tree measured
  gains more, while each guesses at a server; a `public/` misreads Vite's `/src/main.tsx` (2026-10-24, #424).

## Revisit if

A real tree's imports lead through a bundler's alias or a server root that no config states; none seen yet.
