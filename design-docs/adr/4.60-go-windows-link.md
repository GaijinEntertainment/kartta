# Link the Go binding on Windows against the `windows-gnu` archive

- **Date:** 2026-11-02
- **Governs:** `bindings/go/kartta.go`, `bindings/go/doc.go`, the Windows entry of the `go` job of
  `.github/workflows/ci.yml`
- **Pinned by:** the Windows entry of the `go` job of `.github/workflows/ci.yml`
- **Implementation:** pending — the release does not carry the `x86_64-pc-windows-gnu` archive yet (#345)

cgo on Windows links with MinGW-w64, and MinGW's linker refuses the archive the `x86_64-pc-windows-msvc` target builds.
The Go module links a static `libkartta_ffi.a` of the `x86_64-pc-windows-gnu` target; the trade is a second Windows
archive in the release, and a Rust target beside the one every other Windows channel builds.

## Decision

- **The archive.** On Windows the module links `libkartta_ffi.a` of `x86_64-pc-windows-gnu`, which the release ships as
  `kartta-ffi-X.Y.Z-x86_64-pc-windows-gnu.tar.gz`, and [the package](/bindings/go/doc.go) names it. The MSVC
  `kartta_ffi.lib` stays the archive for C consumers, and that target stays the one the Node addon builds. The gnu
  target ships this one archive and nothing else.
- **The link line.** `kartta.go` lists what `rustc --print native-static-libs` names for the archive, and leaves out
  `kernel32`, which gcc links by default.
- **The compiler.** A consumer needs a MinGW-w64 `gcc`, with either C runtime. CI pins one: gcc 15.2 of mingw-builds
  with UCRT, the runtime of the runner's own MinGW, and downloads it by digest because the runner's MinGW moves with
  the image.

## Why

- `go build` drives gcc or clang (`src/cmd/cgo/doc.go:124`, `src/cmd/dist/build.go:353`), and with anything but a clang
  that targets MSVC, Go's linker adds MinGW's own libraries (`src/cmd/link/internal/ld/lib.go:2005-2008`).
- The MSVC archive leaves `__chkstk` and vcruntime's `??_7type_info@@6B@` undefined under MinGW's linker, with either C
  runtime, in rustc's own std and with no C of kartta's involved (mingw-w64 12.0, binutils 2.44, 2026-11-02).
- The gnu archive linked and answered under Wine in all four pairs of the C runtime that built it and the C runtime
  that linked it, and the binaries import system DLLs alone. rustc lists it at Tier 1 and states its floor
  (`src/doc/rustc/src/platform-support/windows-gnu.md`).

## Consequences

- The release builds one more archive for Windows, and each Windows run of the `go` job downloads 103 MB. Accepted.
- Only the `go` job runs this target: the `test` job runs the Rust suites on the MSVC target. Accepted.
- rustc's page says the gnu targets have no maintainers and may be demoted. See Revisit if.

## Rejected

- **The MSVC archive under MinGW** — the link fails on the two names above.
- **Those two names from a small C file** — the link then passes, but on hand-written stand-ins for private names of
  vcruntime, which every consumer would have to carry.
- **A DLL** — it linked and answered like the archive, but a debug `kartta_ffi.dll` of 213 MB must then travel beside
  every binary, and it reopens the crate type [ADR 4.2](/design-docs/adr/4.2-c-abi-wire.md) rejected.
- **A clang that targets MSVC as cgo's `CC`** — Go's linker can drive one (`src/cmd/link/internal/ld/lib.go:3177`), but
  every consumer would set `CC` and hold Visual Studio's libraries. Not built.

## Revisit if

rustc demotes `x86_64-pc-windows-gnu`, or a Windows consumer cannot install MinGW-w64: a DLL built on the MSVC target is
then the candidate. Medium confidence until CI ran the suite on a Windows host.
