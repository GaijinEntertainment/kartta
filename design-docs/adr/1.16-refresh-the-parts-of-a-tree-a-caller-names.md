# Refresh the parts of a tree a caller names

- **Status:** accepted
- **Date:** 2026-10-15
- **Revised:** 2026-10-22
- **Initiative:** `01-kartta-fs-port`

ADR 1.15 refreshes an index by walking the whole tree again, which suits a consumer that asks for an up-to-date index
now and then. A consumer that follows the filesystem's notifications learns which paths changed, a few at a time, and a
whole walk for each batch costs 47–51s on the data volume. That consumer needs a refresh whose cost follows what
changed.

**`Index::refresh_paths` walks again only the paths it is given and splices what they hold into the index in place.**
Each path names something that changed, and a directory is walked again with everything below it; a change no path
names is not seen. The result is what `Index::refresh` would make of those parts: the same ignore sources, binary
extensions, content index storage, stamps and threads, and the same ids, stamps and carrying of unchanged files. A path
with a `..` component returns `BuildError::OutsideTree` before anything is walked, and a returned error leaves the
index answering as it did.

**A path that cannot be walked alone widens, and the outcome says so.** The splice replaces an indexed subtree, or
inserts one where the tree order puts it, so a path's parent has to be an indexed directory that is still a directory
on disk; until it is, the path widens to the parent, and a file in a new directory walks the new directory. Each
parent is checked once a call, which took 12,176 paths in one directory of the data volume from 98–102 ms to 58–61 ms.
While ignore rules apply, a `.gitignore` widens to the directory that holds it, and so does a `.git` below the root,
since both decide the rules of everything below that directory; with `IgnoreSources::None` a `.gitignore` is an
ordinary file and a `.git` changes nothing. A path inside `.git` names nothing the index holds and is skipped, as is a
`.git` at the root, where no rules are inherited to cut. Paths are sorted into tree order and a path below another is
dropped. One that widens to the root makes the call a whole `Index::refresh`. `RefreshOutcome::walked` lists what was
walked, so a consumer sees when a few changed paths cost a large directory or the whole tree.

**The rules above a part are read again, once a call for each directory.** A walk learns which control files a
directory holds from the listing it already made; a directory above a part walked again was not listed, so while
ignore rules apply it is asked for `.git` and `.gitignore` by name, two stats a directory, and a `.gitignore` it holds
is stat'd again, read and parsed. The parts arrive in tree order, so the directories above them are worked out in that
order and each is read once a call. Reading them once per directory took a batch of 1,000
paths on the game-engine checkout from 53–121 ms to 15–19 ms. Those `.gitignore` files lie outside the parts, so the
visitor is not handed them. Nothing is kept between calls: an index holds no rules, and a stale rule kept for a
`.gitignore` that changed unnamed would hide files without a trace.

**The splice builds the new arrays beside the old ones and installs them at the end.** The old index stays whole until
the content index is merged, the one step after the walk that can still fail, so a failure leaves it untouched. Every
entry outside the walked parts is copied once, a run between two parts at a time, so a call costs one pass over the
index's per-entry arrays whatever the number of paths, plus a copy of those arrays held until the call returns: 176–180
MiB on the data volume, below the build's own peak, and freed when it returns. A slot table for carrying files is
built only for the positions inside the walked parts, rather than one slot per entry as a whole refresh builds.

An engine that follows a tree makes that copy on every change it takes in, on top of what its build left rather than
beside a build, and it does not set the process's peak. On 16 copies of the game-engine checkout side by side, 2,923,440
entries, an engine built with stamps took 200 one-file refreshes, each of a file its graphs hold, appended to, spread
over the tree, under a load average of 26 to 94. Each call's heap rose 101.6 MiB over where it began and came back when
the call returned; the most it reached, 5,774 MiB, stayed 574 MiB below the build's heap peak of 6,348 MiB. The highest
footprint across the calls, 9,853 MiB, stayed 422 MiB below the build's peak of 10,275 MiB: a call that raised it
raised it 15 to 27 MiB, p10 to p90, until macOS took back 998 to 1,560 MiB at once, three times in the 200 calls, and
it stood at 7,917 MiB after the last call against 9,776 MiB after the build. The resident set rose from 13,179 MiB
after the build to 14,732 MiB after the calls while the footprint fell. The data volume was not followed: an engine over
it extracts every source file of the checkouts and the 16 copies it holds, and other processes write it while a series
runs.

**What a call reads goes into a segment of its own, merged by ADR 1.15's rule.** Past eight segments the call merges
the ones after the first, at most eight calls that read text apart under a watcher, and at a cost that follows what
those calls read: 3–7 ms on the checkout and under 30 ms on `~/wrk`. Merging every segment, once more than a quarter
of the files they hold lists for are gone, costs about what the build's merge costs: 0.1s for the checkout's 117 MiB
content index, 0.85–1.05s for the 1 GiB of `~/wrk`. The ids a stopped refresh handed out are retired by the next call
that completes, whichever kind it is.

**Revised 2026-10-20: `Index::parts_of` answers the parts a call walks without walking them, and the engine's limit
counts those parts, not the paths.** `Engine::refresh_paths` walks named paths apart up to a limit that grows with the
entries the index holds, at least 50, and past it refreshes the whole tree (ADR 3.33). The limit counted every named
path, so a build inside an ignored directory, which names its outputs by the thousand, made a whole refresh of paths
that change nothing: 60 paths inside a nested worktree's ignored `target/` answered `walked="tree" widened="60"
limit="50"`. The
parts are those of the rules above, worked out from what the index holds: a path inside a directory the index does not
hold widens to that directory, so an ignored `target/`, a nested worktree's or a new directory's paths count once
together, and a path inside `.git` or through a pruned name counts for nothing. The count reads no ignore rule, so a
file the rules hide in a directory the index holds still counts as a part: knowing that it is hidden takes the rules
above it, read again each call as above, and a part the rules hide costs the walk a stat, not a read and an
extraction. Nothing stale decides a part either: one the index last saw ignored is walked under the rules read for
this call, so a `.gitignore` edit takes in the paths it shows whether the edit is named or not. A call named no more
paths than the limit works nothing more out, since its parts cannot outnumber its paths; one named more works its
parts out, then works them out again as the walk does.

On the data volume, 6.2 million entries and a limit of 41,387–42,183, under a load average of 15–28, four processes a
side, alternating, each making three or five calls: 45,525–46,401 files inside the ignored `target/` of a checkout took
18.0–36.6 ms as their one part, against a whole refresh of 9.3–19.2 s on `main`, and raised the footprint 0–6 MiB over
where the call found it, against 30–465 MiB. 100 files spread over the tree, walked apart on either side, took
9.0–15.5 ms after a process's first call against 10.0–38.7 ms, and 63–77 ms against 54–94 ms in it. A call past the
limit that still widens works its parts out before the whole refresh: `Index::parts_of` of 45,775 spread files took
61–72 ms, and 1.06 s in a process's first call, against 9.7–12.9 s for the whole refresh on `main` and 10.6–17.0 s
with the parts first, three processes a side; of 45,775 files inside `target/`, which stat nothing, it took 28–58 ms.

**Revised 2026-10-20: the parts that are files are read on the index's threads.** A call took its parts one after
another and read each file on the calling thread, where a whole refresh reads on every thread, so past a few hundred
named paths a whole refresh was the cheaper call (ADR 3.33). Sampled at 1 ms, reads and extraction were 84% of the
calling thread's samples in an engine's refresh of 1,714 named paths on the game-engine checkout and 90% on the Go
monorepo snapshot, the graph's resolution the rest, and the splice under 0.5%. The calling thread still takes every part
in tree order, its stat and the rules above it, and walks a directory part on the index's threads as before; the parts
that are files are then read on those threads, each file's text dropped once its visitor returns, as a build drops it.
A call with one file among its parts, or one that reads nothing because it has no visitor and no content index, stays
on the calling thread: handing one changed file to the threads took an engine's one-file call on the checkout from a
median 1.4 ms to 1.5 ms. A one-file call therefore costs what it did: unchanged, 0.16–0.18 ms on an inert index of the
checkout and 0.70–0.72 ms on an engine of it, and 6.0–7.5 ms on an inert index of the 8.1 million entries of the data
volume, medians of two and five processes a side against the same on `main`.

**Revised 2026-10-20: a path takes the name the disk holds.** A volume that folds case, as macOS and Windows volumes do
by default, finds an entry by a name in another case than the one it holds, while the index holds each name as the walk
listed it and looks a path up byte for byte. A path spelled in another case than its entry therefore matched nothing the
index held, widened to the first name it spelled otherwise, and the walk found that name on disk and took it as
spelled, so the index held a second copy of everything below it. `modules/application/hooks/config.converters.ts`,
named for `modules/Application/` on the Go monorepo snapshot, added 20 entries to an inert index of it, and a file named
through `flightModels/WeaponPresets/` for `weaponPresets/` on the game-engine checkout added 12,177. A rename that
changed only a name's case kept both names, because `FSEvents` reports the old name beside the new one and the old name
still finds the entry. A part the index does not hold now takes the name the filesystem answers for it, and the path so
respelled widens again, each of its names respelled at most once; a part the walk finds on disk under another name than
its own is gone, as a part no longer on disk is. macOS answers through `getattrlist` with `ATTR_CMN_NAME`, which names
the entry the lookup found, a hard link by its own name, in the Unicode normalization form the volume holds, so a path
in the other form takes the disk's form too; Windows answers through `FindFirstFileExW`, at a cost not measured there.
Linux takes a path as spelled: a Linux volume folds case only in a directory that opts into it or on a mount of a
folding volume, and no call there answers a name short of listing the directory. On a case-sensitive APFS volume
`Dir/f.rs`, `dir/f.rs` and a new `DIR/f.rs` stay three entries, as a build makes them. A watcher on macOS hands over
another spelling only for such a rename: `FSEvents` reported an append through `dir/f.rs`, a rewrite through
`DIR/F.RS` and a file made through `dir/new.rs` each under the disk's `Dir/`.

**Revised 2026-10-21: `RefreshOutcome::walked_over` says whether a refresh walked the part that holds a path.** A
consumer that keeps what it derived from a file asks this of each such file after a refresh, and a test of every path
against every part walked costs the two counts multiplied: the engine's test of the files its resolvers read took up to
1.05 s of a refresh at its limit on 2.92M entries (ADR 3.33). The parts are kept in tree order, none below another, so
the one part that can hold a path is the last at or before it in that order, which a binary search of
`RefreshOutcome::walked` finds; the order is the index's own, so the search is too.

**Revised 2026-10-21: a refresh says where it moved the entries it kept.** A consumer that keeps something for each
position of the index, as an engine that follows its tree keeps the files its resolvers find by name (ADR 3.33), could
only build it again from every entry after a refresh, since a splice shifts every position after a part whose count of
entries changed. `RefreshOutcome::kept_positions` answers whether every position holds the entry it held before, path
and kind, as after a refresh that only read files again; `RefreshOutcome::position_after` maps a position from before
the refresh to after it, `None` inside a part walked again, by a binary search of the runs the splice replaced; and
`RefreshOutcome::walked_positions` gives the positions those runs hold now, one run for parts that lay side by side.
The splice already compares each run before and after it to list the files added and removed, so it notes the run and
whether an entry came, went or changed kind as it goes, 32 bytes a run.

The index's own part of a one-file refresh is small beside the engine's. On 16 copies of the game-engine checkout side
by side, 2,923,440 entries, an engine built with stamps took one file of each of its 12 languages a round, appended to,
then a copy added beside it, then the copy removed, each named alone; three rounds, medians of 36 calls, under a load

a file removed 48.0 ms, the index 7.5 ms and the splice 6.3 ms. On the game-engine checkout an appended file took

**A refresh that kept every position still copies the arrays.** It could write its parts' entries into the arrays where
they stand and leave the rest, and a prototype did so for a call with no content index segment to merge: the merge is
the step after the walk that can fail, and a failure must leave the old arrays whole. On the copies it took an appended
file from 16.8 ms to 11.1 ms (8.1–186.0), the index's part from 8.0 ms to 3.7 ms, and the heap a call holds while it
runs from 101.7 MiB to 0.4 MiB; a file added or removed moves positions and is copied as before, 67.5 ms against
64.7 ms and 57.3 ms against 55.4 ms. On the checkout an appended file took 3.7 ms against 4.3 ms. The copy stays:
writing in place is a second way to apply a splice, about 100 lines beside the copy that every call moving positions
keeps, which an index keeping a content index never takes; the 5.7 ms it saves is a third of a call that answers in
17 ms, and the heap it saves is given back when the call returns and does not set the process's peak, as above.

## Considered Options

- **Apply the change in place, moving each array's tail** — no second copy of the arrays, but a content index merge that
  fails afterwards would leave a half-applied index, and the copy stays below the build's peak.
- **Write a refresh that kept every position into the arrays in place** — 5.7 ms of a 16.8 ms one-file call on 2.92M
  entries, and 101.3 MiB of heap held while it runs, at a second way to apply a splice that an index keeping a content
  index cannot take, as the fifth revision measures.
- **Keep a refresh's entries in a delta beside the arrays, merged later** — not built: writing in place bounds what any
  splice that touches only its parts saves at 4.3 ms of the index's 8.0 ms on 2.92M entries, and a delta adds a lookup
  to every read of an entry.
- **Keep each directory's parsed rules in the index between calls**, checked by the `.gitignore`'s stamp or by the
  directory's — saves nothing on a process's first call and still asks every directory for a stamp; on later calls it
  won where a client answered the stamps from its cache and lost on paths no call had named, by a share of the rules
  read side by side, at 152 KiB to 3.0 MiB on the game-engine checkout held for the index's life, as the sixth
  revision measures. On the network mounts measured the stamp it checks is no staler than a read.
- **Read every directory above the parts on the index's threads** — the network mounts' gain, at the cost of waking
  the threads on a local call: 0.43–0.61 ms against 0.28–0.36 ms for one path under a load average of 5–7.
- **Start a call's reads on the threads when the last call met a slow directory** — saves at most the directory read
  in turn before the hand-off, 11.4 ms against 5.3 ms for one path a minute apart over NFSv3 with 1 ms, at a state kept
  between calls that a process's first call never has; the parts' own stats cost such a call as much again.
- **Take the parts' rules from the index's last walk** — the index keeps no rules, and keeping them costs the same as
  the option above.
- **Refuse a path that cannot be walked alone** — leaves every consumer to work out the widening, which needs the
  index's own view of what is indexed.
- **Apply the ignore rules before the engine counts the parts** — drops a file the rules hide in a directory the index
  holds, at a read of the rules above every part before the count, made again by the walk, or with the limit moved
  into the index between its rules and its reads. Such files are few: `git status --ignored=matching` lists 35 outside
  an ignored directory in the Go monorepo's checkout, 8 in this repository's and none in the game-engine checkout, most
  of them editor settings, while a build's outputs go to an ignored directory.
- **Take every part on the index's threads**, its stat, its rules and a directory's walk included — level with reading
  only the files there, as the table above shows, at a part's rules read before its stat tells whether it exists, and
  with the calling thread's share already at 1–2%.
- **Read the largest files first**, so the longest extraction starts early — slower on both trees, as the table above
  shows.
- **Compare folded names in the index on a volume that folds** — asks nothing for a part the index holds, but a part it
  does not hold scans the entries of its parent, 0.37 ms more for a new file in the directory of 12,176 files, as the
  table of the third revision shows. Its fold is not the volume's, so a name in the other normalization form still
  makes a second copy, a rename that changed only case keeps the old name where a whole refresh takes the new one, and
  it has to learn which volumes fold.
- **Ask `realpath` or `F_GETPATH`** — `realpath` answers every name of the path and follows a final symlink, and
  `F_GETPATH` needs the entry opened; each costs several times the one name `getattrlist` answers.

Revisit the parts' own stats when a consumer follows a tree on a network mount, where they cost a call one round trip
after another on the calling thread, and the names Linux takes as spelled when a consumer there follows a tree on a
volume that folds case. Revisit
writing in place when the copy sets a follower's peak, or when it is most of a call a consumer waits on.
