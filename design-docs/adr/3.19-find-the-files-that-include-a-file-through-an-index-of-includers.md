# Find the files that include a file through an index of includers

- **Status:** accepted
- **Date:** 2026-10-17
- **Updated:** 2026-10-17
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta-graph/src/dependents.rs` (`Graph::dependents`, `Dependents`),
  `crates/kartta-graph/src/graph.rs` (`included_by`, `includers_of`)
- **Pinned by:** `crates/kartta-graph/tests/graph/dependents.rs`

`Graph::dependents` asks the reverse of the includes each file's slot keeps
([ADR 3.5](./3.5-keep-the-graph-a-file-at-a-time.md)): the files that include a file, then the files that include
those, to a depth. The graph keeps the includers of each path, a file at a time, and walks them one depth at a time,
at the price of an index that grows with the include edges.

## Decision

**The graph keeps the includers of each path, a file at a time.** An insert lists the slot of the file under every path
it includes, and a removal or a replacement unlists it, so the index changes with the file as the slots do. The index is
keyed by the included path, not by the slot that holds it: a file that includes one the graph does not hold yet counts
as its includer when that file arrives, in whatever order a build inserts them. The includers are what each language's
resolution makes of its imports: a Go import is an include of every file outside test code in the package the import
resolves to ([ADR 3.150](./3.150-resolve-a-go-import-to-the-package-the-go-command-builds.md)), so every importer of a
package is an includer of each of its files.

**The walk takes one depth at a time.** Every includer one include away comes first, then the files two away, each file
once, at the depth where it is nearest, and in path order within a depth. The file asked about is never its own
dependent, though a cycle reaches it again.

**An answer says what it left out.** `max_files` caps the files listed, and 0 sets no cap. A cap keeps the nearest
files, in path order within the depth that it cuts, counts the includers it turned away at that depth, and stops there.
The files listed whose own includers the walk did not read are counted as unexpanded: those at the depth bound, those
the cap kept at the depth where it stopped the walk, and the file asked about at a depth of 0; the files the cap turned
away count only as turned away. A file the graph does not hold answers `None`, and a file nothing includes answers an
empty list.

## Why

- A query through the index answers from the includers it reaches: all 100 most-included Go files of a Go monorepo of
  39,771 Go files took 1.5 ms at one include, against 88 ms for a scan of every include of the family (2026-10-17).
- A depth-first walk with one set of seen files marks a file at the depth of the first path that reaches it and does
  not expand it again from a shorter path, so its depth bound cuts files within the bound: for the 100 most-included
  files of each of the C++ game-engine tree's three families, it listed 286,005 dependents within three includes where
  this walk lists 355,403 (2026-10-17).

## Consequences

- The index takes 8.3 MB for the 949,111 Go include edges of that monorepo, 2.9% of the heap after the build; Go's
  import-as-include makes its edges many times its files; accepted.

## Rejected

- **Scan the includes of every slot at each depth** — no memory, and a query that reads every include of the family at
  each depth it walks, a cost that grows with the family, not with the answer.
- **A depth-first walk with one set of seen files** — the same index and a simpler walk, whose depth bound cuts files
  that a shorter path reaches within it, and which listed a file among its own dependents through a cycle.
- **The index keyed by the slot of the included file** — a key that names the file directly, and an includer inserted
  before the file it includes, which the insert of that file then has to find through a second index of the paths not
  held yet.

## Revisit if

The include edges of a family make the index more than a few percent of its graph. Medium confidence: Go's import
edges came to 2.9% on the measured monorepo.
