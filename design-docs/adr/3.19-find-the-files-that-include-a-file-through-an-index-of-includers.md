# Find the files that include a file through an index of includers

- **Status:** accepted
- **Date:** 2026-10-17
- **Initiative:** `03-code-graph`

ADR 3.5 keeps the graph a file at a time, and the slot of each file keeps the paths it includes. `dependents` asks the
reverse: the files that include a file, then the files that include those, to a depth. Go records an import as an
include of every file outside test code in the imported package, so a Go tree holds many more include edges than files:
949,111 for the 39,771 Go files of a Go monorepo, against 188,977 for the 43,356 C++ files of a game-engine tree.

**The graph keeps the includers of each path, a file at a time.** An insert lists the slot of the file under every path
it includes, and a removal unlists it, so the index changes with the file as the slots do. The index is keyed by the
included path and not by the slot that holds it: a file that includes one the graph does not hold yet counts as its
includer when that file arrives, in whatever order a build inserts them.

**The walk takes one depth at a time.** Every includer one include away comes first, then the files two away, each file
once, at the depth where it is nearest, and in path order within a depth. The file asked about is never its own
dependent, though a cycle reaches it again. A walk that goes depth first with one set of seen files marks a file at the
depth of the first path that reaches it and does not expand it again from a shorter path, so its depth bound cuts files
that are within the bound. For the 100 most-included files of each of the game-engine tree's three families, C++, Go,
and TypeScript with JavaScript, this walk lists 355,403 dependents within three includes, 354,720 of them for the C++
files; a depth-first walk over the same index listed 286,005, 11 of them the file asked about, and how many it misses
depends on the order in which it meets the includers.

**An answer says what it left out.** A cap keeps the nearest files, in path order within the depth that it cuts, counts
the includers it turned away at that depth, and stops there. The files listed whose own includers the walk did not
read are counted as unexpanded: those at the depth bound, those the cap kept at the depth where it stopped the walk,
and the file asked about at a depth of 0; the files the cap turned away count only as turned away. A file that the graph
does not hold answers `None`, and a file that nothing includes answers an empty list.

## Measured

On the Go monorepo, which also holds 4,196 TypeScript and JavaScript files, and on the C++ game-engine tree, with a warm
extraction cache, three interleaved rounds on an 18-core machine at a load of 9 to 11. Main is the graph without
`dependents`; index is this decision; scan answers the same walk by reading every include of the family at each depth.
The queries ask for the 100 files of each family that the most files include directly.

The includers follow each language's resolution of its imports. The Go monorepo holds a second checkout of itself in a
worktree directory, and a Go import names the vendored copy in the vendor directory of the importing file's own module:
of the includers listed within one include of the 100 most-included Go files, 55,516 are files of that checkout listed
under its own vendored copies. A resolution through the root's vendor directory alone lists 47,631 such files under the
root's copies instead, and 427 files of two modules nested in a replaced module, which declare modules of their own that
no build of the repository compiles against the root's vendor directory (ADR 3.2).

The index takes 8.3 MB for the 949,111 Go include edges, 2.9% of the heap after the build, and 2.3 MB on the game-engine
tree, 0.5%. The build times overlap across the three variants at that load. A query for all 100 files took 1.5–1.6 ms
through the index and 88–93 ms through the scan at one include on the Go monorepo, and 9.0 ms against 431–455 ms at
three.

## Considered Options

- **Scan the includes of every slot at each depth** — no memory, and a query that reads every include of the family at
  each depth it walks: 60 to 110 times slower on the Go monorepo, 21 to 35 times on the game-engine tree, and a cost
  that grows with the family and not with the answer.
- **A depth-first walk with one set of seen files** — the same index and a simpler walk, whose depth bound cuts files
  that a shorter path reaches within it: for the same files of the three families of the game-engine tree it listed
  286,005 dependents within three includes where this walk lists 355,403, and it listed a file among its own
  dependents through a cycle.
- **The index keyed by the slot of the included file** — a key that names the file directly, and an includer inserted
  before the file it includes, which the insert of that file then has to find through a second index of the paths not
  held yet.

Revisit when the include edges of a family make the index more than a few percent of its graph, or when a query needs
the includers of a file ranked by what they use from it.
