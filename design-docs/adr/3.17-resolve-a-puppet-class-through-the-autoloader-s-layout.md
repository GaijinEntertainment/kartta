# Resolve a Puppet class through the autoloader's layout

- **Status:** accepted
- **Date:** 2026-10-16
- **Updated:** 2026-10-16
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta-lang-puppet/src/walk.rs`, `crates/kartta-lang-puppet/src/class.rs`,
  `crates/kartta-lang-puppet/src/resolve.rs`
- **Pinned by:** `crates/kartta-lang-puppet/tests/puppet.rs`

Puppet code refers to a class by name, `include apache` or `apache::vhost { 'example.com': }`, and no import statement
says which file defines it. `kartta-lang-puppet` reads each class reference as a call of the class and an include of
the manifest the module autoloader's layout names, and takes a manifest found only by its tail when it is the one
match, at the price of no include for a module that several environments hold.

## Decision

- A class reference is a call of the class and an include of its manifest. The graph binds the call to the class or
  defined type of that name, as it binds any call. The include is a file edge to the manifest the layout names, and it
  does not depend on which definitions share the class's name.
- The layout is the autoloader's: `foo` is in `foo/manifests/init.pp`, and `foo::bar::baz` in
  `foo/manifests/bar/baz.pp`, under a module root.
- An `include`, `require` or `contain` statement with a bare or a quoted name, a `contain(...)` call, a resource whose
  type has a `::`, and the class that a class `inherits` are class references. The inherited class is the class's
  parent as well as a call and an include.
- The grammar reads `include` and `require` as keywords and parses no call of them, so `include('foo')` records
  nothing, and neither does a resource-form declaration, `class { 'foo': }`.
- A resource of a one-segment type, `file` or `package`, is a call of the type only.
- A reference that names no class records nothing. A class name is lowercase segments joined by `::`, with an optional
  leading `::`; `Class['foo']` is a type reference, and `$name` or a `*` is a computed name.
- The module roots are the repository root, `modules/`, `site/`, `site-modules/` and `dist/`. For a module under two
  of them, the first in that list wins; `environment.conf` is not read.
- A manifest under no module root is taken when it is the only file whose path ends in the layout; two matches give no
  include.
- A file under `spec`, `tests`, `test` or `examples` is test code when the directory sits beside a `manifests/` that
  holds a file. Inside `manifests/` the same name is part of a class name, `mymod::test::foo`; a directory of that name
  that holds `manifests/` is a module, `modules/test/manifests/init.pp`; and one with no `manifests/` beside it holds
  modules, as the environment `environments/spec/` does.

## Why

- The extraction reads one file and has only the class's name; the autoloader finds the class by a fixed layout, so
  the layout names its manifest.
- The call binds by name and can bind a namesake; the include follows the layout and cannot.
- Puppet declares the parent class before the child, so `inherits` loads the parent as an `include` does. On the
  `stdlib`, `apache`, `mysql` and `postgresql` modules under `modules/`, 35 of 504 class references come from an
  `inherits` and 19 from a quoted name, `include 'mysql::server::config'` (2026-10-16).
- A built-in type shadows a module of the same name, so a one-segment resource names no class.
- The extraction cannot read a computed name, and a call of `Class` binds to nothing that the reference means.
- The roots are the layouts of a single module and of a control repository. A repository with directory environments
  holds the same module once in each, and the extraction cannot know which environment loads the file. A wrong include
  is worse than a missing one: an agent that follows it reads code that the reference never loads.

## Consequences

- A module that two environments hold, outside the module roots, gets no include from any reference to it; the call
  still binds by name. Accepted.
- Where `environment.conf` orders the module path otherwise, a module under two roots includes the wrong one. Accepted.

## Rejected

- **Every file whose path ends in the layout** — finds a module in any layout, but gives one include for each
  environment that holds it.
- **A call of the keyword, `include`** — binds every class reference to one name that no symbol has.
- **A class reference for a one-segment resource type** — names a manifest for `file` and `package` when a module of
  that name exists, which the built-in type shadows.

## Revisit if

The extraction reads `environment.conf` or a `Puppetfile`, which name the module path. Medium confidence: until then the
conventional roots and a tail only one file matches are all the extraction knows of the module path.
