# Follow the indexed tree, and refresh it on request

- **Status:** accepted
- **Date:** 2026-10-18
- **Revised:** 2026-10-20
- **Initiative:** `04-consumer-surfaces`

The agent a server answers edits the tree the server indexed. An index was the snapshot `index_repo` took (ADR 4.1),
so every answer after the first edit described a tree that no longer existed, and the one way to catch up was another
build, 13 s on the C++ game-engine tree. The engine refreshes in place (ADR 3.33), and `kartta-fs` follows a tree
through the operating system's change notifications (ADR 1.17).

**Every build keeps stamps**, so a refresh reads again only the files that changed and those a change reaches through
their resolution, and a refresh of named paths walks only those parts, up to a number of parts that grows with the
tree, past which it walks the whole tree and says so (ADR 3.33). On the game-engine tree (182,714 entries) stamps
cost no build time beyond the spread between runs, 12.5–14.1 s against 12.9–13.8 s without, and 10–40 MB of peak
footprint, 1,016–1,044 MiB against 1,006–1,013 MiB, three runs each through the engine directly. ADR 3.33 counts
the kept data at about 27 MB there. Without stamps a server whose watch is off would read every file again on each
`refresh`, so one switch for both would cost more than it saves.

**A built index follows its tree by default.** Once a build is done, the build's thread starts a `kartta_fs::Watcher`
over the index and runs one whole `Engine::refresh`, since a change made before the watcher starts, during the build
included, is not reported. On Linux the watcher watches the directories the index held when it started, so a directory
made after the build walked its parent is indexed by that refresh and not yet watched; `Watcher::cover` then watches
each such directory, and the paths it names are refreshed for what changed inside them before their watches went on
(ADR 1.17). Only then is the index published, so no query sees it between the build and that refresh; `index_repo`
pays that refresh, 0.2 s on the game-engine tree, and on Linux the cover, about 6 ms there. A thread of its own,
`kartta-watch`, then waits on the watcher a second at a time and hands each batch of changed paths to
`Engine::refresh_paths`. It holds the index through a `Weak` and upgrades it only for one refresh, so a rebuild that
waits for the engine it replaces to be released (ADR 4.1) waits at most for that refresh, which the rebuild cancels
through the engine's own `CancelToken`; the thread ends at its next wake. A watch that stops, or meets the inotify limit
while it runs, is dropped and started again as at the first start, a new watcher, a whole refresh and a cover, and the
watch is off if any of them fails. The stopped watcher goes first, since inotify counts every watch the user holds
against the limit, and the cover watches the directory that met the limit once the refresh has indexed it. The first
start is not retried: a watcher that cannot start, or a cover that meets the inotify limit, turns the watch off with
its reason, and the index then takes a change in only through `refresh` or another `index_repo`. `KARTTA_WATCH` set to
`off`, `0`, `false` or `no`, in any case, or `Config::watch` set false by a library caller, turns the watch off.

**Queries read the index under a read-write lock, and a refresh writes it.** A query waits for a refresh under way,
tens to hundreds of milliseconds with stamps, rather than answering from an engine halfway through it, and no lock is
held across an `.await`. A refresh that panics poisons the lock, and every query then answers that the index may be
half updated, naming `index_repo` as the fix. The file count and the graph rows of the index answer are counted when
it renders, 5 ms and 5–10 ms on the game-engine tree, rather than after each of the many small refreshes a watch
drives.

**`index_stats` and `index_repo` say `watch="following"`, or `watch="off: <reason>"`**: the server configuration,
which `KARTTA_WATCH` sets for the binary, the inotify limit with the directories watched and wanted, a stopped watch, a
refresh that failed, or a platform without notifications. It is the fact an agent needs to know that an answer can be
older than the tree, and the description of `refresh` names it as the cue. That a query waits for a refresh is not
said: an agent can do nothing with it.

**A `refresh` tool takes in what the watch does not**: any change while the watch is off, and a change made where
notifications do not reach, such as a network mount or a container bind mount. It takes optional repo-relative
`paths`, none for the whole tree, and answers a `<refresh>` envelope: `walked`, the number of parts walked again or
`tree`; each only when it is not zero, `added`, `removed`, `extracted`, `resolved_again`, `dropped`, `reconfigured`,
`rebuilt`, and `widened`, the paths named, with `limit` when they came to more parts than the engine walks apart (ADR
3.33); `elapsed_ms`; and the refresh's failures as `<errors>`, five listed and the rest counted. A refresh that
changed nothing says so.

**The index answer's errors list what the tree fails now, not a history.** A refresh replaces the failures under the
parts it walked and those it met again, so the list holds a path once; a failure that names no path in the tree, such
as an unwritable cache, stays until a whole refresh or until a refresh meets it again. The list is bounded by the paths
the tree fails, and the answer lists five and counts the rest.

## Measured

On the game-engine tree, a release build of the server driven over stdio, on an 18-core macOS machine beside other
builds and reviews:

| | |
| --- | --- |
| `index_repo`, this change, three runs | 12.9–13.5 s, peak footprint 925–1,004 MiB, max RSS 1,204–1,252 MiB |
| `index_repo` before it, three runs alternating | 11.8–12.9 s, peak footprint 849–974 MiB, max RSS 1,209–1,243 MiB |
| CPU with the watch on, 30 s without edits, two runs | 0.00 s |
| an edit, a function appended to a new file, until `find_symbols` finds it | 33–70 ms, median 57 ms, one first 117 ms |
| resident set after the build, and after 20 watch refreshes | 1,280 and 1,305 MiB; 1,181 and 1,214 MiB |
| `refresh` of the whole tree, the first reading one changed file | 238–252 ms, then 187–196 ms |

Of the build's extra time, about 0.2 s is the whole refresh before the index is published; the rest is inside the
spread between runs. That refresh holds the old and the new file index at once (ADR 1.15), which can lift the peak
footprint above a build's own; the maximum resident set did not move.

## Considered Options

- **Refresh before every query** — every answer would pay a pass over the tree, 0.2 s on the game-engine tree and a
  walk of 47–51 s on the data volume (ADR 1.16), where a watch pays per change and idles at no measurable CPU.
- **Keep the old engine serving during a refresh** — a refresh with stamps changes a few files in place in tens of
  milliseconds; a second engine to answer meanwhile doubles the memory, as ADR 4.1 found for a rebuild, to spare a
  query that wait.
- **Watch off by default** — the agent edits between two queries and rarely knows to refresh, so answers would be
  stale by default, to save a cost measured at nothing while idle.
- **No `refresh` tool** — a watch that is off or stopped, and a change notifications never report, would leave no
  recovery short of a rebuild.
- **Stamps off, or kept only while the watch is on** — a refresh without stamps reads every file again and builds every
  graph again, 13.1–14.9 s on the game-engine tree (ADR 3.33), as long as a build, while stamps cost no build time
  beyond the spread between runs.

Revisit when a `Watcher` can start from a root before the build walks it: the whole refresh after each build would go,
0.2 s here and a walk of tens of seconds on the data volume, and the cover after it.
