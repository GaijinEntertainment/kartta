# Follow the indexed tree, and refresh it on request

- **Status:** accepted
- **Date:** 2026-10-18
- **Updated:** 2026-10-22
- **Initiative:** `04-consumer-surfaces`
- **Governs:** `crates/kartta/src/follow.rs` (`Follower`), `crates/kartta-mcp/src/state.rs`,
  `crates/kartta-mcp/src/config.rs` (`Config::watch`, `KARTTA_WATCH`), `crates/kartta-mcp/src/render.rs` (`index`)
- **Pinned by:** the tests of `crates/kartta/src/follow.rs`, `crates/kartta-mcp/tests/refresh.rs`
  (`a_watched_index_takes_in_an_edit_by_itself`)

The agent a server answers edits the tree the server indexed, so an index that stays the snapshot `index_repo` took
answers for a tree that no longer exists. The server's index follows its tree through the operating system's change
notifications and refreshes in place, and a `refresh` tool takes in what the notifications miss; the trade is a thread
per followed index and queries that wait for each refresh.

## Decision

**Stamps.** Every build the MCP server runs keeps stamps, so a refresh reads again only the files that changed and
those their resolution reaches, and a refresh of named paths walks only their parts
([ADR 3.33](./3.33-follow-a-tree-through-the-questions-each-file-s-resolution-asked.md),
[ADR 1.16](./1.16-refresh-the-parts-of-a-tree-a-caller-names.md)).

**The follow.** A built index follows its tree by default. `KARTTA_WATCH` set to `off`, `0`, `false` or `no`, in any
case, or `Config::watch` set false by a library caller, turns the watch off; `on`, `1`, `true` and `yes` keep it, and
any other value warns and keeps it. `kartta::Follower` runs the policy, for the server and for a wire build that asks
to watch, which a C ABI build does only on request, with `watch` false by default
([ADR 4.33](./4.33-follow-the-tree-over-the-wire-only-when-a-build-asks.md) states its wire surface), through the
owner's lock
([ADR 4.43](./4.43-run-the-follow-in-the-engine-s-crate-over-a-lock-its-owner-lends.md)):

1. The build runs through `Engine::build_watched`, which starts the watcher on the root before the walk
   ([ADR 1.17](./1.17-follow-a-tree-through-its-change-notifications.md)).
2. Once the build is done, `Follower::caught_up` drains the watcher and refreshes the paths it names under it, and only
   then is the index published. A drain that asks for a restart is answered by the restart, whose new watcher is
   drained the same way, until a drain leaves the watcher covering the tree; `index_repo` answers once those restarts
   are done. So no query sees the index miss a change made while it was built, except one that macOS or Windows reports
   more than 50 ms after a drain began, which a later wait takes in (ADR 1.17).
3. `Follower::follow` then runs a thread of its own, `kartta-watch`, which waits on the watcher a second at a time and
   refreshes each batch under the watcher through `Engine::refresh_paths_watched`, so a directory the refresh takes in
   is watched. After a restart of its own the thread drains nothing: its next wait hands the new watcher's changes
   over.
4. The thread holds the index through a `Weak` and upgrades it only for one refresh, so a rebuild that waits for the
   index it replaces to be released
   ([ADR 4.21](./4.21-hold-one-repository-s-engine-per-process.md)) waits for the thread at
   most for that one refresh. The rebuild cancels the index's token, which stops that refresh before its walk ends; the
   thread ends at its next look.
5. A batch that names the whole tree, and a `WatchError` that ADR 1.17 has the follow answer with a restart, from a
   drain, a wait or a refresh under the watcher, each drop the watcher and start a new one over a whole refresh
   through `Engine::refresh_watched`, at a drain before publishing and on the thread alike. The old watcher goes
   first, since inotify counts every watch the user holds against its limit. Any other `WatchError` ends the follow.
6. The watch is off, with its reason, when `Engine::build_watched` answers any `WatchError` beside the build, such as a
   watcher that cannot start, a platform without notifications, or a build walk that met the inotify limit, which names
   the directories watched and wanted: the restart of step 5 answers only an error that a drain, a wait or a refresh
   under the watcher reports, not one `Engine::build_watched` answers. It is off too when the follow ends on a
   `WatchError`; when a restart fails, the reason then naming what asked for the restart, such as a watch that
   stopped; when a refresh fails; and when the thread cannot start. A follow that its token's cancel ends, as a
   rebuild's does, records no reason, even when a refresh it ran failed for the cancel. A watch off before publishing
   leaves the index as built, with no drain; it then takes a change in, one made while it was built included, only
   through `refresh` or another `index_repo`.

**Queries and refreshes.** Queries read the index under a read-write lock and a refresh writes it, so a query waits
for a refresh under way rather than answering from an engine halfway through it; no lock is held across an `.await`. A
refresh that panics poisons the lock, and every query then answers that the index may hold half of it, naming
`index_repo` as the fix. The file count and the graph rows of the index answer are counted when it renders.

**What the agent is told.** `index_stats` and `index_repo` say `watch="following"`, or `watch="off: <reason>"`,
rendered from `Watch::off`. Beside the follow's reasons of step 6 the server records two of its own: the server
configuration, `turned off in the server configuration`, and an index a later `index_repo` replaced. The count of
restarts is not shown, and neither is that a query waits for a refresh: an agent can do nothing with either. The
`refresh` tool's description names `watch` off as the cue.

**On request.** A `refresh` tool takes in what the watch does not, and the index answer's errors list what the tree
fails now; [ADR 4.44](./4.44-refresh-on-request-and-list-what-the-tree-fails-now.md) states both.

## Why

- Catching up through another build took 13 s on the C++ game-engine tree (2026-10-18); with the watch on, an edit
  reached `find_symbols` in a median 57 ms there, and 30 s without edits cost no measurable CPU.
- A watcher started before the walk holds every change the walk could not see, so the first drain replaces a second
  walk of the whole tree (ADR 1.17).
- Without stamps a refresh reads every file again and builds every graph again, and a server whose watch is off still
  refreshes on request, so one switch for stamps and the watch would cost more than it saves; stamps cost no build
  time beyond the spread between runs.
- On Linux a directory moved while inotify dropped changes goes on reporting under the path it had to the old watcher,
  so only a new watcher over a whole refresh follows the tree as it is (ADR 1.17).
- Counting at render costs 5 ms and 5–10 ms on the game-engine tree, once per answer, where counting after each refresh
  would pay it for each of the many small refreshes a watch drives.

## Consequences

- `index_repo` pays the first drain and its refresh, nothing when nothing changed, and the time its reads of a deep
  queue take: a median 260 ms for 1,000,000 queued notifications in a Linux container (2026-10-20). Accepted.
- Each restart before publishing adds one drain, about the 50 ms it waits for FSEvents on macOS. Accepted.
- A query waits for a refresh under way, tens to hundreds of milliseconds with stamps. Accepted.
- Stamps lift a build's peak footprint by 10–40 MB on the game-engine tree (2026-10-18). Accepted.

## Rejected

- **Refresh before every query** — every answer would pay a pass over the tree, 0.2 s on the game-engine tree and a walk
  of 47–51 s on the data volume, where a watch pays per change and idles at no measurable CPU.
- **Keep the old engine serving during a refresh** — a second engine doubles the memory, as
  [ADR 4.21](./4.21-hold-one-repository-s-engine-per-process.md) found for a rebuild, to spare a query a wait of
  milliseconds.
- **Watch off by default** — the agent edits between two queries and rarely knows to refresh, so answers would be stale
  by default, to save a cost measured at nothing while idle.
- **Stamps off, or kept only while the watch is on** — a refresh without stamps took 13.1–14.9 s on the game-engine
  tree, as long as a build.
- **Refresh the whole tree under the old watcher when a batch was dropped** — a directory moved meanwhile goes on
  reporting by the path it had, and a new watcher costs about what that refresh does.

## Revisit if

A tree raises more notifications while it is built than the system's queue holds, as a matter of course: each start
then pays a whole refresh again. Medium confidence that it does not: the data volume overflowed only while other builds
wrote across it.
