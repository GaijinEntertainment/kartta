# Follow the indexed tree, and refresh it on request

- **Status:** accepted
- **Date:** 2026-10-18
- **Revised:** 2026-10-22
- **Initiative:** `04-consumer-surfaces`

The agent a server answers edits the tree the server indexed. An index was the snapshot `index_repo` took (ADR 4.1),
so every answer after the first edit described a tree that no longer existed, and the one way to catch up was another
build, 13 s on the C++ game-engine tree. The engine refreshes in place (ADR 3.33), and `kartta-fs` follows a tree
through the operating system's change notifications (ADR 1.17).

**Every build keeps stamps**, so a refresh reads again only the files that changed and those a change reaches through
their resolution, and a refresh of named paths walks only those parts, up to a number of parts that grows with the
tree, past which it walks the whole tree and says so (ADR 3.33). On the game-engine tree (182,714 entries) stamps
cost no build time beyond the spread between runs, 12.5–14.1 s against 12.9–13.8 s without, and 10–40 MB of peak
footprint, 1,016–1,044 MiB against 1,006–1,013 MiB, three runs each through the engine directly. ADR 3.33 counts
the kept data at about 27 MB there. Without stamps a server whose watch is off would read every file again on each
`refresh`, so one switch for both would cost more than it saves.

**A built index follows its tree by default.** The build runs through `Engine::build_watched`, which starts a
`kartta::Watcher` on the root before the build walks the tree (ADR 1.17), so the watcher holds every change made while
the build walked. Once the build is done, the build's thread drains the watcher and refreshes the paths it names, and
only then is the index published, so with a watcher running no query sees it miss a change made while it was built,
except one that macOS or Windows reports more than 50 ms after the drain began, which the first wait takes in;
`index_repo` pays that drain and its refresh, nothing when nothing changed. A thread of its own, `kartta-watch`, then
waits on the watcher a second at a time and hands each batch of changed paths to `Engine::refresh_paths_watched`, which
refreshes them under the watcher, so a directory the refresh takes in is watched (ADR 1.17). It holds the
index through a `Weak` and upgrades it only for one refresh, so a rebuild that waits for the engine it replaces to be
released (ADR 4.1) waits at most for that refresh, which the rebuild cancels through the engine's own `CancelToken`;
the thread ends at its next wake. A watch that stops, a refresh under it that meets the inotify limit, or a batch that
names the whole tree because changes were dropped, at that first drain or later, drops the watcher and starts it again
through `Engine::refresh_watched`, a new watcher before one whole refresh, and the watch is off if that fails. Before
the index is published, the new watcher is drained as the first was, so the index holds the changes made while that
refresh walked; the watch thread's next wait hands them over after its own restarts. A dropped batch restarts the
watch rather than refreshing under the old watcher because on Linux the move of a directory went with the dropped
changes, and the old watcher would go on naming that directory's changes by the path it had. The stopped watcher goes
first, since inotify counts every watch the user holds against the limit. A watcher that cannot start, or whose build
walk met the inotify limit, turns the watch off with its reason: the index is then published as it was built, with no
drain, and takes a change in, one made while it was built included, only through `refresh` or another `index_repo`.
`KARTTA_WATCH` set to `off`, `0`, `false` or `no`, in any case, or `Config::watch` set false by a library caller, turns
the watch off.

**Queries read the index under a read-write lock, and a refresh writes it.** A query waits for a refresh under way,
tens to hundreds of milliseconds with stamps, rather than answering from an engine halfway through it, and no lock is
held across an `.await`. A refresh that panics poisons the lock, and every query then answers that the index may be
half updated, naming `index_repo` as the fix. The file count and the graph rows of the index answer are counted when
it renders, 5 ms and 5–10 ms on the game-engine tree, rather than after each of the many small refreshes a watch
drives.

**`index_stats` and `index_repo` say `watch="following"`, or `watch="off: <reason>"`**: the server configuration,
which `KARTTA_WATCH` sets for the binary, the inotify limit with the directories watched and wanted, a stopped watch, a
refresh that failed, or a platform without notifications. It is the fact an agent needs to know that an answer can be
older than the tree, and the description of `refresh` names it as the cue. That a query waits for a refresh is not
said: an agent can do nothing with it.

**A `refresh` tool takes in what the watch does not**: any change while the watch is off, and a change made where
notifications do not reach, such as a network mount or a container bind mount. It takes optional repo-relative
`paths`, none for the whole tree, and answers a `<refresh>` envelope: `walked`, the number of parts walked again or
`tree`; each only when it is not zero, `added`, `removed`, `extracted`, `resolved_again`, `dropped`, `reconfigured`,
`rebuilt`, and `widened`, the paths named, with `parts`, the parts they came to, and `limit` when those were more parts
than the engine walks apart (ADR 3.33); `elapsed_ms`; and the refresh's failures as `<errors>`, five listed and the
rest counted. A refresh that changed nothing says so.

**The index answer's errors list what the tree fails now, not a history.** A refresh replaces the failures under the
parts it walked and those it met again, so the list holds a path once; a failure that names no path in the tree, such
as an unwritable cache, stays until a whole refresh or until a refresh meets it again. The list is bounded by the paths
the tree fails, and the answer lists five and counts the rest.

## Measured

On the game-engine tree, a release build of the server driven over stdio, on an 18-core macOS machine beside other
builds and reviews:

| | |
| --- | --- |
| `index_repo`, this change, three runs | 12.9–13.5 s, peak footprint 925–1,004 MiB, max RSS 1,204–1,252 MiB |
| `index_repo` before it, three runs alternating | 11.8–12.9 s, peak footprint 849–974 MiB, max RSS 1,209–1,243 MiB |
| CPU with the watch on, 30 s without edits, two runs | 0.00 s |
| an edit, a function appended to a new file, until `find_symbols` finds it | 33–70 ms, median 57 ms, one first 117 ms |
| resident set after the build, and after 20 watch refreshes | 1,280 and 1,305 MiB; 1,181 and 1,214 MiB |
| `refresh` of the whole tree, the first reading one changed file | 238–252 ms, then 187–196 ms |

Of the build's extra time then, about 0.2 s was the whole refresh before the index was published, which the revision
below removes; the rest was inside the spread between runs. That refresh held the old and the new file index at once
(ADR 1.15), which could lift the peak footprint above a build's own; the maximum resident set did not move.

**Revised 2026-10-20: the watcher starts before the build, and the whole refresh after it is gone.** The watcher was
started over the built index, so `index_repo` paid a whole refresh and, on Linux, a cover before it published the
index; a watcher started before the walk holds what that refresh was for (ADR 1.17). Driven over stdio with the watch
on, alternating this change with the server before it at load averages of 13 to 22, the game-engine tree took
15.6–20.8 s against 14.7–21.5 s to `index_repo` over 6 rounds each, peak footprint 1,055–1,257 MiB against
1,018–1,204 MiB: the 0.2 s refresh is inside a spread of seconds there. The data volume, 7,567,311 files, took
545–1,221 s against 547–1,030 s over 3 rounds each at load averages of 16 to 31, peak footprint 16,605–18,046 MiB
against 16,606–17,810 MiB, a spread that swallows the refresh too. Through kartta-fs alone on the same volume, at load
averages of 12 to 18, a build, a watcher and a whole refresh took 57.1–64.6 s, the refresh 25.2–32.3 s of it, against
30.2 s for a watched build whose drain handed over 37 paths in 0.08 s. In the other 2 of those 3 rounds the volume,
written across by builds elsewhere, raised more notifications while the build walked than the watcher's queue of 65,536
holds, and the drain named the whole tree: its refresh took 25.6–42.2 s, what a start cost before this change every
time, and the server answers such a batch with a new watcher over that refresh. Peak footprint there was 998–1,041 MiB
against 972–999 MiB, the queued notifications beside the build's own peak. With the watch off, the game-engine tree
built in 13.3–18.1 s against 13.2–20.4 s cold and in 3.5–7.2 s against 3.5–4.2 s from a warm content cache, medians
3.59 s and 3.58 s, 5 rounds each, at peak footprints of 1,000–1,224 MiB against 1,008–1,277 MiB cold and 852–966 MiB
against 925–994 MiB warm.

**Revised 2026-10-20: the first drain reads every change queued while the index was built.** The drain stopped at
500 ms and handed over what it had read, so where inotify queues more than a drain reads in that time, as the 1,048,576
of a Docker VM allow, a build that met a flood published an index without the changes queued behind what was read, a
directory made while inotify dropped changes among them. The overflow marker behind them restarted the watch only once
a later wait read it. The drain reads on past 500 ms until it has read what was queued when it began (ADR 1.17), so
on Linux the index is published with every change made while it was built, or after the restart an overflow marker
among them asks for. On macOS and Windows a change the system reports more than 50 ms after the drain began is still
taken in by a later wait, after the index is published (ADR 1.17). The server's test of a directory made while the
watcher dropped changes, in a debug build in a Linux container beside 40 busy loops and alternated with the server
before it, failed 8 of 8 runs before and passed 8 of 8 after. `index_repo` pays for a deep queue the time its reads
take, 0.22–1.11 s for 1,000,000 notifications on the copies of a game tree, where closing the drain at 500 ms would
cost the whole refresh of a new watcher.

**Revised 2026-10-20: a restart before the index is published is drained too.** A first drain that asked for a
restart handed the new watcher on undrained, so the index was published without the changes made while the restart's
whole refresh walked, and only the watch thread's first wait took them in. The server's test of a directory made while
the watcher dropped changes now also writes one while the restart walks; it failed 3 of 3 runs before, on macOS and in
a Linux container, and passed 3 of 3 after on each. The new watcher is drained as the first was, and one whose drain
asks for another restart is restarted again before the index is published, where the watch thread restarted it right
after: the restarts are the same ones, and `index_repo` answers once they are done. Each restart before publishing
adds one drain. On the game-engine tree, through the engine directly, 6 restarts each at load averages of 5 to 14, a
drain of the new watcher found nothing in 53–60 ms on macOS after whole refreshes of 239–264 ms, the 50 ms it waits for
FSEvents to report, and in 4–6 µs in a Linux container after refreshes of 269–386 ms. The watch thread drains nothing
after its own restart: no index is published between the two, and its next wait hands the new watcher's changes over
at once, as after any refresh it runs.

**Revised 2026-10-20: each batch is refreshed under its watcher.** On Linux the watcher watched each directory made
after the start as it read the directory's creation, ignored build output included, and the watch refreshed each batch
without the watcher. The watcher reads no creation into a watch now, so the watch refreshes each batch, at the first
drain, after a restart and on the watch thread, through `Engine::refresh_paths_watched`, whose walk watches what the
refresh keeps, at a watch call for each directory it keeps: a median 28 ms more for a whole refresh of 111,061
directories on Linux (ADR 1.17). A refresh that meets the inotify limit restarts the watch as a wait that met it did,
and a directory a `.gitignore` edit shows is followed once the refresh takes it in, where it was never watched. The
server's test of such a directory failed before and passes after, in a Linux container. With the watch off nothing a
build or a refresh answers changes: the parity harness on the game-engine tree answered its 21,096 calls identically
on both sides.

**Revised 2026-10-21: a widened refresh says how many parts its paths came to.** The answer gave the paths named and
the limit, but not the parts the limit counts (ADR 3.33), so an agent could not see how far past the limit a call went,
or whether naming fewer paths would have kept the refresh apart: 60 paths inside an ignored `target/` are one part, and
60 files of a source directory are 60. A call that names more paths than the limit works its parts out before it
chooses between walking them and the whole tree, so the engine holds the count when it answers, and `parts` adds no
work to a call.

**Revised 2026-10-22: the follow lives in the engine's crate, and the server lends it its lock.** A wire consumer
follows a tree on request too (ADR 4.2), and the policy above, the drain before the index is published, each batch
refreshed under its watcher, the restarts and the reasons a watch is off, lived in the server's own watch loop, which a
second consumer would have copied. `kartta::Follower` holds it, behind the crate's `watch` feature, which is off by
default: `Follower::caught_up` takes in what the watcher holds before the owner publishes the engine, and
`Follower::follow` runs the `kartta-watch` thread, which holds the owner through a `Weak` as before. The owner
implements `kartta::Followed`: the token that ends the follow, a refresh run under its own write lock, where it takes
the refresh's failures in beside the engine, and `watched`, which records a `kartta::Watch`, the reason the watch is off
and the watchers the follow started over. The server records two reasons of its own, the configuration and an index a
later `index_repo` replaced, and renders `watch=` from `Watch::off` as it did; the count of restarts it does not show.
The policy's tests moved with it and pass on macOS and in a Linux container. With the watch off, the parity harness
answered its 21,096 calls on the game-engine tree and its 24,238 on the Go monorepo snapshot as `main` did, and
`index_repo` of the game-engine tree took 14.3–32.5 s against 14.2–27.7 s cold, medians 15.4 s and 15.8 s, and
3.5–8.2 s against 3.6–5.9 s from a warm content cache, medians 4.1 s and 4.0 s, 6 rounds each at load averages of 25 to
41, at median peak footprints of 1,137 MiB and 1,158 MiB cold and 910 MiB and 906 MiB warm.

Three shapes were weighed, the first two built through both consumers and measured against each other:

- **Kept: the owner lends its lock, and the library runs the loop.** As prototyped, 170 lines of the library's, against
  `main` the server 108 lines shorter and the C ABI 120 longer, 182 more in all, counting neither tests, comments nor
  blank lines; as landed, 176, 108 fewer and 136 more, 204 in all. Three public items, `Followed` with three methods,
  `Follower` with two and `Watch` with two fields.
- **A handle the owner drives:** the library takes a batch in on the engine the owner hands it and answers whether to go
  on, start over or stop, and each owner runs the loop and the thread. 119 lines of the library's, the server 23 lines
  shorter and the C ABI 197 longer, 293 more in all, the loop of about 45 lines kept in each owner, and five public
  items: `Follower` with five methods, `Batch`, `Took` and `Ended` with three variants each, and `Watch`.
- **An engine the library shares under a lock of its own:** the lock and its poisoning would leave both owners, every
  query path of each would change to read the engine through it, and the library would still need a call back to take
  a refresh's failures in where each owner keeps them. Not built.

Both shapes built run the same refresh for a batch, and the measurements did not tell them apart. Through the C ABI
wire, each round alternating the two: on a tree of 603 entries, 30 edits a round over 3 rounds at load averages of 24 to
33, an edit reached a query in a median 38.8–42.7 ms against 38.7–42.7 ms, and 10 s without edits took 0.00–0.01 s of
CPU on both. On the data volume, 7,070,989–7,075,094 entries indexed with no graph, 20 edits a round over 2 rounds at
load averages of 19 to 27, builds took 13.3–15.3 s and an edit reached a query in a median 45.8–54.0 ms against
50.6–222.8 ms, at peak footprints of 934–981 MiB against 1,168–1,485 MiB: the handle's rounds met the volume's own
writes, one of them restarting its watch twice on dropped notifications, the other answering its last 11 edits in
214–277 ms.

## Considered Options

- **Refresh before every query** — every answer would pay a pass over the tree, 0.2 s on the game-engine tree and a
  walk of 47–51 s on the data volume (ADR 1.16), where a watch pays per change and idles at no measurable CPU.
- **Keep the old engine serving during a refresh** — a refresh with stamps changes a few files in place in tens of
  milliseconds; a second engine to answer meanwhile doubles the memory, as ADR 4.1 found for a rebuild, to spare a
  query that wait.
- **Watch off by default** — the agent edits between two queries and rarely knows to refresh, so answers would be
  stale by default, to save a cost measured at nothing while idle.
- **No `refresh` tool** — a watch that is off or stopped, and a change notifications never report, would leave no
  recovery short of a rebuild.
- **Stamps off, or kept only while the watch is on** — a refresh without stamps reads every file again and builds every
  graph again, 13.1–14.9 s on the game-engine tree (ADR 3.33), as long as a build, while stamps cost no build time
  beyond the spread between runs.
- **Refresh the whole tree under the old watcher when a batch was dropped** — its walk watches a directory made while
  inotify dropped changes, but a directory moved meanwhile goes on reporting its changes by the path it had; a new
  watcher costs about what that refresh does, a watch call for each directory its walk keeps (ADR 1.17).
- **The follow as a handle each owner drives, or an engine the library shares under its own lock** — the first keeps
  the loop in every owner for more code and more public items, and the second takes each owner's lock and query paths;
  the revision of 2026-10-22 above has the numbers.

Revisit when a tree raises more notifications during a build than the watcher's queue holds as a matter of course: each
start then pays the whole refresh again, and a queue that keeps one entry a path, not one a notification, would hold
more of them.
