# Follow the indexed tree, and refresh it on request

- **Date:** 2026-10-18
- **Governs:** `crates/kartta/src/follow.rs` (`Follower`), `crates/kartta-mcp/src/state.rs`,
  `crates/kartta-mcp/src/config.rs` (`Config::watch`, `KARTTA_WATCH`), `crates/kartta-mcp/src/render.rs` (`index`)
- **Pinned by:** the tests of `crates/kartta/src/follow.rs`, `crates/kartta-mcp/tests/refresh.rs`
  (`a_watched_index_takes_in_an_edit_by_itself`)

The agent a server answers edits the tree the server indexed, so an index that stays the snapshot `index_repo` took
answers for a tree that no longer exists. The server's index follows its tree through the operating system's change
notifications and refreshes in place, and a `refresh` tool takes in what the notifications miss; the trade is a thread
per followed index and queries that wait for each refresh.

## Decision

- **Stamps.** Every build the MCP server runs keeps stamps, so a refresh reads again only the files that changed and
  those their resolution reaches, and a refresh of named paths walks only their parts
  ([ADR 3.33](/design-docs/adr/3.33-refresh-dependency-tracking.md),
  [ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md)).
- **The follow.** A built index follows its tree by default. `KARTTA_WATCH` set to `off`, `0`, `false` or `no`, in any
  case, or `Config::watch` set false by a library caller, turns the watch off; `on`, `1`, `true` and `yes` keep it,
  and any other value warns and keeps it. `kartta::Follower` runs the policy, for the server and for a wire build that
  asks to watch, which a C ABI build does only on request, with `watch` false by default
  ([ADR 4.33](/design-docs/adr/4.33-wire-follow.md) states its wire surface), through the owner's lock
  ([ADR 4.43](/design-docs/adr/4.43-follow-policy-placement.md)). [`Follower`](/crates/kartta/src/follow.rs)
  documents each step of the follow and each reason it ends.
- **Caught up before publishing.** The build starts the watcher on the root before the walk
  ([ADR 1.17](/design-docs/adr/1.17-change-notifications.md)), and the index is published only once
  `Follower::caught_up` has taken in every change the watcher holds, the drains of the restarts it asks for included;
  `index_repo` answers once those restarts are done. So no query sees the index miss a change made while it was built,
  except one that macOS or Windows reports more than 50 ms after a drain began, which a later wait takes in
  ([ADR 1.17](/design-docs/adr/1.17-change-notifications.md)).
- **Following.** `Follower::follow` then refreshes each batch the watcher reports, under the watcher, on a thread of
  its own, `kartta-watch`. The thread holds the index only for one refresh, so a rebuild that waits for the index it
  replaces to be released ([ADR 4.21](/design-docs/adr/4.21-mcp-engine-slot.md)) waits for the thread at most for that
  one refresh; the rebuild cancels the index's token, which stops that refresh before its walk ends.
- **Restarts.** A batch that names the whole tree, and a `WatchError` from a drain, a wait or a refresh under the
  watcher, are answered as [ADR 1.17](/design-docs/adr/1.17-change-notifications.md) maps them, a root gone as
  [ADR 1.73](/design-docs/adr/1.73-watched-root-loss.md) does, at a drain before
  publishing and on the thread alike. A restart lets the old watcher go before its whole refresh through
  `Engine::refresh_watched`, since inotify counts every watch the user holds against its limit.
- **When the watch is off.** The watch is off, with its reason, when `Engine::build_watched` answers a `WatchError`
  beside the build, which no restart answers; when the follow ends on a failure, a restart that failed included; and
  when the thread cannot start. A follow that its token's cancel ends, as a rebuild's does, records no reason, even
  when a refresh it ran failed for the cancel. A watch off before publishing leaves the index as built, with no drain;
  it then takes a change in, one made while it was built included, only through `refresh` or another `index_repo`.
- **Queries and refreshes.** Queries read the index under a read-write lock and a refresh writes it, so a query waits
  for a refresh under way rather than answering from an engine halfway through it; no lock is held across an
  `.await`. A refresh that panics poisons the lock, and every query then answers that the index may hold half of it,
  naming `index_repo` as the fix. The file count and the graph rows of the index answer are counted when it renders.
- **What the agent is told.** `index_stats` and `index_repo` say `watch="following"`, or `watch="off: <reason>"`,
  rendered from `Watch::off`. Beside the reasons of **When the watch is off** the server records two of its own: the
  server configuration, `turned off in the server configuration`, and an index a later `index_repo` replaced. The count
  of restarts is not shown, and neither is that a query waits for a refresh: an agent can do nothing with either. The
  `refresh` tool's description names `watch` off as the cue.
- **On request.** A `refresh` tool takes in what the watch does not, and the index answer's errors list what the tree
  fails now; [ADR 4.44](/design-docs/adr/4.44-mcp-refresh-tool.md) states both.

## Why

- Catching up through another build took 13 s on the C++ game-engine tree (2026-10-18); with the watch on, an edit
  reached `find_symbols` in a median 57 ms there, and 30 s without edits cost no measurable CPU (#80).
- A watcher started before the walk holds every change the walk could not see, so the first drain replaces a second
  walk of the whole tree ([ADR 1.17](/design-docs/adr/1.17-change-notifications.md)).
- Without stamps the engine refuses a refresh ([ADR 3.33](/design-docs/adr/3.33-refresh-dependency-tracking.md)), and a
  server whose watch is off still refreshes on request, so one switch for stamps and the watch would leave it no
  refresh; stamps cost no build time beyond the spread between runs.
- On Linux a directory moved while inotify dropped changes goes on reporting under the path it had to the old watcher,
  so only a new watcher over a whole refresh follows the tree as it is
  ([ADR 1.17](/design-docs/adr/1.17-change-notifications.md)).
- Counting at render costs 5 ms and 5–10 ms on the game-engine tree, once per answer, where counting after each refresh
  would pay it for each of the many small refreshes a watch drives.

## Consequences

- `index_repo` pays the first drain and its refresh, nothing when nothing changed, and the time its reads of a deep
  queue take: a median 260 ms for 1,000,000 queued notifications in a Linux container (2026-10-20). Accepted.
- Each restart before publishing adds one drain, about the 50 ms it waits for FSEvents on macOS. Accepted.
- A query waits for a refresh under way, tens to hundreds of milliseconds with stamps. Accepted.
- Stamps lift a build's peak footprint by 10–40 MB on the game-engine tree (2026-10-18). Accepted.

## Rejected

- **Refresh before every query** — every answer would pay a pass over the tree, 0.2 s on the game-engine tree and a walk
  of 47–51 s on the data volume, where a watch pays per change and idles at no measurable CPU.
- **Keep the old engine serving during a refresh** — a second engine doubles the memory, as
  [ADR 4.21](/design-docs/adr/4.21-mcp-engine-slot.md) found for a rebuild, to spare a query a wait of milliseconds.
- **Watch off by default** — the agent edits between two queries and rarely knows to refresh, so answers would be stale
  by default, to save a cost measured at nothing while idle.
- **Stamps off, or kept only while the watch is on** — a refresh without stamps took 13.1–14.9 s on the game-engine
  tree, as long as a build.
- **Refresh the whole tree under the old watcher when a batch was dropped** — a directory moved meanwhile goes on
  reporting by the path it had, and a new watcher costs about what that refresh does.

## Revisit if

A tree raises more notifications while it is built than the system's queue holds, as a matter of course: each start
then pays a whole refresh again. Medium confidence that it does not: the data volume overflowed only while other builds
wrote across it.
