# Run each channel's tests natively on every target of the support matrix

- **Date:** 2026-11-02
- **Governs:** `.github/workflows/ci.yml` (jobs `clippy`, `docs`, `test`, `test-musl`, `go`, `node-musl`),
  `scripts/node-musl.sh`
- **Pinned by:** `.github/workflows/ci.yml` (jobs `test-musl`, `node-musl`)

[ADR 4.46](/design-docs/adr/4.46-release-scope.md) promises only what a check can hold, and the Rust crates, the Go
binding and the Node addon each left targets of its matrix unchecked. Each channel's tests run natively on each target,
and each platform's code is linted on that platform; the trade is eight more job runs on every pull request, four of
them cold builds.

## Decision

- **Rust.** `test` runs on x64 and arm64 Linux with glibc, macOS and Windows. `test-musl` runs the workspace's tests on
  both musl targets, in the image of [ADR 4.56](/design-docs/adr/4.56-go-musl-job.md), without `kartta-node`.
- **Go.** `go` runs on arm64 Linux with glibc as well, and on Windows against the `windows-gnu` archive
  ([ADR 4.60](/design-docs/adr/4.60-go-windows-link.md)); `go-musl` holds both musl targets.
- **Node.** `node-musl` builds the addon through `scripts/build.ts` and runs `vp test` on both musl targets. The
  format, lint and type checks stay in `node` alone.
- **Node inside the Rust image.** `scripts/node-musl.sh` runs in the Rust image, the one image that holds cargo and a C
  compiler. A `node:*-alpine` image pinned by digest fills a volume, which the Rust image mounts read-only.
- **Lints.** `clippy` runs on `ubuntu-24.04`, `macos-26` and `windows-2025-vs2026`. Neither arm64 nor musl gets a leg,
  and `docs` stays on Linux.

## Why

- On arm64 Alpine and arm64 Debian 3,420 workspace tests pass and none fail, and 78 Node tests pass on arm64 Alpine
  (2026-11-02).
- Clippy on the Windows target refused `kartta-mcp`'s tests for two unused imports, which no Linux run reaches
  (2026-11-02).
- `kartta-node` holds no test, and rustc refuses its cdylib on a musl target with `crt-static` on, so leaving it out of
  `test-musl` loses nothing. `npm run build` stops the same way with `scripts/build.ts`'s flag taken out.
- Between arm64 and x64 the code differs by the one `POLLS` constant in `watch/inotify.rs`'s tests, and each
  `target_env` branch for musl is the one macOS compiles, so an arm64 or a musl clippy leg would repeat an existing one.
  No public item sits under a platform `cfg`, so rustdoc on another platform would too.
- `go` on arm64 repeats neither of its neighbours: `go-musl` links the musl archive, and x64 another target's, so only
  this run links the arm64 gnu archive a glibc consumer gets.

## Consequences

- Every run adds four cold debug builds on the musl jobs, which take no Rust cache. Accepted.
- `node-musl` tests a debug addon, as `node` does; a release addon on musl stays unproved until the release builds it
  (#138).
- The Node image repeats `.nvmrc`, and no bot moves it; a stale image passes (#1097).

## Rejected

- **`apk add` of Rust and gcc in the Node image** — it moves with the Alpine branch, where a digest pins the rest.
- **The tarballs of `unofficial-builds.nodejs.org`** — each architecture needs a checksum in the workflow, where one
  digest pins both.
- **Build in the Rust image, test in the Node image** — `scripts/build.ts` needs Node and cargo in one place, and its
  musl flag is what the job has to hold.
- **`crt-static` off for all of `test-musl`, with `kartta-node` in it** — the crate holds no test, and the other tests
  would then run a dynamic link where the target defaults to a static one, as `cargo install` of `kartta-mcp` builds.
- **A clippy leg on arm64 or musl, and rustdoc on macOS and Windows** — each repeats a leg that exists, as Why states.

## Revisit if

A crate gains code under `target_arch` or `target_env` past a test constant, or the cold builds outgrow what a pull
request can wait for. High confidence in the coverage; medium in the cost, which waits for a first run.
