# Publish the npm packages from the release, each version once

- **Date:** 2026-11-06
- **Governs:** `.github/workflows/release.yml` (jobs `npm-pack` and `npm-publish`), `scripts/npm-publish.sh`
- **Implementation:** pending — the `npm` environment and its `NPM_TOKEN` do not exist yet, so no run has published
  (#1058)

The release built the addon of no target, and nothing published the packages of
[ADR 4.40](/design-docs/adr/4.40-node-addon-packaging.md). The release workflow packs all seven on every run and
publishes them on a tag push, with provenance, behind an approval; the trade is a token that outlives the run, and a
re-run that trusts the registry's answer for each version.

## Decision

- **Packs.** Each target's package packs in that target's row of the `build` job, from the addon built there under
  [ADR 4.55](/design-docs/adr/4.55-release-workflow.md) and [ADR 4.49](/design-docs/adr/4.49-distribution-profile.md).
  The main package packs in `npm-pack`. Each pack is an artifact `npm-<package>`, and the GitHub release carries none.
- **Order.** `scripts/npm-publish.sh` checks that all seven tarballs are present before it publishes any, then
  publishes each target's package and `kartta` last, at the version of `bindings/node/package.json`, which the
  `versions` job holds to the tag.
- **Dry run.** `npm-pack` runs the same script with `--dry-run` on every run, so a pull request that touches a release
  input checks the order and the registry's answers. It reads the main package's tarball from the working tree where
  `npm pack` left it, and each target's from its artifact.
- **A version once.** Before each publish the script asks the registry for `GET /{package}/{version}`. A 200 skips the
  package, a 404 publishes it, and any other answer fails the job.
- **Credential.** Only `npm-publish` publishes, on a tag push alone. It references the GitHub environment `npm`, which
  requires approval, and reads its secret `NPM_TOKEN` through `setup-node`'s `registry-url`.
- **Provenance.** `npm-publish` holds `id-token: write`, runs on a GitHub-hosted runner, and publishes with
  `--provenance --access public`.

## Why

- npm refuses a name and version it already holds, even after an unpublish (`npm-publish.md` of npm/cli, read
  2026-11-06), so a re-run of a release that failed midway fails on the first package it reached unless it skips it.
- The registry's API documents `GET /{package}/{version}` (`docs/REGISTRY-API.md` of npm/registry). On 2026-11-06 it
  answered 200 for `typescript/7.0.2`, and 404 for `typescript/99.0.0` and for `kartta/0.0.0`, a package it does not
  hold. `npm view` answers `E404` for both misses alike, so it settles the question only through its error text.
- `kartta` names every target's package in `optionalDependencies`, and npm skips one the registry lacks
  ([ADR 4.40](/design-docs/adr/4.40-node-addon-packaging.md)), so `kartta` published first would install without an
  addon until the rest arrive.
- A job that references an environment with required reviewers reads none of its secrets until a reviewer approves it
  (`deployments-and-environments.md` of github/docs, read 2026-11-06).
- A job's listing of the run's artifacts can miss one the same job finalized seconds before: on 2026-11-24 the listing
  two seconds after `npm-kartta` finalized held the six artifacts of the `build` job alone, and a re-run passed
  (#1260).
- Provenance needs `id-token: write`, a GitHub-hosted runner and npm 9.5 or later (npm's "Generating provenance
  statements", read 2026-11-06), and npm 11.19.1 refuses provenance for a package the registry does not hold yet
  without `--access public` (`workspaces/libnpmpublish/lib/publish.js:222`).

## Consequences

- A token in the environment outlives the run, where trusted publishing would mint one per run; #138 asks for the
  token, and #1058 holds the choice between the two.
- Each run uploads seven more artifacts, about 5 MB per target's pack on macOS arm64 (2026-11-06). Accepted.
- Required reviewers serve a private repository only on GitHub's Enterprise plan; the repository turns public before
  the first tag (#144). Accepted.

## Rejected

- **Parsing `npm publish`'s refusal** — a failed publish of one package and a held version read alike until npm's
  message is matched, and that text is no contract.
- **`npm view <package>@<version>`** — it answers `E404` for a version and for a package it lacks, so a network fault
  needs its error text to tell apart.
- **Publishing from each target's row** — `kartta` could go out before a target's package, and each row would need the
  token and the approval.
- **Gating on the GitHub release** — the channels fail and re-run apart, so one channel's failure would hold the other.

## Revisit if

npm documents a status for a version it lacks other than 404, or the maintainer chooses trusted publishing (#1058).
High confidence in the order and the skip; the publish itself waits for a first run with the token.
