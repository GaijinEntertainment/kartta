# Front-code the stored paths

- **Status:** accepted
- **Date:** 2026-10-14
- **Updated:** 2026-10-18
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/index.rs` (`Encoder`, `Overflow`, `Paths`, `Index::paths`, `Index::search`,
  `tree_order`), `crates/kartta-fs/src/list.rs` (`past_subtree`), `kartta_fs::Entry`, `kartta_fuzz::Ranking`
- **Pinned by:** `crates/kartta-fs/src/index.rs` (`a_value_too_wide_for_its_array_is_kept_aside_and_read_back`,
  `a_block_past_what_a_u16_offset_reaches_reads_back_whole`,
  `tree_order_agrees_with_the_byte_by_byte_order_on_either_side_of_a_word`)

On a tree of millions of entries the paths are most of an index's memory, and in depth-first order each path shares most
of its bytes with the one before it. The index stores each path past that shared prefix, so no path exists whole and
every answer names entries by position; reads and queries pay for rebuilding paths.

## Decision

**The layout.** The index stores each path past the prefix it shares with the previous path, and the first entry of
each block, a restart, stores its whole path. A build lays a block at every 128th entry;
[ADR 1.65](/design-docs/adr/1.65-refresh-path-encoding.md) states how a change re-lays blocks. Per entry the
index keeps a `u8` shared length and a `u16` offset counted from its block's start; each block keeps the `u32` position
of its first entry and the `u32` start of its bytes. A value too wide for its `u8` or its `u16` sits in a side table
kept in position order and searched by position.

**Answers name positions.** No path but a restart exists whole, so an answer cannot borrow one. Queries answer
positions, and `Index::paths` rebuilds each path into one buffer it reuses. `Entry` owns its path. The scorer takes
candidates one at a time with their positions through `kartta_fuzz::Ranking`, because a reused buffer lends one
candidate at a time.

**Building.** The build walks the tree depth-first twice, once to size the stored bytes exactly and once to write them.
Each pass builds every path into one reused buffer, and the shared length is the parent's length plus how far the old
and the new tail agree. The shared length is floored to a character boundary, so every stored suffix is valid UTF-8 on
its own and the stored bytes are sliced without a boundary check. The walk's tree the build reads holds each entry's
payload in 8 bytes, with a symlink's target beside it, as
[ADR 1.66](/design-docs/adr/1.66-symlink-target-storage.md) states.

**Reading.** A reader at most four positions behind the one asked for steps forward, copying each entry's stored bytes.
Further behind, or ahead, it rebuilds the asked path outright, walking back to the last entry that stores each part of
its prefix, so every byte of the path is copied once.

**Finding.** A lookup by path is a binary search over the restarts, then a forward scan of one block that compares
stored bytes without rebuilding a path: an entry that shares more with its predecessor than the last entry passed
shares with the path is passed without a look at its bytes. The comparison finds the first differing byte eight bytes
at a time. It orders bytewise with `/` below every other byte, which is the depth-first order only while `kartta-walk`
sorts siblings bytewise by name. A listing finds where a directory's subtree ends without rebuilding a path: the entry
right after the directory settles an empty or a leaf directory, and otherwise a binary search over the restarts finds
the block the subtree ends in, inside which an entry following one beneath the directory is beneath it exactly when it
shares at least `dir/` with it.

## Why

- Depth-first order makes the shared prefix most of each path: resident memory after a build fell to 130–131 MB from
  617–619 MB with whole paths (data volume, 4.45M entries, 2026-10-14).
- The trade gives up speed for memory because every call stays under 500 ms on the largest tree measured, and below
  that bound memory and the amount of code outrank speed.
- The build's peak belongs to the walk, which no storage layout changes, so the layout is judged by what the index
  holds after the build.
- A boundary check on each slice would read every byte of the stored bytes on a sweep that only needs where each
  entry's bytes lie; comparing a byte at a time made a lookup four times slower.

## Consequences

- Reads cost more than borrowed paths: the unbounded fuzzy ranking for `e`, the call nearest the bound, took 458–470 ms
  against 180–186 ms on the same tree. Accepted.
- A lookup by path stays under 1 µs.
- The lookup's binary search breaks if `kartta-walk` stops sorting siblings bytewise. Accepted; the comparison's
  constraint marker names the coupling.

## Rejected

- **Whole paths with an offset per entry** — the fastest reads, at four to five times the memory.
- **The walk's tree kept, with a parent link per entry** — a path rebuilt by climbing its parents; about 70 MB more than
  front-coding, and the slowest listing.
- **Lengths stored inline before each entry's bytes, as varints** — the least memory, but a read decodes forward from
  its restart, and the unbounded fuzzy ranking passed 500 ms.
- **A `u8` stored length per entry in place of the `u16` offset, summed across the block on a random read** — 4 MB less
  at 4.4M entries, but the unbounded fuzzy ranking reached 473 ms, and fast in-order reads need a running start in the
  reader.
- **A restart every 64 or 256 entries** — 64 stores 0.9 B more per entry; 256 saves 0.4 B per entry and brings the
  unbounded fuzzy ranking near the bound.
- **A ranking that borrows every candidate at once** (`Matcher::rank`, `Matcher::merge`) — a reused buffer lends one
  candidate at a time, nothing but the scorer's own tests called it, and two ranking paths had to agree on every
  tiebreak; a caller that holds every candidate offers each with its index.

## Revisit if

A call nears 500 ms on a larger tree. The restart interval is the knob: a shorter one buys speed back at a known cost
per entry. Medium confidence: the unbounded fuzzy ranking for `e` left 30–40 ms of room on 4.45M entries.
