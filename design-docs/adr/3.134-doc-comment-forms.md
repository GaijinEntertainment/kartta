# Find a doc comment by the comment forms of its language

- **Status:** accepted
- **Date:** 2026-10-17
- **Updated:** 2026-10-19
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta-lang/src/doc.rs`, `Language::doc_comments`, `DocComments`, `DocComments::first_line`, each
  language crate's `doc_comments`
- **Pinned by:** `crates/kartta-lang/src/doc.rs` (tests), `crates/kartta-lang-jsts/tests/doc.rs`

The comment above a definition is no part of what an extraction records: only the language knows which lines above a
definition document it, in which comment forms, and which attributes, decorators or template headers the declaration
carries there. Each language states its forms, and `Engine::sources`
([ADR 3.25](/design-docs/adr/3.25-definition-source-text.md)) scans the lines above the
definition when asked, so the build reads no doc and keeps nothing for it.

## Decision

- `Language::doc_comments` answers a `DocComments`: the line comments, the block comments and the carried lines of the
  language, none by default.
- `DocComments::first_line` takes the run of lines directly above the definition that start, after their leading
  whitespace, with one of them; a blank line ends the run.
- A line that ends with a block comment's closing token, a line comment after it aside, closes a comment that counts
  whole up to the nearest line above that starts with the opening token and leaves a comment open at its end, whatever
  the lines between hold. A line between them that ends another comment means the token closes none: the closer of a
  comment opened after code, `int x; /* counts the` then `rows */`, reaches no comment above the code.
- An opening token in the middle of a line opens nothing the scan takes.
- A block comment whose closer can end code too, Lua's `]]` and Ruby's `=end`, closes only on a line of its own.
- The languages state:

  | Language | Line comments | Block comments | Carried lines |
  | --- | --- | --- | --- |
  | Go, TypeScript, TSX, JavaScript, daslang, DSHL | `//` | `/* */` | |
  | C++ | `//` | `/* */` | `template ` and `template<` |
  | Rust | `//` | `/* */` | `#[`, an attribute |
  | PHP, Quirrel | `//`, `#` | `/* */` | |
  | Python, Bash | `#` | | |
  | Puppet | `#` | `/* */` | |
  | Ruby | `#` | `=begin` to `=end` | |
  | Lua | `--` | `--[[ ]]` and its levels to `--[===[ ]===]` | |

- A Python definition's lines start at its first decorator, a TypeScript or JavaScript declaration's at the first
  decorator of the run directly before it, and a daslang definition's at its annotation, as their extractions record
  them, so none of them carries a line. A Python docstring is inside the body and comes with it. BLK states nothing: it
  extracts no definition.

## Why

- Comment text holds an opening token as often as code does, `src/*.c` and `http://*` among it, so a mid-line opener
  would start comments that are not there.
- tree-sitter keeps a TypeScript class member's decorators, and those written before `export`, beside the declaration
  rather than inside it, so a decorated method or exported class started below its decorators: its doc comment above
  them was not found and its text left them out.
- The scan is cheap where it runs: 0.8 to 1.4 µs at the 99th percentile for a definition (2026-10-17).

## Consequences

- A doc comment in a form its language does not state, as a Lua `--[====[` comment past the four levels, is not found.
  Accepted.

## Rejected

- **Record each definition's doc start in its extraction at the build** — 4 bytes a definition, 5.99 MB more heap after
  the build on the C++ game-engine tree, about 0.9%, to save a scan of at most 1.4 µs on a definition whose file the
  answer reads anyway.
- **Carry `@` as a TypeScript line** — `@Input() a: T;` is a field of its own, which a carried `@` reads as a decorator
  of the field below it: carrying it took in the decorators of 12 classes and as many wrong lines.

## Revisit if

A language's extraction records comments, so its doc lines can come from the tree instead of the line scan. Not
planned.
