# Let the caller bound the index's threads

- **Date:** 2026-10-14
- **Governs:** `crates/kartta-fs`, `crates/kartta-walk/src/walk.rs`, `kartta_fs::BuildOptions::threads`,
  `kartta_fs::BuildError::ThreadPool`, `kartta_fs::Index::threads`, `kartta_fs::Index::on_threads`
- **Pinned by:** `crates/kartta-fs/tests/index.rs` (`an_index_runs_on_exactly_the_thread_count_its_build_named`,
  `an_index_with_no_thread_count_runs_on_the_ambient_pool`), `crates/kartta-fs/tests/refresh.rs`
  (`a_refresh_runs_on_the_threads_the_index_was_built_with`,
  `the_named_files_a_refresh_reads_are_read_on_the_index_threads`)

An index works in parallel, and a container runtime that misreports its CPU quota hands the process the host's core
count. `BuildOptions::threads` gives the index one pool of the size the caller names, which every parallel step of the
index runs on; unnamed, the index takes the ambient pool and every core it reports.

## Decision

- **One bound.** `BuildOptions::threads` bounds all of the index's parallel work. A named count gets the index a pool of
  exactly that size, built once with the index and kept for its lifetime. The walk, the reads a content visitor asks
  for, every search, and both kinds of refresh run on it, but for a scoped refresh with one file part, which reads that
  file on the calling thread. `Index::threads` reports the count the index runs on.
- **Consumers share it.** `Index::on_threads` runs a consumer's parallel work on the same threads, so the engine's
  resolution shares the bound.
- **The ambient pool.** Unnamed, the index runs on the ambient rayon pool, which takes the machine's reported cores
  unless the process configured it otherwise.
- **A pool that fails.** A pool the index cannot start is `BuildError::ThreadPool`, and the build does not begin.
- **The walk takes no count.** `kartta-walk` takes no thread count: a walk runs on whatever pool it is called from.
- **Deterministic.** The index does not depend on the count: two builds of an unchanged tree are identical.

## Why

- One pool rather than one per call is what makes the count a bound: two searches running together divide its threads
  instead of each starting as many again.
- Only the caller knows the quota it runs under. The caller that knows names a count; the one that does not is not
  slowed by a guess at what else the machine runs.
- The index's pool already runs the walk, so a walk's own pool was an option the index never set.

## Consequences

An index built without a count oversubscribes a container whose runtime misreports its quota, by as many threads as
the host has cores past it. Accepted: the caller names the count.

## Rejected

- **Three quarters of the reported cores by default** — idles a quarter of a machine dedicated to the index, and still
  oversubscribes a container whose runtime misreports the quota, which only an explicit count fixes.
- **A worker count per call** — concurrent calls add their counts together, so no one number bounds what the index does
  at once.
- **Leave pools to the caller, through `ThreadPool::install`** — every caller has to know that each of the index's
  methods is parallel and wrap each one.
- **Always own a pool, of the reported cores when unnamed** — the same answer as the ambient pool, plus a second pool's
  threads beside the one a rayon-using process already has.

## Revisit if

Searches and builds need different bounds, such as a long build beside interactive searches; the second count is then
named on the search, not inferred. Medium confidence: no consumer has asked for one.
