A C++ `#include` pastes the included text in place, so a file sees every header its headers include, and most C++ code
reaches its engine's logging, math and container headers through a module header of its own. Where includes are
transitive, the include tier reads the whole closure of a file's includes, for a name few definitions share, and the
name's one callable binds only where that closure, or the closure of a file that includes the caller's, reaches it.

## Decision

- **Transitive reach.** Where `Conventions::include_reach` is `IncludeReach::Transitive`, as C++'s is, and the files the
  caller's file includes offer no candidate, the one file of those the includes reach in turn that offers the name binds
  at the include tier's 70, under the direct tier's rule: a file that offers the name on two owners, or two files that
  offer it, leave the call to the tiers below.
- **Definition limit.** A name that more than 32 definitions share is read through direct includes alone.
- **Member calls on a value.** A member call on a value takes a member alone there.
- **Receivers that name an owner or an import.** A call whose receiver names an owner or an import is not read through
  includes; the receiver's tiers answer it.
- **The one callable.** The one callable of a name
  ([ADR 3.172](/design-docs/adr/3.172-bare-call-binding.md), tier 7)
  binds a call only where the closure of the caller's file, or of a file that includes the caller's file directly,
  holds that callable's file or the file of a declaration linked to it. Elsewhere the call binds nothing.
- **Computed when asked.** The closure of a file's includes is computed when a query asks, as the link from a
  declaration to its definition computes it, and nothing more is stored.
- **Direct reach.** `IncludeReach::Direct`, the default, reads only the files a file includes itself: an import names
  one module, and what that module imports is not in the importer's scope.

## Why

- Read through direct includes alone, such a call fell to nearness or bound nothing, and nearness took a namesake in
  another namespace: `debug()` bound a `statsd::debug` two directories away. Through the closure, every sampled bare
  call and 90% of sampled member calls on a value bind the definition called (C++ game-engine tree, 2026-10-17, #65).
- A common name's one definition in the closure is most often a namesake of code outside the graph.
- A free function the closure offers a member call is a member whose class head the extraction misreads, two times in
  three, or a namesake (2026-10-17).
- A translation unit sees only what its includes paste in, so the one callable of a name that no include reaches is
  most often the tree's shim of a name the platform or the toolchain declares: an SSE intrinsic bound to `sse2neon`,
  `strcmp` bound to a PhysX wrapper in its own namespace. 70 of 80 sampled pairs this rule unbinds were such false
  edges (C++ game-engine tree, 2026-10-23, #174).
- A macro is no symbol, so the one callable of a macro's name can be a function a second vendored copy holds in a
  branch of a header the caller never includes: the rule ends all 12 such edges between the tree's two PhysX copies
  (2026-10-30, #408).
- A header or an `.inc` file is compiled inside the files that include it, so their closures stand for its own.

## Consequences

- A call of a member the extraction does not offer binds the one namesake the closure holds: one sampled member call on
  a value in ten, `sunBlk.getPoint3()` on a `DataBlock` binding `ContainerPropertyControl::getPoint3`.
- Resolving a C++ call reads its file's include closure, computed once per query and file, and a call that reaches the
  one callable of its name reads the closures of the files that include its file.
- A call whose include the resolver cannot follow loses its one-callable edge: an include spelled in another letter
  case than the file, a declaration a macro writes, an include of a file outside the C++ set such as `.i`. 10 of the
  80 sampled pairs; accepted.

## Rejected

- **A limit of 64 definitions** — binds 6,659 more caller and callee pairs, of which 70% of those sampled are right,
  and 55% for member calls, under the 90% a rule is taken at (C++ game-engine tree, 2026-10-17).
- **The one callable only where the caller's own closure reaches it** — 17 of 40 sampled pairs it unbinds are right: a
  header or an `.inc` file leans on what its includer pastes before it (2026-10-23).
- **No namespaced callable for a call from outside its namespace** — keeps every global shim, the SSE intrinsics among
  them, and 11 of 40 sampled pairs it unbinds are right, an `.inc` file pasted inside its includer's namespace
  (2026-10-23).
- **Every file above the caller's in the include graph** — binds 1% more of the sites the rule unbinds, for a walk of
  every file that includes the caller's in turn (2026-10-23).

## Revisit if

The C++ extraction reads the templates an `INLINE` macro hides and every class head, so that a lone namesake in the
closure is more often the definition meant; the limit then needs a new measurement. Medium confidence.
