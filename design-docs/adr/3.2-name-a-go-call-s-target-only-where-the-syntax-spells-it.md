# Name a Go call's target only where the syntax spells it

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-17
- **Initiative:** `03-code-graph`

The Go extraction reads one file and infers no types. A call's target is a name, and the graph resolves that name: by
the file's import table when the receiver names an import, or by the owners of the symbols it knows, which in Go are
bare type names. A target that the syntax does not spell gives the graph a name that matches by accident. A wrong edge
is worse than a missing one: an agent that follows it reads code that the call never reaches.

**A receiver is spelled the way Go spells an owner.** Go owners are bare type names, so only an identifier operand is a
receiver: `s.Close()` records `s`. Any other operand records the empty receiver, a member call on a value of no known
type, which the graph never reads as a bare call. On the Go repositories this was built against, the rule empties the
receiver of 94,537 call sites in the two common shapes — `s.client.Do()` at 72,271 sites and `f().g()` at 22,266 — of
the 98,050 sites whose operand is not an identifier. The rest are index, parenthesized and other forms, and their
receivers are empty for the same reason.

Two other spellings were measured on the same repositories:

- **The operand as written**, `s.client`, reaches no tier. No import binding has that name, and all 27,217 distinct Go
  owners are bare type names, none with a dot. It costs one string per site and adds no edge.
- **The last segment**, `client`, reaches the owner match. But the segment is a field name and an owner is a type name,
  so the two agree only by naming convention. 94,227 sites have a last segment and 30,056 of those name a known type;
  of these, 26,103 name a type with no definition in the calling directory, and 23,248 a type that more than one
  directory defines. Most of the edges it adds are wrong.

**A receiver the caller declares as a value names no type.** A parameter, a `:=`, `var`, range or type-switch variable
holds a value whose type the call does not spell, and its name matches an owner only by naming convention: of the 11,448
calls the graph bound through an owner of the receiver's name on a Go monorepo of 39,771 Go files, 11,161 had a receiver
the caller declares, `span.End()` on a `span :=` variable binding an unrelated vendored `span` type. A call on such a
value records the empty receiver. The method's own receiver is the exception, because its declaration spells its type:
`w.draw()` in `func (w *Widget) run()` records `Widget`. On that monorepo, of the 1,118,178 call sites whose receiver is
an identifier, 385,147 name a value the caller declares and 135,776 the method's own receiver.

A language whose owners are whole object expressions — the owner of `gui.Widget.build` is `gui.Widget` — keeps a complex
receiver as written under the same rule, because there the receiver and the owner have one spelling. To find the type
of `s.client`, an extraction needs field-type inference, which the Go extraction does not do.

**A chained call records every call in the chain.** `obj.Chain().Method()` records `Chain` with the receiver `obj`, and
`Method` with the empty receiver. A computed callee, `(*p)()` or `fns[i]()`, records nothing. A bare call of a local
value that has no symbol — a parameter, a `:=` variable — records nothing too, because no symbol of the graph is its
target. A bare call of a local `var`, `const` or `type` is a local call of that symbol.

**An index call names the generic it instantiates when its indices are type arguments.** `f[T](x)` calls `f`, and
`v.F[T](x)` calls `F` on `v`. The syntax does not tell a type from a value, so an index is a type argument unless the
file declares it as a value: a local binding, or a package-level `var` or `const` of the file. An index of such a value
calls an element of it and records nothing. The extraction reads one file, so a package-level variable that another
file of the package declares passes as a generic function.

**A function bound to a package-level variable is the variable alone.** `var Handler = func() {}` gives the `Handler`
variable and no function. Its body is no caller, so the graph drops the calls in it as calls from file scope. The
declared `func` is the common callable form of Go, and a closure bound to a package-level variable is rare enough that
the lost calls are accepted.

**An import names a package directory.** The resolver reads every `go.mod` outside a `vendor` directory: a vendored
`go.mod` belongs to a third-party package, and a checkout can hold thousands of them. A vendored build prefers the
vendored copy, so `vendor/<import path>` wins when the repository holds files there. Otherwise the module whose path is
the longest prefix of the import decides alone, and a directory under it that holds no files is not in the repository.
Where several modules declare that path, as a checkout's nested copies of itself do, the importing file's own module is
the one the go command builds, so it wins. A file sees the vendor directory and the replace directives of the module
that builds it: its own module, or, for a module with no vendor directory of its own that another module replaces onto
its directory, that other module, as the go command builds the dependencies of its main module. On a Go monorepo of
39,771 Go files this adds 64 include pairs from a replaced module to the root's vendored packages, and leaves external
the 427 pairs of two modules nested in it that declare modules of their own and that no replace reaches.
A `replace` onto a local directory is one more module; a `replace` onto another module path, or onto a directory above
the repository root, names no directory. A Go import takes a whole package, so a resolved import includes every Go file
of the directory that is not a test file.

**Revised 2026-10-17.** ADR 3.29 replaces the rule for a receiver the caller declares: a receiver records the path to
its value's type. The calls of a package-level `var` or `const` initializer, a function literal's body among them, are
those of the name each value initializes, or of the first name where the values do not line up with the names, as
one call's results do. An unaliased import whose path ends in a major version, `math/rand/v2` or `gopkg.in/yaml.v3`,
binds the element before it, and a selector on a name the file declares as nothing is kept for the graph, which binds
it only to an import, because a package clause need not match its path. An external test package's import of the package
beside it sees that package's test files, which the go command compiles with it, so the 44 calls of `export_test.go`
helpers on the monorepo bind. A bare call binds only in the package its file declares, test files only from a test
file, and no tier past the package reaches another package's function: `call()` in `package mcp_test` bound the
unexported `mcp.call` through the include of the package it tests. A type defined over anything but a struct or an
interface is a `SymbolKind::DefinedType`, and only `type X = Y` is an alias.

## Considered Options

- **The operand as written, for a complex receiver** — no edge, and one string per call site.
- **The last segment, for a complex receiver** — more edges, most of them wrong.
- **The name of a value the caller declares, as written** — matches a type of that name: the 11,161 calls above, each
  bound at a confidence of 85.
- **The type a parameter or a `var` declaration spells** — names the type where the declaration does, but a `:=`, the
  common declaration, spells none, and a qualified type needs the import's package to tell its owner apart.
- **Field-type inference** — finds the type of `s.client`, but needs the declarations of the packages a file imports,
  which one file's bytes do not hold.
- **A function and a caller for a closure bound to a variable** — keeps the calls in its body, for a form that is rare
  in Go.

Revisit when the graph knows the types the paths of ADR 3.29 cannot spell: a local value that a function literal
captures, and the underlying type of a defined type.
