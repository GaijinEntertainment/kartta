# Own the filesystem walk

- **Status:** accepted
- **Date:** 2026-08-11
- **Updated:** 2026-10-18
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-walk`, `kartta_walk::walk`, `kartta_walk::Policy`, `kartta_walk::Tree`
- **Pinned by:** `crates/kartta-walk/tests/walk.rs` (`records_the_tree_depth_first_with_children_name_sorted`,
  `state_is_inherited_down_the_tree_and_not_across_it`,
  `a_subtree_walk_shows_the_policy_the_paths_the_whole_walk_would`,
  `the_tree_is_identical_however_many_threads_walk_it`)

The index needs the tree a traversal discovers, and the mature walkers stream a flat sequence that has to be rebuilt
into one. kartta owns the traversal, in `kartta-walk`, and returns the tree directly; it pays for that with a walker of
its own to maintain.

## Decision

- `kartta-walk` lists each directory, hands the listing to the caller's `Policy`, walks the subtrees the policy keeps in
  parallel, and returns an arena `Tree`. Matching gitignore rules stays with `gix-ignore`
  ([ADR 1.50](./1.50-match-gitignore-rules-with-gix-ignore.md)); query globs and content search stay with ripgrep's
  engine crates ([ADR 1.4](./1.4-take-the-query-glob-dialect-from-globset.md),
  [ADR 1.10](./1.10-search-content-through-ripgrep-s-engine.md)).
- `Policy::enter` derives each directory's state from its parent's, which is where an inherited `.gitignore` stack
  accumulates on the way down. The `initial` state and `WalkOptions::subtree` make a partial re-walk of one subtree an
  ordinary walk with a different root.
- While the walk runs, each directory's recorded entries stay nested in its parent's and own their subtrees, so no node
  is copied or renumbered before one serial pass flattens them into the arena depth-first.
- Each subtree counts its nodes and name bytes on the way up, so the arena and its name buffer are allocated once, at
  their final size.
- Each listed entry keeps its decoded name beside it, because `DirEntry::file_name` allocates a new name on every call
  and the sort and the lookups by name read it many times.
- An entry's path is built in a reused buffer that already holds its directory's prefix: one per directory, and one
  per parallel split where a large directory is classified in parallel, rather than one per entry.
- The crate carries no benchmark, and it is not documented, benchmarked or tested against another walker. A change to
  the walk is measured on a real tree of millions of entries, with `cargo run --release --example survey -- <tree>` for
  the walk alone and `kartta-fs`'s `probe` for the build it feeds.

## Why

- Rebuilding a tree from a stream costs a global sort for parent-before-child order, a lookup per entry to find its
  parent, a sort of each directory's children, and a second owned copy of every path to key that lookup by. On a real
  tree of about 1.35M entries the time to a name-sorted tree came out within a few percent either way; memory decides,
  since the rebuild holds the flat list, the arena and a map keyed by a copy of every path (2026-08-11).
- Most of a streaming walker is configured away here: kartta reads in-tree ignore files only, so global ignore sources,
  hidden-file filters, file-type selectors and parent-directory rules are all switched off.
- Dependency weight is no argument: dropping a streaming walker removes about 12.6k lines across three crates, while the
  content-search engine kartta keeps pulls one dependency of about 138k lines (2026-08-11).
- A small generated tree misleads. On the 7,604-entry tree the crate's old benchmark used, this walk looked 1.55 times
  faster than a streaming walker that came out even with it on 1.35M entries (2026-10-18).

## Consequences

- The flatten is serial, so it bounds what the parallel traversal can win; accepted until it shows on a large tree.
- A regression in the walk shows only when someone measures it on a real tree; accepted.

## Rejected

- **Keep a streaming walker and rebuild the tree** — the rebuild is the cost being avoided, and it copies every path.
- **Shell out to `git ls-files`** — needs the git binary, fails outside a git directory, and yields no sizes or
  structure: a second code path, not a replacement.
- **A gitoxide-based directory walker** — gates its features on a git index, so it cannot walk a plain directory.
- **A crate built for grouped results with inherited state** — the one that exists is deprecated by its maintainer, and
  its fork has a single maintainer.
- **Own the content searcher too** — where the dependency weight is, but also where the subtle bugs live: bounded line
  buffers, context windows, binary detection.
- **A regression benchmark on a generated tree** — misleads on time and memory at the size it can be generated, and
  nothing ran it.

## Revisit if

The walk falls materially behind on a real tree, a maintained crate returns per-directory grouped results with inherited
state, or a re-walk needs what the seed state cannot express. High confidence: no such crate is maintained today.
