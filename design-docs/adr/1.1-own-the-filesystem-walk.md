# Own the filesystem walk

- **Status:** accepted
- **Date:** 2026-08-11
- **Revised:** 2026-10-14
- **Initiative:** `01-kartta-fs-port`

The filesystem index needs the structure a traversal discovers, not just the paths it finds. A traversal already knows
which entries sit under which directory, but the mature general-purpose walkers stream: they emit a flat sequence and
discard the grouping, because their callers filter and print rather than build a structure. Recovering the tree from a
stream costs a global sort of every path to get parent-before-child order, a lookup per entry to find its
parent, a per-directory sort of children, and a second owned copy of every path to key that lookup by. On top of that,
most of what such a crate offers is configured away here — we need in-tree ignore files only, so global ignore sources,
hidden-file filters, file-type selectors and parent-directory rules are all switched off.

So the traversal is ours, in `kartta-walk`: it reads directories, hands each listing to a caller-supplied policy, walks
surviving subtrees in parallel, and returns an arena tree. The pieces where an existing crate beats anything we would
write stay external — `gix-ignore` for gitignore matching (base-relative pattern lists, git's own `wildmatch`, exact
relative-path matching, so a stack of layers lives naturally in the walk's inherited policy state) and the ripgrep
engine crates for query-side globs and content search. Owning the walk also buys the two things a stream cannot give:
a hook where an inherited `.gitignore` stack accumulates on the way down, and a seed-state parameter that makes a
partial re-walk of one subtree an ordinary walk with a different root.

While the walk runs, each directory's recorded entries stay nested in its parent's and own their subtrees, so no node is
copied or renumbered before one serial pass flattens them into the arena depth-first. Each subtree counts its nodes and
name bytes on the way up, so the arena and its name buffer are allocated once at their final size. Each listing keeps
every entry's decoded name beside it, because `DirEntry::file_name` allocates a new one on every call, and the sort and
the lookups by name read it many times. Every entry's path is built in one buffer per directory that already holds the
directory's prefix, so the walk allocates a path per directory rather than per entry.

Measured on a real tree of about 1.35M entries, time to a name-sorted arena tree came out within a few percent either
way; the difference that is not noise is memory, since reconstruction needs the flat list, an arena, *and* a map keyed by
a duplicate of every path, where a tree-returning walk needs only per-node component names. Dependency weight was checked
rather than assumed and turned out to be no argument at all: dropping a streaming walker removes roughly 12.6k lines
across three crates, while the content-search engine we keep pulls a single ~138k-line dependency by itself. Because the
comparison is settled, it does not live in the crate — `kartta-walk` is not documented, benchmarked or tested against
another walker, and its own benchmark measures only its own regressions. This record is the evidence that alternatives
were measured rather than dismissed.

## Considered Options

- **Keep a streaming walker and reconstruct the tree** — the reconstruction is the cost being avoided, and it duplicates
  every path in memory.
- **Hand-roll the gitignore matcher** — its dialect is a compatibility surface with git, so a divergence is a silently
  wrong index rather than a crash.
- **Reuse part of an existing gitignore crate** — compiled patterns are private in the obvious candidate; it is
  all-or-nothing.
- **Shell out to `git ls-files`** — needs the git binary, fails for non-git directories, and yields no sizes or
  structure: a second code path, not a replacement.
- **A gitoxide-based directory walker** — gates its features on a git index, so it cannot walk a plain directory.
- **A crate purpose-built for grouped results with inherited state** — the one that exists is deprecated by its own
  maintainer; its fork is single-maintainer.
- **Own the content searcher too** — where the real dependency weight is, but also where the subtle bugs live: bounded
  line buffers, context windows, binary detection.

Revisit if the traversal falls materially behind on a real tree (`cargo run --release --example survey`), a maintained
crate appears that returns per-directory grouped results with inherited state, or incremental re-indexing needs something
the seed-state parameter cannot express.
