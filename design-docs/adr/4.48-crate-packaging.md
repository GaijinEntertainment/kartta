# Check on every pull request what a published crate carries

- **Date:** 2026-11-02
- **Governs:** `.github/workflows/ci.yml` (job `package`), `crates/*/LICENSE`, `crates/*/README.md`,
  `crates/*/Cargo.toml` (`package.metadata.docs.rs`)
- **Pinned by:** `.github/workflows/ci.yml` (job `package`)

A crate's package holds only its own directory, and crates.io and docs.rs read that package and nothing else. Each
published crate carries the licence, its feature-gated items and links that resolve from a package, and one CI job holds
all of it, at the cost of a copy of one file per crate and an unstable rustdoc feature behind a cfg.

## Decision

- **Licence.** Each published crate holds a copy of the root `LICENSE`, byte for byte, and its manifest keeps
  `license.workspace = true` alone. A new published crate takes a copy; `kartta-node` is unpublished and holds none.
- **Features on docs.rs.** A published crate with a feature sets `all-features = true` under
  `[package.metadata.docs.rs]` and enables `doc_cfg` under the `docsrs` cfg at its root. The attribute is the only
  source of each item's marker: no item writes `doc(cfg(...))`, because rustdoc reads the marker off the item's own
  `cfg`.
- **README links.** A crate's README links a repository file by a path relative to the README, never from the
  repository root. This is the exception to citing an ADR from the root, which a crate page cannot resolve.
- **The job.** The `package` job packages and verifies every published crate with `cargo package`, and fails when a
  package's licence differs from the root's, a README links from the root, a crate with a feature lacks the metadata,
  or rustdoc under `docsrs` marks no gated item.

## Why

- crates.io drops a link's leading slash and joins the rest to the crate's own directory (`SanitizeUrl::evaluate` in
  its `crates_io_markdown`, read 2026-11-02), so a root path on a crate page leads inside the crate. A relative path
  is normalized to the repository's, and rumdl's MD057 checks it where it skips a root path.
- docs.rs sets `docsrs` itself on the crate it documents (its Builds page, read 2026-11-02), so the metadata names no
  rustdoc argument.
- `doc_cfg` covers what a per-item attribute would have to repeat: on 1.99.1, its markers reach the
  re-exports in `kartta` and the methods of `Engine`.

## Consequences

- A change to the licence edits every copy, and the job fails on a copy it misses. Accepted.
- `doc_cfg` is unstable: the job compiles it on the pinned stable through `RUSTC_BOOTSTRAP`, which is not the nightly
  docs.rs runs, and `cargo doc` on stable shows no marker. Accepted.
- What only a publish shows stays unchecked: that docs.rs builds these crates, that its other default targets
  cross-compile their C grammars, and how its crate page renders a README's links (#1059).

## Rejected

- **A symlink per crate** — on a checkout with `core.symlinks` off the package holds the link's path as the licence
  text (probe, 2026-11-02).
- **`license-file` beside `license`** — cargo warns on both fields at every call, and `license-file` alone loses the
  SPDX expression.
- **A sentence or a `doc(cfg(...))` on each gated item** — it repeats the item's `cfg`, and a new gated item would need
  it by hand.
- **An `https://` URL for each repository link** — no check sees it break when an ADR is renamed.
- **`cargo publish --workspace --dry-run` as the job's first step** — it leaves no `.crate` for the licence check to
  read.

## Revisit if

`doc_cfg` stabilizes, which drops the `docsrs` attribute and the bootstrap flag, or docs.rs or crates.io changes how it
reads a package. High confidence in the licence and link rules; medium in the markers until a first publish shows them.
