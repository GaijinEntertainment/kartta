# Index what a refresh reads in a segment of its own

A refresh that carries files over unread (ADR 1.40) keeps their posting lists, so the content index must hold lists of
files read at different times. It is a list of segments, each over its own range of ids: what a refresh reads goes into
a new segment, and the small segments merge once there are many. Lists of files read again stay behind until then.

## Decision

- **Segments.** The content index (ADR 1.14) is a list of segments, each over its own range of `ContentId`s. A search
  reads every segment and skips the ids the id map says are gone.
- **A new segment for what a refresh reads.** A refresh that carries a text file over and reads a text file into the
  content index adds a segment with its own 768 KiB bucket table, and leaves the old lists of the files it read again
  behind. A refresh that carries no text file, as every refresh without stamps, writes a single segment as a build does.
  `Index::refresh_paths` keeps every segment it holds and adds what it reads as one more (ADR 1.16).
- **Merging the tail.** Past eight segments, the refresh merges the ones after the first into one. The first segment,
  written by the build or by the last merge of everything, keeps the lists of the files read again since.
- **Merging everything.** Once more than a quarter of the files the segments hold lists for are gone, the refresh
  merges all of them into one.
- **What a merged tail counts.** The merged segment counts as its files the live ids in its range whose entries are text
  and not left unindexed, which are exactly the files it holds lists for.
- **How a merge writes.** A merge writes through the build's own partitioned writer, with each trigram's live ids drawn
  from the old segments in place of the build's spilled runs. The writer merges each partition from that partition's
  own input inside the task that writes it, and drops the input when the task ends. Ids keep their numbers through a
  merge, so the merged lists still span the ids that are gone.

## Why

- The first segment holds most of the files, and each refresh since added one holding what that refresh read, so
  merging only the segments after the first bounds the merge by what refreshes read since: a call of ADR 1.16 naming
  100 files took 51.6 ms on `~/wrk`'s 1 GiB content index with the tail merge, against 1,073 ms merging everything
  (2026-10-15).
- Counting exactly the files a merged segment lists keeps the share of gone files, which decides the next whole merge,
  exact.
- Merging each partition inside its own task frees its input once it is written: inputs held until the last partition
  was written, and merges built for every partition before the first write, each raised a build's peak.

## Consequences

- Until a whole merge, lists stay sized for every id handed out: after half the game-engine checkout's files were read
  again and merged, the content index held 128.8 MiB against a fresh build's 116.6 MiB (2026-10-15; accepted).
- A merge of everything costs about what the build's own merge costs (accepted).

## Rejected

- **Merge every segment past eight** — costs about the build's merge every eighth refresh that reads text: 1,073 ms for
  a 100-file call on `~/wrk`, against 51.6 ms for the tail.
- **Rebuild the content index from scratch on each refresh** — reads every text file again: 98 GB on the data volume.
- **Renumber the ids when merging** — ADR 1.15 keeps ids for the life of an index.

## Revisit if

A tree's retired ids leave its merged lists sized far past the files that remain. Medium confidence: the quarter rule
bounds it, and only the game-engine checkout's churn was measured.
