# List a method's callers through the parents its owner implements

A call on a value typed as an interface, a trait or a base class binds that parent's method, the right edge for the
call, so the implementor's method had no caller in `find_callers`. The callers walk now also takes, for a method, the
callers of the methods of its name that its owner's parents declare, each marked with the method it binds, so an agent
reads both who may run the method and that the call may run another implementor instead.

## Decision

- **Which methods are a method's parents.** For a method, the parents are the methods of its name that a type its
  owner implements, extends or includes declares, transitively. The owner's class is the one its body or its
  declaration sits in; the types above it are those its written parents name, read as `find_implementations` reads a
  parent ([ADR 3.20](/design-docs/adr/3.20-implementor-resolution.md)), and those an assertion in the method's own file
  names for it, as a Rust impl apart from its type does. A constructor has no parents: a construction names its class.
  `Conventions::implements` says how a language implements:
  - **Declared** (the default): every method of the name such a type declares, as PHP, TypeScript, JavaScript,
    Python, Ruby, Quirrel and daslang override a member by its name: PHP redeclares it (PHP language specification,
    `spec/14-classes.md`, General), Python's derived class overrides it and a base's own call may run the override
    (`Doc/tutorial/classes.rst`, Inheritance), JavaScript looks a property up by its key along the prototype chain
    (ECMA-262, OrdinaryGet), TypeScript pairs a derived member with the base's by its name (`src/compiler/checker.ts`,
    `checkKindsOfPropertyMemberOverrides`), Ruby searches a method by its name up the superclass chain (`vm_method.c`,
    `search_method0`), Quirrel copies the base's members into the derived class and sets a member by its key
    (`squirrel/sqclass.cpp`, `SQClass::SQClass` and `NewSlot`), and daslang's `def override` replaces the inherited
    method field of the name (`src/parser/parser_impl.cpp`, "structure field is not overriding anything").
  - **Overrides** (C++): only a virtual member the method overrides: one declared `virtual`, `override` or `final`,
    of the same parameter types and cv- and ref-qualifiers, the method not deleted (`source/classes.tex`,
    [class.virtual]). A member of another parameter list, or one not virtual, hides and does not dispatch, and a
    signature the reader cannot split into its parameters overrides nothing.
  - **Traits** (Rust): the traits a parent names alone. A trait impl names a trait (Rust Reference,
    `src/items/implementations.md`, `items.impl.trait.intro`), so a struct a parent's name ties to is a namesake.
  - **Method sets** (Go): every interface whose methods the owner's package gives the owner, each of the same name and a
    signature that reads as the same type once package qualifiers are dropped, with no declaration (`doc/go_spec.html`,
    Implementing an interface; Type identity), declared in the owner's package, in one it imports, or in one that
    imports it. An interface that embeds a type the graph does not hold, or that spells no method, is implemented by no
    type.
- **Which callers reach a method through a parent.** A caller of a parent method reaches the method through it, unless
  the caller's call binds the method itself, or the caller is the method. A caller in a class that the parent's type is
  or sits above, as the parents read for implementors or the member walk of
  [ADR 3.193](/design-docs/adr/3.193-receiver-class-members.md) reach it, calls on its own class's value or on its
  base's own member, so it reaches the method only where the method's owner is the caller's class or below it:
  `$this->boot()` in a sibling class runs no other branch's override. A caller anywhere else may hold any implementor. A
  method set has no hierarchy, so every caller of a Go interface's method counts.
- **What the answer says.** `Reached::through` names the parent method a caller reaches the method through, and its
  confidence is that call's. A caller that calls the method directly and through a parent is listed once, as a direct
  caller. `find_callers`, `find_call_path` and the impact tools take these callers at every hop, as the walk takes any
  caller ([ADR 3.22](/design-docs/adr/3.22-change-impact-analysis.md)); the MCP marks each with `through=`, and the
  wire carries `through` on `Reached`. `references` lists the sites that bind the symbol and no others, and
  `find_unused` keeps its own reading of a dispatched method ([ADR 3.23](/design-docs/adr/3.23-dead-code-judgment.md)).
- **No bound.** The walk up a method's parents has no depth bound and no cap, so it leaves nothing out to count; a
  parent the graph does not hold binds no call to start from.

## Why

- A caller listed through a parent is right on 29 of 30 sampled PHP pairs (Symfony and Laravel), 28 of 30 Rust (this
  repository and four Rust trees), 30 of 30 Go (the Go monorepo snapshot), 28 of 30 C++, 28 of 30 Quirrel and 30 of 30
  daslang (dagor), 29 of 30 JavaScript, 29 of 30 Ruby and 30 of 30 Python (2026-11-03).
- Without the hierarchy rule and the constructor rule, PHP was right on 26 of 30 pairs; Rust without its trait rule
  on 24 of 30; C++ reading every base member of the name on 12 of 30, and of the pairs the override rule removes, 27
  of 30 hold no override; Quirrel without the member walk's reading of the caller's class on 22 of 30.
- Go names no implemented interface. Matching method names alone was right on 11 of 30 sampled pairs; matching method
  sets in any package held the relation the call could run on 17 of 30, a message type's `Reset()` matched to an
  unrelated library's `Resettable`. Of the pairs the package rule removes, 28 of 30 hold no such relation.

## Consequences

- A call on a value whose class the source fixes, `(new Pass())->process()` or a static `Base::make()`, still reaches
  every override of what it binds: 1 of 30 sampled PHP pairs and 1 of 30 JavaScript (#1165).
- A call bound to the wrong member of the name reaches that member's overrides: 2 of 30 sampled Rust pairs, a
  `futures_io::AsyncWrite` call bound to tokio's trait
  ([#650](https://github.com/GaijinEntertainment/kartta/issues/650)), and 1 of 30 C++, a call bound to another
  overload (#443).
- A call on the base's own member from inside the hierarchy runs no override, yet the caller's class and those below it
  read as reached: PHP's `parent::f()` (`parent` "refers to the class the current class extends from", PHP language
  specification, `spec/10-expressions.md`, Scope-Resolution Operator), Python's `Base.f(self)` (a class attribute
  reference looks in that class, `Doc/reference/datamodel.rst`, Custom classes), Quirrel's `base.f()` and a C++
  `Base::f()`: 2 of 30 sampled Quirrel pairs and 1 of 30 C++ (#1166).
- A C++ call bound to a member that overrides without writing `virtual`, `override` or `final` reaches no override below
  that member (#1167), and a Go type that implements an interface through a method an embedded type promotes is not
  found (#1168).
- The Go package rule and the C++ override rule drop a relation the call could run on: 2 of 30 sampled Go pairs and 3
  of 30 C++ pairs that they remove. Accepted.

## Rejected

- **Bind the call to each implementor** — the call is made on the parent, and the edge `callees` and `references` read
  would then name every implementor as the callee.
- **Count the parents `find_unused` reads as dispatching** — it reads any interface declaring the name, which suits a
  method kept out of a dead list and lists unrelated callers here.

## Revisit if

A language records which members dispatch beyond what its signatures spell, or the Go monorepo snapshot's answers
prove too wide to read; neither is planned.
