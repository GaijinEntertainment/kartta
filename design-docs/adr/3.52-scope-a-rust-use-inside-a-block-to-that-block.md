# Scope a Rust `use` inside a block to that block

- **Status:** accepted
- **Date:** 2026-10-22
- **Updated:** 2026-10-23
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta-lang-rust/src/walk/imports.rs` (`record_import`, `kept_paths`, `imported_names`),
  `crates/kartta-lang-rust/src/walk/blocks.rs` (`scope_use_to_block`, `in_use_scope`, `bare_block_calls`)
- **Pinned by:** `crates/kartta-lang-rust/tests/crates.rs`
  (`a_use_inside_a_function_binds_a_name_only_for_the_calls_of_its_block`,
  `a_use_inside_an_inline_module_binds_a_name_only_for_the_calls_of_that_module`,
  `a_use_inside_a_block_binds_a_macro_name_only_for_the_invocations_of_its_block`),
  `crates/kartta-lang-rust/tests/modules.rs::self_in_a_use_list_shadows_a_block_item_of_its_module_s_name`,
  `crates/kartta-languages/tests/engine.rs` (`a_rust_use_inside_a_function_binds_no_call_outside_its_block`,
  `a_rust_use_inside_an_inline_module_binds_no_call_outside_the_module`)

A `use` inside a function body or an inline module is in scope there alone, but a file's bindings hold one path per
name for the whole file. The walk keeps a block's `use` for the calls inside the block and lets a call outside it break
the binding, so a name called through on both sides binds neither call rather than the wrong one.

## Decision

- A `use` inside a function body is in scope in that block alone. A `use` inside an inline module is in scope in the
  module's body alone, and not in a module nested in it, which Rust does not let see it either. A `use` outside both is
  in scope in the whole file, inside its inline modules too, though Rust reaches it there only through `use super::*`
  or a path.
- A file's bindings hold one path per name
  ([ADR 3.50](./3.50-bind-a-rust-path-into-another-crate-through-its-library-s-module-files.md)), so a name that only
  block `use`s bind cannot be kept for their blocks and dropped elsewhere. Outside those blocks a path call reads the
  name as the crate it spells, which binds the name to a second path, and a bare call or a macro invocation of the name
  leaves it none. So one call through the name outside the blocks leaves the name no path at all, for the calls inside
  the blocks too, as two `use`s of the name to two paths do. A file-level `use` of the name keeps it everywhere.
- Every macro invocation is checked against the blocks, one in another function and one invoked as an item outside an
  inline module among them.
- A block's `use` also scopes the names the walk reads from the block: `self` in a list, `use nix::socket::{self}`,
  shadows a block item of its module's name
  ([ADR 3.53](./3.53-record-no-rust-call-through-a-value-and-bind-a-body-s-item-as-a-local-call.md)).

## Why

- A call bound through a `use` not in scope where it is written: tokio's `socket.connect()` in `tests/io_async_fd.rs`
  took nix's `connect` through another test function's `use nix::sys::socket::{self, ...}` (cargo registry,
  2026-10-22), and `mod tests { use other_crate::m; }` gave `m::f()` in a function outside the module the `f` of
  `other_crate` at 95 (#360).

## Consequences

- A name that a block's `use` binds and the file calls through outside the block binds no call through the `use`, in
  the block or out of it. Accepted: of the 17
  names a function body's `use` binds into another crate on this repository, the Go monorepo snapshot and tree-sitter,
  none is called through outside its block (2026-10-22).

## Rejected

- **The path a block's `use` names as the receiver of each call inside the block**, so a call inside binds through the
  `use` and one outside does not — changes the receiver that every tier below the import reads for such a call, also
  where the `use` names a crate outside the tree, and no file of the three trees holds a call it would bind
  differently.

## Revisit if

The call record carries a path per call (#236), so that a call inside a block and one outside it can hold different
paths for one name. Open.
