# Run the follow in the engine's crate over a lock its owner lends

- **Date:** 2026-10-22
- **Governs:** `crates/kartta/src/follow.rs` (`Followed`, `Follower::caught_up`, `Follower::follow`, `Watch`),
  `crates/kartta/src/engine.rs` (`Engine::check_watched`, `Engine::build_watched`), `crates/kartta-fs/src/build.rs`
  (`BuildError::WatchWithoutStamps`), `crates/kartta/Cargo.toml` (`watch`), `crates/kartta-ffi/src/built.rs`
  (`Shared`), `crates/kartta-mcp/src/state.rs` (`Served`)
- **Pinned by:** the tests of `crates/kartta/src/follow.rs`, `crates/kartta/tests/engine.rs`
  (`a_watched_build_without_stamps_is_refused_before_it_walks`)

Two owners follow a tree, the MCP server and a wire build that asks to watch
([ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md), [ADR 4.33](/design-docs/adr/4.33-wire-follow.md)), and the
follow policy is the same for both. The `kartta` crate runs the policy and its thread, and each owner lends it the lock
it already keeps the engine under; the trade is a trait each owner implements.

## Decision

- **The `watch` feature.** `kartta::Follower`, `kartta::Followed` and `kartta::Watch` live behind the `kartta` crate's
  `watch` feature, which is off by default, so a consumer that never watches builds none of it.
- **Catching up and following.** `Follower::caught_up` takes in what the watcher holds before the owner publishes the
  engine, and `Follower::follow` runs the `kartta-watch` thread, which holds the owner through a `Weak`.
- **`Followed`.** The owner implements `Followed` with three methods: `token`, the token that ends the follow, which the
  owner cancels as it lets the engine go; `refreshed`, which runs a refresh under the owner's own write lock and takes
  the refresh's failures in beside the engine; and `watched`, which records a `Watch`, the reason the watch is off and
  the count of watchers the follow started over.
- **A follow keeps stamps.** `Engine::check_watched` answers `BuildError::WatchWithoutStamps` for options without
  stamps, and `Engine::build_watched` calls it before it starts a watcher or walks: each change the follow takes in is
  a refresh, and without stamps a refresh reads every file again and builds every graph again
  ([ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md)). An owner that must refuse before it lets its engine go, the
  wire ([ADR 4.33](/design-docs/adr/4.33-wire-follow.md)), calls `Engine::check_watched`; none holds a copy of the
  condition. It lives on `Engine`, beside the build it guards, since both of its callers build engines: the index's
  own `build_watched` reads no file without a visitor and refuses nothing.
- **The owner's lock.** The owner keeps its own lock, its poisoning and its query paths. The MCP server's `Served` and
  the C ABI's `Shared` each implement `Followed` over the lock their queries read.

## Why

- The policy, the drain before publishing, each batch refreshed under its watcher, the restarts and the reasons a watch
  is off, lived in the server's own loop, which a second owner would have copied (#154).
- Of the shapes built through both owners, this one keeps the loop out of both and adds three public items; the edit
  to query latency did not tell the shapes apart (2026-10-22).

## Consequences

- The library carries the follow code, and each owner a `Followed` implementation. Accepted.

## Rejected

- **A handle the owner drives** — the library takes a batch in on the engine the owner hands it and answers whether to
  go on, start over or stop: each owner keeps a loop of about 45 lines and its thread, for five public items and about
  110 more lines in all.
- **An engine the library shares under a lock of its own** — the lock and its poisoning would leave both owners, every
  query path of each would read the engine through it, and the library would still need a call back to take a
  refresh's failures in where each owner keeps them.

## Revisit if

An owner needs to follow a tree under a lock it cannot lend for the length of a refresh. High confidence that none
does: both owners already hold the engine under one read-write lock.
