# Look a repository path up without ASCII case through a table built when first asked

- **Status:** accepted
- **Date:** 2026-10-17
- **Initiative:** `03-code-graph`

The game trees the code graph reads are built on Windows and shipped in vromfs archives, whose lookup lowercases a
path over names the packer stores lowercased, so a BLK include or a Quirrel import that differs from its file only in
letter case loads in the game (ADRs 3.9 and 3.10). A resolver sees the tree only through `Repository` (ADR 3.1), which
matched a path byte for byte, so such a target named no file.

**`Repository::files_ignoring_case` answers the regular files whose path equals the asked one when ASCII letters are
compared without case**, the asked path among them when it is a file, in index order; a byte outside ASCII matches only
itself. A resolver asks it after an exact miss and takes the one file it answers, abstaining between several. The
trait's default answers the exact path alone, so a repository that cannot compare without case still serves every
resolver.

**The index answers from a table of folded path hashes that the first lookup builds.** The table holds 8 bytes per
regular file, the low half of a hash of the lowercased path and the file's position in the index, sorted by hash, as
the table that `files_named` answers from holds a hash of the file name. A second array cuts the table into buckets by
the top bits of the hash, one bucket per 64 files and at most 65,536 of them, 4 bytes each, so that a lookup, which
nearly always misses, searches a run of tens of entries instead of the whole table. The table belongs to the repository
the resolvers share for one resolve pass and is dropped with it, so it adds to the build's peak and not to what the
engine holds after it, and a build whose resolvers never miss, a tree with no BLK and no Quirrel file among them, never
builds it.

## Measured

The resolvers miss far more often than an include differs in case: on the C++ game-engine tree the BLK and Quirrel
resolvers ask 993,606 times, for the mount directories the ancestors of a stating file might hold and for the place
beside a script before its base paths, and 20 of those lookups find a file; on the macOS data volume, which holds copies
of that tree among 7.5 million entries, they ask 5,759,663 times. The cost of a miss decides between the variants:

- **bucketed** — the chosen table;
- **sorted** — the same table searched whole;
- **name fold** — the table `files_named` answers from, keyed by the hash of the lowercased name, which a lookup reads
  for every file of the name;
- **walk** — no table: each directory of the path listed through the index and its names compared without case.

Each was built over the real index and asked 20,000 BLK and Quirrel paths of its tree, on the C++ tree (182,714
entries) / the data volume (7,623,061 entries):

| variant   | memory added    | built in         | own name, elsewhere | name absent    | file in another case |
| --------- | --------------- | ---------------- | ------------------- | -------------- | -------------------- |
| bucketed  | 1.39 / 55.4 MB  | 11.1 / 390 ms    | 68 / 196 ns         | 34 / 73 ns     | 304 / 459 ns         |
| sorted    | 1.37 / 55.2 MB  | 10.9 / 379 ms    | 130 / 1,244 ns      | 94 / 684 ns    | 340 / 2,051 ns       |
| name fold | none            | +2 / +40 ms      | 613 / 6,375 ns      | 73 / 77 ns     | 834 / 6,773 ns       |
| walk      | none            | none             | 34 / 876 µs         | 33 / 761 µs    | 67 / 1,291 µs        |

The name fold's lookup reads every file of the name: BLK and Quirrel names are shared by a median of 2 files and at
most 186 on the C++ tree, and by a median of 26 and at most 2,418 on the data volume, whose build reads 203.5 million
candidates for its 5.76 million lookups, about 50 s of the build's threads at the rate measured, where the bucketed
table spends about 1 s. The walk lists every directory along the path for each miss. A table of every entry, a
directory too, reads the paths without an allocation each and builds in 289 ms on the data volume instead of 381 ms,
for 5.8 MB more; both are under 500 ms, where the memory decides.

Against `main`, in interleaved runs with the content cache warm, at a load of 6 to 20:

- the C++ tree builds in 3,263–3,945 ms on `main` and 3,304–3,576 ms with this, at a peak footprint of 687–752 MB and
  724–748 MB; its heap after the build is 613.3 MB on both, and the heap's peak 629.1 MB and 630.4 MB, the table;
- the Go monorepo builds in 1,351–1,442 ms and 1,356–1,458 ms, at 467–482 MB and 467–491 MB; its heap after the build
  is 284.7 MB on both and its peak 356.9 MB and 357.1 MB. It holds no BLK and no Quirrel file, so no table is built.

The build times and footprints differ by less than their spread. A whole build of the data volume was not compared.

## Considered Options

- **Name fold** — no memory added, and a lookup that reads every file of the name: 30 times the bucketed table's cost
  for a miss on the data volume, 50 s of the build's threads there.
- **Walk** — no table, and hundreds of microseconds a miss on the data volume.
- **Hash every entry, a directory too** — 92 ms less to build on the data volume, for 5.8 MB more.
- **Build the table on several threads** — 33 ms instead of 289 ms on the data volume, but the table is built inside a
  cell that resolver threads of the index's pool wait on, and a thread of that pool waiting for its share of the
  parallel work can take a resolve job that asks for the same cell, which then never returns.
- **Build the table with the index** — every build pays for it, where only a tree whose resolvers miss needs it.

Revisit when a third language's loader ignores case, when the misses of the BLK and Quirrel resolvers show in a build's
time, or when a lookup that ignores case is needed for a file name rather than a path, as a BLK `#` path would need.
