# Look a repository path up without ASCII case through a table built when first asked

- **Status:** accepted
- **Date:** 2026-10-17
- **Updated:** 2026-10-17
- **Initiative:** `03-code-graph`
- **Governs:** `kartta_lang::Repository::files_ignoring_case`, `crates/kartta/src/repository.rs` (`FoldedPaths`,
  `folded_hash`, `IndexRepository::files_ignoring_case`), `crates/kartta-lang-blk/src/resolve.rs` (`indexed`),
  `crates/kartta-lang-quirrel/src/resolve.rs` (`loaded`)
- **Pinned by:** `crates/kartta/src/repository.rs` (`every_file_is_found_in_another_case_across_the_table_s_buckets`,
  `a_path_hashes_alike_in_any_ascii_case_past_one_buffer`), `crates/kartta-lang/src/memory.rs`
  (`a_path_compared_without_case_finds_each_file_that_differs_only_in_ascii_case`)

The game trees the code graph reads are built on Windows and shipped in vromfs archives, whose lookup lowercases a path
over names the packer stores lowercased, so a BLK include or a Quirrel import that differs from its file only in letter
case loads in the game
([ADR 3.142](./3.142-take-the-one-file-that-differs-only-in-case-where-a-game-s-vromfs-loads-it.md)). A resolver sees
the tree only through `Repository`
([ADR 3.1](./3.1-plug-languages-in-through-a-trait.md)), so the repository answers a path without ASCII case, from a
table of folded path hashes that the first such lookup builds, at the price of 8 bytes per regular file for a build
whose resolvers miss.

## Decision

**The lookup.** `Repository::files_ignoring_case` answers the regular files whose path equals the asked one when ASCII
letters are compared without case, the asked path among them when it is a file, in index order; a byte outside ASCII
matches only itself. The trait's default answers the exact path alone when it is a file, so a repository that cannot
compare without case still serves every resolver.

**Who asks.** The BLK and Quirrel resolvers ask it only after the exact path names no file, and take the one file it
answers, abstaining between several. A file whose path matches exactly wins over its case variants.

**The table.** The index's repository answers from a table of folded path hashes that the first lookup builds: 8 bytes
per regular file, the low half of a hash of the lowercased path and the file's position in the index, sorted by hash,
as the table that `files_named` answers from holds a hash of the file name. A second array cuts the table into buckets
by the top bits of the hash, 4 bytes each: one bucket per 32 to 64 files, capped at 65,536 buckets, so a table of more
than about 4 million files holds more per bucket. A lookup, which nearly always misses, searches one bucket's run
instead of the whole table.

**Its lifetime.** The table belongs to the repository the resolvers share for one resolve pass. A build drops it with
that repository, so it adds to the build's peak and not to what the engine holds after it, and a build whose resolvers
never miss, a tree with no BLK and no Quirrel file among them, never builds it. A followed engine keeps the table a
refresh's repository built
([ADR 3.83](./3.83-keep-the-tables-a-followed-engine-s-resolvers-find-files-in-across-refreshes.md)).

## Why

- The resolvers miss far more often than an include differs in case: on the C++ game-engine tree the BLK and Quirrel
  resolvers ask 993,606 times, for the mount directories a stating file's ancestors might hold and for the place beside
  a script before its base paths, and 20 of those lookups find a file (2026-10-17). The cost of a miss decides.
- A miss whose name is absent took 73 ns through the bucketed table on the macOS data volume of 7,623,061 entries,
  against 684 ns through the same table searched whole (2026-10-17).

## Consequences

- The table holds 55.4 MB for the data volume while the build resolves, built in 390 ms; the C++ tree's heap peak rose
  by 1.3 MB, and its heap after the build did not move; accepted.

## Rejected

- **Fold the table `files_named` answers from** — no memory added, and a lookup that reads every file of the name: BLK
  and Quirrel names are shared by a median of 26 files on the data volume, so its 5.76 million lookups read about 50 s
  of the build's threads, where the bucketed table spends about 1 s.
- **Walk the path's directories** — no table, and hundreds of microseconds a miss on the data volume.
- **Hash every entry, a directory too** — reads the paths without an allocation each and builds 92 ms faster on the
  data volume, for 5.8 MB more; both build under 500 ms, so the memory decides.
- **Build the table on several threads** — 33 ms instead of 289 ms on the data volume, but the table is built inside a
  cell that resolver threads of the index's pool wait on, and a thread of that pool waiting for its share of the
  parallel work can take a resolve job that asks for the same cell, which then never returns.
- **Build the table with the index** — every build pays for it, where only a tree whose resolvers miss needs it.

## Revisit if

The misses of the BLK and Quirrel resolvers show in a build's time, or a third language's loader ignores case. High
confidence on the measured trees: the table and the misses added 1 to 2 s of CPU to a data-volume build of over 260 s.
