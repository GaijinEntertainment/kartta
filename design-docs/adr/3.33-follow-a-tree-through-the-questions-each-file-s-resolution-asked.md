# Follow a tree through the questions each file's resolution asked

- **Status:** accepted
- **Date:** 2026-10-18
- **Initiative:** `03-code-graph`

The index refreshes in place (ADRs 1.15, 1.16, 1.17) and the graph keeps its files apart (ADR 3.5), so a file read
again goes back into its graph by itself. What a resolver makes of a file does not stay its own: a C++ include finds a
header that was added, a Go import lists the files of a package that gained one, a re-export names a file that went
away. So a refresh must resolve again the files a change reaches, from their raw extractions, which the build drops once
it has resolved them. The first consumer builds once and never refreshes, so following a tree must cost it nothing.

**An engine built with stamps keeps, for each file its graphs hold, the questions its resolution asked of the tree.**
The repository a resolver sees files each question under a 32-bit key of its kind and the path, directory, name or
lowered path it names, and a file keeps its keys once each, sorted. A file added or removed answers again every question
that names it, its directory, its name or its lowered path; a file read again answers again a read of it.
`kartta_fs::RefreshOutcome` lists the regular files a refresh added and removed, so files no language claims, a Go
package directory's README or an extensionless header, count as well. A refresh reads again from disk, extracts and
resolves each file holding a reached key; a key two questions share only resolves one file more. What a resolver asks
while it is built, the `go.mod` files, `tsconfig.json` and `.sqconfig`, is kept per language with a hash of every
answer, and a refresh builds again the resolver of a language whose questions it reached or whose read files lie inside
a part it walked: a changed hash resolves every file of the language again. The contract this rests on is stated on
`kartta_lang::Resolver`: `resolve` asks on the calling thread, asks again for each file, and reads no file's content.

**An engine built without stamps keeps nothing.** Its refresh walks the whole tree, which reads every file again as
the index's own refresh without stamps does, and builds every graph again from what it read; `Engine::refresh_paths`
is then `Engine::refresh`. Stamps already mark an index that will be refreshed, so one switch says both, and the
consumer that never refreshes pays neither. `EngineRefresh` reports what the graphs took in, resolved again and dropped,
and the languages reconfigured, beside the index's own outcome.

**Past a number of paths that grows with the tree, `Engine::refresh_paths` refreshes the whole tree, and says so.** The
index walks named paths one after another, and each named file is read and extracted on that one thread, while a whole
refresh reads and extracts on every thread and carries the rest by their stamps. Named paths cost about their number,
and a whole refresh about the tree's entries. The limit is one path for every 150 entries the index holds and never
fewer than 50, which `Engine::refresh_paths_limit` answers; a call named more paths refreshes the whole tree, and
`EngineRefresh::widened` gives the number named and the limit they passed. The caller does not pick: the crossover
follows the index's entries and the engine's own extraction, which the engine counts and the caller does not.

## Measured

On the C++ game-engine tree (182,714 entries, 146,752 files the graphs hold) and the Go monorepo (69,999 entries,
44,443 files), every language, on an 18-core macOS machine under the load of other builds:

| per tree | game-engine tree | Go monorepo |
| --- | --- | --- |
| raw extractions, encoded | 300.6 MiB, 2,148 B a file | 211.6 MiB, 4,992 B a file |
| questions kept, 4 B each | 2.34M, 8.9 MiB | 0.40M, 1.5 MiB |
| extract a file / resolve a decoded one, CPU | C++ 1.7 ms / 14 µs | Go 1.05 ms / 23 µs |
| files one file's adding or removal reaches | p50 0, p90 4, p99 63, max 2,987 | p50 3, p90 56, p99 171, max 2,008 |

Over 5,000 commits of the monorepo's history, the files a commit's adds and deletes reach are p50 0, p90 11, p99 77,
max 1,034, and a day's p50 39, p90 276, max 3,393; 206 commits touch a configuration a resolver read, mostly `go.mod`,
and each resolves every Go file again. An engine with stamps keeps the keys above and, per held file, its path, its
language and a map slot: about 27 MB on the game-engine tree and 7 MB on the monorepo by the counts above, against
622 MB and 293 MB of heap after a build. Resident sets after a build moved by more than that between runs (1,022 MB with
stamps against 1,069 MB without on the monorepo), so the kept data is counted, not read off them.

Refresh against a fresh build, scripted edits to source files in a scratch copy (85% of them appending a definition, the
rest deleting, adding beside a sibling, one rename and one header gaining an include), answers compared over every count
of `Engine::stats` and `Engine::resolution` and the callers and dependents of 300 sampled files and the edited ones; no
answer differed in any run, out of 254 to 1,478 compared. The named paths were walked apart in every run, the limit
below not yet in place:

With stamps, the resident set after a refresh lay between 29 MB below and 22 MB above where the build left it. Without
stamps a refresh holds the old graphs while it builds the new ones, and its resident set rose by 300 MB on the monorepo.
Reporting the regular files added and removed costs a whole index refresh one pass over the paths before and after it:
145 ms to 151 ms on the game-engine tree and 902 ms to 916 ms on 457,477 entries of `~/wrk`. On the 8,988,546 entries
of the data volume, two whole index refreshes a process took 49.9–58.4 s against 48.8–56.7 s on `main`, at a peak
footprint of 1,195–1,202 MB against 1,166–1,235 MB, inside the spread between runs.

Three runs on the game-engine tree reached a `.blk` file a resolver had read and resolved 80,000 files again, 2.3 s to

a whole refresh took 13–19 ms whatever the batch, and named paths matched it between 50 and 107. A fixed count would
widen a few hundred paths on the 5.5 million entries of the data volume into a walk of 47–51 s (ADR 1.16), so the
limit follows the entries, at one path for every 150, between the two trees, and at least 50 on a small tree. After
all 42 calls on each tree the engine answered as a fresh build: 0 of 583 and 0 of 684 answers differed.

## Considered Options

- **Keep every file's raw extraction to resolve it again without a read** — 300.6 MiB and 211.6 MiB, half the heap a
  built engine holds, to save a read and an extraction of the few files a change reaches: 77 files a commit at p99
  is about 80 ms of CPU. It pays only when a configuration changes and every file of a language resolves again: the
  monorepo's Go in 0.9 s of CPU from the kept extractions against 42 s from the files.
- **Resolve every file of a family again on any add or remove** — no keys, and the raw extractions of every file kept,
  or read again at the cost of a build, for a change that reaches 0 to 4 files at the median.
- **A resolver that resolves only the directives of a file** — would keep a few bytes a file and resolve again without
  a read, at a change to the contract of every language crate and a graph that replaces part of a file.
- **Read the files a change reaches through the content cache** — needs the index to hash and look up bytes it did not
  read during a walk; the files a commit reaches are few enough that extracting them is cheaper than that interface.
- **Widen past a fixed number of named paths** — the smaller tree's crossover, about 540, turns 541 paths on a tree of
  millions of entries into a whole walk that costs over a hundred times what the paths do.
- **Let the caller choose between named paths and a whole refresh** — leaves every consumer to learn a crossover that
  depends on counts only the engine holds.

Revisit when a configuration a resolver reads changes often enough that resolving every file of its language costs a
consumer: a resolver could answer a fingerprint of what it derived from its configuration, the modules and replaces of
`go.mod` rather than its bytes, so a dependency bump would resolve nothing again. Revisit the limit on named paths when
the index reads the files of named paths on its threads: named paths would then cost what a whole refresh pays for the
same files, and the crossover would move out with the number of threads.
