# Follow a tree through the questions each file's resolution asked

- **Status:** accepted
- **Date:** 2026-10-18
- **Revised:** 2026-10-20
- **Initiative:** `03-code-graph`

The index refreshes in place (ADRs 1.15, 1.16, 1.17) and the graph keeps its files apart (ADR 3.5), so a file read
again goes back into its graph by itself. What a resolver makes of a file does not stay its own: a C++ include finds a
header that was added, a Go import lists the files of a package that gained one, a re-export names a file that went
away. So a refresh must resolve again the files a change reaches, from their raw extractions, which the build drops once
it has resolved them. The first consumer builds once and never refreshes, so following a tree must cost it nothing.

**An engine built with stamps keeps, for each file its graphs hold, the questions its resolution asked of the tree.**
The repository a resolver sees files each question under a 32-bit key of its kind and the path, directory, name or
lowered path it names, and a file keeps its keys once each, sorted. A file added or removed answers again every question
that names it, its directory, its name or its lowered path; a file read again answers again a read of it.
`kartta_fs::RefreshOutcome` lists the regular files a refresh added and removed, so files no language claims, a Go
package directory's README or an extensionless header, count as well. A refresh reads again from disk, extracts and
resolves each file holding a reached key; a key two questions share only resolves one file more. What a resolver asks
while it is built, the `go.mod` files, `tsconfig.json` and `.sqconfig`, is kept per language with a hash of every
answer, and a refresh builds again the resolver of a language whose questions it reached or whose read files lie inside
a part it walked: a changed hash resolves every file of the language again. The contract this rests on is stated on
`kartta_lang::Resolver`: `resolve` asks on the calling thread, asks again for each file, and reads no file's content.

**An engine built without stamps keeps nothing.** Its refresh walks the whole tree, which reads every file again as
the index's own refresh without stamps does, and builds every graph again from what it read; `Engine::refresh_paths`
is then `Engine::refresh`. Stamps already mark an index that will be refreshed, so one switch says both, and the
consumer that never refreshes pays neither. `EngineRefresh` reports what the graphs took in, resolved again and dropped,
and the languages reconfigured, beside the index's own outcome.

**Past a number of parts that grows with the tree, `Engine::refresh_paths` refreshes the whole tree, and says so.** The
index reads and extracts the named files on its threads, as a whole refresh does, unless a call has one file among its
parts, which it reads on the calling thread (ADR 1.16). It takes each part on the calling thread, a stat and the ignore
rules above it, and splices the parts in, while a whole refresh walks every entry on every thread and carries the rest
by their stamps. Beside the files both read, named paths cost about the number of their parts, and a whole refresh about
the tree's entries. The limit is one part for every 30 entries the index holds and never fewer than 50, which
`Engine::refresh_paths_limit` answers. The parts are those the index walks for the paths (ADR 1.16): every path inside a
directory the index does not hold is one part, and a path inside `.git` or through a pruned name is none. A call whose
paths come to more parts refreshes the whole tree, and `EngineRefresh::widened` gives the number of paths named and the
limit their parts passed. The caller does not pick: the crossover follows the index's entries and the engine's own
extraction, which the engine counts and the caller does not.

**Revised 2026-10-20: the limit counts parts, not named paths.** A build inside an ignored `target/` names its outputs
by the thousand, and each path counted, so the paths of a build the index never holds made a whole refresh.

**Revised 2026-10-20: the limit is one part for every 30 entries, not 150.** The index read each named file on the
calling thread, so named paths stopped paying near 540 of them on the Go monorepo and near 1,020 on the game-engine
tree. It reads them on its threads now (ADR 1.16). The series below, run again on both sides, puts the crossover
between 107 and 214 paths on `main` and near 1,714 with the change on the monorepo snapshot's 34,506 entries, one for
every 20, and between 857 and 1,714 against near 3,429 on the game-engine tree's 182,714, one for every 53; on four
threads it sits at the same counts on both trees, since both modes read on the same threads. Past the crossover the two
modes stay level for a while: within 22% from 1,714 to 13,714 paths on the snapshot, and within 5% from 3,429 to 6,857
on the game-engine tree, where 13,714 took 1.8 times a whole refresh. The limit sits between the two trees' crossovers,
as the old one did: 1,150 parts on the snapshot, below its crossover, and 6,090 on the game-engine tree, above its
crossover but inside the stretch where the two modes stay within 5%.

## Measured

44,443 files), every language, on an 18-core macOS machine under the load of other builds:

## Considered Options

- **Keep every file's raw extraction to resolve it again without a read** — 300.6 MiB and 211.6 MiB, half the heap a
  built engine holds, to save a read and an extraction of the few files a change reaches: 77 files a commit at p99
  is about 80 ms of CPU. It pays only when a configuration changes and every file of a language resolves again: the
  monorepo's Go in 0.9 s of CPU from the kept extractions against 42 s from the files.
- **Resolve every file of a family again on any add or remove** — no keys, and the raw extractions of every file kept,
  or read again at the cost of a build, for a change that reaches 0 to 4 files at the median.
- **A resolver that resolves only the directives of a file** — would keep a few bytes a file and resolve again without
  a read, at a change to the contract of every language crate and a graph that replaces part of a file.
- **Read the files a change reaches through the content cache** — needs the index to hash and look up bytes it did not
  read during a walk; the files a commit reaches are few enough that extracting them is cheaper than that interface.
- **Widen past a fixed number of named paths** — the smaller tree's crossover, about 540 and about 1,714 since named
  files are read on the index's threads, turns a few more paths on a tree of millions of entries into a whole walk that
  costs over a hundred times what the paths do.
- **Let the caller choose between named paths and a whole refresh** — leaves every consumer to learn a crossover that
  depends on counts only the engine holds.

Revisit when a configuration a resolver reads changes often enough that resolving every file of its language costs a
consumer: a resolver could answer a fingerprint of what it derived from its configuration, the modules and replaces of
`go.mod` rather than its bytes, so a dependency bump would resolve nothing again. Revisit the limit on named paths when
the index takes the parts themselves on its threads, their stats and the rules above them, which is what named paths
still pay apart from a whole refresh, or when a consumer follows a tree whose whole refresh costs far more for each
entry than on these two, such as one on a network mount.
