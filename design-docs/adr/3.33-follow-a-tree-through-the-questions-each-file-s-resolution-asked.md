# Follow a tree through the questions each file's resolution asked

- **Status:** accepted
- **Date:** 2026-10-18
- **Revised:** 2026-10-22
- **Initiative:** `03-code-graph`

The index refreshes in place (ADRs 1.15, 1.16, 1.17) and the graph keeps its files apart (ADR 3.5), so a file read
again goes back into its graph by itself. What a resolver makes of a file does not stay its own: a C++ include finds a
header that was added, a Go import lists the files of a package that gained one, a re-export names a file that went
away. So a refresh must resolve again the files a change reaches, from their raw extractions, which the build drops once
it has resolved them. The first consumer builds once and never refreshes, so following a tree must cost it nothing.

**An engine built with stamps keeps, for each file its graphs hold, the questions its resolution asked of the tree.**
The repository a resolver sees files each question under a 32-bit key of its kind and the path, directory, name or
lowered path it names, and a file keeps its keys once each, sorted, as its run of one buffer every followed file shares,
or no run when it asked nothing. A file added or removed answers again every question that names it, its directory,
its name or its lowered path; a file read again answers again a read of it. `kartta_fs::RefreshOutcome` lists the
regular files a refresh added and removed, so files no language claims, a Go package directory's README or an
extensionless header, count as well. A refresh finds the files holding a reached key in one pass over the buffer, each
key tested against a bit set at the low bits of every reached key before the set of them, and reads each again from
disk, extracts and resolves it; a key two questions share only resolves one file more. What a resolver asks
while it is built, the `go.mod` files, `tsconfig.json` and `.sqconfig`, is kept per family with a hash of every
answer, beside the resolver itself, and a refresh builds again the resolver of a family whose questions it reached or
whose read files lie inside a part it walked: a changed hash resolves every file of the family again, unless the
rebuilt resolver resolves as the kept one (revised below). The contract
this rests on is stated on `kartta_lang::Resolver`: `resolve` asks on the calling thread, asks again for each file,
and reads no file's content.

**An engine built without stamps keeps nothing.** Its refresh walks the whole tree, which reads every file again as
the index's own refresh without stamps does, and builds every graph again from what it read; `Engine::refresh_paths`
is then `Engine::refresh`. Stamps already mark an index that will be refreshed, so one switch says both, and the
consumer that never refreshes pays neither. `EngineRefresh` reports what the graphs took in, resolved again and dropped,
and the families reconfigured, beside the index's own outcome.

**Past a number of parts that grows with the tree, `Engine::refresh_paths` refreshes the whole tree, and says so.** The
index reads and extracts the named files on its threads, as a whole refresh does, unless a call has one file among its
parts, which it reads on the calling thread (ADR 1.16). It takes each part on the calling thread, a stat and the ignore
rules above it, which go to the index's threads once a directory answers as slowly as a network mount does, and
splices the parts in, while a whole refresh walks every entry on every thread and carries the rest by their stamps.
Beside the files both read, named paths cost about the number of their parts, and a whole refresh about the tree's
entries. The limit is one part for every 30 entries the index holds and never fewer than 50, which
`Engine::refresh_paths_limit` answers. The parts are those the index walks for the paths (ADR 1.16): every path inside a
directory the index does not hold is one part, and a path inside `.git` or through a pruned name is none. A call whose
paths come to more parts refreshes the whole tree, and `EngineRefresh::widened` gives the number of paths named, the
parts they came to and the limit those passed (ADR 4.4). The caller does not pick: the crossover follows the index's
entries and the engine's own extraction, which the engine counts and the caller does not.

**Revised 2026-10-20: the limit counts parts, not named paths.** A build inside an ignored `target/` names its outputs
by the thousand, and each path counted, so the paths of a build the index never holds made a whole refresh.

**Revised 2026-10-20: the limit is one part for every 30 entries, not 150.** The index read each named file on the
calling thread, so named paths stopped paying near 540 of them on the Go monorepo and near 1,020 on the game-engine
tree. It reads them on its threads now (ADR 1.16). The series below, run again on both sides, puts the crossover
between 107 and 214 paths on `main` and near 1,714 with the change on the monorepo snapshot's 34,506 entries, one for
every 20, and between 857 and 1,714 against near 3,429 on the game-engine tree's 182,714, one for every 53; on four
threads it sits at the same counts on both trees, since both modes read on the same threads. Past the crossover the two
modes stay level for a while: within 22% from 1,714 to 13,714 paths on the snapshot, and within 5% from 3,429 to 6,857
on the game-engine tree, where 13,714 took 1.8 times a whole refresh. The limit sits between the two trees' crossovers,
as the old one did: 1,150 parts on the snapshot, below its crossover, and 6,090 on the game-engine tree, above its
crossover but inside the stretch where the two modes stay within 5%.

**Revised 2026-10-21: a refresh finds the files a change reaches by one pass over a buffer of every followed file's
keys, behind a bit filter of the reached keys, not by an index from each key to its files.** The pass went to each
file's own box of keys through the file's slot in the map, and probed the set of reached keys for every key. On 16
copies of the game-engine tree side by side, 2.92M entries and 2.35M followed files, that took 0.24 to 0.31 s of a
named refresh of 1.1 to 2.5 s. The filter and the buffer take it to 0.04 s, and the engine holds 3.4 MiB less on the
game-engine tree after a build. The smaller index by key would find them in under 2 ms, but needs upkeep after each
refresh and holds 186.5 MiB more on the copies (below). A run whose file left stays until such runs hold a quarter of
the keys, and then one pass moves the others to the front.

**Revised 2026-10-21: a refresh finds the walked part that holds a resolver's read file by a search of the parts, not
by a test against each.** Both counts grow with the tree: a named refresh at the limit walks one part for every 30
entries, and a resolver reads a `package.json`, a `go.mod` or a `.sqconfig` for each package that has one. On 16
copies of the game-engine tree, 2.92M entries, testing 2,800 read files against 97,448 parts took 0.28 to 1.05 s of a
refresh at the limit. The walked parts are in tree order, none below another, so `RefreshOutcome::walked_over` finds
the one part that can hold a file by a binary search (ADR 1.16), in 0.66 to 12.6 ms there (below).

**Revised 2026-10-21: an engine with stamps keeps the tables its resolvers find files in, and a refresh that added and
removed no file skips the pass over the followed keys.** The repository a resolver asks builds its table of files by
name, and its table of paths folded to one case, from every entry of the index the first time a resolver asks for one,
and a refresh made a new repository each time. On 16 copies of the game-engine tree, 2,923,440 entries, building the
table by name took 222.7 ms of a one-file refresh of 305.9 ms at the median, paid by a refresh of a C++, DSHL, Go,
JavaScript, TypeScript, TSX, PHP or Quirrel file and not by one of a Bash, Daslang, Lua or Python file, whose resolvers
ask nothing by name; ADR 1.16 gives the rest of the call. The engine keeps the tables a refresh's repository built and
hands them to the next refresh's repository: a refresh that kept every position (ADR 1.16) leaves them as they are, and
one that moved entries reads the files its walked runs hold now, moves every kept entry through
`RefreshOutcome::position_after` and merges the two, a pass over each table. A table is built from every entry only the
first time a refresh's resolver asks for it, and the build's own tables are dropped with its repository: the table of
folded paths answers only a Quirrel or Blk path that names no file, which few refreshes ask, and one kept from the build
would be moved by every refresh that moves entries. `resolve` reads no file's content, as the contract on
`kartta_lang::Resolver` states, so no file's keys hold a read of a file and only a file added or removed reaches one: a
refresh that only read files again skips the pass over the buffer, 34.6 ms of the same call.

## Considered Options

- **Keep every file's raw extraction to resolve it again without a read** — 300.6 MiB and 211.6 MiB, half the heap a
  built engine holds, to save a read and an extraction of the few files a change reaches: 77 files a commit at p99
  is about 80 ms of CPU. It pays only when a configuration changes and every file of a language resolves again: the
  monorepo's Go in 0.9 s of CPU from the kept extractions against 42 s from the files.
- **Resolve every file of a family again on any add or remove** — no keys, and the raw extractions of every file kept,
  or read again at the cost of a build, for a change that reaches 0 to 4 files at the median.
- **A resolver that resolves only the directives of a file** — would keep a few bytes a file and resolve again without
  a read, at a change to the contract of every language crate and a graph that replaces part of a file.
- **Read the files a change reaches through the content cache** — needs the index to hash and look up bytes it did not
  read during a walk; the files a commit reaches are few enough that extracting them is cheaper than that interface.
- **Widen past a fixed number of named paths** — the smaller tree's crossover, about 540 and about 1,714 since named
  files are read on the index's threads, turns a few more paths on a tree of millions of entries into a whole walk that
  costs over a hundred times what the paths do.
- **Let the caller choose between named paths and a whole refresh** — leaves every consumer to learn a crossover that
  depends on counts only the engine holds.
- **An index from each key to the files that asked it** — finds the files a refresh reaches in under 2 ms on both the
  game-engine tree and its 16 copies. Sorted, it holds 10.9 MiB more on the game-engine tree and 186.5 MiB more on the
  copies, 4.9 bytes a key asked, and its upkeep after each refresh, with a rebuild once a quarter of it is stale,
  brings its highest calls over the series above the pass's; a hash map holds three times as much. Over the filtered
  buffer it saves 2 ms on the game-engine tree and 40 ms on the copies, for that memory held as long as the engine.
- **The filter alone, each file's keys in a box of its own** — saves 3.6 ms on the game-engine tree and 109 ms on the
  copies at no cost in memory; the buffer takes another 3.2 ms and 126 ms off, and 3.4 MiB.
- **A set of the walked parts, probed with each read file and every directory above it** — relies on no order, at a
  slot for each part built on every refresh that walks parts apart: 1.0 to 17.8 ms on the copies against 0.66 to
  12.6 ms for the search, which holds nothing.
- **Keep the tables the build made** — saves the first refresh that asks by name its pass over every entry, 222.7 ms
  on the copies and 16.5 ms on the game-engine tree, at 42.1 MiB held from the build on there, and every refresh that
  moves entries then moves the table of folded paths too, which few refreshes ask: a removal took 64.7 ms against
  49.2 ms on `main`, one process a side under a load average of 50 to 90, where keeping what a refresh built took
  55.2 ms against 48.0 ms in one engine.
- **Keep the tables only across a refresh that kept every position**, building them again after one that moved entries
  — no pass to move them, but a file added pays the whole table again: 273.0 ms against 62.9 ms on the copies.
- **Build the table by name again on each refresh, faster** — on the copies' 2,746,048 files, five builds of an inert
  index under a load average of 19 to 35, it took 263 to 291 ms as built, 179 to 196 ms without an allocation a file
  and 16 to 19 ms on the index's 18 threads, and the table of folded paths 237 to 251 ms as built; on the game-engine
  tree 16 to 19, 11.5 to 12.4 and 2.3 to 2.7 ms. Each is still a pass over every entry on every refresh that asks,
  where a kept table costs one that kept every position nothing and one that moved entries a pass over the table.

Revisit the limit on named paths when
the index takes the parts themselves on its threads, their stats and the rules above them, which is what named paths
still pay apart from a whole refresh, or when a consumer follows a tree whose whole refresh costs far more for each
entry than on these two, such as one on a network mount. Revisit an index by key when the pass is again a large part
of the refresh a consumer waits on: over the buffer it took about 17 ns a followed file on the 16 copies, where
building the resolvers a refresh wants took 0.43 to 1.16 s.
