# Extract TypeScript and JavaScript as one family

- **Status:** accepted
- **Date:** 2026-10-16
- **Initiative:** `03-code-graph`

TypeScript, TSX and JavaScript are three tree-sitter grammars over one module system. A frontend mixes them freely, and
much of what a reviewer asks about — a component, an event handler, a hook — is a function with no declaration of its
own, bound to a name, wrapped in a call or passed as an argument. ADR 3.1 makes each a language of its own; this decides
how `kartta-lang-jsts` extracts and resolves them.

**Three languages share one walk and one family, `jsts`.** Each parses its files with its own grammar; the walk is the
same, because the kinds only TypeScript has never appear in a JavaScript tree. React frontends keep shared code in `.ts`
and the components that use it in `.tsx`, so most imports and calls cross from one grammar to the other: building the
three as separate graphs severed 34% of the resolved import edges on the frontends this was built against.

**A function bound to a name owns the calls in its body; an anonymous callback does not.** An arrow in a `const`, a
function wrapped in `memo`, `forwardRef`, `useCallback`, `useMemo`, `observer` or `debounce`, an object property, a
class field and an anonymous default export each become a function symbol with a call scope. Without the scope every
call in an arrow body belongs to the file, and a caller query dead-ends on exactly the components and handlers a review
is about. An inline JSX prop arrow opens no scope: it has no name to address, so its calls belong to the component
around it, which is the consumer a reviewer asks about.

**A test registration is the one callback that opens a scope.** A test file is built from registrations — `describe`,
`it` and `test` with their `x` and `f` forms, `suite` and `bench`, each bare or behind a `.skip`, `.only`, `.todo`,
`.concurrent`, `.sequential` or `.failing` modifier — whose bodies bind no name, so without a scope it declares no
symbol, the walk drops its calls as it drops every call made before a file's first symbol, and a function called only
from tests looks dead. The description names the symbol, flat rather than qualified by the enclosing `describe`, the
way object keys stay flat; a lifecycle hook is named for itself. A description that is not a plain string — a template
literal, a variable — names nothing, and a shape outside that list, such as the table form `it.each(rows)(...)`, is no
registration the walk recognises; either way the body stays with the enclosing registration. A call named `describe`
in a production file still opens its scope, but the file's own name decides whether the symbol is test code.

**Some of the language is not modelled.** Export assignments, `module.exports = …` and `exports.f = …`, are ordinary
assignments to the walk, so a CommonJS module has no export surface and a function that exists only on the right side of
one has no symbol. No symbol is an entry point: a program's entry is a bundler's or a `package.json`'s notion, and it
names a file, not a symbol. A type-only import or re-export is an include like any other, because a type dependency is a
real dependency to the blast radius of a change.

**A file is test or generated code by its name or its banner.** A `.test.` or `.spec.` name, or a `__tests__` or
`tests` directory, is test code, as Jest, Vitest and Mocha find tests; a directory named `test` is not, because it is a
common name for a feature or a command. A `@generated` or `DO NOT EDIT` banner in the comments before the first code is
generated code, but only outside a backtick span, where documentation of the convention quotes it. A `.gen.`,
`.generated.`, `_pb`, `.pb` or `.min` name is generated too: a minified bundle is machine output, and four committed
vendor bundles carried about 10% of the symbols on the frontends this was built against. A `-min.js` name is not
matched, because no such file was found and hand-written names end in `-min`, and a `.d.ts` file is not generated,
because such files are commonly written by hand.

**Imports resolve the way the compiler and the bundlers resolve them, from the repository's own configuration.** The
resolver reads every `tsconfig.json` and `package.json` outside `node_modules` and `vendor` directories when it is built
— vendored ones belong to third-party packages, and a checkout can hold thousands — and a `tsconfig*.json` only when one
of those extends or references it, which is the only way such a variant takes part. A relative specifier probes the
script extensions, declaration files and `index` files, and on a miss the TypeScript source an ESM `./m.js` stands for.
The nearest `tsconfig.json` alone governs a file's `paths`, one that yields none included, after one `extends` hop
whose fields the child replaces whole, a path the base supplies staying relative to the base; a config that declares no
`paths` but references sibling configs in its own directory takes theirs, as the current Vite scaffold splits them, and
a reference into a subdirectory is that subproject's. A `#` specifier takes the `imports` of the nearest
`package.json`, which stops the lookup whether it declares any or not. A specifier that names a package of the
repository takes its `exports` — an object whose keys are conditions being the target of `.` — conditions tried source
first; failing those, the package's bare name takes its `module` or `main` and then its directory, and a subpath the
file under the package's directory. Where Node rejects a bare import of a package whose `exports` omits `.`, the
resolver falls through to `main`, because that is the module most bundler setups load, and an include edge is worth
more than strictness here. A monorepo of independent frontends can declare one package name twice, so the longest name
that prefixes the specifier wins, then the package nearest the importing file, and two equally near resolve to neither:
a missing edge is better than one no bundler would make. A Vite `?query` is stripped only after the specifier misses
as written, so a file whose name holds a `?` still resolves.

**A re-export names the file its specifier resolves to, by the same rules.** The graph used to match a re-export's
specifier against the files the re-exporting file includes, by stem, by path segment or by appending `.ts` or `.tsx`:
it could not see an ESM `.js` specifier, an alias, an `index.tsx` barrel or a package, and it knew a language's
extensions. The resolver resolves a re-export together with the import of its statement, so it costs no second
resolution.

**The fingerprint covers the walk and the grammar.** A build script digests the crate's sources; at run time the
digest takes in the crate's name and version, the language's name, and its grammar's declared version, node types, ABI
version and counts of node kinds, parse states and fields. A change in `kartta-lang` is covered by
`kartta_lang::FINGERPRINT`, which a cache keys beside it. It cannot see a change in the tree-sitter runtime, or in a
grammar that keeps all of those equal: a maintainer who updates either bumps the crate's version, which the fingerprint
takes in.

## What it costs

On a monorepo checkout of 374,827 files, of which 172,660 are scripts holding 1.51 GB with their `node_modules`, one
thread on macOS extracts the scripts in 74.5 s and resolves them in 0.45 s, and the three resolvers read the
configuration in 0.11 s together — each language builds its own, so the configuration is read three times. The files
yield 5.95 million symbols, 6.52 million calls, 352,630 includes and 236,018 imports kept as written; 118,642 of the
166,762 re-exports name a file, each at the cost of a copy of its path.

## Considered Options

- **A family per grammar** — severs the imports between `.ts` and `.tsx` files, a third of a frontend's edges.
- **The graph matching re-exports to includes** — the graph would keep a language's extension rules, against ADR 3.1,
  and keep guessing where the language knows.
- **Resolving each re-export on its own** — one more resolution per re-exported name, where a statement re-exporting
  many names resolves the same specifier once.
- **Reading every `tsconfig*.json` up front** — a repository finds files by their exact name, and a variant matters only
  as the target of a config that names it.
- **Modelling CommonJS exports** — a function assigned to `exports` would gain a symbol, at the cost of an arm for every
  assignment shape; nothing that consumes the graph has asked for it.
- **Node's strict `exports`** — drops the include edge of a package whose `main` is what its bundler loads.

Revisit when a consumer needs the export surface of CommonJS modules, or when the contract lets one family share one
resolver.
