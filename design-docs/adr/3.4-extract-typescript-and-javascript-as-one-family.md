# Extract TypeScript and JavaScript as one family

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-23
- **Initiative:** `03-code-graph`

TypeScript, TSX and JavaScript are three tree-sitter grammars over one module system. A frontend mixes them freely, and
much of what a reviewer asks about — a component, an event handler, a hook — is a function with no declaration of its
own, bound to a name, wrapped in a call or passed as an argument. ADR 3.1 makes each a language of its own; this decides
how `kartta-lang-jsts` extracts and resolves them.

**Three languages share one walk and one family, `jsts`.** Each parses its files with its own grammar; the walk is the
same, because the kinds only TypeScript has never appear in a JavaScript tree. React frontends keep shared code in `.ts`
and the components that use it in `.tsx`, so most imports and calls cross from one grammar to the other: building the
three as separate graphs severed 34% of the resolved import edges on the frontends this was built against.

**A function bound to a name owns the calls in its body; an anonymous callback does not.** An arrow in a `const`, a
function wrapped in `memo`, `forwardRef`, `useCallback`, `useMemo`, `observer` or `debounce`, an object property, a
class field and an anonymous default export each become a function symbol with a call scope. Without the scope every
call in an arrow body belongs to the file, and a caller query dead-ends on exactly the components and handlers a review
is about. An inline JSX prop arrow opens no scope: it has no name to address, so its calls belong to the component
around it, which is the consumer a reviewer asks about.

**A test registration is the one callback that opens a scope.** A test file is built from registrations — `describe`,
`it` and `test` with their `x` and `f` forms, `suite` and `bench`, each bare or behind a `.skip`, `.only`, `.todo`,
`.concurrent`, `.sequential` or `.failing` modifier — whose bodies bind no name, so without a scope it declares no
symbol, its calls are calls from file scope that the graph keeps only as names (ADR 3.23), and no test is their
caller. The description names the symbol, flat rather than qualified by the enclosing `describe`, the way object keys
stay flat; a lifecycle hook is named for itself. A description that is not a plain string — a template
literal, a variable — names nothing, and a shape outside that list, such as the table form `it.each(rows)(...)`, is no
registration the walk recognises; either way the body stays with the enclosing registration. A call named `describe`
in a production file still opens its scope, but the file's own name decides whether the symbol is test code.

**A receiver the file declares as a value names no type.** An owner is a class, an interface or a namespace, so a call
`x.f()` on a parameter, a `let`, `const` or `var`, a destructured name, a catch binding, a loop variable, a function
declared inside a function body or the name of a function expression inside it records the empty receiver inside the
scope that declares it; an import binding, a class, a namespace, a class declared in a nearer scope and a function at
module or namespace level, which TypeScript merges with a namespace of its name, keep their name, and a call on `this`
names the class around the method. On the TypeScript and JavaScript of the game-engine tree, the receiver tier bound
1,245 calls, 220 of them through such a value, mostly in minified bundles where a one-letter variable shares a
one-letter class name, and all 86 that it bound into another directory, a `t.toString()` in a script to the `toString`
of a minified class `t` in a vendored bundle among them; 1,025 remain, all of them in the caller's directory and every
one sampled a call on `this` or on a class or a namespace by name. The walk reads once, so a name declared below its
first use, a module-level `const` under the function that calls it, keeps its name, and a `var` is held to its block, so
a call after the block keeps the name too: a miss, never a wrong empty receiver. The walk holds each declared name while
the function, block, catch clause, loop or `switch` that declares it is open, and the name that one shadows; extracting
the 2,075 TypeScript and JavaScript files of a monorepo on one thread takes a median of 561 ms against 545 ms before,
inside the spread of 514 to 564 ms between runs, at the same peak footprint.

**Some of the language is not modelled.** Export assignments, `module.exports = …` and `exports.f = …`, are ordinary
assignments to the walk, so a CommonJS module has no export surface and a function that exists only on the right side of
one has no symbol. No symbol is an entry point: a program's entry is a bundler's or a `package.json`'s notion, and it
names a file, not a symbol. A type-only import or re-export is an include like any other, because a type dependency is a
real dependency to the blast radius of a change.

**A file is test or generated code by its name or its banner.** A `.test.` or `.spec.` name, or a `__tests__` or
`tests` directory, is test code, as Jest, Vitest and Mocha find tests; a directory named `test` is not, because it is a
common name for a feature or a command. A `@generated` or `DO NOT EDIT` banner in the comments before the first code is
generated code, but only outside a backtick span, where documentation of the convention quotes it. The scan starts
after a UTF-8 byte order mark, which until 2026-10-19 hid the banner behind it; no file's flag changes on the
game-engine tree, the Go monorepo or the Go module cache. A `.gen.`,
`.generated.`, `_pb`, `.pb` or `.min` name is generated too: a minified bundle is machine output, and four committed
vendor bundles carried about 10% of the symbols on the frontends this was built against. A `-min.js` name is not
matched, because no such file was found and hand-written names end in `-min`, and a `.d.ts` file is not generated,
because such files are commonly written by hand.

**Imports resolve the way the compiler and the bundlers resolve them, from the repository's own configuration.** The
resolver reads every `tsconfig.json` and `package.json` outside `node_modules` and `vendor` directories when it is built
— vendored ones belong to third-party packages, and a checkout can hold thousands — and a `tsconfig*.json` only when one
of those extends or references it, which is the only way such a variant takes part. A relative specifier probes the
script extensions, declaration files and `index` files, and on a miss the TypeScript source an ESM `./m.js` stands for.
The nearest `tsconfig.json` alone governs a file's `paths`, one that yields none included, after one `extends` hop
whose fields the child replaces whole, a path the base supplies staying relative to the base; a config that declares no
`paths` but references sibling configs in its own directory takes theirs, as the current Vite scaffold splits them, and
a reference into a subdirectory is that subproject's. A `#` specifier takes the `imports` of the nearest
`package.json`, which stops the lookup whether it declares any or not. A specifier that names a package of the
repository takes its `exports` — an object whose keys are conditions being the target of `.` — conditions tried source
first; failing those, the package's bare name takes its `module` or `main` and then its directory, and a subpath the
file under the package's directory. Where Node rejects a bare import of a package whose `exports` omits `.`, the
resolver falls through to `main`, because that is the module most bundler setups load, and an include edge is worth
more than strictness here. A monorepo of independent frontends can declare one package name twice, so the longest name
that prefixes the specifier wins, then the package nearest the importing file, and two equally near resolve to neither:
a missing edge is better than one no bundler would make. A Vite `?query` is stripped only after the specifier misses
as written, so a file whose name holds a `?` still resolves.

**A re-export names the file its specifier resolves to, by the same rules.** The graph used to match a re-export's
specifier against the files the re-exporting file includes, by stem, by path segment or by appending `.ts` or `.tsx`:
it could not see an ESM `.js` specifier, an alias, an `index.tsx` barrel or a package, and it knew a language's
extensions. The resolver resolves a re-export together with the import of its statement, so it costs no second
resolution.

**The fingerprint covers the walk and the grammar.** A build script digests the crate's sources; at run time the
fingerprint takes in the crate's name and version, that digest, and its grammar's declared version, node types, ABI
version and counts of node kinds, parse states and fields. The three languages differ in their grammars, so the
language's name adds nothing to tell them apart. A change in `kartta-lang` is covered by
`kartta_lang::FINGERPRINT`, which a cache keys beside it. It cannot see a change in the tree-sitter runtime, or in a
grammar that keeps all of those equal: a maintainer who updates either bumps the crate's version, which the fingerprint
takes in.

**Revised 2026-10-22: the family reads its configuration once.** Each of the three languages built its own resolver, so
a build read every `tsconfig.json` and `package.json` three times and held three copies of what it read while it
resolved, and a followed engine kept and compared three. The engine builds one resolver for a family, from the first of
its languages (ADR 3.1), and the three build the same one, so the family's files resolve through it and a refresh that
reaches the configuration reads it once and names `jsts` (ADR 3.33). Built alone over an index and timed nine times
each, under a load average of 30 on an 18-core macOS machine, the configuration took p50 0.83 against 2.49 ms on the
game-engine tree, reading 16 files against 48; 3.45 against 11.23 ms on the Go monorepo snapshot, 73 against 219; and
9.45 against 19.17 ms on 16 copies of the game-engine tree, 256 against 768, where the family's resolvers held 76 KiB
against 229 KiB. A build's live Rust heap peaks at the same 750 MiB on the game-engine tree, inert and 785 MiB with
stamps, within 0.7 MiB between runs either way, and a build with stamps keeps 10 KiB less. The build's time and peak
footprint moved within the spread between runs on all three trees, the two binaries alternating, six rounds each and
eight on the game-engine tree, where the medians were 14.93 against 14.15 s cold, with `main`'s runs spanning 11.78 to
23.70 s, and 3.52 against 3.54 s warm at a peak footprint of 894 against 913 MiB. On the snapshot they were 3.91
against 4.15 s cold, and on the copies 242 against 232 s cold, `main`'s runs spanning 190 to 242 s, and 95.6 against
96.2 s warm at 9,609 against 10,120 MiB. No JavaScript and TypeScript monorepo of the size below is on the machine this
was measured on.

**Revised 2026-10-23: a namespace owns the variables it declares.** A `const`, `let` or `var` in a `namespace` or a
`declare module` block was a symbol with no owner, while a function, a class or an enum beside it was the namespace's
member, so `Ns.limit` selected nothing and `Ns.make()` of an arrow bound only by its name. Such a variable is the
namespace's member now, a class with no name that it binds takes its qualified name as its methods' owner, and a class's
static block, which is a body, owns nothing, as a function's body does not. On the Go monorepo snapshot 16 constants of
9 wildcard module declarations, `declare module "*.svg" { const content: string }`, take their module as their owner,
on the TS/JS of two more frontends 3, and no other symbol, call or use moves on the six trees measured.

**Revised 2026-10-23: a member call through a package import binds nothing in the repository.** A name imported from a
package told the graph nothing, so a member call through it fell to the tiers that bind by name: `<Dialog.Footer>` with
`Dialog` from `@chakra-ui/react` bound the snapshot's own `Footer` at a guess, `<Field.Root>` the `Root` of a file the
caller imports, `<Menu.Content>` a `Content` the caller's file declares, and `path.extname()` an `extname` of a minified
bundle. Each name an `import` of a bare specifier binds, where the specifier resolves to no file, is an import binding
outside the repository (`ImportBinding` with no target), which the graph answers as a call into an external import.
The calls dropped are 86 of the snapshot's 11,855 caller-callee pairs, 31 of 22,166 on SillyTavern and 29 of 4,821 on
a TypeScript monorepo of 1,134 scripts; each of the 146 runs through a package's name, `@chakra-ui/react` 112 times and
a `node:` builtin 26, and each bound a repository definition that only shares the member's name: none was right. No
pair is added, and the snapshot counts 2,763 of its 44,934 call sites as external imports, of which 130 bound, 1,745
counted as undefined, 657 as ambiguous and 231 as not admitted. Binding the names of every specifier that resolves to
no file dropped 5 more pairs on SillyTavern, 3 of them right, `MacrosParser.registerMacro` through
`'/scripts/macros.js'`, a path a web server roots at `public/`: a specifier that starts with `.`, `/` or `#` names a
file of the repository even where none resolves, so it binds nothing. The reference engine keeps every pair the
snapshot drops. The walk
keeps the names of a bare import on its directive, 9,030 names on the snapshot, and the build cost moves within the
noise: on the snapshot under 8 threads and a load average of 10 to 14, the cold build took a median 3.59 against
3.66 s over six alternating rounds, peaking at 441 against 466 MiB, and the warm one 0.89 against 0.88 s over eight,
at 355 against 369 MiB.

## What it costs

On a monorepo checkout of 374,827 files, of which 172,660 are scripts holding 1.51 GB with their `node_modules`, one
thread on macOS extracts the scripts in 74.5 s and resolves them in 0.45 s, and the three resolvers read the
configuration in 0.11 s together, each reading all of it for its own; the family reads it once since 2026-10-22. The
files
yield 5.95 million symbols, 6.52 million calls, 352,630 includes and 236,018 imports kept as written; 118,642 of the
166,762 re-exports name a file, each at the cost of a copy of its path.

## Considered Options

- **A family per grammar** — severs the imports between `.ts` and `.tsx` files, a third of a frontend's edges.
- **The graph matching re-exports to includes** — the graph would keep a language's extension rules, against ADR 3.1,
  and keep guessing where the language knows.
- **Resolving each re-export on its own** — one more resolution per re-exported name, where a statement re-exporting
  many names resolves the same specifier once.
- **Reading every `tsconfig*.json` up front** — a repository finds files by their exact name, and a variant matters only
  as the target of a config that names it.
- **Modelling CommonJS exports** — a function assigned to `exports` would gain a symbol, at the cost of an arm for every
  assignment shape; nothing that consumes the graph has asked for it.
- **Node's strict `exports`** — drops the include edge of a package whose `main` is what its bundler loads.

Revisit when a consumer needs the export surface of CommonJS modules.
