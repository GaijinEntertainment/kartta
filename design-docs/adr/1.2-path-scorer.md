# Own the path scorer

- **Date:** 2026-08-11
- **Governs:** `crates/kartta-fuzz`, `kartta_fuzz::Ranking`
- **Pinned by:** `crates/kartta-fuzz/tests/ranking.rs` (`basename_hit_outranks_directory_hit`,
  `a_basename_hit_outranks_a_directory_hit_across_case`)

Path search ranks candidates for a language model, so the ranking decides which files the model reads first, and the
maintained Rust matchers do not prefer a filename hit to a directory hit. kartta owns its scorer, `kartta-fuzz`, and
puts that preference inside the alignment; it pays in throughput, which a tool call does not feel.

## Decision

- **Basename bonus.** `kartta-fuzz` scores each candidate by an optimal alignment of each query term, and a match inside
  the basename, the last path segment, earns a bonus on every matched character, inside the alignment recurrence.
- **Fixed weights.** Its weights and separators are fixed constants
  ([ADR 1.51](/design-docs/adr/1.51-path-score-weights.md)).
- **No comparison.** The crate's docs, benchmark and tests name no other matcher and measure none; the docs say why a
  general matcher does not fit and point to this record. Its benchmark, `benches/rank.rs`, measures only its own
  regressions.

## Why

- A model that asks for `main` and is handed a directory first is the most common failure of repository path search,
  and the one behavior a path-aware scorer exists to prevent.
- Neither maintained matcher, `nucleo-matcher` 0.3.1 and `frizbee` 0.12.0, ranks a filename hit above a directory hit:
  for `main` over `main/lib.rs` and `src/main.rs`, nucleo scores both 109 and frizbee prefers the directory, 76 against
  68 (2026-08-11).
- The gap is structural. Both award boundary bonuses uniformly per delimiter, neither exposes a per-position hook, and
  both keep their scoring internals private, so a bonus that applies only inside the last segment cannot be configured
  or added short of a fork. Inside an owned recurrence it costs nothing.

## Consequences

- The scorer is slower than either matcher: over 473k synthetic repository paths, a scalar prototype answered a
  six-character query matching 108k of them in about 62 ms, where nucleo took 19 ms and frizbee 8 ms (2026-08-11).
  Tens of milliseconds sit inside a tool call's round trip; accepted while no interactive picker consumes the crate.

## Rejected

- **Adopt `nucleo-matcher`** — ties a filename hit with a directory hit and an exact basename with a directory of the
  same name, and its MPL-2.0 licence turns a technical choice into a licence-policy decision.
- **Adopt `frizbee`** — fastest and dependency-free, but prefers the directory hit, ties a camelCase hump with a flat
  match under its default case handling, brings about 600 lines of unsafe SIMD over four backends into a crate exported
  through a Go binding and a Node addon, and scores in `u16`, which panics on a pattern longer than 10922 characters
  where a saturating `i32` degrades.
- **Adopt either and recover the basename preference around it** — two matcher calls per candidate, path and basename,
  and a weighting with nothing to tune it against; the option to take if throughput starts to bind.
- **Fork one and add a per-position bonus** — the scoring internals are private in both, so this is a fork to
  maintain, not a dependency to track.
- **Hide a matcher behind a trait so the engine stays swappable** — one implementation behind an interface is
  indirection; borrowed `&str` in and positions out already make a later swap non-breaking.
- **A generic string-distance crate** — no alignment model and no path awareness; the most-downloaded candidate was last
  released in 2020.

## Revisit if

An interactive consumer appears and tens of milliseconds begin to bind, or either matcher grows a per-position or
per-segment scoring hook. High confidence: every consumer today answers a language model.
