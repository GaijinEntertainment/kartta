A content index of a large tree is gigabytes, and a build node may be short of memory. The caller chooses whether the
index and the build's spill live in the heap or in scratch files read by position or mapped. A file-backed index then
costs disk room and reads, and a directory that fails costs the index alone.

## Decision

- **Three storages.** `ContentIndexStorage::Memory` holds the index and the build's spill in the heap. `File` and
  `Mapped` keep both in scratch files under a directory the caller names, read by position or mapped, so a build short
  of memory holds neither beyond the pages in use.
- **Written by position.** The build writes the index by position, never through a writable mapping.
- **Private scratch files.** A scratch file is private to the process and leaves nothing behind however the process
  ends. On Linux it is created with no name where the filesystem allows. Elsewhere on unix it is unlinked the moment it
  is created, the one moment a process of the same user could open it. On Windows it is opened delete-on-close with no
  sharing.
- **A failed scratch file in a build.** A build that cannot create, write or map a scratch file collects
  `BuildError::ContentIndex` naming the directory and hands back everything else it made, file index and graphs
  included. The index then answers as one built without a content index, so grep opens every candidate.
- **The reason stays.** `Index::content_index_failure` keeps the failure's text for the index's life. The wire's stats
  answer it as `content_index_failure` and the MCP `<index>` as `grep_index`, because the collected failure goes when a
  refresh of the whole tree replaces it, and a list capped per answer can leave it out.
- **Only a build tries again.** A refresh does not rebuild a content index the build gave up, so the failure's reason
  holds until the next build, which is how a caller retries.
- **A failed scratch file in a refresh.** A refresh returns `BuildError::ContentIndex` and leaves the index, its content
  index included, answering as it did.

## Why

- A writable mapping keeps every page it wrote in the process's resident set: 6.5 GB against 3.6 GB on the 3.08M-entry
  data volume (2026-10-15, #20). On a full filesystem it kills the process with SIGBUS, where a write returns an error.
- A content index only narrows grep, which finds the same lines without it, so its loss must not cost what it serves: a
  returned failure lost the file index and every graph of a finished walk, and the handle answered `not_built` (#1029).
- A refresh that carries a file over does not read it, so it holds no trigrams to retry with, and reading every file
  again is a build's cost hidden in a refresh.
- In memory, the build holds its spill beside the index it writes, so it peaks at about twice the index: 5.8 GB on the
  data volume, where file and mapped builds peaked at 640 MB of footprint (2026-10-15, #20).

## Consequences

- The directory needs room for about twice the index while the build runs, and once the index when it is done.
  Accepted.
- File storage pays a read per list a search reads. Accepted.
- On unix outside Linux, a process of the same user can open a scratch file in the moment between its creation and its
  unlink. Accepted.
- A failure during the walk still surfaces at its end, so the build reads and scans the remaining files for an index it
  will drop. Accepted: only a failed build pays it.
- A caller that needs the index must read the failure, because the build answers success. Accepted.
- A build gives no count of what the lost index would have held: a failure before the walk reads nothing to count, and
  the answer's `entries` bounds what a grep reads. Accepted.

## Rejected

- **Return the failure and let the caller build again without the index** — a second walk and every extraction again,
  for a graph the first build had finished.
- **Answer a new wire code** — the answer holds a working engine, so `ok` with the reason is what the caller can act on.
- **Report the failure again on every refresh** — refreshed failures go to the end of the stored list, past its cap on
  a tree with many unreadable files.
- **Write the index through a writable mapping** — no write buffer, and every page written stays resident until the
  build ends, and a full filesystem kills the process.
- **Map the spill once per partition** — Linux counts a page once for each mapping that holds it: the checkout peaked at
  795–825 MiB against 230–235 MiB.
- **Read a partition's runs into the heap** — the data volume's footprint grew from 0.6 GB to 2.3 GB.
- **Advise the system to drop a partition's spill pages once merged** — no effect on macOS, and 233–236 MiB against
  230–235 MiB on Linux.

## Revisit if

A platform offers a write path that keeps written pages out of the resident set and reports a full disk as an error.
High confidence: no mapping does on macOS or Linux.

A consumer needs the content index badly enough that a build without it is worthless to it. Medium confidence: Kensai
treats its loss as never fatal, and the failure stays readable for one that does.
