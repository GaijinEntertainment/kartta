# Keep the content index in memory, a scratch file or a mapping

- **Status:** accepted
- **Date:** 2026-10-14
- **Updated:** 2026-10-14
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/content_index/storage.rs`, `ContentIndexStorage`, `BuildError::ContentIndex`
- **Pinned by:** `crates/kartta-fs/tests/grep.rs` (`an_index_kept_in_a_file_or_a_mapping_answers_as_one_in_memory_does`,
  `a_scratch_directory_that_does_not_exist_fails_the_build_naming_it`), `crates/kartta-fs/src/content_index.rs`
  (`every_storage_holds_the_index_memory_holds`, `a_scratch_file_leaves_no_name_behind`)

A content index of a large tree is gigabytes, and a build node may be short of memory. The caller chooses whether the
index and the build's spill live in the heap or in scratch files read by position or mapped. A file-backed index then
costs disk room and reads.

## Decision

- `ContentIndexStorage::Memory` holds the index and the build's spill in the heap. `File` and `Mapped` keep both in
  scratch files under a directory the caller names, read by position or mapped, so a build short of memory holds
  neither beyond the pages in use.
- The build writes the index by position, never through a writable mapping.
- A scratch file is private to the process and leaves nothing behind however the process ends. On Linux it is created
  with no name where the filesystem allows. Elsewhere on unix it is unlinked the moment it is created, the one moment a
  process of the same user could open it. On Windows it is opened delete-on-close with no sharing.
- A build that cannot create, write or map a scratch file returns `BuildError::ContentIndex` naming the directory.

## Why

- A writable mapping keeps every page it wrote in the process's resident set: 6.5 GB against 3.6 GB on the 3.08M-entry
  data volume (2026-10-15). On a full filesystem it kills the process with SIGBUS, where a write returns an error.
- The build was asked for an index it cannot hand back, so the failure is returned, not collected.
- In memory, the build holds its spill beside the index it writes, so it peaks at about twice the index: 5.8 GB on the
  data volume, where file and mapped builds peaked at 640 MB of footprint (2026-10-15).

## Consequences

- The directory needs room for about twice the index while the build runs, and once the index when it is done.
  Accepted.
- File storage pays a read per list a search reads. Accepted.
- On unix outside Linux, a process of the same user can open a scratch file in the moment between its creation and its
  unlink. Accepted.

## Rejected

- **Write the index through a writable mapping** — no write buffer, and every page written stays resident until the
  build ends, and a full filesystem kills the process.
- **Map the spill once per partition** — Linux counts a page once for each mapping that holds it: the checkout peaked at
  795–825 MiB against 230–235 MiB.
- **Read a partition's runs into the heap** — the data volume's footprint grew from 0.6 GB to 2.3 GB.
- **Advise the system to drop a partition's spill pages once merged** — no effect on macOS, and 233–236 MiB against
  230–235 MiB on Linux.

## Revisit if

A platform offers a write path that keeps written pages out of the resident set and reports a full disk as an error.
High confidence: no mapping does on macOS or Linux.
