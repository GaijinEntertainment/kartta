# Watch the macOS data volume through its firmlinks in one stream

- **Status:** accepted
- **Date:** 2026-10-15
- **Updated:** 2026-10-21
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/watch.rs` (`event_prefixes`, `through_firmlinks`, `relative`),
  `crates/kartta-fs/src/watch/notified.rs` (`Backend::start`)
- **Pinned by:** the firmlink tests of `crates/kartta-fs/src/watch.rs` and `crates/kartta-fs/src/watch/notified.rs`,
  `a_root_spelled_through_the_data_volume_is_watched_by_its_firmlinked_path` in `crates/kartta-fs/tests/watch.rs`

`FSEvents` names a change on the data volume by its firmlinked path, `/Users/...` rather than
`/System/Volumes/Data/Users/...`, and a stream on the data-volume spelling of a root hears nothing. The macOS watcher of
[ADR 1.17](/design-docs/adr/1.17-change-notifications.md) watches the paths the events are named by, all
in one stream; the trade is a dropped-events notice above one firmlink that loses the whole tree.

## Decision

- The root is made canonical, and its paths are read from `/usr/share/firmlinks`. A root inside a firmlink is watched
  by its firmlinked path. A root that holds firmlinks, such as the data volume itself, is watched through its own path
  and each firmlink below it that exists on the machine; a firmlink the list names and the machine lacks is skipped. A
  root off the data volume is watched as it is.
- Every path goes into one notify `update_paths` call, so one stream starts over all of them.
- An event's path is named from the watched path that leaves the fewest components below it, the firmlink's part of
  the tree prefixed to what is below it; an event below none of the watched paths is outside the tree.

## Why

- notify's `FSEvents` backend stops the stream and starts a new one over every path so far for each `watch` call that
  adds a path no watched path covers, so the data volume, watched through its own spelling and 18 firmlinks, built 19
  streams to keep the last; one call starts one, in a median of 6.2 ms on the data volume against 35.7 ms
  (2026-10-21).
- `FSEvents` refuses a path that does not exist, and the list names firmlinks a machine may not have, such as
  `/AppleInternal`.

## Consequences

- A rescan `FSEvents` names above one firmlink alone, such as `/usr` above `/usr/local`, loses the whole tree, as
  ADR 1.17 states. Accepted.

## Rejected

- **One `FSEvents` stream on `/`, which covers every firmlink and the data volume's own spelling** — saves 2.4 ms and
  0.6 MiB once a start, but needs a path for the stream beside the paths the events are named by, and the stream then
  covers every path outside the tree, where a rescan `FSEvents` names loses the batch.
- **One `watch` call a path** — restarts the stream for each path after the first.

## Revisit if

notify adds the paths of one `watch` call to a running stream without restarting it, or macOS names data-volume events
by their data-volume path. Low confidence in either.
