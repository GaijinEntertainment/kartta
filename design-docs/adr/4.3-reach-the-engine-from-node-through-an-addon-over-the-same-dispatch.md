# Reach the engine from Node through an addon over the same dispatch

- **Status:** accepted
- **Date:** 2026-10-18
- **Updated:** 2026-10-22
- **Initiative:** `04-consumer-surfaces`
- **Governs:** `crates/kartta-node/src/lib.rs`, `bindings/node/src/kartta.ts`, `bindings/node/src/wire.ts`
- **Pinned by:** `bindings/node/test/kartta.test.ts`, `bindings/node/test/golden.test.ts`

Node consumers need the engine without a second wire to keep. A napi-rs addon calls `kartta-ffi`'s dispatch through
its rlib and translates nothing, and the npm package `kartta` types the wire and owns the JavaScript side of each call's
life; the trade is a native addon per platform and a thread or a pool slot per call in flight.

## Decision

**The addon.** `crates/kartta-node` is a `cdylib` with `publish = false`, shipped inside the npm package. The method
table, the error codes and the wire stay in `kartta-ffi` ([ADR 4.2](./4.2-reach-the-engine-through-one-json-call.md)).
It exports `open` and a handle with `build`, `refresh`, `call`, `cancel` and `close`; each but `close` takes the wire's
params as a JSON string, and each of `build`, `refresh`, `call` and `cancel` answers the wire's envelope as the
dispatch's bytes in a `Buffer`, which the package decodes as it parses.

- `build` and `refresh` each run on a thread of their own, named `kartta-<method>`, and settle a promise.
- `call`, which answers every other wire method, runs on libuv's pool as a napi `AsyncTask`; neither a query nor a
  grep holds the event loop.
- `cancel` answers at once on the calling thread, so a cancel is never queued behind the work it stops.
- `open` answers the handle, or the wire's `{code, message}` error object, never a napi error, whose code would be
  napi's status rather than the wire's.
- `close` drops the handle's engine. A call in flight holds its own reference and answers first, and the engine goes
  with the last of them; a handle the garbage collector takes frees its engine the same way. The engine's going ends
  the watch of a build that asked for one
  ([ADR 4.33](./4.33-follow-the-tree-over-the-wire-only-when-a-build-asks.md)), whose thread lets its watcher go
  within about a second.
- A panic answers `internal`: `Kartta::call` catches it, so the addon carries no guard of its own.

**The package.** `bindings/node` answers one typed call per wire method, named in camelCase, its params and answer
spelled field for field as the wire spells them, the shape the Go binding reads.

- `call(method, params)` reaches the wire untyped. It runs `build`, `grep` and `refresh` as the typed calls do, and
  `cancel` at once.
- A failure rejects with a `KarttaError` carrying the wire's code, or `closed`, the binding's own, for a call on a
  closed handle.
- Each call's params are serialized with `JSON.stringify`, and each answer decoded and parsed with `JSON.parse`, on
  the event loop, the only steps that run there.
- The wire types are held to the golden files of `kartta-ffi` at compile time: the type check fails, naming the field,
  when a golden answer or params hold a field the type does not name, and when a golden answer is not of its type. The
  tests replay every golden file through its typed call and compare the answer exactly but a `score`, which agrees
  within a relative 1e-12 of the pinned one, and check that the typed calls cover the methods `version` lists.

[ADR 4.42](./4.42-stop-a-node-call-by-a-binding-id-its-handle-gives-it.md) states how a signal and `close` stop a
build, a grep or a refresh. [ADR 4.40](./4.40-ship-the-node-addon-as-one-npm-package-per-target.md) states the targets
and how the package ships them, and
[ADR 4.41](./4.41-check-the-node-package-with-the-vite-plus-that-its-lockfile-pins.md) the toolchain.

## Why

- A walk of three million entries takes tens of seconds, and libuv's pool has four threads that every `fs` call of the
  process shares, so a build or a refresh on the pool would stall the process's file I/O.
- Spelling the wire as it is keeps one shape across bindings; renaming every field would copy every answer and part
  the types from the golden files.
- Search scores pass through `ln_1p`, which Apple's libm and glibc round apart in the last bits.

## Consequences

- The event loop pays to serialize the params and parse the answer, by what the answer weighs: kilobytes for a capped
  answer, more for a grep or a listing whose cap the caller lifted. Accepted.

## Rejected

- **koffi over the C ABI** — no Rust for Node, but a third party's native addon in the process, hand-written types, and
  every answer freed by hand.
- **`node:ffi`** — experimental, absent from Node 24, and synchronous only.
- **Builds or refreshes on libuv's pool** — each holds a pool thread for its whole walk, a whole refresh for seconds on
  a large tree, and four of them stall the process's file I/O and every cancel queued behind them.

## Revisit if

Node gains a stable, asynchronous FFI that can call the C ABI without an addon. Medium confidence that none comes
soon: `node:ffi` is still experimental.
