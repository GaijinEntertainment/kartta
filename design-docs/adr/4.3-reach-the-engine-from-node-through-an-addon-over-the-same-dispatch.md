# Reach the engine from Node through an addon over the same dispatch

- **Status:** accepted
- **Date:** 2026-10-18
- **Initiative:** `04-consumer-surfaces`

Node consumers reach the engine through a napi-rs addon that calls `kartta-ffi`'s dispatch directly, through its rlib
(ADR 4.2): the method table, the error codes and the wire stay in that crate, and the addon translates nothing. The
npm package `kartta` in `bindings/node` types the wire in TypeScript and owns the JavaScript side of the lifecycle:
the build ids, the signal, and closing.

## The addon

`crates/kartta-node` is a `cdylib`, `publish = false`: npm is its channel. It answers four calls, each taking the
wire's params as a JSON string and answering the wire's envelope as the dispatch's bytes in a `Buffer`, which the
package decodes as it parses.

- **`build` runs on a thread of its own** and settles a promise. A walk of three million entries takes tens of seconds,
  and libuv's pool has four threads that every `fs` call of the process shares.
- **Every other method runs on libuv's pool,** as a napi `AsyncTask`. A query is short, but a grep over the whole tree
  is not, and neither holds the event loop.
- **`cancel` answers at once on the calling thread,** so a cancel is never queued behind the work it stops.
- **`open` answers the handle or the wire's error object,** never a napi error, whose code would be napi's status rather
  than the wire's.
- **`close` drops the handle's engine;** a call in flight holds its own reference and returns first, and the engine
  goes with the last of them. A handle the garbage collector takes frees its engine the same way.
- **A panic answers `internal`:** `Kartta::call` catches it itself, so the addon carries no guard of its own.

## The package

- **One typed call per wire method,** named in camelCase, its params and answer spelled field for field as the wire
  spells them, the shape the Go binding reads. Renaming every field would copy every answer and part the types from
  the golden files. `call(method, params)` reaches the wire untyped; it runs `build` as the typed call does, under an
  id the handle picks in place of one the params give, so no two builds share an id, and `cancel` at once.
- **Failures reject with a `KarttaError`** carrying the wire's code, or `closed`, the binding's own, for a call on a
  closed handle.
- **`build(options, { signal })`** gives each build an id; an abort cancels that id, so it stops the build waiting or
  running, and the rejection carries the signal's reason as its cause. A signal aborted before the call rejects with
  its reason and leaves the handle as it was, as a done context does in the Go binding.
- **`close` cancels each build in flight by its id,** which the library remembers for a build that has not entered,
  then every build that has, then drops the handle. A build it cancels rejects with `build_cancelled`, a `closed` error
  its cause.
- **The wire types are checked against the golden files at compile time:** the type check fails, naming the field,
  when a golden answer or params hold a field the type does not name, and when a golden answer is not of its type. The
  tests replay every golden file through its typed call and compare the answer exactly, and check that the typed calls
  cover the methods `version` lists.
- **Each answer is decoded and parsed on the event loop** with `JSON.parse`, the only step that runs there. Its cost
  follows the answer's size: kilobytes for a capped answer, more for a grep or a listing whose cap the caller lifted.

## Platforms and distribution

The addon ships for macOS on arm64 and for Linux with glibc on x64 and arm64, each built and tested in CI on its own
runner. N-API is stable across Node majors, so one build per target serves every Node the package supports.

- **One package per target,** `kartta-<target>` with `os`, `cpu` and `libc` set, holding `kartta.<target>.node`: the
  naming napi-rs's tooling uses. Their manifests are committed under `bindings/node/npm`. The package loads the file a
  checkout builds beside it, then the target's package. A release adds the targets' packages to the package's
  `optionalDependencies` at its own version and publishes each; nothing is published yet.
- **Left out:** Windows, which no consumer asks for and which nothing here tests; and Linux with musl, whose Rust
  target links the C runtime statically and builds no shared library until told not to.
- **Node:** `engines` asks for 24 or later; CI runs the version `.nvmrc` pins, which runs the tests' TypeScript without
  a build step.
- **Pinning:** napi, napi-derive and napi-build resolve through `Cargo.lock`; `typescript` and `@types/node` are exact
  in `package.json`, with the lockfile committed and installed with `npm ci --ignore-scripts`. `npm run build` is a
  script of forty lines over `cargo build`; `@napi-rs/cli` would bring its own tree, a GitHub client and cross
  toolchains among it, for the same file copy.

## Considered Options

- **koffi over the C ABI** — no Rust for Node, but a third party's native addon in the process, hand-written types, and
  every answer freed by hand.
- **`node:ffi`** — experimental, absent from Node 24, and synchronous only.
- **The signal handled in the addon** — napi's `AsyncTask::with_signal` only drops a task that has not started; the
  build's id, cancelled from JavaScript, stops one running or waiting alike.
- **Builds on libuv's pool** — a build holds a pool thread for its whole walk, and four of them stall the process's file
  I/O and every cancel queued behind them.
- **`@napi-rs/cli` with its generated loader** — a loader for every platform napi-rs knows, regenerated on each build,
  where the package loads three targets in a dozen lines.
