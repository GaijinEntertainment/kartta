# Find a daslang module by its file name

- **Date:** 2026-10-16
- **Governs:** `crates/kartta-lang-daslang/src/resolve.rs` (`target`), `crates/kartta-lang-daslang/src/walk.rs`
  (`require`, `include`)
- **Pinned by:** `crates/kartta-lang-daslang/tests/resolve.rs`

The compiler binds `require x` to the module that declares `module x`, wherever its module path puts it, and that path
is a compiler input no repository holds. The resolver reads the repository's file names as the module index, because a
module almost always declares its own file stem, so no pass over every file builds one; a module whose clause differs
from its stem is missed. What a qualifier or an alias binds through the file found is the rule of
[ADR 3.195](/design-docs/adr/3.195-daslang-module-qualifiers.md).

## Decision

- **Directives.** A `require` and an `include` resolve by one lookup, which parts them only on a relative specifier. A
  directive that names a file is an include of it; one that names no file is an import, kept as written, so a dependency
  on a builtin module, a native binding or a generated stub stays visible.
- **The specifier.** A `require` takes its `name` field; the guard of `require ?guard target` is no part of it. An
  `include` takes its file name as the compiler's lexer does: the run of non-blank characters after the keyword, so a
  quoted name keeps its quotes and names no file.
- **The lookup.** The resolver reads `\` as `/` and tries, in order, stopping at the first that names a file:
  - an `include` that starts with `./` or `../`, or a `require` that also ends in `.das` or `.das_project`: that path
    from the importer's directory, as written;
  - any other `require` that starts with `./` or `../`: a module name, so its dots read as slashes, which leaves `.` and
    `..` empty components: `../x` and `./x` both name the `x.das` beside the importer, and nothing else;
  - any other specifier: its dots read as slashes, under each directory of the importer from the nearest to the root,
    the first of them the compiler's default lookup (`src/simulate/debug_info.cpp:1016`); then the one file anywhere
    whose path ends with it at a directory boundary; then the one file whose path ends with it below its first
    component, which the compiler reads as a mount point; then the one file named for its last component, since a
    dotted specifier is a path through the module namespace, which need not follow the directories.

  An explicit `.das` is not doubled, and every step but the first reads only `.das` files, as the compiler's module
  path does.
- **Two candidates.** A step that two files could satisfy names neither.
- **Case.** Every match is case-sensitive, as the compiler's is. A specifier that matches a file only without case
  names a native module, which the compiler binds by its registered name and never through a file.

## Why

- The module path is set where the compiler runs, so the repository's file names are the one module index it holds:
  1,290 of 1,293 `module` clauses on the game-engine tree name their own file stem (2026-10-16, #36).
- The compiler's default lookup reads the importer's directory alone (`src/simulate/debug_info.cpp:1016`); everything
  else is `module_get`, a project's program (`src/simulate/fs_file_info.cpp:239`), or a mount it or a `.das_module`
  registers (`src/simulate/fs_file_info.cpp:303`). The bytes of a tree show what those answers have in common: a
  project root above the importer, as `require profile` in `enlisted/profileServer/actions/` reads, and a mount's name
  in the first component with the path below it kept, as `require llvm/daslib/llvm_tune` reads. With both, 159 more
  `require`s on the game-engine tree name a file, which adds 132 pairs and moves 3 up a tier, removing none, 30 of 30
  sampled right (2026-11-01, #845).
- The compiler takes an `include` as the importer's directory plus the name (`src/simulate/debug_info.cpp:993`), and a
  `require` as a path only where it both starts with `./` or `../` and ends in `.das` or `.das_project`
  (`src/simulate/fs_file_info.cpp:253`, `doc/source/reference/language/modules.rst`). Any other `require` reaches the
  default lookup, whose `getModuleFileName` turns every dot of `../x` into a slash, and the repeated slashes open the
  `x.das` beside the importer.
- A guess between two candidates binds a module to a namesake the compiler does not load for that importer.
- The compiler's lexer reads an `include` as a run of non-blank characters, so a quoted name is the name with its
  quotes.

## Consequences

- A module whose `module` clause differs from its file stem is found only where its path matches the specifier: 3 of
  1,293 clauses on that tree. Accepted.
- A `require` whose mount only a project's table tells apart stays unnamed, as two files end in `dm/dm_events` below
  `danetlibs.`: 39 of 26,161 `require`s on that tree, 10 of them the native `matching` beside two namesakes. Accepted
  (#845).
- The nearest ancestor reads no project, so where two ancestors hold a module it takes the nearer, which a project
  rooted at the other need not: no `require` on that tree. Accepted.
- A project's `module_get` answers a relative `require` before the default lookup and can read `../x` as the file above
  the importer, which the rule misses: no `require ../x` without its extension on that tree. Accepted (#853).

## Rejected

- **A module index from every file's `module` clause** — exact for the 3 clauses of 1,293 that differ from their stem,
  at the price of a pass over every file before any resolves.
- **Case-insensitive matching** — adds edges to files that the compiler never loads for the specifier.
- **The first of several candidates** — adds an edge that is wrong as often as the candidates are many.
- **`../x` as the `x.das` above the importer** — the spelling's plain reading, which the compiler's default lookup never
  opens; a `require` that means that file writes `../x.das` (#853).
- **The remaps of a `.das_project`** — a project overrides the default lookup through its `module_get` and `include_get`
  functions, which the compiler evaluates as daslang code, so which file a directive loads is decided by a program the
  engine does not run (#195, #845).

## Revisit if

A tree shows `module` clauses that differ from their file stems often enough to pay for a pass over every file, or the
engine can read what a project's `module_get` or `include_get` returns. Held with high confidence for the first on the
tree measured; the second is not planned.
