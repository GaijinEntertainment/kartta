The compiler binds `require x` to the module that declares `module x`, wherever its module path puts it, and that path
is a compiler input no repository holds. The resolver reads the repository's file names as the module index, because a
module almost always declares its own file stem, so no pass over every file builds one; a module whose clause differs
from its stem is missed.

## Decision

- **Directives.** A `require` and an `include` resolve by one lookup. A directive that names a file is an include
  of it; one that names no file is an import, kept as written, so a dependency on a builtin module, a native binding or
  a generated stub stays visible.
- **The specifier.** A `require` takes its `name` field; the guard of `require ?guard target` is no part of it. An
  `include` takes its file name as the compiler's lexer does: the run of non-blank characters after the keyword, so a
  quoted name keeps its quotes and names no file.
- **The lookup.** The resolver reads `\` as `/` and tries, in order, stopping at the first that names a file:
  - a specifier that starts with `./` or `../`: the path relative to the importer's directory;
  - a dotted or slashed specifier: its dots read as slashes, under each directory of the importer from the nearest to
    the root; then the one file anywhere whose path ends with it at a directory boundary; then the one file named for
    its last component, since a dotted specifier is a path through the module namespace, which need not follow the
    directories;
  - a bare name: the one file named for it.

  Each candidate takes `.das` where the specifier does not end in it, and an explicit `.das` is not doubled.
- **Two candidates.** A step that two files could satisfy names neither.
- **Case.** Every match is case-sensitive, as the compiler's is. A specifier that matches a file only without case
  names a native module, which the compiler binds by its registered name and never through a file.
- **Qualifiers.** A qualifier names the module its file declares by name, or a file with no `module` clause by its
  stem. A call `mod::f()` or a use `mod::f`, `@@mod::f` among them, in a file that directly includes, by `require` or
  `include`, a file declaring `module mod`, or `mod.das` with no clause, binds that file's definition of `f` outside
  every owner, at 95, ahead of the caller's own file. A call binds the same way through the one file that declares
  `module mod`, whoever requires it, and binds nothing where that file does not define `f`. A qualifier that
  names the file's own module binds as a bare name, as [ADR 3.173](/design-docs/adr/3.173-data-use-binding.md) states
  for a use. Any other qualifier leaves a call to the tiers below and a use unbound.
- **Aliases.** The alias of `require x as y` adds a name to the module, which keeps its own, as the compiler reads it.
  Where the `require` names a file, `y` binds as a qualifier of that file, by the rules above, whatever module the file
  declares, and a call whose name that file lacks binds nothing, whichever module shares the specifier's name. Where
  it names a module outside the repository, `y` binds as `x` does below, and a call through it binds a file that
  declares `x` by the Qualifiers rule. A `require` of two candidates binds no alias, as it binds no name.
- **Native modules.** A `require` that no file is named for names a module outside the repository, most often a native
  one, compiled into the runtime. It binds the specifier's last component outside the repository, so a call that
  qualifier writes is an external import and binds nothing, unless one file declares the module under another name. A
  `require` of two candidates does not bind it: its module is the graph's. An `include` never does: it pastes text and
  names no module.

## Why

- The module path is set where the compiler runs, so the repository's file names are the one module index it holds:
  1,290 of 1,293 `module` clauses on the game-engine tree name their own file stem (2026-10-16, #36).
- A guess between two candidates binds a module to a namesake the compiler does not load for that importer.
- The compiler's lexer reads an `include` as a run of non-blank characters, so a quoted name is the name with its
  quotes.
- A `require` binds no name in the graph, so a qualified call bound by its name alone, most often to a namesake in its
  own file, the wrapper that makes the call: 140 calls on the game-engine tree named another module and bound their own
  file. Each of the 240 calls the qualifier binds names the function the source calls, 104 of those 140 among them
  (2026-10-24, #472, #537).
- The compiler reads `mod::f` through `mod` and what `mod` requires publicly, so neither the caller's file nor a
  namesake elsewhere can answer it: 42 of the 44 pairs these rules remove called something else, and each of the 6 they
  add is the function the source calls, with no include closure computed (2026-10-31, #559).
- The compiler names a required file with no `module` clause for its `require`, whose last component is the file's
  stem under the default lookup, so a qualifier of that stem names the file: all 12 pairs that reading moves on that
  tree name the function the source calls (2026-10-31, #803).
- Two files can share a module name or declare none, as `event.das` and `sub/event.das` do on that tree, so an alias
  read as a module name reaches the wrong file: `require sub/event as sub_event` names one file, and only the file the
  `require` resolved to keeps them apart (2026-10-31, #802).

## Consequences

- A `require` of two candidates leaves its alias to the tiers below, where a namesake can bind it. Accepted (#802).
- A bare call of a `require` alias's name that its own file does not answer reads as outside the graph, as one of a
  native module's name does: no call on that tree. Accepted (#802).
- A module whose `module` clause differs from its file stem is found only where its path matches the specifier: 3 of
  1,293 clauses on that tree. Accepted.
- An `include` resolves by the module rule, not relative to the including file as the compiler's default does: where a
  bare name has files in two directories, the include names neither. Accepted (#195).
- A native module only another module's `require` reaches leaves no trace in the caller's file, so its qualifier goes
  to the tiers below and a namesake can bind it: no call on that tree binds its own file this way, and 19 pairs bind a
  wrapper in another file, `imgui::` through `imgui_boost` (#559).
- A native module that compiles a `.das` file into itself lies outside the graph with that file: 2 of the 44 pairs,
  `UnitTest::start_effect`. Accepted.
- A file with no `module` clause answers its qualifier only where the caller's own file requires or includes it, since
  no symbol declares its name: 41 sites on that tree write no `require` of it, 38 of them `ecs::`, a native module's
  name. Accepted.
- An `include` of a file with no `module` clause names its stem as a `require` does, since the graph keeps no directive
  kind, which would take a field on every include of every language: 6 `include`s on that tree, and no qualifier of
  their stems. Accepted.
- A definition a module's public `require` brings, or a macro generates, binds nothing through that module: 84 calls on
  that tree.

## Rejected

- **A module index from every file's `module` clause** — exact for the 3 clauses of 1,293 that differ from their stem,
  at the price of a pass over every file before any resolves.
- **Case-insensitive matching** — adds edges to files that the compiler never loads for the specifier.
- **The first of several candidates** — adds an edge that is wrong as often as the candidates are many.
- **An `include` relative to the including file and through the remaps of a `.das_project`** — a project overrides the
  default through its `include_get` function, which the compiler evaluates as daslang code, so which file an include
  loads is decided by a program the engine does not run (#195).
- **A qualifier read through every file the includes reach** — binds 7 more calls on that tree, at the price of each
  file's include closure, which a language with direct includes never computes otherwise; the declaring file answers
  the same qualifier with no closure.
- **Nothing for a qualifier two files declare** — turns away 40 pairs that are right, `log::` and `fs::` of tools that
  each carry their own, which proximity tells apart.
- **A `require` of a module the graph holds stored as an import binding** — reaches the qualifier through the binding
  tier, whose module rules are Rust's, visibility and macros included, and a use through a binding reads a directory's
  exports, not a file's.
- **An alias read as the module name it stands for** — binds `sub_event::fn_event()` to the wrong one of two files of
  one name, and binds nothing where a file declares no module.
- **Only what the module exports** — moves no call or use on that tree: code that compiles qualifies no definition a
  module keeps `private`.
- **Nothing for a name the required module lacks, where two files declare it** — moves no call on dagor or daScript:
  code that compiles reaches such a name only through what the module requires publicly, which the tiers below can
  bind.

## Revisit if

A tree shows `module` clauses that differ from their file stems often enough to pay for a pass over every file, or the
engine can read what a project's `include_get` returns. Held with high confidence for the first on the tree measured;
the second is not planned.
