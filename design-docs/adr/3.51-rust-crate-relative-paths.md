A path through the caller's own crate or module names a module file as a path into another crate does, but where it
starts depends on which crate root and module the caller's file belongs to. The resolver finds them from Cargo's layout,
and the walk keeps such a path only where it can tell the module the path is written in; a binding through one is an
import's, at 95.

## Decision

- The walk keeps a path through `crate::`, `self::` or `super::` by the rules of
  [ADR 3.50](/design-docs/adr/3.50-rust-cross-crate-paths.md): each name a `use`
  binds, the receiver of a path call, `crate::m::f()` for `m`, and, where the path ends at `crate`, `self` or `super`,
  the name it calls, `super::f()` for `f`, as a macro invocation keeps its macro's.
- A path call through `crate::` or `super::` that ends at a name the file declares at its top level, `super::new()`
  inside `fn new`, cannot keep that name, which is the file's own. It records the path's last keyword as its receiver
  and keeps the keyword with the path, `super` for `super`, so the call binds the item of the module the path names.
  `self::new()` names the file's own item, which the same-file tiers bind, and keeps nothing.
- Inside an inline module a path through `self::` or `super::` keeps nothing, and so does a `use` of one; a path through
  `crate::` is kept there.
- A `use` or a glob whose first segment is a module the file declares where the `use` is written starts at `self::`:
  `use m::helper;` beside `mod m;` keeps `self::m::helper`, and inside an inline module that declares the module it
  keeps nothing. A `use` keeps a name the file declares only as a module, `use parse::parse;` beside `mod parse;`, which
  Rust keeps apart from the function or type the `use` binds.
- A path call outside every inline module whose first segment is a module that a bodiless `mod NAME;` of the file's top
  level declares, without a `#[path]`, starts at `self::` too: `benchmark::run()` beside `mod benchmark;` keeps
  `self::benchmark`. A path call keeps the name of such a module wherever its path ends at it, `crate::benchmark` too.
  A path through an inline module keeps nothing and binds by the same-file tiers.
- `crate::` starts at the caller's crate root: the file itself where it is one (ADR 3.11), else the `main.rs` of the
  target directory under `src/bin/`, `examples/`, `tests/` or `benches/` it lies in, else the library whose directory
  holds it, else, below `src/`, the main binary. The library wins where both sit in one directory, and a library at its
  package's root, `[lib] path = "lib.rs"`, leaves the files under `src/` to the binary. A file of `tests/`, `examples/`
  or `benches/` outside a target directory, `tests/common/mod.rs`, starts none. The root must be in the tree.
- `self::` starts at the file's own module, so a crate root, the `[lib] path` file among them, starts it beside itself.
  Each `super::` starts at the module above: the crate root where the module's directory lies in the root's, else the
  file Cargo's layout names for the directory above, `NAME.rs` or `NAME/mod.rs`; past the crate root there is none.
- Each segment after the start walks the module files as ADR 3.50's do. What a call through the binding binds, private
  items included, is [ADR 3.45](/design-docs/adr/3.45-module-file-bindings.md)'s.

## Why

- Such a call bound only by its name: on the Go monorepo snapshot `Lang::extract` had no callee though it calls the
  `extract` of 13 language modules 15 times through `use crate::{go, cpp, ...}` (2026-10-23).
- Each target of a package is a crate of its own, so an integration test's or a binary's `crate::` is not the
  library's; a file `tests/common/mod.rs` is a module of every test target beside it.
- Since the 2018 edition a path's first segment names an item of the module it is written in before a crate:
  tree-sitter's `pub use wasm_language::*;` beside `mod wasm_language;` bound nothing read as a crate (#399), and its
  xtask's 11 commands, dispatched as `benchmark::run()` beside `mod benchmark;`, had no callee (2026-10-23).
- The resolver walks module files, and an inline module has none, so a path through one started at `self::` would
  reach the file itself and bind its top-level namesake of the item, `fn run` beside `mod inline { fn run() }`, as an
  import's 95.
- A file's bindings hold one path per name, so a name the file declares cannot also hold a path; the keyword can,
  since no item is named `crate` or `super`. Without it none of the 8 calls `crate::file(...)`, `crate::graph(...)` and
  `crate::call(...)` of kartta-graph's test modules, each inside a helper named like the one of `main.rs` it calls,
  bound a callee (this repository, 2026-10-23).
- The resolver walks from the file's own module; the extraction cannot tell it where an inline module's directory is.
- rustc resolves such a path the same way, and what the resolver cannot follow, a module a `#[path]` places or an item
  of an inline module, binds nothing rather than something else, so the import's 95 holds.

## Consequences

- A path call through a module file the file declares, written inside an inline module after `use super::*;`, keeps no
  path of its own and binds by name unless a call outside the module keeps the name. Accepted.
- A module a `#[path]` places keeps no path for a call through it, and binds by name. Accepted.
- Two spellings of one module, `crate::root()` beside `super::super::root()`, are two paths of one name and bind
  neither (#236).
- A `self::` or `super::` path inside an inline module binds by the same-file tiers alone. Accepted.
- Two such calls through `super::` and `super::super::` in one file hold two paths of `super` and bind neither (#236).

## Rejected

- **`crate::` from the library alone** — loses 275 pairs and 61 raised ones in this repository, from integration tests
  and binaries (2026-10-23).
- **No crate root where a package has both `src/lib.rs` and `src/main.rs`** — loses right pairs, as kartta-mcp's
  `use crate::render;`, which names `src/render.rs` from either root: 117 raised pairs in tree-sitter (2026-10-23).
- **Inline modules spelled after `self`**, `super::f` inside `mod tests` kept as `self::f` — binds the same pairs on
  three trees, since such a path names what the file's own tiers bind, at the cost of a path per inline `use`.
- **A confidence of its own for a path within the crate** — tells an agent nothing the import's 95 does not, and the
  MCP answers count both as certain.
- **The `use` read in the resolver**, its first segment matched against the file's bodiless `mod` declarations — sees
  no inline module and not the module the `use` is written in, so it reads `use m::x` inside `mod tests` as the file's
  `m`.
- **No exception for a name declared only as a module** — 13 of tree-sitter's 14 raised pairs stay at 70.
- **Every module the file declares started at `self::`, inline ones too** — binds the same pairs on this repository,
  tree-sitter and the Go monorepo snapshot, and risks the file's top-level namesake above (2026-10-23).
- **A path call inside an inline module started at the file's module too**, as `use super::*;` in `mod tests` makes it
  — binds the same pairs on the three trees, and there the inline module's own names come first (2026-10-23).
- **Keeping a module file's name only for a path that starts at `self::`** — binds the same pairs on the three trees,
  with a check per kept name (2026-10-23).
- **The keyword as receiver for every path call through `crate::` or `super::`** — binds the same pairs on this
  repository, tree-sitter and the Go monorepo snapshot, and any file that calls through two depths of `super::` then
  holds two paths of `super` and binds neither (2026-10-23).

## Revisit if

The extraction places each inline module in its file's module tree, so a path inside one could start where Rust starts
it. No consumer asks yet.
