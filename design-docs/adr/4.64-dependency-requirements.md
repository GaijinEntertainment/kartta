# Hold each dependency requirement at the version Cargo.lock resolves

- **Date:** 2026-11-06
- **Governs:** the registry dependencies of `Cargo.toml` and of every `crates/*/Cargo.toml`, `.github/workflows/ci.yml`
  (job `package`), `.github/dependabot.yml` (the `cargo` entry)
- **Pinned by:** `.github/workflows/ci.yml` (job `package`, step `every registry requirement names the version
  Cargo.lock resolves`)

A published crate's requirement is the lowest version a consumer's resolve may give it, and CI builds the version
`Cargo.lock` holds, or in `fresh-resolve` the newest one: no job builds the floor. Each requirement names the locked
version, Dependabot raises it with the lock, and CI fails a requirement the lock has passed; the trade is a consumer
held to versions newer than kartta strictly needs.

## Decision

- **The requirement.** Every registry dependency of a workspace crate, dev- and build-dependencies included, is written
  as the full version `Cargo.lock` resolves for it, as a caret requirement and never `=` (`.claude/rules/rust.md`).
- **Dependabot.** The `cargo` entry sets `versioning-strategy: increase`, so a bump writes its version into the
  requirement and the lock together.
- **The check.** The `package` job reads `cargo metadata --locked --all-features` and fails on each registry
  requirement of a workspace crate that is not a caret on a version the lock resolves for that crate, naming the crate,
  the requirement and the locked version.

## Why

- On 2026-11-06, 12 requirements named a version below the lock, `rmcp` 3.5.1 against 3.8.0 among them. The grouped
  bump `98729d2f` moved `Cargo.lock` and no `Cargo.toml`.
- Dependabot's cargo updater raises a requirement only when it no longer admits the new version unless a strategy is
  set (`cargo/lib/dependabot/cargo/update_checker.rb` in `dependabot/dependabot-core` at `31740e0f`); `increase`
  "always increase[s] the minimum version requirement to match the new version" (GitHub's Dependabot options reference,
  `versioning-strategy`).
- Dependabot covers its own bumps alone. A hand `cargo update`, a dependency added below its newest release, and another
  crate whose requirement raises a shared dependency each move the lock past a requirement with no Dependabot run.
- Without `increase`, the check fails every grouped bump that stays in range until someone edits the manifests by hand.

## Consequences

- A consumer takes each dependency at the version kartta was tested on or newer, even where kartta uses nothing the
  newer version added, and a lock that holds an older one is moved on. Accepted.
- A hand `cargo update` fails CI until the manifests name what it resolved. Accepted.
- Dev-dependencies are held too, though no consumer resolves them: one rule for every requirement. Accepted.

## Rejected

- **`increase` alone** — it leaves the hand update, the new dependency and the shared dependency unchecked.
- **The check alone** — each in-range Dependabot bump fails it and waits for a hand edit.
- **Dependabot's default, `increase-if-necessary` or `lockfile-only`** — each moves the lock alone for an in-range bump.
- **`widen`** — it keeps the old floor, and the cargo updater refuses it: its allowed strategies are `lockfile_only`,
  `bump_versions` and `bump_versions_if_necessary` (`cargo/lib/dependabot/cargo/update_checker/requirements_updater.rb`
  at `31740e0f`).
- **Testing the floors with `-Z direct-minimal-versions`** — the pinned cargo 1.99.1 refuses `-Z` off the nightly
  channel, and the floors would cost a second build and test of the workspace on every pull request.
- **`cargo upgrade` from cargo-edit in CI** — a pinned tool download for what `cargo metadata` and `jq` already answer.

## Revisit if

Dependabot's cargo updater raises an in-range requirement by default, or Cargo's resolver can test the floors on a
stable toolchain. High confidence that the guard covers each way the lock moves; medium that the raised floors cost
consumers nothing in practice, which no consumer has reported on.
