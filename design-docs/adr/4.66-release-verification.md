# Verify a published release from its registries on every target

- **Date:** 2026-11-06
- **Governs:** `.github/workflows/verify-release.yml`, `scripts/release-check.sh`

The cut's acceptance names four install checks on every target of the support matrix and a check of the release's
checksums, and the maintainer's machine covers one target. A workflow the maintainer runs after a publish installs each
artifact from its public registry on every target; the trade is that its registry path first runs at the first publish,
with a Release run's artifacts standing in until then.

## Decision

- **Runs.** The maintainer dispatches `verify-release.yml` on the release's tag with its version once both publish
  branches finish (`RELEASING.md`). No push, tag or pull request runs it.
- **Checks.** On each target of [ADR 4.46](/design-docs/adr/4.46-release-scope.md)'s matrix, `scripts/release-check.sh`
  checks that `kartta-mcp --version`, installed by `cargo install --locked`, prints `kartta-mcp <version>`, that a
  scratch crate on `kartta = "=<version>"` builds a reference to `kartta::Engine`, that a scratch Go program on the
  module at `v<version>` runs against the release's archive and its library answers `<version>`, and that
  `npm install kartta` at `<version>` loads an engine that answers `<version>`. The Go program on Windows links the
  `windows-gnu` archive ([ADR 4.60](/design-docs/adr/4.60-go-windows-link.md)). One job checks every tarball of the
  release against `SHA256SUMS`, and that the file lists no other. A failed check does not stop the next one of its
  target.
- **Where.** The glibc, macOS and Windows targets run on the runner, with the pinned Rust toolchain, the Go of the `go`
  job and the Node of `.nvmrc`. The musl targets run in the images the release builds them in, with the runner's Go
  mounted, as the `go-musl` job does.
- **A Release run.** With the `run` input set, that run's artifacts stand in for the GitHub release and npm, and the
  crates and Go module of the dispatched branch or tag for crates.io and the Go module proxy.

## Why

- A version is out only when both publish branches finish, and they finish apart, each behind its own approval
  ([ADR 4.55](/design-docs/adr/4.55-release-workflow.md)), so the check waits on the maintainer, not on a job.
- A default requirement can update to any SemVer-compatible version (Cargo's `specifying-dependencies.md`), so only `=`
  holds the crate check to the version the release published.
- On 2026-11-06 a scratch crate on the crates.io `0.0.0` placeholder of `kartta` built with `use kartta as _`, and
  failed with E0425 once it named `kartta::Engine`, which the placeholder lacks.
- A Release run uploads the same tarballs and packs the publish takes, so a run on its artifacts checks every target's
  archive and addon before a version exists, and leaves only the registries' serving to the first publish.
- A dispatch reaches a workflow only once its file is on the default branch, and then runs on any branch or tag
  (GitHub's "Events that trigger workflows", `workflow_dispatch`), so no pull request can run it on its own branch.

## Consequences

- The registry path, which is crates.io's resolution of the published manifests, the Go proxy's fetch through
  `dev.gaijin.team` (#131), npm's choice of a target's package and the release's download, first runs at the first
  publish (#144). Accepted.
- A run builds `kartta-mcp` and a crate on `kartta` on each of six targets: 95 s and 18 s at 2 jobs on macOS arm64
  (2026-11-06). Accepted.
- The scratch crate resolves the newest version each requirement allows, as a consumer's first build does, so a
  dependency's release can fail it while every `--locked` build passes. Accepted.
- The targets are listed in the workflow, apart from the release's matrix; a target added to one is added to the other
  by hand. Accepted.

## Rejected

- **A job of the release workflow after the publishes** — a failed check would fail the run whose uploads stand, and a
  re-run of its failed jobs would reach the publishes again.
- **A pull request trigger** — no registry holds the version a pull request builds.
- **One job per check and target** — each of 24 jobs would set up a toolchain its target's other checks share.

## Revisit if

A registry offers a staging upload the checks could read before the publish, or the support matrix changes. Medium
confidence in the Windows rows, which no run has reached yet.
