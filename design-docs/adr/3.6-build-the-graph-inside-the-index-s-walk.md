# Build the graph inside the index's walk

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-21
- **Initiative:** `03-code-graph`

The code graph needs every source file's whole content. A pass over the tree after the index's walk would read each
file a second time, after the filesystem's caches of the tree have moved on (ADR 1.12), and the review hosts kartta is
built for run several builds at once over nearly identical trees, under a tight memory limit.

**The engine extracts each file in the walk's own read.** `kartta::Engine::build` builds the index with a
`ContentVisitor` that wants every file one of its languages claims; the first language that claims a file takes it, and
extracts it on the walk's thread from the bytes the walk read. With a content cache, the extraction is taken from the
cache, or computed and given to it (ADR 2.2), under a namespace per language whose fingerprint is the language's,
followed by `kartta_lang::FINGERPRINT`: the code of the contract crate, its encoding included, shapes the cached bytes
as much as the language does.

**Extractions wait encoded.** Resolution needs the whole repository, so no extraction can be resolved before the walk is
done, and the build holds every one until then. It holds each in the encoded form the cache stores, which a cache hit
hands over as it is and a miss produces anyway to cache it, and decodes each when it resolves it. On a Go monorepo of
119,888 Go files and 4.12M definitions, on macOS with 18 cores and no cache, holding them encoded peaks at 1.16–1.19 GB
of footprint against 2.90–2.96 GB for holding them decoded, for 8.7–10.9 s against 8.3–8.9 s of build and about 10%
more CPU time: about 1.75 GB saved for one decode per file.

**Resolution runs in batches on the index's threads.** Once the walk is done, the extractions are put in path order and
resolved a batch of 1,024 at a time on `Index::on_threads`, and each batch goes into its family's graph in path order
before the next is resolved, so at most one batch is held resolved. A language is asked for its resolver only when it
claimed a file the build read, so a language the tree does not use reads none of its configuration. A cancel token
stops the build between batches as it stops the walk.

**Revised 2026-10-18: no separate codec identity.** `RawExtraction::CODEC`, a name of the encoding's layout kept by
hand, is gone: the encoding is code of `kartta-lang`, whose source `kartta_lang::FINGERPRINT` digests, so a change to
the layout already names a new namespace.

**Revised 2026-10-21: 1,024 files resolve at a time.** A batch's decoded extractions are held beside the graphs grown so
far and the encodings not yet resolved, so the batch sets how far the build peaks above what it keeps, and once the
walk's pages are trimmed, glibc's resident set peaks there too. Measured with a harness that read the batch size from
the environment, so every size ran in one binary, interleaved with the others, each build with stamps and all sixteen

peaks alike at 1,024 to 4,096 and keeps 10 MiB more after the build at 1,024, where the monorepo peaks 56 MiB lower and
keeps 31 MiB less. The walk's peak still sets the monorepo's cold peak on macOS. 512 lowers the heap's peak by another
6–9 MiB and the warm footprint by 10–16 MiB in the series that ran both, for resolution 1.5–1.9 times as long on
macOS. At 1,024, resolution takes 0.2–0.4 s longer than at 4,096 on macOS, where 18 threads share a loaded host, and
0.1–0.2 s longer under glibc; under musl it is faster, and no Linux build moved beyond its spread.

## Considered Options

- **A second walk for the graph** — keeps the index and the graph apart, and reads every source file twice.
- **Holding extractions decoded** — no decode per file, and 2.5 times the peak footprint on that monorepo.
- **Resolving inside the walk** — no extraction held at all, and impossible: a resolver asks the repository about files
  the walk has not reached yet.
- **4,096 files at a time** — 53–57 MiB more of glibc's resident peak on both trees, 15 and 57 MiB more of the heap's on
  macOS and 56 MiB more of musl's on the monorepo, for 10 MiB less resident under musl on the game-engine tree.
- **512 at a time** — 9 and 6 MiB less heap than 1,024 on macOS and 10 and 16 MiB less warm footprint, for resolution
  1.5–1.9 times as long there.
- **2,048 at a time** — 14–23 MiB above 1,024's peaks on the monorepo and under glibc, and no faster beyond the spread.
- **16,384 at a time** — 50–75 MiB more heap than 4,096 and 201 MiB more of glibc's peak on the game-engine tree.
- **A batch bounded by the bytes of its encodings rather than by files** — sized to what it decodes, which a tree of
  uneven files would show; not built, since at 1,024 files a batch's time showed only with 18 threads on a loaded host.

Revisit when the call graph changes where the build's peak is, or when decoding is a measurable share of a build.
