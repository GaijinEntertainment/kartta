# Build the graph inside the index's walk

- **Status:** accepted
- **Date:** 2026-10-16
- **Initiative:** `03-code-graph`

The code graph needs every source file's whole content. A pass over the tree after the index's walk would read each
file a second time, after the filesystem's caches of the tree have moved on (ADR 1.12), and the review hosts kartta is
built for run several builds at once over nearly identical trees, under a tight memory limit.

**The engine extracts each file in the walk's own read.** `kartta::Engine::build` builds the index with a
`ContentVisitor` that wants every file one of its languages claims; the first language that claims a file takes it, and
extracts it on the walk's thread from the bytes the walk read. With a content cache, the extraction is taken from the
cache, or computed and given to it (ADR 2.2), under a namespace per language whose fingerprint is the language's,
followed by `kartta_lang::FINGERPRINT` and by `RawExtraction::CODEC`: the code of the contract crate and the encoding
shape the cached bytes as much as the language does.

**Extractions wait encoded.** Resolution needs the whole repository, so no extraction can be resolved before the walk is
done, and the build holds every one until then. It holds each in the encoded form the cache stores, which a cache hit
hands over as it is and a miss produces anyway to cache it, and decodes each when it resolves it. On a Go monorepo of
119,888 Go files and 4.12M definitions, on macOS with 18 cores and no cache, holding them encoded peaks at 1.16–1.19 GB
of footprint against 2.90–2.96 GB for holding them decoded, for 8.7–10.9 s against 8.3–8.9 s of build and about 10%
more CPU time: about 1.75 GB saved for one decode per file.

**Resolution runs in batches on the index's threads.** Once the walk is done, the extractions are put in path order and
resolved a batch of 4,096 at a time on `Index::on_threads`, and each batch goes into its family's graph in path order
before the next is resolved, so at most one batch is held resolved. A language is asked for its resolver only when it
claimed a file the build read, so a language the tree does not use reads none of its configuration. A cancel token
stops the build between batches as it stops the walk.

## Considered Options

- **A second walk for the graph** — keeps the index and the graph apart, and reads every source file twice.
- **Holding extractions decoded** — no decode per file, and 2.5 times the peak footprint on that monorepo.
- **Resolving inside the walk** — no extraction held at all, and impossible: a resolver asks the repository about files
  the walk has not reached yet.

Revisit when the call graph changes where the build's peak is, or when decoding is a measurable share of a build.
