# Read a Go selector by depth through the embedded types the graph can see

- **Date:** 2026-11-01
- **Governs:** `crates/kartta-graph/src/typed.rs` (`member_value`, `member`)
- **Pinned by:** `crates/kartta-graph/tests/graph/typed.rs`
  (`an_embedded_field_beside_an_import_binds_at_any_depth`,
  `a_shallower_embedded_field_outranks_a_deeper_promoted_member_of_its_name`,
  `a_name_no_embedded_field_gives_stays_outside_the_graph_beside_an_import`), `crates/kartta-mcp/tests/graph.rs`
  (`find_callees_binds_a_call_through_a_field_embedded_beside_an_import`)

A Go selector takes the name at its shallowest depth, and an imported type's fields and methods are unknown to the
graph. The read walks the embedded types the graph holds, shallowest first, and answers from any type that gives the
name, so an import beside it costs no edge; only a name no held type gives counts as the import's, at the cost of a
wrong edge where an import nearer the receiver really holds the name.

## Decision

- **One walk by depth.** A read of a member walks the type and its embedded types breadth first, and at each type takes
  the member it declares, or the embedded field of the name, an embedded `Base` or `*pkg.Base` being named `Base`.
- **An import at the same depth.** A held type at the depth an import's members sit at answers. An imported member of
  that name at that depth would make the selector illegal, so a tree that compiles cannot hold both.
- **An import shallower than the name.** A held member deeper than an imported type's members also answers. The
  imported type shadows it when it holds the name, which the graph cannot see, and that pair is wrong.
- **An embedded field beside an import.** The field sits at the depth of the struct that embeds it, one above the
  members of the imported type beside it, so the field answers whatever the import holds.
- **A name no held type gives.** The read reaches outside the graph, also for a name no symbol holds, and the call
  counts as `Miss::ExternalImport` ([ADR 3.29](/design-docs/adr/3.29-go-receiver-types.md) states what such a path
  binds).

## Why

- The spec's selector rule: `x.f` denotes the `f` at the shallowest depth, and more than one there makes the selector
  illegal (`doc/go_spec.html`, Selectors). `lookupFieldOrMethodImpl` searches one depth at a time, a struct's embedded
  fields among its fields, and answers a collision at a depth with no object
  (`cmd/compile/internal/types2/lookup.go:174`, `:212`, `:215`).
- go1.27.3 refuses `o.Transport` on `struct { http.Client; Mid }` with `Mid` embedding `Transport`,
  `ambiguous selector`, and takes `http.Client`'s field past a `Transport` embedded a level deeper.
- On the Go monorepo snapshot the walk adds 195 caller and callee pairs, 30 of 30 sampled right, and removes 59, all of
  them `c.Config.M()` bound through `base.Config`'s named field `Config` past the embedded `base.Config` itself
  (2026-11-01, #815).

## Consequences

- A held member past a nearer import that holds its name binds wrongly. Of the snapshot's 3,060 reads of an embedded
  field, none has an import at or above its depth, and of its declared members 2 calls have one nearer, both of
  `MarshalJSON` through an alias of two build declarations, and both right (2026-11-01, #815). Accepted.
- A method promoted through an import stays unbound, counted as `Miss::ExternalImport`. Accepted.

## Rejected

- **Answer from outside the graph once the walk meets an import** — binds nothing for `o.Base.M()` beside `http.Client`,
  the 136 pairs the import alone hid on the snapshot (#815).
- **Answer from outside the graph past a nearer import only** — needs a depth per walked type, for no read of an
  embedded field on the snapshot (#815).
- **Declared members first, embedded names in a second walk** — a deeper promoted member hides a shallower embedded
  field, the 59 wrong pairs (#815).

## Revisit if

The graph learns the members of imported types, which decides what this rule assumes. High confidence in the rest: it
follows the compiler's walk.
