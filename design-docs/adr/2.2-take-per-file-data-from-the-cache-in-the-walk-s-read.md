# Take per-file data from the shared cache in the walk's read

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-18
- **Initiative:** `02-shared-cache`

ADR 2.1 built a store that processes on one node share without coordination. This decides how `kartta-fs` uses it. Two
producers compute data per file from the walk's one read (ADR 1.12): the content index, which scans each text file for
its trigrams (ADR 1.14), and a `ContentVisitor` — the code graph next — which parses the files it wants. Both repeat
that work for every file of every tree a node builds, though the trees differ by a few files.

**A build given `BuildOptions::content_cache` hashes each file it reads and keys both producers by that hash.**
The content index looks a text file's trigram set up in the store before scanning it: a hit decodes the stored set, a
miss scans the file, encodes the set as ascending deltas in varints and adds it to the build's writer. The lookup needs
the hash of the whole file before the scan it would skip. A file a visitor wants is read whole anyway, and so is a file
that ends within the first 64 KiB chunk; a longer file only the index reads still streams through that chunk, read once
to hash it and, when the store lacks it, again to scan it. The second read hashes what it scans and keys the entry by
that, so a write between the two reads cannot file one content's set under another's hash; such a file is hashed twice,
and every other file once. The cache stays off by default, and a build without one is unchanged.

**One store and one writer per build serve both producers.** The visitor is lent the store, keyed by the build's hash of
each file: `Content::cached` answers what the store holds for the content under a
namespace the visitor names, and `Content::cache` adds the visitor's own entry to the writer the content index uses. A
build publishes one pack when its walk is done, then merges the directory's packs when they pass eight; a refresh does
the same for the files it reads. A store, hash and writer per producer would hash every file twice and publish two packs
per build, so merges would come twice as often. A cache directory opens for a visitor alone, without a content index.

**The trigram namespace's fingerprint is derived, not kept by hand.** It is the encoded trigram set of a probe holding
every byte value and every sequence the case folding folds, so a change to the folding, the window or the encoding
changes the namespace without anyone remembering to bump it, and builds of different versions sharing one directory
never serve each other's sets.

**A failure costs only the sharing.** A directory that cannot be opened, written, published to or merged is reported as
`BuildError::Cache` among the build's collected errors; the content index is whole, because the build computed what it
could not take from the store.

## What it costs

A content-index build of the game-engine checkout, 169,188 text files and 1.82 GB, its trigram sets a 227 MB pack:

| | macOS, 18 cores | Linux, 4 CPUs |
| --- | --- | --- |
| no cache, before this change | 2.73–3.11s | 1.44–1.52s |
| no cache | 2.73–2.98s | 1.37–1.45s |
| the store holds nothing | 2.86–2.87s | 2.24–2.28s |
| the store holds every file | 2.71–2.73s | 1.16–1.17s |
| with a visitor that wants and hashes the graph's languages, no cache | 2.75–2.83s | 1.60–1.61s |
| the same visitor sharing the build's hash, the store holds nothing | 2.83–2.85s | 2.20–2.29s |
| the same, the store holds every file | 2.74–2.86s | 1.16–1.20s |

On Linux a build that finds every file saves 15–20%, and 25–28% beside a visitor that needs the hash anyway: the graph's
languages are 144,946 of the checkout's 171,722 files and 1.45 of its 2.37 GB, so most of the hashing is paid by the
graph. What a hit cannot remove is the rest of the build — sorting every file's trigram pairs and writing the posting
lists, about 0.6s of the 1.16s, and reading and hashing the files, about 0.4s. A build that finds nothing pays for
hashing (about 0.26s), sorting and encoding each set (about 0.26s), inserting (0.1–0.2s), publishing (about 0.08s)
and reading and hashing a second time the long files it scans, which took 0.04–0.08s against reading them whole. On
macOS opening the files to read them is about 95% of the build, so the cache changes it by a few percent either way.

Memory: on Linux the resident set is 306–307 MiB without a cache, 303–306 MiB when the store holds nothing, and 413 MiB
when it holds every file — the pack's pages a build touches are mapped, clean and given back under pressure. On macOS,
where the footprint leaves mapped pages out, it is 351–373 MB without a cache, 344–350 MB when the store holds every
file and 355–387 MB when it holds nothing, where the writer holds its index until it publishes.

## Considered Options

- **No trigram cache, the store for the graph alone** — leaves what a warm build saves on Linux unclaimed, while the
  cost of a build that finds nothing is paid once per content by all the builds sharing a directory.
- **Reading whole every file the index reads, when a cache is given** — one read per file, but the reason the index
  streams (ADR 1.12) comes back: on the checkout a build that finds nothing peaked 45–95 MB higher in footprint on
  macOS and 24–40 MiB higher in resident set on Linux to save 0.04–0.08s, and whole reads of the data volume's text
  files held multi-gigabyte files at once.
- **Scanning while hashing and looking the set up after it** — the hash is complete only at the end of the file, after
  the scan the lookup was to skip.
- **A content index shared across trees** — posting lists over distinct contents rather than over one tree's files,
  mapped by every process, would skip the per-build sort and merge as well and share their pages between processes. It
  changes what a content id names, and with it refreshes and compaction (ADRs 1.15, 1.16); set aside until the
  per-build sort and merge are shown to be what limits the nodes.
- **Radix-sorting each set before encoding it** — saved at most 0.05s of a build that finds nothing, within the noise.
- **A fingerprint kept by hand** — a change to the folding that forgets the bump serves sets computed by the old rules.

Revisit when the content index's per-build sort and merge are what limit the nodes, or when, measured on the nodes' own
CPUs, the hashing a hit pays comes close to the scan it skips.
