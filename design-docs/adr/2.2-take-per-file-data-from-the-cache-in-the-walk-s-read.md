# Take per-file data from the shared cache in the walk's read

- **Status:** accepted
- **Date:** 2026-10-16
- **Updated:** 2026-10-18
- **Initiative:** `02-shared-cache`
- **Governs:** `kartta_fs::BuildOptions::content_cache`, `kartta_fs::Content::{cached, cache}`,
  `crates/kartta-fs/src/cache.rs`, `crates/kartta-fs/src/policy.rs` (`stream_text`, `stream_cached`),
  `crates/kartta-fs/src/trigram.rs` (`fingerprint`, `encode`)
- **Pinned by:** `crates/kartta-fs/tests/cache.rs`

Two producers compute data per file from the walk's one read
([ADR 1.12](./1.12-read-each-wanted-file-once-during-the-walk.md)): the content index, which scans each text file for
its trigrams ([ADR 1.14](./1.14-narrow-content-search-with-a-trigram-index.md)), and a
`ContentVisitor`, which the code graph uses to parse. A build given a cache directory hashes each file it reads and
lets both take their data from the store of
[ADR 2.1](./2.1-share-per-file-data-through-content-addressed-packs.md) by that hash, at the price of the hashing and,
when the store lacks a long file, a second read of it.

## Decision

- **The hash.** A build given `BuildOptions::content_cache` hashes each text file it reads for the content index or
  a visitor, and keys both producers by that hash; a file with a NUL in its first 64 KiB is not hashed. `None`, the
  default, shares nothing, and a build without a cache is unchanged. A build with neither a content index nor a visitor
  does not open the directory; a build with a visitor alone opens it. The directory is created when absent.
- **The content index.** It looks a text file's trigram set up in the store before scanning it. A hit decodes the
  stored set; a set that does not decode is a miss. A miss scans the file, encodes the set as ascending deltas in
  varints, and adds it to the build's writer.
- **The reads.** A file a visitor wants is read whole, and so is a file that ends within the first 64 KiB chunk; both
  are hashed once from that read. A longer file only the content index reads streams through that chunk: read once to
  hash it and, when the store lacks it, read again to scan it. The second read hashes what it scans and keys the entry
  by that hash, so a write between the two reads cannot file one content's set under another's hash.
- **One store and one writer per build** serve both producers. The visitor is lent the store, keyed by the build's hash
  of each file: `Content::cached` answers what the store holds for the content under a namespace the visitor names, and
  `Content::cache` adds the visitor's entry to the writer the content index uses, the first payload of a key kept.
- **Publishing.** Once its walk is done, a build publishes what it and the visitor added as one pack, and no pack when
  they added nothing. It then merges the directory as
  [ADR 2.4](./2.4-merge-a-cache-s-packs-once-they-pass-eight.md) states, whether or not it published a pack. A refresh
  does the same for the files it reads, through the directory the build named.
- **The trigram fingerprint** is derived, not kept by hand: it is the encoded trigram set of a probe that holds every
  byte value and every sequence the case folding folds, so a change to the folding, the window or the encoding changes
  the namespace.
- **A failure costs only the sharing.** A directory that cannot be opened, written, published to or merged is reported
  as `BuildError::Cache` among the build's collected errors; the content index is whole, because the build computed
  what it could not take from the store.

## Why

- The lookup needs the hash of the whole file before the scan it would skip, so a file the build streams has to be
  read once before it is known whether to scan it.
- On Linux at a 4-CPU quota, a content-index build of the game-engine checkout that finds every file took 1.16 s against
  1.37-1.45 s without a cache (2026-10-16). Beside a visitor that hashes the graph's languages anyway, 144,946 of the
  checkout's 171,722 files, most of the hashing is already paid.
- One store, hash and writer for both producers spares a second hash of each file for the other producer, and keeps
  one pack per build.

## Consequences

- A build that finds nothing pays for hashing, encoding, inserting, publishing and the long files' second reads:
  2.24-2.28 s against 1.37-1.45 s on Linux. All the builds that share a directory pay it once per content. Accepted.
- A hit cannot remove the rest of the build: sorting every file's trigram pairs and writing the posting lists, about
  0.6 s of the 1.16 s, and reading and hashing the files, about 0.4 s. Accepted.
- On macOS, opening the files is about 95% of the build, so the cache moves it by a few percent either way. Accepted.
- A warm build maps the pack's pages it touches: the Linux resident set was 413 MiB against 306-307 MiB without a
  cache. The pages are clean and given back under pressure. Accepted.

## Rejected

- **No trigram cache, the store for the graph alone** — leaves the warm Linux saving unclaimed, while the cost of a
  build that finds nothing is paid once per content by every build sharing the directory.
- **Reading whole every file the index reads, when a cache is given** — one read per file, but the reason the index
  streams comes back: a build that finds nothing peaked 45-95 MB higher in footprint on macOS and 24-40 MiB higher in
  resident set on Linux to save 0.04-0.08 s, and whole reads of the data volume's text files held multi-gigabyte files
  at once.
- **Scanning while hashing and looking the set up after** — the hash is complete only at the end of the file, after the
  scan the lookup was to skip.
- **A store, hash and writer per producer** — hashes every file twice and publishes two packs per build, so merges come
  twice as often.
- **A content index shared across trees** — posting lists over distinct contents, mapped by every process, would skip
  the per-build sort and merge, but change what a content id names, and with it refreshes and compaction
  ([ADR 1.15](./1.15-refresh-an-index-in-place-from-a-second-walk.md),
  [ADR 1.16](./1.16-refresh-the-parts-of-a-tree-a-caller-names.md)).
- **Radix-sorting each set before encoding it** — saved at most 0.05 s of a build that finds nothing, within the noise.
- **A fingerprint kept by hand** — a change to the folding that forgets the bump serves sets computed by the old rules.

## Revisit if

The content index's per-build sort and merge are what limit the nodes, or the hashing a hit pays comes close to the scan
it skips on the nodes' own CPUs. Moderate confidence: both are measured on a 4-CPU container, not on the nodes.
