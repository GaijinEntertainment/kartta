# Announce a cap unless the order already explains it

- **Status:** accepted
- **Date:** 2026-08-24
- **Revised:** 2026-10-14
- **Initiative:** `01-kartta-fs-port`

Three query surfaces take a cap. `Index::glob` returns a `Capped` and `Index::list` a `Listing`, and both
carry a `truncated` that reports whether the cap turned an item away; `Index::fuzzy` returns what fits and says
nothing about what did not.

**A capped answer announces the cap unless the answer's own order explains what is missing.**

Ranking explains it. "The ten best matches for `main`" is answered in full by ten paths, and no caller ever believed the
index held only ten — the order itself says the rest scored lower. A flag there would be set on nearly every call with a
cap, which is how a flag stops being read.

Index order explains nothing. Ten paths in depth-first order look exactly like the first ten of two hundred, and
`glob` is explicit that it does not rank — a cap takes the first paths in index order rather than the best. So it
reports, for the same reason a listing does.

A listing is the clearest case of the same rule. "What is in `src`" answered with twenty entries asserts that `src`
holds twenty entries. If it holds two hundred, the caller has a wrong answer and nothing to detect it with.

**The earlier form of this rule drew the line in the wrong place.** It asked whether an answer was "about a place",
which put `glob` on the ranked side of a line it does not belong on: it is unranked, and being about a set of
files rather than a directory changes nothing about what its order can explain. Ordering is the test; a review caught
the gap.

This is the objection that removed the entry cap from `kartta-walk`, applied to a surface that can meet it. There, a
truncated tree could not be told apart from a complete one *and* the surviving subset depended on thread scheduling, so
the guard produced arbitrary wrong answers and was dropped in favour of failing the walk. A listing clears both halves:
`Index::entries` is depth-first and deterministic, so a cap takes a defined prefix rather than an arbitrary subset, and
the flag makes what it cut visible.

`truncated` is set by an actual rejection and never inferred from `items.len() == limit`. An answer holding exactly the
cap is complete and says so. Inferring would get the flag wrong in precisely the case where a caller most needs it
right. Keeping it exact under a cap of *n* costs one item: the query looks for the *n+1*th and reports whether it was
there.

**A capped answer is materialized; an iterator takes no cap.** The two rules meet at `Index::inspected`, which sweeps
every entry and has no limit at all. An iterator ends when the caller stops pulling, so there is nobody to set a flag
and nowhere to put one — a capped iterator would quietly reintroduce the answer this ADR exists to prevent. Anything
bounded returns a materialized answer that carries the flag; anything unbounded may be an iterator.

The consequence is that this is a per-surface judgement, not a crate-wide convention to apply by reflex, and the
question to ask is always the same: can a caller tell from the order alone that something is missing? Content search is
the next case to decide, and it decides as a listing does — matches within one file arrive in file order, which
explains nothing. It is also the exception to looking for the *n+1*th item: that one match can lie anywhere in the files
not yet read, so ADR 1.11 has a limited content search count what it did not cover instead.

## Considered Options

- **Report truncation on every capped surface** — consistent to read, and the flag becomes noise on the ranked query,
  where it is set whenever the index holds more matches than the caller asked for. That is the ordinary case, so the
  flag carries no information and trains the caller to ignore it where it matters.
- **Report it nowhere** — the cheapest surface, and it leaves a capped listing indistinguishable from a small
  directory. Dropping the listing's flag to match the other two queries would trade a correct answer for a symmetrical
  one.
- **Return the count of what the cap cut instead of a flag** — strictly more information, at the cost of the work the
  cap exists to avoid. Counting what a depth bound, a collapse and an exclusion would still have let through past the
  cap means visiting it, and a listing skips a subtree by binary search precisely so it never touches what it is not
  returning. The index's own total under the listed directory is a different number and costs no such scan; a listing
  reports it beside the flag (ADR 1.8).
- **Leave the caller to ask for one more than it wants** — this works, and it is the caller reimplementing the flag
  with an off-by-one at each call site, then discarding the extra entry, against an index that already knows the
  answer. It is also exactly what the query does internally, once, where a mistake is made in one place rather than
  in every caller.
- **Return an iterator from the capped queries and let the caller stop where it likes** — no flag needed because no
  cap exists, and the caller then cannot distinguish exhausting the matches from stopping early on its own count. The
  question this ADR answers would simply move to the call site unanswered.

Revisit if a caller needs the count of what was cut rather than the fact of it, which arrives as its own named thing
and never by widening `truncated` into a number.
