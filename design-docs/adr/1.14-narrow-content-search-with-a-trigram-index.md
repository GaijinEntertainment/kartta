A content search reads every candidate it cannot settle unopened, on every query, and an agent asks many in one
session. A build asked for an index records which files hold which trigrams, taking content from the reads the walk
already makes (ADR 1.12), and a search opens only the files that could match. The build then reads every text file.

## Decision

- **Opt-in.** `BuildOptions::content_index` names where the index is kept. `None`, the default, builds none, and a
  build that reads nothing still reads nothing.
- **What a build reads.** With an index, the build reads every regular file the rules keep whose extension is not
  binary: whole when a visitor wants it, in 64 KiB chunks otherwise. It records each text file's distinct trigrams
  under its `ContentId`. [ADR 2.2](./2.2-take-per-file-data-from-the-cache-in-the-walk-s-read.md) states the reads a
  content cache adds.
- **The trigram.** A trigram is three bytes with ASCII letters folded to lowercase, and KELVIN SIGN and LONG S folded to
  `k` and `s`: the two code points Unicode's simple case folding joins to an ASCII letter. A case-insensitive pattern
  therefore narrows whichever spelling a file holds.
- **What a pattern requires.** `Patterns` reads each pattern under the settings `grep-regex` translates it with, and
  takes the trigrams every matching line must contain: the runs of literal bytes and single-spelling letter classes,
  and an alternation as a choice of its branches. An optional piece, a look-around or a wide class requires nothing, and
  so does a pattern the derivation cannot read.
- **Narrowing never loses a match.** The derivation can only widen the set, so a search through the index finds what a
  full search finds, as of the content the build read. A file the build could not read stays a candidate for every
  search. What the index skipped is counted in `Matches::ruled_out` (ADR 1.11). A pattern that needs no trigram, such
  as `\w+`, reads every candidate.
- **Content as the build read it.** A file changed since the build is ruled in or out by the content the build read,
  until a refresh reads it again (ADR 1.15).
- **Lists.** A posting list is Elias-Fano, or a bitmap where that is smaller. The layout follows from the list's length
  and the number of ids handed out alone, so a list is written into a zeroed region of exactly its size and read without
  a stored length. Lists hold `ContentId`s rather than positions, so a refresh adds files under new ids and drops
  replaced ones from the id-to-position map without rewriting a list.
- **Directory.** Per trigram, the directory stores its third byte and its list's length, grouped by the first two bytes
  behind a table of 65,537 offsets. A lookup reads one bucket's entries and one list.
- **Intersection.** The rarest list goes first and each next one only filters what is left. A list is read only when
  its turn comes, so file storage stops reading once nothing is left.
- **Segments.** The index is a list of segments over ranges of ids, each with its own directory and lists in this
  layout. A search narrows through every segment and drops the ids the map says are gone.
  [ADR 1.41](./1.41-index-what-a-refresh-reads-in-a-segment-of-its-own.md) states when a refresh adds a segment and
  when it merges them.
- Where the index is kept: [ADR 1.71](./1.71-keep-the-content-index-in-memory-a-scratch-file-or-a-mapping.md). How a
  build writes it: [ADR 1.72](./1.72-build-the-content-index-from-sorted-runs-merged-in-place.md).

## Why

- A literal search of the 171,628-file game-engine checkout took 2.7 s, nearly all of it reading files that cannot
  match. Through the index, `G_ASSERT` read 5,960 of 168,885 files in 0.08–0.14 s (2026-10-15).
- The walk already reads files while it is in their directory, so the index adds no second open (ADR 1.12).
- Rarest-first intersection makes a requirement cost about its rarest trigram's list, however common the others are.

## Consequences

- A build with an index reads every text file, which is nearly all of its cost: 2.72–2.90 s against 0.18 s without one
  on the checkout (2026-10-15). Accepted: opt-in.
- A per-file index narrows by files, not bytes. The files it cannot rule out include the largest ones, which hold
  nearly every common trigram. Accepted.
- A narrowing passes over a bitmap of every id handed out per list it intersects, and fills one of every entry for the
  search to consult: a few hundred KiB each on a 3M-entry tree. Accepted.
- The fixed bucket table is 768 KiB per segment, whatever the tree's size. Accepted.

## Rejected

- **Build the index after the walk, opening every file again** — a second resolution of every path once the walk's
  caches have moved on, which ADR 1.12 measured a sixth slower on a tree past the vnode cache.
- **Varint deltas with the same bitmap fallback** — 137 MiB of lists on the checkout against 115 MiB.
- **Positional trigrams, or a mask of the bytes that follow each one** — lists that store more than an id per file, and
  `G_ASSERT` already reads 5,960 files for 4,529 that match.
- **A sparse bucket table** — less than 768 KiB on a small tree, for a search before every lookup.

## Revisit if

Agents' query logs show false candidates dominating a search, or a tree's distinct trigrams make the directory a
noticeable part of the index. Medium confidence: `G_ASSERT` reads 1.3 files per matching file.
