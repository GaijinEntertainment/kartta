# Narrow content search with a trigram index built from the walk's reads

- **Status:** accepted
- **Date:** 2026-10-14
- **Revised:** 2026-10-15
- **Initiative:** `01-kartta-fs-port`

Content search reads every candidate it cannot settle unopened on every query — every text file the filter selects,
unless a kept size puts it over the limit (ADR 1.10) — and an agent asks many in one session: a literal search of a
171,628-file checkout takes 2.7s, nearly all of it spent reading files that cannot match. An index that
records which files hold which trigrams lets a search open only the files that could, and the build already reads
files while the walk is in their directory (ADR 1.12), so the index takes its content from those reads.

**A build asked for one indexes every text file's trigrams.** `BuildOptions::content_index` names where the index is
kept; `None`, the default, builds none, and a build that reads nothing still reads nothing. With one, every regular
file the rules keep whose extension is not binary is read once — whole when a visitor wants it, in 64 KiB chunks
otherwise — and each text file's distinct trigrams are recorded under its `ContentId`. A trigram is three bytes with
ASCII letters folded to lowercase, and with KELVIN SIGN and LONG S folded to `k` and `s`, the two code points Unicode's
simple case folding joins to an ASCII letter, so a case-insensitive pattern narrows whichever spelling a file holds. A
file's distinct trigrams are found with a 2 MiB seen-bitmap per reading thread, pooled for the build and zeroed lazily,
so only the pages a file's trigrams touch are resident.

**A search reads only the files the index leaves able to match.** `Patterns` reads each pattern as `grep-regex`
translates it and takes the trigrams every matching line must contain: the runs of literal bytes and single-spelling
letter classes, an alternation as a choice of its branches, nothing from an optional piece, a look-around or a wide
class. The derivation can only widen the set — a pattern it cannot read requires nothing — so a search through the
index finds what a full search finds, as of the content the build read. A file the build could not read stays a
candidate for every search. What the index skipped is counted in `Matches::ruled_out`, a sixth place a candidate can
land beside the five ADR 1.11 named, revised to say so; nothing about a search that needs no trigram changes: `\w+`
reads every candidate.
The index holds content as the build read it, as the structure holds the tree as the walk saw it, so a file changed
since the build is ruled in or out by that content until a refresh reads it again (ADR 1.15).

**A posting list is Elias-Fano, or a bitmap where that is smaller.** The layout follows from the list's length and the
number of ids handed out alone, so a list is written into a zeroed region of exactly its size and read without a
stored length. Lists hold `ContentId`s rather than positions, so a refresh adds files under new ids and drops replaced
ones from the id-to-position map without rewriting a list. The directory stores, per trigram, its third byte
and its list's length, grouped by the first two bytes behind a table of 65,537 offsets; a lookup reads one bucket's
entries and one list. Rarest lists are intersected first and each next one only filters what is left, so the lists a
requirement reads cost about its rarest trigram's; beside them a narrowing passes over a bitmap of every id handed out
per list it intersects, and fills one of every entry for the search to consult, a few hundred KiB each on a
3M-entry tree. A list is read only when its turn comes, so file storage stops reading once nothing is left.

**The build spills sorted runs and merges them in place.** Ids are handed out and a file's trigrams appended to the run
under one lock, so a run's pairs arrive in id order and a stable radix sort on the trigram leaves every list ascending.
A run of 2^20 pairs is spilled as the same lists over the run's own ids, which makes the spill about the size of the
finished index. The merge first sums each trigram's length from the run headers alone, so every list's final size and
offset is known before a byte is written, then merges the 256 first-byte partitions in parallel, each writing its
lists straight into place. Reading buffers, run buffers and seen-bitmaps are pooled for the build, because filling
fresh allocations under the id lock, and the allocator's retention of freed ones, cost a first prototype a 2.9 GB
footprint for 0.5 GB of live data.

**The index is kept in memory, in a scratch file, or in a mapping.** `ContentIndexStorage::Memory` holds the index
and the build's spill in the heap; `File` and `Mapped` keep both in scratch files under a directory the caller names,
read by position or mapped, so a build node short of memory holds neither beyond the pages in use. The build writes the
index by position, never through a writable mapping: a mapping keeps every page it wrote in the process's resident set,
and a full filesystem kills the process with SIGBUS where a write returns an error. A scratch file is private to the
process and leaves nothing behind however the process ends: created with no name on Linux, where the filesystem allows
it; unlinked the moment it is created elsewhere on unix, the one moment a process of the same user could open it; opened
delete-on-close with no sharing on Windows. A build that cannot create, write or map one returns
`BuildError::ContentIndex` naming the directory, because it was asked for an index it cannot hand back.

## What it costs

Measured on macOS, against the same two trees as ADR 1.12:

| | entries | text files | trigrams | index | build | peak, memory / file / mapped |
| --- | --- | --- | --- | --- | --- | --- |
| game-engine checkout | 182,714 | 168,885 | 376,660 | 116.6 MiB | 2.72–2.90s | 347–374 / 115–120 / 118–120 MB |
| data volume | 3.08M | 1.91M | 3.72M | 2,576 MiB | 178.6–188.4s | 5,767 / 639 / 640 MB |

The peaks are the process's footprint. A mapping's pages are the system's to reclaim and are not in it: the build reads
its spill through one, and the file and mapped builds peaked at 237–251 MB resident on the checkout and 3.6 GB on the
data volume. In memory, the build holds its spill beside the index it writes, which is the data volume's 5.8 GB.
Without an index the checkout builds in 0.18s at 37 MB and the data volume in 15–21s at 0.44 GB; with one, reading every
text file is nearly all of the cost — 98 GB on the data volume.

Searches on the checkout:

| pattern | full search | through the index | files read |
| --- | --- | --- | --- |
| `G_ASSERT` | 2.66–2.71s | 0.08–0.14s | 5,960 of 168,885 |
| `getBlockByName` | 2.64–2.71s | 0.02–0.03s | 1,445 |
| `fn main` | 2.66–2.68s | 0.01–0.03s | 455 |
| `\bfunction\b` | 2.67–2.68s | 0.39–0.49s | 29,284 |
| `\w+` | 3.46–3.51s | 3.47–3.52s | every file |

On the data volume the same narrowing reads 4,840 of 2.6M candidates for `println!` and 31,289 for `fn main`, in 6.8s
and 8.7s: the volume's text does not fit the page cache, and the files the index cannot rule out include the largest
ones, which hold nearly every common trigram. A per-file index narrows by files, not by bytes.

A build asked for no index pays nothing: against `main`, six interleaved data-volume builds took 16.6–20.6s against
14.8–21.2s and peaked at 433–446 MB against 433–441 MB.

## Considered Options

- **Build the index after the walk, opening every file again** — independent of the build, and a second resolution of
  every path once the walk's caches have moved on, which ADR 1.12 measured a sixth slower on a tree past the vnode
  cache, before any trigram is counted.
- **Varint deltas with the same bitmap fallback** — simpler to write, and 137 MiB of lists on the checkout against
  115 MiB.
- **Spill runs as varint deltas** — 169–178 MiB of spill against 112–122 MiB as lists, for a format the merge then has
  to tell apart from the final one.
- **One run buffer per thread, ids interleaved** — no shared lock, and lists that arrive unordered across runs, so the
  merge has to sort each one; the shared lock costs about 0.3s of thread time on the checkout and nothing on the wall.
- **A single-threaded heap merge** — 0.62s on the checkout against 0.06–0.12s for the partitioned one in the same
  prototype, and an output that has to grow rather than land in place.
- **Write the index through a writable mapping** — no write buffer, and every page written stays resident until the
  build ends: 6.5 GB against 3.6 GB on the data volume, 361–374 MB against 237–251 MB on the checkout, and 345–357 MiB
  against 232–236 MiB on Linux.
- **Map the spill once per partition** — 2.4 GB resident on the data volume against 3.6 GB, but Linux counts a page
  once for each mapping that holds it, and the checkout peaked there at 795–825 MiB against 230–235 MiB.
- **Read a partition's runs into the heap** — 179 MiB resident on Linux on the checkout, for a partition's runs held
  whole: the data volume's footprint grew from 0.6 GB to 2.3 GB.
- **Advise the system to drop a partition's spill pages once merged** — no effect on macOS, and 233–236 MiB against
  230–235 MiB on Linux.
- **Positional trigrams, or a mask of the bytes that follow each one** — fewer false candidates, for lists that store
  more than an id per file; `G_ASSERT` reads 5,960 files for the 4,529 that match, which leaves little to gain.
- **A sparse set of seen trigrams** — sized to a file's trigrams rather than up to 2 MiB per thread, and a hash on every
  byte of every text file the build reads.
- **A sparse bucket table** — less than the fixed 768 KiB on a small tree, and a search before every lookup.

**Revised 2026-10-15: the index is a list of segments over ranges of ids.** A refresh (ADR 1.15) keeps the segments that
hold the files it carried and adds one for the files it read, each with its own directory and lists in the layout
above; a search narrows through every segment and drops the ids the map says are gone. Past eight segments, or once more
than a quarter of the files they hold lists for are gone, the refresh merges them into one, through the same partitioned
writer the build's merge uses.

Revisit when agents' query logs show false candidates dominating a search, or when a tree's distinct trigrams make the
directory a noticeable part of the index.
