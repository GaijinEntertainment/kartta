# Search content in batches folded in index order

- **Date:** 2026-10-14
- **Governs:** `crates/kartta-fs/src/grep.rs` (`BATCH`, `MIN_FILES_PER_SCANNER`, `Fold`), `crates/kartta-fs/src/scan.rs`
  (`Scanner`), `Index::grep`
- **Pinned by:** `crates/kartta-fs/tests/grep.rs` (`files_answer_in_index_order_with_lines_in_file_order`,
  `repeated_searches_answer_identically_across_batches`,
  `a_cut_inside_a_file_keeps_the_last_kept_matchs_trailing_context_only`,
  `a_file_that_crosses_the_limit_another_file_left_it_is_cut_where_the_limit_runs_out`,
  `a_cancelled_search_reports_what_it_covered_and_an_uncancelled_one_is_whole`)

A content search reads files in parallel, and an agent needs the same answer from the same tree on every run. Candidates
are searched in fixed batches and folded in index order, which makes the answer independent of scheduling, at the price
of reading the rest of the batch whose match proves a limit's cut.

## Decision

- **Batches folded in index order.** Candidates are searched in parallel batches of 256 and folded in index order. The
  answer, the matches a limit keeps and the account of the rest are therefore identical across runs and thread counts.
- **Cancellation.** A cancellation is the one exception. Each file checks the cancel token when its turn comes, so
  which files of a batch it turns away is the scheduler's choice, and the answer says it was cancelled.
- **A file's room under the limit.** Each file of a batch may keep as many matching lines as the limit had room for
  when the batch began. The fold cuts a file where the limit runs out and keeps the trailing context of the last match
  it keeps.
- **Pieces of 16 files.** A batch is split into parallel pieces no smaller than 16 files, so a scanner is built at most
  once per 16 files of a batch; a batch shorter than 16 files runs as one piece.
- **The probe buffer.** A scanner allocates its 64 KiB probe buffer on the first file the index has not already settled
  as text, so a scanner that meets only known text never zeroes one.

## Why

- A batch is what a search holds at once and what it reads past the match that proves a limit's cut
  ([ADR 1.11](/design-docs/adr/1.11-content-search-limits.md) states when the search stops), so a smaller batch holds
  less and also parallelizes less. In batches of 16, a limit-of-one search for a pattern found nowhere took 8–18 s
  against 2.7 s in batches of 256 (171k-file game-engine checkout, 2026-10-14, #19).
- Rayon builds a worker's scanner once per piece, not once per thread, and a scanner zeroes about 136 KiB of buffers
  when it is built. Split freely, a full search spent over a third of its user time zeroing them; the 16-file bound cut
  user time from 3.2 s to 2.0 s with wall time unchanged (same tree, 2026-10-14, #19).

## Consequences

- A limited search reads the rest of the batch in which a match proves its cut, up to 255 files it does not report.
  Accepted.
- Two cancelled searches of one tree may cover different files. Accepted: the answer says it was cancelled.

## Rejected

- **Batches that start small and grow** — a limited search proven early reads fewer files past the proof, and one
  whose pattern is rare runs its first batches on one thread: the limit-of-one search took 7.9–17.7 s.
- **One scanner per thread for the whole search** — saves the same zeroing as the 16-file bound, and holds 10 MB more.

## Revisit if

A limited search's read past the match that proves its cut shows in an agent's latency, or a scanner's buffers outgrow
the 16-file bound. High confidence: both costs are measured above.
