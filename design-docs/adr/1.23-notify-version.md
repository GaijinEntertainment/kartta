# Ship kartta-fs on notify 9 under a caret requirement

- **Date:** 2026-10-20
- **Governs:** `crates/kartta-fs/Cargo.toml` (`notify`), `crates/kartta-fs/src/watch/notified.rs`,
  `.github/workflows/ci.yml` (`fresh-resolve`)
- **Pinned by:** the `fresh-resolve` CI job, `crates/kartta-fs/tests/watch.rs`

The macOS and Windows watcher of [ADR 1.17](/design-docs/adr/1.17-change-notifications.md) goes through
notify, and the first notify that reports an overflowed Windows buffer is 9.0.0. kartta-fs 1.0 requires the newest
notify 9 release under a caret requirement, so the lock CI tests holds what a fresh downstream build takes, and one CI
job builds what such a build resolves; the trade is that a downstream build takes every later 9.x release unasked.

## Decision

- **The requirement.** kartta-fs requires `notify = "9.0.0"`, the newest release on crates.io, as a caret
  requirement, optional under the `watch` feature and built only for macOS and Windows. Linux builds no notify.
- **Upgrades.** Move to each later 9.x release. Before raising the requirement and the lock, check in notify's changelog
  that a Windows completion with no bytes, or `ERROR_NOTIFY_ENUM_DIR`, is still a rescan that names no path; that an
  `FSEvents` rescan still names the directory the system names; that an `FSEvents` root change still carries the
  `root changed` info; and that a deleted Windows root is still reported as the removal of its path. Then run the watch
  tests, on Windows through CI.
- **A release the tests fail on.** Find out first whether it loses a change or reports it late. A lost change holds
  the requirement below the release; a late one is taken: kartta-fs moves, and states the new delay in
  [ADR 1.17](/design-docs/adr/1.17-change-notifications.md).
- **The fresh resolve.** The `fresh-resolve` job runs `cargo update`, then builds and tests the workspace on Linux,
  macOS and Windows, on the pinned toolchain and actions. It is the one job not under `--locked`: what it moves with is
  what it exists to read.

## Why

- notify 8.2.0, the last 8.x release, ignores the byte count a Windows completion reports, so an overflowed buffer
  loses its changes with no sign; notify 9 reports it as a rescan, which the watcher turns into a lost batch.
- A caret requirement lets a downstream build that resolves afresh take each 9.x release once published, whatever this
  repository's lock holds (#127). Naming the newest release keeps CI on the version a new consumer downloads.
- A later version that changes what the watcher calls fails that build, and one that changes what a rescan or a root
  change means changes the watcher's answers; the checks above are the meanings the watcher reads.
- rc.7 passed its build and failed the watch tests on macOS, unseen by every job under `--locked`, while `cargo install`
  without `--locked` already took it (#1054). It starts each stream at `FSEventsGetCurrentEventId()` where rc.6 asked
  for `kFSEventStreamEventIdSinceNow`, so `FSEvents` sends history before it goes live (`FSEvents.h`, the `sinceWhen`
  steps of the stream's lifecycle). The change was late, not lost: 0 of 800 paths lost over 200 starts, the latest
  reported 323 ms after its write, and rc.7 with the old start id alone reported within 12 ms (2026-11-02). 9.0.0
  keeps that start id (`src/fsevent.rs:827-829`).

## Consequences

- A notify release that breaks the build or changes a meaning reaches downstream builds before this repository sees
  it, and costs a release of kartta-fs. Accepted.
- `fresh-resolve` fails every change, not only the one that met the release, until a release that breaks kartta is
  answered, and it spends a second full test run on each platform. Accepted: that failure is what a consumer meets.

## Rejected

- **notify 8.2.0 everywhere** — the silent loss of an overflowed Windows buffer, and on Linux an event for every open
  and close: one read of every file on 1.8 million entries raised 1,690,730 of them, past a distribution's queue.
- **notify 8.2.0 on Windows alone** — back to the silent loss notify 9 was taken for, with two major versions of
  one crate to keep.
- **An exact `=9.0.0` requirement** — Cargo keeps one version of a crate per compatible range, so a consumer that
  requires any other notify 9 fails to resolve, and no consumer takes a notify fix without a release of kartta-fs.
- **`>=9.0.0-rc.6, <9.0.0-rc.7`, a requirement that stops below rc.7** — the same refusal as an exact requirement, for
  a change that is only late, and it keeps the Windows handles rc.7 stopped closing under a pending read.
- **Own `FSEvents` and `ReadDirectoryChangesW` backends** — the same system calls the crate makes, as unsafe code to
  keep, for no measured difference, and the Windows backend would be code only CI runs.

## Revisit if

notify publishes 9.0.1 or a later 9.x release, or 10.0. High confidence that one will come, with no date.

## History

- 2026-11-24 — The requirement: notify published 9.0.0, the release the candidate requirement waited for, with the four
  meanings the watcher reads unchanged from rc.9, so kartta-fs requires the release and follows 9.x releases
- 2026-11-02 — The requirement: rc.7 reached every fresh resolve untested and its watch-test failures were late reports,
  not lost changes, so the requirement moves and a job reads what such a resolve takes (#1054)
