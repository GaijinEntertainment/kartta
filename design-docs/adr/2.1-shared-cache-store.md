# Share per-file data through content-addressed packs

- **Date:** 2026-10-16
- **Governs:** `crates/kartta-cache/src/key.rs`, `crates/kartta-cache/src/pack.rs`, `crates/kartta-cache/src/writer.rs`,
  `kartta_cache::Store::{open, get, stats}`
- **Pinned by:** `crates/kartta-cache/tests/store.rs`

Processes on one node index trees a few files apart, and each computes the same per-file data cold. `kartta-cache`
lets one process reuse what another computed for the same bytes: entries are keyed by content and by what computed
them, and live in immutable packs that every process maps and none writes after publishing. The trade is a hash of
every file a producer reads, and a lookup that serves damage as a miss rather than an error.

## Decision

- **The key.** An entry is keyed by the content it was computed from and by what computed it, never by a path. The
  content half, `ContentHash`, is the blake3 hash of the file's bytes, so identical contents share one entry wherever
  they sit and whichever tree holds them. The other half, `Namespace`, is derived from the kind of data and a
  fingerprint of the code that computed it, which the producer derives from its rules, grammar and encoding rather than
  keeping it by hand. A new fingerprint is a new namespace, so an entry computed by older code is never served to newer
  code, and two versions of a producer that share one store keep their own entries. Each producer and each language
  have their own namespace, so a grammar change drops one language's entries and nothing else. The trigram index has a
  fingerprint too, derived as [ADR 2.2](/design-docs/adr/2.2-build-cache-lookup.md) states.
- **Packs.** Entries live in packs, not in a file each. A process gathers what it computed in one `PackWriter`, which
  the threads of a build share, and publishes one pack. `Store::open` maps every pack in the directory, and
  `Store::get` answers from the mapped indexes, opening nothing per entry.
- **Publishing.** A pack is published once and never written again. The writer hard-links the finished file under a
  hash of its index, and a link creates a name only where none exists, so a pack appears whole or not at all and no
  file a reader mapped is ever replaced. Processes therefore read and publish in one directory with no lock and nothing
  shared but the files. The directory has to allow hard links.
- **The check.** Each index entry carries a 64-bit check over its namespace, content hash and payload, verified before
  the payload is returned: damage escapes it only with a chance of 2^-64, and otherwise reads as a miss, never as data.
  The check guards against damage, not against a writer: a process that can write the directory can publish any pack
  it likes.
- **What a store reports.** `Store::stats` reports the packs and entries a store mapped, and nothing else.
- **Pack count and age.** [ADR 2.4](/design-docs/adr/2.4-cache-pack-merge.md) bounds the number of packs, and
  [ADR 2.3](/design-docs/adr/2.3-cache-entry-expiry.md) expires entries by the time each was published.

The [crate docs](/crates/kartta-cache/src/lib.rs), [`PackWriter`](/crates/kartta-cache/src/writer.rs) and
[`Store`](/crates/kartta-cache/src/store.rs) state every case: the pack layout, the writer's buffer, a second publish of
the same pack, what a store sees of packs published or removed after it opened, and what a damaged key or file reads
as.

## Why

- A content-index build of the game-engine checkout took 1.38-1.40 s at a 4-CPU quota on Linux, about 85% of it
  extracting and writing trigrams, redone for 169,188 text files when a hundred of them differ (2026-10-16). The code
  graph repeats its per-file parsing the same way.
- On macOS a file open costs more than computing a small entry again: three million lookups took 47-64 s as one file
  per entry, whichever directory fan-out held them, and 0.054 s in one mapped index (2026-10-16, #26).
- Collision resistance is load-bearing: the bytes come from repositories, and a collision would hand one file the entry
  computed for another.
- A cache that served wrong data would turn into wrong answers wherever the data is used, so damage must read as a
  miss.

## Consequences

- A hit still pays for reading and hashing the file. On Linux that is most of a hit, 0.44 s against 0.97 s to extract
  the trigrams again on the game-engine checkout (2026-10-16); on macOS opening the files is most of either path, so a
  hit saves the extraction and little else. Accepted.
- A build that finds nothing pays for writing, and its threads queue on the writer's lock: 0.1-0.2 s of a cold Linux
  build. Accepted.
- Damage in a key reads as an absent entry, so it is recomputed rather than noticed. Accepted.
- A cold read from a real disk is unmeasured: the Linux figures come from a virtual machine's file-backed disk. Windows
  is covered by the test suite only. Accepted.

## Rejected

- **One file per entry** — on macOS three million lookups spend 47-64 s opening files, whichever fan-out holds them.
- **One index per tree, updated by each process** — a file every process writes cannot be shared without locks, and an
  index keyed by its tree stores two identical trees twice.
- **One record per content holding every producer's data** — producers finish at different times, so the record would
  be completed after it was published, and one producer's new version would discard the others' data.
- **The fingerprint as a check made after the lookup** — two versions of a producer share each key and overwrite each
  other's entries for as long as both run.
- **Publishing by rename** — replaces an existing file under its readers on unix and fails on Windows while one is
  mapped.
- **A portable blake3 build** — needs no C compiler, but hashing the checkout took 0.36 s against 0.20 s with the SIMD
  implementations at the same quota.
- **Write buffers sharded per thread** — would shorten the queue on the writer's lock, which only a build that finds
  nothing pays, 0.1-0.2 s on Linux.
- **Telling a damaged key from an absent one** — would take hashing every index at every open.
- **Counts of hits, misses, damaged lookups and rejected packs** — nothing read them, and the lookup counts cost every
  lookup an atomic increment on one cache line that every thread of a build shares.

## Revisit if

A store has to sit on a filesystem without hard links, or cold builds become frequent enough that the shared writer's
lock matters. Moderate confidence: neither is measured on the nodes, and how often a node's builds find nothing is not
known.
