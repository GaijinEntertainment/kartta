# Read a file's own facts on demand, not during the walk

- **Status:** accepted
- **Date:** 2026-08-24
- **Revised:** 2026-10-14
- **Initiative:** `01-kartta-fs-port`

The index used to say that nothing after a build touches the filesystem. It no longer does. The walk records
**structure** — which entries exist, what each one is, where a symlink points — and that is still one coherent
snapshot. A file's **own facts**, its size and whether it holds binary content, are read when a caller first asks and
kept from then on.

The split is not aesthetic. Measured on a live home directory of 1,418,788 entries and 1,213,028 files:

| | during the walk | on demand |
| --- | --- | --- |
| size | ~3.7s of a ~6.5s build | ~0.3ms per directory listed, once |
| binary | 1.2 to 7.4 minutes for the tree | 295µs per file, once; 1.1µs after |

Stat'ing during the walk spends about half a build on sizes a caller mostly never looks at, and probing during the walk
is not on the table at any tree size — the same measurement puts a full-tree classification between one and seven
minutes against a build of seconds. Meanwhile the work a real caller needs is tiny and clustered: one directory's worth
of contiguous entries stats in 0.3ms cold, and a listing drawn a second time costs nothing at all.

**A small tree cannot show this.** The same comparison on a 65,848-entry source tree made the walk-time stat look like
2% of the build, because the whole inode working set stayed in cache. It is roughly half at 1.4M entries, where it does
not. Any future measurement of this crate's costs belongs on a tree of that order.

## What it costs

**Coherence.** Two sizes taken from one index may describe two different moments, and neither is refreshed once taken.
An index is no longer a single answer about a single instant — it is a fixed answer about structure and a growing set
of answers about content. That is stated on every surface that reads late, because a caller who believes otherwise gets
a subtly wrong answer rather than an error.

**A place for failures to be reported.** `BuildError::Metadata` is gone with the walk-time stat. A build no longer
reads a file's size, so no build failure can name one — it still stats an ignore file it is about to read, and takes
each entry's kind from the directory listing, which is metadata of a different kind failing through its own channels.
A file that will not stat or will not open answers `None` at the point of the ask, where the caller can act on it —
which is the compensation, and a better one than a list drained hours earlier.

**A breaking move.** `Entry::size` could not survive: `Entry` holds no root and no reference back to the index, so it
has no route to the filesystem to fill a value with. Both late answers are therefore `Index` methods keyed by path.

## How it is stored

Two tables of atomics, one slot per entry, positionally aligned with the entry list — an `AtomicU64` for the size with
two reserved values standing for unread and unreadable, an `AtomicU8` for the classification. Nine bytes per entry,
about 12 MB on the tree above, allocated in ~1ms. Unread is zero in both tables, and a size is stored plus one, so a new
table is a zeroed allocation. On the platforms this runs on, one that large comes as fresh pages the allocator hands out
without writing, so a page of slots costs resident memory only once a query fills one of them.

Queries take `&self` and two may run at once, so filling a slot cannot take an exclusive borrow. Relaxed atomics with
no lock are enough because nothing is published alongside the value — no reader depends on any other write becoming
visible with it.

**The first read to publish wins.** Two threads racing on one entry both read the filesystem, and their reads can
disagree: a file rewritten between them has two truthful sizes. Each publishes with `compare_exchange` and a losing
thread answers with the value already in the slot rather than its own, so one entry has one answer. Letting both store
would leave the slot holding whichever call finished last and hand two callers different answers, against a contract
that promises the first answer and then holds it.

## The binary rule

Two layers, in order. An extension naming a format that is binary by construction answers with nothing opened.
Everything else is settled by whether a NUL appears in the first 64 KiB.

The extension list is **one-sided**: it says "binary, do not open" and never says text. Its two possible mistakes are
not symmetric. A text format listed here is answered without a probe, reported binary, and passed over by any content
search — a file nobody can find. A binary format left off is probed, found to hold a NUL, and answered correctly at
the cost of one read. So a format earns its place only by being binary *by construction*, and the list stays short
rather than complete.

That asymmetry is also the case against a companion list of text extensions. Such a list would have to claim
unconditionally that a format never holds binary content, and `json`, `txt` and `xml` all routinely carry an embedded
blob. On the measured tree it would have covered 43.1% of files, which is the temptation, and it would have been wrong
about some of them in the expensive direction, which is why there is not one.

On that tree the binary list answers 8.2% of files for free, and those are the archives, media, disk images and model
weights that hold the bulk of the bytes.

64 KiB is chosen for what it catches, not what it costs. Cost is flat — 56.2µs per file at a 1 KiB probe against
57.0µs at 1 MiB, because the open dominates and a read returns only what the file holds. Accuracy is not: across
10,026 sampled files holding 2,076 NULs, a 1 KiB probe misses 11, git's 8000 bytes misses 4, 64 KiB misses 1, and
256 KiB misses none. 64 KiB is what `grep-searcher` reads at a time, so a searcher applying its own rule to the same
file agrees with this one — one concept with two answers is the defect worth more than the last 0.05%.

The verdict therefore describes a **prefix**, not a file. Text for 64 KiB and binary after reports text.

## Considered Options

- **Keep both at walk time, as the port arrived** — one coherent snapshot and a simple contract, at half a build spent
  on sizes nobody reads. Classification could never join it at all, so the crate would have had two different answers
  to "when is this read" regardless.
- **Make it a `BuildOptions` flag, eager or lazy** — every caller then has to know which index it holds, and
  `Entry::size` would mean two different things depending on a field set somewhere else. Two sources for one concept is
  exactly what the shared vocabulary exists to prevent.
- **A `RwLock<HashMap>` keyed by entry, paying only for what is asked** — no 12 MB table, at a lock and a hash on
  every read of a value the atomic table answers with one load. The table is allocated once in about a millisecond;
  the map would be paid for on every ask forever.
- **`OnceLock` per entry instead of raw atomics** — the right abstraction for "compute once", at 24 bytes per slot
  against nine, and it buys a guarantee (exactly-once) that is worth nothing here because a repeated read is
  idempotent.
- **Return a `Result` rather than `Option` from the late reads** — more honest about why an answer is missing, and it
  makes the failure uncacheable in a byte, so a caller looping over an unreadable directory pays the syscall on every
  pass.
- **Refresh a cached answer when the file changes** — correct, and it needs a watcher or a stat before every read,
  which is the cost the whole design exists to avoid. An index is already a snapshot; a caller who needs current
  answers rebuilds.

Revisit if a caller needs content answers to be coherent with the structure, which means eager reads under an explicit
name rather than a flag on this path; if a tree turns up where the extension list's shape rather than its contents is
wrong; or if a searcher lands that probes to a different depth, in which case the two constants become one.
