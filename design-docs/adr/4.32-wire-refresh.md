# Refresh the wire's engine in place where its build kept stamps

- **Date:** 2026-10-21
- **Governs:** `crates/kartta-ffi/src/built.rs` (`Built::refresh`, `Shared`), `crates/kartta-ffi/src/handle.rs`
  (`Kartta::refresh`), `crates/kartta-ffi/src/wire/refresh.rs`, `crates/kartta-ffi/src/wire/build.rs` (`StoredErrors`),
  `bindings/go/wire/refresh.go`
- **Pinned by:** `crates/kartta-ffi/tests/dispatch.rs`, `crates/kartta-ffi/src/handle.rs` tests,
  `crates/kartta-ffi/tests/golden/refresh.json`, `refresh-paths.json`

A `build` of [ADR 4.2](/design-docs/adr/4.2-c-abi-wire.md) walks every entry and builds every graph again while every
query answers `building`, a high price for a wire consumer to take in a change to its tree. `refresh` brings the engine
up to the tree in place ([ADR 3.33](/design-docs/adr/3.33-refresh-dependency-tracking.md)), and only for a build that
kept stamps, so a consumer that will refresh pays the stamps' memory and one that never does pays nothing.

## Decision

- **Stamps.** `build` takes `stamps`, false by default and true when `watch` asks for a follow
  ([ADR 4.33](/design-docs/adr/4.33-wire-follow.md)), which keeps each file's stamp and what its resolution asked of
  the tree for as long as the engine lives ([ADR 3.33](/design-docs/adr/3.33-refresh-dependency-tracking.md)).
- **`refresh {id?, binding_id?, paths?}`.** `paths` absent or null refreshes the whole tree. A list refreshes the
  root-relative paths it names, walking only their parts, up to one part for every 30 entries and never fewer than 50;
  past that it walks the whole tree and answers `widened`: `named`, `parts` and `limit`, the counts the engine gives
  ([ADR 3.80](/design-docs/adr/3.80-named-refresh-widening.md)). `[]` walks nothing and leaves the engine as it was. A
  path the engine refuses by its spelling ([ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md)) answers
  `invalid_params`, the engine's message naming the fault. The wire asks `PathFault` before it reads the handle's
  state, so a wrong path answers it before `not_built` or `no_stamps` could, neither of which reaches the engine. Go's
  `wire.RefreshParams.Paths` takes no `omitempty`, so a nil slice asks for the whole tree and an empty one for nothing.
- **The answer.** The answer carries the engine's counts: `walked`, `tree`, `added`, `removed`, `extracted`,
  `resolved_again`, `dropped` (absent where every graph was built again), `reconfigured`, `rebuilt`, `widened`,
  `errors`, the refresh's own failures as `total` and the first 20 `listed`, and `watch`
  ([ADR 4.33](/design-docs/adr/4.33-wire-follow.md)). It carries no elapsed time, so a golden of it is deterministic.
- **Failures.** `stats` then counts the build's failures with those under what the refresh walked, and those it met
  again, given way to the refresh's, the rule the MCP server's `refresh` follows
  ([ADR 4.44](/design-docs/adr/4.44-mcp-refresh-tool.md)). The stored failures keep every one, and an answer lists the
  first 20. One that names a path carries it as `path`, native, for an operator; one in the tree spells it from the root
  as given and also carries `file`, the root-relative form `paths` takes, so a consumer can retry the failure it was
  told of. A name that is not UTF-8 has neither form: `path` and `file` hold replacement characters and do not name it.
- **No stamps.** A refresh of an engine built without stamps answers `no_stamps`, its message naming
  `build {"stamps": true}`. `rebuilt` stays in the answer, false in every one while the refusal stands, so lifting it
  removes one check and changes no shape.
- **The lock.** The slot holds the engine under an `RwLock`. A query holds the read lock for its whole run and a refresh
  the write lock, so a query waits for a refresh under way rather than reading an engine halfway through it, and
  refreshes run one at a time. A refresh that panics poisons the lock, and every call that reads the engine then answers
  `internal`, naming `build`, which replaces the engine and its lock.
- **Cancel.** A refresh is cancelled by its ids as [ADR 4.30](/design-docs/adr/4.30-wire-cancellation.md) states. A
  cancel stops a refresh only before its walk ends, since the engine brings its graphs up to a replaced index whatever
  the cancel says. A cancelled refresh answers `refresh_cancelled`, a failed one `refresh_failed`, and after either the
  engine answers as it did before.
- **A build over a refresh.** A build cancels the refreshes in flight before it empties the slot, under the refreshes'
  lock, which a refresh holds while it reads the slot and enters its registry, so every refresh that read the engine
  the build drops is cancelled and none reads it after. A refresh past its walk finishes on the dropped engine, which
  it keeps until it answers, as a running query does, and answers what it changed there; the build does not wait for it.

## Why

- A rebuild took 16-29 s on the C++ game-engine tree, every query answering `building` throughout, where a refresh of
  one edited file takes milliseconds (2026-10-21, #316).
- A refresh without stamps reads every file again and builds every graph while holding the old ones, so it takes about
  a build's time and peaks higher than one, 1,596 MiB against 883 MiB on the C++ tree (2026-10-21), while every query
  waits on the write lock. A build does the same work for less and lets a query answer `building` at once.
- Stamps cost memory a consumer that never refreshes would carry for nothing: 31.7 MiB more on the C++ tree
  (2026-10-21).
- A refresh's own failures must give way: a refresh that kept only the first 20 could not drop those past them, and
  `stats` would go on counting failures the tree no longer has.

## Consequences

- A query waits behind a refresh under way, milliseconds for an edit and the whole refresh for a widened one: accepted.
- A consumer that builds without stamps and later wants a refresh pays a second build: accepted.
- A stored failure in the tree holds a second string, as long as its path less the root: accepted, since a refresh then
  reads it and spells no stored failure's path again.

## Rejected

- **A refresh without stamps, `rebuilt` set** — a build's time at a higher peak, and a query that waits behind it has
  no `building` to read.
- **Stamps on by default** — every consumer that never refreshes would keep their memory; the MCP server keeps them
  because its watch refreshes ([ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md)).
- **A `Mutex` on the engine** — queries run concurrently, and each would queue behind the others.
- **The old engine serving during a refresh** — a second engine doubles the memory to spare a wait of milliseconds
  ([ADR 4.4](/design-docs/adr/4.4-mcp-index-follow.md)).
- **The first 20 failures and a count, as a build kept them** — a refresh could not give way those past the 20.
- **`path` alone, documented as native** — every consumer would strip the root and turn Windows separators by hand to
  retry a path `refresh` refuses as it stands (#1047).

## Revisit if

A refresh without stamps comes to cost a fraction of a build, or queries cannot afford to wait behind a refresh. High
confidence: the refusal's figures hold on the tree measured.
