# Resolve a BLK include as the engine loads it, and read the mount table from the files that state it by name

- **Status:** accepted
- **Date:** 2026-10-16
- **Initiative:** `03-code-graph`

BLK files configure the game trees the code graph reads — units, weapons, shaders, builds — and include one another by
paths whose meaning the engine fixes. A BLK file declares no symbol and makes no call, so its includes are all it gives
the graph.

**A path is resolved as the engine reads it, and kept as written where it names no file.** The include resolves the
value the engine's reader yields: the `~` escapes decoded, the block comments and trailing blanks of an unquoted path
dropped, the CR bytes and the final line end of a triple-quoted path dropped, and `\` read as `/`. A path that names no
file is an import that keeps the path as written, without its quotes, so it is the spelling an agent searches for.

**Only a text that can include a file or state a mount is parsed.** A file the engine loads as binary, as its header
shows, holds no text. A text that can spell neither the `include` keyword — in any case, through `~` escapes, or split
by the CR bytes a triple-quoted name drops — nor a bare `mountPoints` name holds nothing the graph keeps. The check
reads bytes, not syntax, so it errs toward parsing: a text it admits, such as one with an `includes:i=1` parameter, can
still extract to nothing. On the game-engine tree this was built against, 51,549 of 82,254 BLK files extract to nothing,
and none of them is parsed.

**The first character of a path selects how it resolves.** A relative path names the file relative to the including
file. A `#` path is relative to a root the application sets, so it names the one repository file that ends with it at a
directory boundary, and no file when several do. A `%name/rest` path names `rest` below the directory a mount table maps
`name` to. An absolute path, a drive-letter one such as `C:/x.blk` included, and a path relative to the working
directory, `:/`, name no repository file.

**The mount table is the first root `mountPoints` block of the files named `settings.blk`, `application.blk`,
`aot_config.blk` and `libs_aot_config.blk`.** The engine takes the table from whatever file an application names; the
reference extraction compiles it from the walk of every BLK file. A resolver sees only the `Repository`, which finds a
file by its name and cannot list files by extension, and a second read of every BLK file breaks the single read per file
that the index gives. The four names are the conventions of the settings file of a game, the configuration of a tool and
the `--config` files of the daScript AOT compilers. A child block maps its name to its `forSource` directory. That
directory is relative to the working directory of an application, which no file states, so the part after its leading
`..` names a directory below an ancestor of the stating file, and exactly one ancestor must hold the target. A `t`
parameter maps its name to a directory relative to the stating file. The mappings stated nearest the including file,
which share the most leading path components with it, decide, and they must place the same file.

On that tree, 23 files open a root `mountPoints` block, and 6 of them have other names, such as `eden.settings.blk` and
`wt_aot_config.blk`. Every mount-path include is in one game, whose three `settings.blk` files state its mounts, and no
include resolves differently without the other six files.

**Every match is case-sensitive.** The engine reads the shipped files from a vromfs that lowercases each path, and the
reference resolves a target to the one file that differs from it only in case. A `Repository` has no lookup that ignores
case, so such a target names no file. On that tree, this loses 35 includes, all in one file that writes `gameData` for a
`gamedata` directory.

Extraction matches the reference extraction on all 82,254 files. Of 316,430 includes, 316,365 resolve, and the resolved
includes match the reference on every file but the one above. The mount table costs 44 reads, one for each file of
the four names on that tree, in 9 ms, and the extraction takes 6.1 s on one thread against 6.2 s for the reference.

## Considered Options

- **A second read of every BLK file in the resolver** — the full table, at the cost of 82,254 more reads per build.
- **A resolver built over the raw extractions of the files its language claims** — the full table without a second
  read, because every BLK extraction already holds its mount directives. This changes the `kartta-lang` contract of ADR
  3.1, so it needs a decision of its own.
- **Case-insensitive matching through `files_in_dir`** — it finds a file name that differs in case but not a directory
  name, and it lists a directory for each include that does not resolve.

Revisit when a resolver can see the extractions of the files its language claims, when `Repository` can find a path
without case, or when a tree states the mounts that its includes need in a file of another name.
