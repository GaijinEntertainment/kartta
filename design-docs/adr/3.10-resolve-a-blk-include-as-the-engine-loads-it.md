# Resolve a BLK include as the engine loads it

- **Status:** accepted
- **Date:** 2026-10-16
- **Updated:** 2026-10-16
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta-lang-blk/src/{lib,text,walk,resolve}.rs`
- **Pinned by:** `crates/kartta-lang-blk/tests/extract.rs`, `crates/kartta-lang-blk/tests/resolve.rs`

BLK files configure the game trees the code graph reads — units, weapons, shaders, builds — and include one another by
paths whose meaning the engine fixes. A BLK file declares no symbol and makes no call, so its includes are all it gives
the graph; each resolves as the engine's reader yields it, and a file that cannot include anything is not parsed.

## Decision

1. **A path is read as the engine's reader yields it:** the `~` escapes of a quoted path decoded, the block comments
   and trailing blanks of an unquoted path dropped, the CR bytes and the final line end of a triple-quoted path
   dropped, and `\` read as `/`. Every `include` statement with a path is a directive, whatever the case of the
   keyword.
2. **A path that names no file** is an import that keeps the path as written, without its quotes, so it is the spelling
   an agent searches for.
3. **Only a text that can include a file or state a mount is parsed.** A file the engine loads as binary, as its header
   shows, extracts to nothing: a first byte from 1 to 6, a BBF3 header (`\0BBF`, `\0BBz`) on a file of 12 bytes or
   more, and the obsolete `blk 1.1` and `SB`..`blk` headers. A text that can spell neither the `include` keyword, in any
   case, through `~` escapes, or split by the CR bytes a triple-quoted name drops, nor a bare `mountPoints` name
   extracts to nothing and is not parsed. The check reads bytes, not syntax, so it errs toward parsing: a text it
   admits, such as one with an `includes:i=1` parameter, can still extract to nothing.
4. **The first character of a path selects how it resolves:**
   - a relative path names the file relative to the including file;
   - a `#` path is relative to a root the application sets, so it names the one repository file that ends with it at a
     directory boundary, and no file when several do;
   - a `%name/rest` path names `rest` below the directory a mount table maps `name` to, as
     [ADR 3.146](./3.146-read-the-blk-mount-table-from-the-files-that-state-it-by-name.md) states;
   - an absolute path, a drive-letter one such as `C:/x.blk` included, and a path relative to the working directory,
     `:/`, name no repository file.

   A relative or mount target that names no file takes the one file that differs from it only in ASCII case, as
   [ADR 3.142](./3.142-take-the-one-file-that-differs-only-in-case-where-a-game-s-vromfs-loads-it.md) states.

## Why

- The include is the value the engine's `getValue` yields, so the spelling it resolves is the decoded one, and the
  spelling an agent searches for is the one written.
- Most BLK files are data that include nothing: 51,549 of 82,254 on the game-engine tree extract to nothing
  (2026-10-16), and none of them is parsed.
- A `#` root is set by the application, which no file of the repository states, so only a path one file ends with is
  certain.

## Consequences

- A `#` include that two files end with stays an import. Accepted.

## Rejected

- **Parse every text BLK file** — parses the 51,549 files of that tree that give the graph nothing.

## Revisit if

The engine's `DataBlock` reader changes how it reads an include's path. Held with high confidence: each rule follows the
reader's own handling.
