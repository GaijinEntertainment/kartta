# Search content through ripgrep's engine

- **Status:** accepted
- **Date:** 2026-10-14
- **Revised:** 2026-10-19
- **Initiative:** `01-kartta-fs-port`

`Index::grep` searches the content of regular files line by line. The pattern union compiles through `grep-regex` and
each file streams through `grep-searcher` — ripgrep's own matcher and searcher — so a pattern an agent writes for `rg`
means the same here, and the line handling is the one ripgrep has already been hardened on.

**Files are streamed, so no size bound is needed.** The searcher reads a buffer at a time and grows it only to fit the
longest line, which keeps a search's memory on the scale of a line rather than of a file. A caller that wants a size
bound sets one; none is applied by default, because the consumer the index is built for reads whole files, and a
default bound would turn away files no caller chose to skip. One bound is unconditional: a line past 256 MiB fails
its file. A file with no line breaks would otherwise grow the buffer to the file's size, and no such line is worth
reading as a line.

**Byte-order-mark sniffing is off.** The searcher can transcode a UTF-16 file it finds a BOM on, which would search
different bytes from the ones on disk. Off, the bytes searched are the file's bytes — the same bytes the binary rule
reads and a future content index would key on — and a UTF-16 file, which holds NULs, is binary, as `is_binary` already
answers for it.

**`$` matches before `\r\n` too.** The matcher runs in CRLF mode, so a file with Windows line endings answers like one
without, and a reported line drops either ending.

**One file, one open, one rule.** A candidate is opened refusing, on unix, a symlink that took its place since the walk
— on Windows the open still resolves one, the gap the crate already states for every late read — the stat that
confirms it is a regular file supplies its size, and unless the index already knows the file is text its first 64
KiB settle it by the rule `Index::is_binary` applies (ADR 1.6). The searcher is then handed those bytes followed by the
rest of the file, so nothing is read twice, and the size and verdict are kept, so a later search skips a known binary or
oversized file without opening it. A NUL past the first 64 KiB does not make a file binary here, because it does not
there; one concept with two answers is the defect.

**A file is judged by name, then size, then content.** A binary extension skips the file unopened. Otherwise a file
larger than the caller's bound is oversized, and only then does a NUL make it binary: the size is what lets a search
skip the file unread, so it is checked before the bytes. Every place that learns these facts keeps this order — the
planning pass that settles candidates from kept facts as much as the open that learns them — and an open that answers
`Index::is_binary` keeps the size its stat reported, as a search's open does. Revised 2026-10-19: the planning pass
checked a kept binary verdict first, so a file over the bound with an early NUL was oversized on a fresh index and
binary once the build, a listing or `is_binary` had read it — one file, two answers, chosen by history.

**Index order, whatever the scheduling.** Candidates are searched in parallel batches of 256 and folded in index order,
so the answer, the matches a limit keeps, and the account of the rest are identical across runs and thread counts.
A cancellation is the one exception: each file checks it when its turn comes, so which files of a batch it turns away
is the scheduler's choice, and the answer says it was cancelled. Each file of a batch may keep as many matching lines as the limit had room for when the batch began; the fold cuts a
file where the limit runs out and keeps the trailing context of the last match it keeps. A batch is therefore what a
search holds at once and what it reads past a filled limit, and a smaller batch holds less and parallelizes less: in
batches of 16, a limit-of-one search of a 171k-file tree for a pattern found nowhere took 8–18s, against 2.7s in
batches of 256. Each parallel piece of a batch covers at least 16 files, because rayon builds a worker's scanner once
per piece and not once per thread, and a scanner zeroes about 136 KiB of buffers when it is built. Split freely, a full
search spent over a third of its user time zeroing them; the bound cut user time from 3.2s to 2.0s with wall time
unchanged. The 64 KiB a scanner probes files into is allocated on the first file the index has not already settled as
text, so a scanner that meets only known text never zeroes it.

## What it costs

`grep-searcher` links `encoding_rs` unconditionally — about 138k lines, for the BOM sniffing this crate turns off — and
with it the one conjunctive licence in the graph, `(Apache-2.0 OR MIT) AND BSD-3-Clause`, which `deny.toml` now allows.

Measured on a 171,628-file game-engine checkout, warm cache, macOS, against `rg` with the same in-tree ignore rules:
answers are identical in matched lines and files (28,286 and 4,529 for one identifier across the tree; 54,290 and 6,512
for one word across 8,785 script files). A full-tree search takes 2.6–2.7s against `rg`'s 2.8s, which includes its own
walk; peak memory is about 50 MB on both. Wall time is flat from 4 to 18 threads on that machine, while system time
grows with them — the search is bound by the filesystem, and at equal thread counts the two spend the same system time
per search. On a 3.03M-entry data volume, the 32,779 Rust files answer identically to `rg` (7,081 lines in 2,547
files) in 12.0s cold and 0.53s warm; `rg` takes 10.2s, nearly all of it walking a tree the index has already walked.

## Considered Options

- **Own the line scanner over `grep-regex`** — drops `encoding_rs` and its licence. A streaming scanner has to carry a
  partial line across reads, keep leading context across buffer refills and count lines incrementally, which is the
  searcher's whole job; owning it means maintaining a second copy of code ripgrep already maintains, to save a
  dependency that costs compile time and not run time.
- **Read each file whole and search the slice** — simple, and it makes every file's size a memory cost, so it needs a
  default size bound, which the consumer cannot afford.
- **Leave BOM sniffing on** — UTF-16 files become searchable, as in ripgrep. The bytes searched then differ from the
  bytes on disk, so a content index keyed on raw bytes cannot narrow those files, and `is_binary` and the search
  disagree about them.
- **Let the searcher open files by path** — fewer lines, and its open follows a symlink that replaced a file since the
  walk, reading through a link this crate reports and never reads through.
- **Keep a long line's start rather than a window around its match** — the simpler cut, and on a minified line it
  routinely reports a line that does not contain the match it was reported for.
- **Batches that start small and grow** — a limited search that fills early reads fewer files past the limit, and one
  whose pattern is rare runs its first batches on one thread: the limit-of-one search above took 7.9–17.7s.
- **One scanner per thread for the whole search** — saves the same zeroing as the 16-file bound, and holds 10 MB
  more.

Revisit if the dependency's weight starts to matter more than the code it saves — then the line scanner is ours — or if
UTF-16 sources turn up that agents need to search.
