# Make the ignore source set explicit

- **Status:** accepted
- **Date:** 2026-08-24
- **Revised:** 2026-10-20
- **Initiative:** `01-kartta-fs-port`

Git reads ignore rules from four places, and only one of them lives in the tree. The `.gitignore` files inside it are
content of the tree like any other file; `$GIT_DIR/info/exclude`, `core.excludesFile` and its XDG fallback
`~/.config/git/ignore` are machine-local. An index that honours the second group is therefore **machine-dependent**: the
same tree, on a laptop and in CI, indexes to different file sets, and nothing downstream can tell. The guarantee below
that line is over the tree and never over a commit — a build reads the working tree rather than git's index, so two
checkouts of one commit differ wherever their untracked, unignored content does. This is not
hypothetical — measured across four real repositories, the file set matched `git check-ignore --no-index` exactly in
every one, and the single repository that diverged from `git ls-files` diverged at precisely this seam, where six
`.claude/*` files were hidden by one line of that clone's `info/exclude` and by nothing a second clone would have.

So the source set is an enumerated field of `BuildOptions` rather than a flag. `IgnoreSources` is an ordered
non-exhaustive enum whose variants nest — no rules, in-tree only, plus the repository-local file, plus the
machine-global ones — and the default is the reproducible level. A ladder rather than three booleans, because the
sources genuinely nest and because the property worth naming in the type is where reproducibility ends, not which file
is which. Only the implemented levels are spelled: shipping a variant that silently does nothing is worse than not
offering it, and a non-exhaustive enum gains the rest without breaking a caller. The constraint this creates lands on
`kartta-cache` and is stated on the type: a cache key must cover the active source set *and* a content hash of every
source outside the tree, or an index built under one rule set is served under another, which is a wrong answer nothing
else will catch.

Resolution, when those levels arrive, shells out to `git rev-parse --git-dir` and `git config --path --get
core.excludesFile` rather than resolving git configuration in-process. Matching stays in-process with `gix-ignore`,
which already reads `info/exclude` but takes `core.excludesFile` as an `Option<PathBuf>` the caller supplies. Supplying
it faithfully needs git-config precedence with `include`/`includeIf`, the XDG fallback, and real `$GIT_DIR` discovery —
`$GIT_DIR` can be a *file* containing `gitdir: …` for a worktree or submodule. `gix-config` plus `gix-discover` resolves
to 60 crates and drags `walkdir`/`same-file` back into a graph that dropped them, against two subprocess calls once per
build that are exact by construction and degrade to in-tree-only when `git` is absent.

One consequence is worth naming because it looks like a bug: what is modelled is git's ignore *rules*, not git's index.
A file git already tracks stays tracked once a rule would hide it, so a tracked-but-ignored file is not indexed here.
`git check-ignore --no-index` is the command that agrees with this crate; `git ls-files` is the one that does not.
Re-including those files means reading `$GIT_DIR/index`, which is a real git repository and a second large dependency
tree, for a case that arises only when a rule is added after a file.

**Revised 2026-10-20: the MCP server's index answer names the ignore files a build applied.** `index_repo` and
`index_stats` answered `gitignore="respected"`, which an agent reads as the view of the tree `git status` gives. A
build applies the in-tree level, and a root below a repository's top is where the two part: git also applies the
`.gitignore` files from the top down to the directory above the root. With `/opt/homebrew/Library` as the root, the
index held `Homebrew/vendor/portable-ruby/*` and `Taps`, which the top's `.gitignore` hides at lines 23 and 26; with the
C++ game-engine tree's `samples` directory as the root, it holds 4 of its 491 files that way.
- **The answer:** `gitignore="in-tree"`, or `"ignored"` when `index_ignored` applies no rule. A root inside a repository
  whose top is above it reads `gitignore="in-tree: the root is inside the repository at <top>, whose .gitignore files
  above the root were not read"`. What the index holds does not change: whether a root below its top should read those
  files is part of how kartta meets git's layouts, a decision of its own.
- **Finding the top:** the nearest directory, the root or one above it, holding an entry named `.git`, a directory or a
  linked worktree's file, since git's discovery stops at the first. The look runs on the root's path with its links
  resolved, as git reads the directory it runs in, so a root given relative or through a link finds its own top. It
  runs once a build, after the walk: one `realpath` and one `lstat` a directory, up to the first `.git` or `/`. The walk
  lists the root's `.git` but looks at nothing above the root, and `kartta-fs` answers no question about repositories.
- **Cost:** the look took 45–170 µs on the data volume, both trees and two roots below a top, timed on its own by a
  script that resolves the path a component at a time where the server makes one `realpath` call. Builds of the data
  volume with `languages` empty, which run the same look after the walk, `main` against the branch in alternating
  rounds at load 15–29, while the volume moved between 6.70M and 7.51M entries:
  - 6 rounds with `main` first: medians 15.15 s and 18.35 s, peak footprint 967 and 948 MiB;
  - 8 rounds with the branch first: medians 15.84 s and 15.71 s, peak footprint 886 and 880 MiB.

  The side ahead changes with the order of the two, so neither gap is the look's.
- **Measured with the parity harness against `main`:** only the `index_repo` and `index_stats` answers differ, by this
  attribute alone, `respected` against `in-tree`. Both trees are indexed from their repository's top.

Considered:
- **Reading the `.gitignore` files above the root:** the index would match git's view, but what it holds would change,
  and that belongs to the decision on git's layouts.
- **The root's path as given:** a root given relative has no directory above it to look in, and one reached through a
  link would be looked above at the link rather than at the tree.

## Considered Options

- **A `respect_gitignore` boolean** — the shape the port arrived with. It answers "are rules on" and cannot answer
  "which rules", which is the question that decides whether two machines agree.
- **Three booleans, one per source** — expresses combinations that do not occur (global rules without in-tree ones) and
  hides the one property worth reading off the type, which is where reproducibility ends.
- **Honour every source by default, as git does** — right for a command a human runs in their own checkout, wrong for an
  index a cache is keyed on and a model reads through. Machine-dependence should be asked for.
- **Resolve git configuration in-process with `gix-config` and `gix-discover`** — 60 crates, and it restores dependencies
  the walk was written to drop, to compute two strings a subprocess prints exactly.
- **Read `$GIT_DIR/index` so tracked-but-ignored files are indexed** — needs a real git repository, which forecloses
  indexing a plain directory, for a case created by adding a rule after a file.
- **Hand-roll git-config parsing** — precedence, `includeIf` and worktree `gitdir:` files are the whole difficulty, and
  getting them subtly wrong is a silently different index rather than a failure.

Revisit if a consumer needs full git fidelity by default, if `gix-ignore` grows its own `core.excludesFile` resolution
without the config dependency tree behind it, or if indexing a repository whose rules were added after its files turns
out to be common rather than incidental.
