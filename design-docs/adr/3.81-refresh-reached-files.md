# Find the files a refresh reaches by one pass over a buffer of their keys

- **Status:** accepted
- **Date:** 2026-10-18
- **Updated:** 2026-10-21
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta/src/following.rs` (`Asked`, `Run`, `Reached`, `Following::plan`)
- **Pinned by:** `crates/kartta/src/following.rs`
  (`files_that_asked_nothing_leave_no_run_however_often_they_come_back`,
  `the_files_a_key_reaches_are_found_after_their_runs_moved`,
  `the_reached_keys_hold_every_key_of_their_set_and_no_other`)

A followed engine keeps the keys of every question each file's resolution asked
([ADR 3.33](/design-docs/adr/3.33-refresh-dependency-tracking.md)), and each refresh that adds or
removes a file finds the files whose keys it reached. The keys of every followed file sit in one buffer, read in order
behind a bit filter of the reached keys, which costs a pass over every key per refresh and holds nothing beside them.

## Decision

- The keys of every followed file are one buffer of 32-bit keys, a run for each file in the order the files came, and
  each file points at its run. A file that asked nothing takes no run.
- A run whose file left the graphs stays in the buffer until such runs hold a quarter of the keys; then one pass moves
  the runs still held to the front, in their order, and points each file at its new run.
- A refresh finds the files a change reaches by one pass over the buffer. Each key is first tested against a bit set at
  the low bits of every reached key, at least 32 bits for each rounded up to a power of two, and only a key the bit set
  holds is looked up in the set of reached keys.
- A refresh that added and removed no file skips the pass: `Resolver::resolve` reads no file's content, so no file's
  keys hold a read of a file, and only a file's presence reaches them.

## Why

- Going to each file's own box of keys through its slot in the map, and probing the set of reached keys for every key,
  took 0.24 to 0.31 s of a named refresh of 1.1 to 2.5 s on 16 copies of the C++ game-engine tree side by side,
  2.92M entries and 2.35M followed files (2026-10-21). The buffer and the filter take it to 0.04 s.
- The buffer drops the 16-byte box of keys from each slot of the files map and keeps 8 bytes a run, so the engine holds
  3.4 MiB less on the game-engine tree after a build (2026-10-21).
- Most keys a file asked are not reached, and the bit set tells them apart without a probe of the set.

## Consequences

- Every refresh that adds or removes a file pays a pass over every key every followed file asked: about 17 ns a followed
  file on the 16 copies, 41.7M keys; accepted, it is small beside building the resolvers a refresh wants.
- Retired runs hold up to a quarter of the buffer before they are reclaimed; accepted.

## Rejected

- **An index from each key to the files that asked it** — finds the files in under 2 ms, but sorted it holds 186.5 MiB
  more on the 16 copies and 10.9 MiB more on the game-engine tree, 4.9 bytes a key asked, and its upkeep after each
  refresh, with a rebuild once a quarter of it is stale, brings its highest calls above the pass's; a hash map holds
  three times as much.
- **The bit filter alone, each file's keys in a box of its own** — saves 109 ms of the pass on the copies at no cost in
  memory; the buffer takes another 126 ms off, and 3.4 MiB.

## Revisit if

The pass is again a large part of a refresh a consumer waits on, against building the resolvers it wants, 0.43 to
1.16 s on the 16 copies; then an index by key may pay for its memory. High confidence on trees of up to 3M entries.
