# Read each wanted file once, during the walk

- **Status:** accepted
- **Date:** 2026-10-14
- **Revised:** 2026-10-21
- **Initiative:** `01-kartta-fs-port`

Some consumers of an index read file content anyway: a code graph parses every source, a content index reads every
text file. Left to themselves they open each file again after the build, so a tree is walked once for its structure and
then resolved a second time, path by path, for its content. This crate reads content for them instead, and reads each
file a consumer wants once.

**A consumer hands the build a `ContentVisitor`.** `Index::build_with` asks it, per regular file the ignore rules kept,
whether it wants the file, and reads every wanted one while the walk is in that file's directory — the directory was
listed a moment ago, so the open finds the name in the filesystem's caches. A text file's whole content goes to the
visitor; the binary rule is the one `Index::is_binary` applies (ADR 1.6), so an extension in the binary set is never
opened and a NUL in the first 64 KiB ends the read there. A file that will not read is a collected `BuildError::Read`.
`Index::build` hands no visitor and reads nothing, as before. Both the visitor and the cancel token are optional, so a
build that only needs to be cancellable reads nothing either.

**One read serves the ignore rules and the visitor.** A `.gitignore` the rules need is read when the walk enters its
directory, and a visitor that wants the file gets that same read — unless it went through a symlink or the rules ignore
the file itself, because a visitor is handed only files the index holds. An ignored `.gitignore` still applies its
rules, as git applies one. Until its first 64 KiB settle a file, a read reserves no more than those 64 KiB, or the size
the open's stat reported when that is smaller; the rest of a text file is reserved, at that size, only once they settle
it as text. A binary file therefore costs no more than the probe, and a text file too large to reserve fails as a read
rather than aborting the process.

**A read's facts are kept.** The size the open's stat reported and the binary verdict go into the slots
`Index::size` and `Index::is_binary` answer from, so neither reads the file again — also when the read fails past the
open: the size is in from the stat, and the verdict once the first 64 KiB are. This is the eager read under an
explicit name that ADR 1.6 left as its revisit condition: a build that reads nothing still reads nothing, and only the
caller who asked for content pays for it.

**A file read during the walk is named by a `ContentId`.** Positions follow the finished tree, so none exists yet when
the walk reads a file; the id is handed out at the read, and `Index::content_position` maps it to the file's position
once the build is done. The id rides in the walk's per-entry payload, which holds the entry's kind and either that id
or the place of a symlink's target (ADR 1.9), 8 bytes either way, so a node costs the walk nothing more; what each read
learned is kept beside it, 16 bytes per read file, until the index is laid out.

**Revised 2026-10-21: the id is the payload's one field beside the kind.** The payload took 24 bytes, the id in padding
beside a boxed symlink target; with the target's place in a list the walk keeps beside its tree, it takes 8 (ADR 1.9).

**Large directories are classified in parallel.** The walk used to classify a directory's entries one at a time, which
is free when classifying is a name check and serial when it is a read: a flat directory of thousands of sources was
read on one thread while the rest of the pool waited. A directory of 64 entries or more now has its entries decided in
parallel and collected in listing order, so the tree is identical either way; below 64 the fork costs more than the
work it spreads. The entries are decided in runs of 4096, each recorded before the next starts, so the decisions waiting
to be recorded never outgrow one run however large the directory, and a run a cancellation stopped ends the directory.
Each entry's path is built in one buffer per directory, or per parallel piece, that already holds the directory's
prefix, so classifying allocates no path per entry.

**A cancelled build returns `BuildError::Cancelled`** rather than a partial index, because a cancelled walk holds
whichever entries its threads reached. The walk reports a stop only when a cancellation check actually turned an entry
away, so a token cancelled after the last entry no longer marks a complete tree as cancelled.

## What it costs

Measured on macOS against two trees, reading the sources a code graph parses:

| | entries | read | build alone | reading during the walk | build, then a second pass |
| --- | --- | --- | --- | --- | --- |
| game-engine checkout | 182,714 | 144,913 files, 1.45 GB | 0.21s | 2.30s | 2.22–2.29s |
| data volume | 2.97M | 816,196 files, 12.7 GB | 20–22s | 29–41s, ~34s mean | 39–44s, ~41s mean |

The checkout fits the kernel's vnode cache (263,168 on the machine measured), so a second pass costs it nothing extra
and the two are even. The data volume does not, and there reading during the walk is about a sixth faster and peaks at
610–614 MB against 673–677 MB for a second pass that keeps one word per wanted file and rebuilds each path as it
opens it. Parallel classification took the checkout's reading build from 2.69s to 2.30s over eight interleaved rounds,
and left its build that reads nothing at 0.21s either way. The data volume's figures come from a loaded machine and spread by several seconds; the ordering held in every round.

A build that reads nothing pays nothing for any of this. Against `main`, six interleaved rounds of `Index::build` alone
on the data volume took 15.9–19.3s against 18.6–22.1s, faster in five of the six, and peaked at 420–431 MB against
426–434 MB; one `main` round at 11.1s is left out as an outlier of the cache. The volume had grown to 3.03M entries by
then, against the table's 2.97M, which is why these runs compare with each other and not with the table.

## Considered Options

- **A content pass after the build** — simpler to state and to cancel, and it re-resolves every path once the walk's
  caches have moved on: a sixth slower on the tree that does not fit them, and no faster on the one that does.
- **Read inside the classification loop as it was** — no change to the walk, and a large flat directory reads on one
  thread: 15% slower on the checkout.
- **Queue reads to a separate pool as the walk finds files** — the walk would never wait on a read, and it outruns the
  reads by a wide margin, so the queue would grow to every wanted file's path before the reads caught up.
- **Name files by path rather than an id** — no new type, and every consumer that needs a position pays a lookup per
  file to find it.

**Revised 2026-10-14: the content index lands on these reads.** A build asked for one (ADR 1.14) reads every text file
the rules keep, not only those a visitor wants, through the same read, so the index and a visitor share each file's one
open. A file only the index wants is read in 64 KiB chunks rather than whole, because the index keeps each file's
trigrams rather than its bytes: whole reads of every text file on the data volume held multi-gigabyte files in memory
at once. A file a visitor wants is still read whole, since the visitor is handed all of it, and the index takes its
trigrams from that buffer.

Revisit if a consumer needs content in pieces, which would let a visitor's files stream too.
