# Read each wanted file once, during the walk

- **Status:** accepted
- **Date:** 2026-10-14
- **Updated:** 2026-10-21
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/policy.rs`, `crates/kartta-fs/src/content.rs`, `Index::build_with`,
  `ContentVisitor`, `ContentId`, `Index::content_position`, `crates/kartta-walk/src/walk.rs` (`WalkOutcome::cancelled`)
- **Pinned by:** `crates/kartta-fs/tests/content.rs`, `crates/kartta-walk/tests/walk.rs`
  (`a_token_cancelled_after_the_last_entry_leaves_a_complete_walk_reported_complete`)

A code graph parses every source and a content index reads every text file, and each opened its files again after the
build, when the walk's caches had moved on. The build reads each file a consumer wants once, while the walk is in its
directory, at the price of a walk that waits on reads and an id that stands in for a position.

## Decision

**The visitor.** `Index::build_with` takes an optional `ContentVisitor` and an optional `CancelToken`. The build asks
the visitor, once per regular file the ignore rules kept, whether it wants the file, and reads each wanted file while
the walk is in that file's directory. A text file's whole content goes to `ContentVisitor::visit`, on the walk's
threads, many at a time and in no order; a panic in the visitor ends the build. A file is settled by the rule of
[ADR 1.60](./1.60-settle-a-file-as-binary-by-its-extension-else-by-a-nul-in-its-first-64-kib.md): a binary extension is
never opened, and a NUL in the first 64 KiB ends the read there, unvisited. A file that will not read is collected as
`BuildError::Read`, and its entry stays. `Index::build`, and `build_with` with no visitor, read only what
`BuildOptions::content_index` asks for, and with neither they read no file.

**One read of a `.gitignore`.** The ignore rules read a `.gitignore` when the walk enters its directory, and a visitor
that wants the file is handed that same read. It is handed none where the file went through a symlink, or the rules
ignore it, or a name prunes it (ADR 1.19), since a visitor is handed only files the index holds; the rules still apply
in each case, as git applies an ignored `.gitignore`. A `.gitignore` whose read for the rules failed is offered to the
visitor through a read of its own.

**What a read reserves.** Until its first 64 KiB settle a file, a read reserves no more than 64 KiB, or the size the
open's stat reported when that is smaller. The rest of a text file is reserved, at that size, only once those bytes
settle it as text, so a binary file costs no more than the probe, and a text file too large to reserve fails as a read
rather than aborting the process.

**What a read keeps.** The size the open's stat reported and the binary verdict go into the slots `Index::size` and
`Index::is_binary` answer from (ADR 1.6), so neither reads the file again. A read that fails past the open keeps the
size, and the verdict once the first 64 KiB were read; one that fails at the open keeps nothing.

**The id.** A file read during the walk is named by a `ContentId`, handed out at the read, since positions follow the
finished tree; `Index::content_position` maps it to the file's position once the build is done. The id rides in the
walk's per-entry payload, which holds the entry's kind and either that id or the place of a symlink's target
(ADR 1.9), 8 bytes either way. What a read learned is kept beside it, 16 bytes per read file, until the index is laid
out.

**The content index.** A build asked for a content index (ADR 1.14) reads every text file the rules keep through this
same read, so the index and a visitor share each file's one open. A file only the index wants is read in 64 KiB chunks,
because the index keeps trigrams rather than bytes; a file a visitor wants is read whole, and the index takes its
trigrams from that buffer.

**Cancellation.** A cancelled build returns `BuildError::Cancelled`, never a partial index. The walk reports itself
cancelled only when a cancellation check turned an entry away, so a token cancelled after the last entry leaves a
complete tree. [ADR 1.61](./1.61-classify-a-large-directory-s-entries-in-parallel.md) states how the walk spreads a
directory's reads.

## Why

- A second pass re-resolves every path after the walk's caches moved on: on a macOS data volume of 2.97M entries,
  past the kernel's vnode cache, reading during the walk was about a sixth faster than a second pass, and on a
  182,714-entry checkout that fits the cache the two were even (2026-10-14).
- Only the caller who asks for content pays for it: a build that reads nothing still reads nothing, so ADR 1.6's
  on-demand facts hold for every other caller.
- A cancelled walk holds whichever entries its threads reached, which depends on scheduling.
- Whole reads of every text file on the data volume held multi-gigabyte files in memory at once.

## Consequences

- The walk waits on the reads of the directory it is in. Accepted: the reading build was the faster on both trees.
- A consumer that needs index order maps each id to a position after the build.
- A build that reads nothing pays nothing measurable for any of this (PR #19).

## Rejected

- **A content pass after the build** — simpler to state and to cancel, and a sixth slower on a tree past the vnode
  cache, no faster on one inside it.
- **Queue reads to a separate pool as the walk finds files** — the walk outruns the reads by a wide margin, so the queue
  grows to every wanted file's path before the reads catch up.
- **Name files by path rather than an id** — every consumer that needs a position pays a lookup per file.

## Revisit if

A consumer needs content in pieces rather than whole, which would let a visitor's files stream as the content index's
do. Medium confidence; no consumer has asked.
