# Search definitions by the words of their names and paths

- **Date:** 2026-10-17
- **Governs:** `crates/kartta-graph/src/search.rs`, `crates/kartta-graph/src/words.rs`, `Graph::search`
- **Pinned by:** `crates/kartta-graph/tests/graph/search.rs`

An agent that knows what a symbol does but not its exact name asks for it by a word: `config loader`, `HTTPServer`,
`parse request`. `Graph::search` ranks every definition that holds a word of the query by BM25, from word sets each
file builds the first time a search reads it, so a graph that is never searched pays nothing and the first search of a
graph pays for splitting every name once.

## Decision

- **The words a file keeps.** A file's words are those of the qualified names and the names of its definitions and of
  the last three segments of its path, kept as a sorted set of 32-bit hashes, with the count of words its definitions
  hold for the length normalization. A file with no definition keeps no word. The set is built the first time a search
  for a word reads the file and lives in the file's slot until the file is replaced or removed; nothing outside the
  slot is shared, so a removal or a replacement touches nothing else. A query with no word builds no set and reads
  none.
- **The scan.** A search reads every file's set in parallel on the rayon pool it is called on, splits the names only of
  the files whose set may hold a word it asks for, and counts each word exactly there, so a hash collision only adds a
  file it then finds holds nothing. It looks for the first eight distinct words of the query, a repeated word once.
- **How text splits into words.** One function splits names, path segments and the query alike. A word ends at every
  character that is not a letter or a digit, between a lowercase letter or a digit and the capital after it, and before
  the last capital of a run that a lowercase letter follows, so `parseHTTPRequest` holds `parse`, `http` and `request`.
  Words are lowercased by Unicode, and a letter outside ASCII stays in its word. A mark of the Unicode combining-mark
  blocks, U+0300–036F, U+1AB0–1AFF, U+1DC0–1DFF, U+20D0–20FF and U+FE20–FE2F, is dropped wherever it stands, so
  `İstanbul` holds the word `istanbul`. A combining mark outside those blocks stays in its word where Unicode counts it
  alphabetic, as Hebrew's U+05B0, and ends the word where it does not, as Devanagari's U+093C. A path's segments split
  as names do, `httpServer/config_loader.go` holding `http`, `server`, `config` and `loader`, and the extension is cut
  from the file's name alone, so a directory `v1.2` keeps both words.
- **The score.** A definition holds the words of its qualified name, those of its own name once more, and those of its
  file's path, and scores by BM25 over the words it shares with the query, k1 1.2 and b 0.75. That score is then, in
  this order, multiplied by the share it holds of the query's words that some definition holds; doubled when the query
  looks for two or more words and its qualified name holds all of them in query order with no word between; capped at
  500, then halved for generated code and cut by a quarter for vendored code, both read from `SymbolFlags`; and raised
  by 1000 when its name is the query as written, so it leads every other hit, and the lead survives a merge of the hits
  of several language families by score. Equal scores rank a word match before a fill-up hit, then by path and line.
- **The fill-up.** When the words match fewer definitions than the limit, the search adds those whose name, or else
  qualified name, holds the query, its whitespace dropped and lowercased, as a subsequence of its lowercased
  characters: `authent` reaches `Authenticate` and `pcf` reaches `parseConfigFile`. A hit scores the share of its
  name's characters the query spells, or of its qualified name's when only that spells the query, 0 to 1, demoted as a
  word match is; it is marked `fuzzy` and ranks among the word matches by that score. A fill-up reads every
  definition's name.
- **What the answer counts.** `total` counts every definition a word or the exact name matched, before the limit;
  `named` those of them a name matched rather than only a path; `unmatched_words` lists the looked-for words no
  definition holds; `dropped_words` counts the distinct words past the eighth; `fuzzy_total` counts the fill-up's own
  matches when it ran and is absent when it did not. With a limit of 0 the answer holds no hit and the fill-up does not
  run, and every other count is that of any other limit.
- **A name nothing defines.** It is answered with the definitions one edit from it, which
  [ADR 3.131](/design-docs/adr/3.131-missed-name-suggestions.md) decides; the search runs as above.

## Why

- A graph is kept a file at a time ([ADR 3.5](/design-docs/adr/3.5-graph-file-storage.md)), so a per-file set leaves a
  refresh one slot to drop; reading every Go file's set for a word none holds took 0.13 ms at the median on a Go
  monorepo of 39,771 Go files (2026-10-17, #55), so a query's time goes to the files that hold its words.
- A reader splits an acronym as one word and a path stem as words; a split that cuts a capital run into letters leaves a
  symbol unfindable by its acronym, and an unsplit stem meets no split query word.
- The name's own words count twice and the phrase doubles because a query names what the agent wants the definition to
  be called: without the phrase lead, camel-fragment queries' mean reciprocal rank fell from 0.310 to 0.293 on the C++
  game-engine tree (2026-10-17, #55).
- The fill-up's density is taken over the name: over the qualified name it ranked a Python definition by the length of
  its module path, and moving it to the name took camel queries' mean reciprocal rank from 0.234 to 0.310 on the C++
  tree.

## Consequences

- The first search of a graph splits every name once: 29.9 ms at worst on the C++ game-engine tree and 38.9 ms on the Go
  monorepo, against a median of 5.8 ms after it (2026-10-17). Accepted.
- The word sets hold memory once searched: the heap after every query set ran was 2.2% over the graph's on the C++
  tree. Accepted.
- Each graph weighs words by its own definitions, so of the scores of several families' graphs only the exact-name lead
  ranks the same. Accepted.

## Rejected

- **An index of every definition under every word** — 171 MB on the Go monorepo and 178 MB on the C++ tree, where the
  word sets hold 5.1 and 6.5 MB once searched, and a removal walks every word's posting list, up to 0.8 ms at p99.
- **An index of distinct names under their words** — 56 and 68 MB, and a removal over long shared lists up to 23 ms.
- **No index, splitting every name for every query** — about 0.4 CPU-seconds per query.
- **Word sets built at insert** — the same answers, and the single-threaded insert phase about a tenth of the build
  longer; hashing in place of interning still left 160 to 230 ms.
- **Only definitions whose own name holds a query word** — changes 5 to 22% of the top-10 hits; `named` counts the
  same split without losing the path matches.
- **A capital run split into letters, path stems left whole** — leaves 8.7% of the C++ tree's 1,193,586 symbols
  unfindable by their acronym, and 88% of its files' stems unmet by any split query word.

## Revisit if

A family's first search outgrows the latency a query is allowed, or a refresh replaces files often enough that
re-splitting their names on the next search costs more than keeping their sets current at insert. The first holds at
under 40 ms on the measured trees; how often a followed tree's refresh is followed by a search is not measured.
