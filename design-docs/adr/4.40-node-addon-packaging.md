# Ship the Node addon as one npm package per target

- **Date:** 2026-10-18
- **Governs:** `bindings/node/npm/`, `bindings/node/src/target.ts`, `bindings/node/src/kartta.ts` (`load`),
  `bindings/node/scripts/`, `bindings/node/package.json` (`engines`, `optionalDependencies`, `scripts.prepack`)
- **Pinned by:** `bindings/node/test/floor.test.ts`, `bindings/node/test/packages.test.ts`,
  `bindings/node/test/target.test.ts`
- **Implementation:** pending — the release's publish waits for the `npm` environment and its token (#1058)

The Node package needs a native addon for each platform it runs on ([ADR 4.3](/design-docs/adr/4.3-node-addon.md)).
Each target ships in an npm package of its own, which npm installs only where it matches, and N-API lets one build
serve every Node; the trade is a platform with no package getting no addon.

## Decision

- **Targets.** The addon ships for every target of the support matrix in
  [ADR 4.46](/design-docs/adr/4.46-release-scope.md), each built and tested in CI on its own target.
- **A package per target.** One package per target, `kartta-<target>` with `os`, `cpu` and, on Linux, `libc` set,
  holds `kartta.<target>.node`, the naming napi-rs's tooling uses. A target is `<platform>-<arch>`, with `-gnu` or
  `-musl` on Linux and `-msvc` on Windows. Their manifests are committed under `bindings/node/npm`.
- **What a pack holds.** `npm pack` of a target's package copies in the addon a build left in `bindings/node`, the
  repository's `LICENSE` and `notices/THIRD-PARTY-NOTICES.txt`, and fails with no addon there; that of the main package
  copies in `LICENSE`. Nothing it copies is committed under `bindings/node`.
- **Loading.** The package loads the addon a checkout builds beside it, `kartta.<target>.node`, then the target's
  package. A host with neither throws, naming the host's target, the targets that ship and how a checkout builds one.
- **The C library.** On Linux the target's libc is the one the process runs on: `-musl` where a diagnostic report's
  `header.glibcVersionRuntime` is absent, read with `excludeNetwork` set, otherwise `-gnu`.
- **A build for musl.** `scripts/build.ts` turns `crt-static` off for the addon alone on a musl host, because the
  Rust musl targets build no shared library with it on, and every other artifact keeps the workspace's flags.
- **Dependencies.** The package names each target's package in `optionalDependencies` at its own version, and
  `package-lock.json` holds an entry for each, written by hand until the version is on the registry.
- **Releases.** A release publishes each target's package and then the package
  ([ADR 4.65](/design-docs/adr/4.65-npm-publish.md)).
- **Engines.** `engines` asks for Node 24 or later, in the package and in each target's package. Node 24 is a floor,
  independent of which LTS line is the newest, and `.nvmrc`, the Node CI runs, stays on the floor's line.

## Why

- N-API is stable across Node majors, so one build per target serves every Node the package supports: one debug build
  of the addon passed the Node suite on 22.23.4, 24.0.0 and 26.9.0 on macOS arm64 (2026-11-02).
- Raising the floor with each LTS would drop a maintained line for nothing the package needs. Node 26 entered LTS on
  2026-10-28, and Node 24 is in maintenance to 2028-04-30, by
  [the Node.js release schedule](https://github.com/nodejs/Release/blob/c3e8696/schedule.json).
- `os`, `cpu` and `libc` let npm skip a target's package that does not match the host, so an install downloads one
  addon.
- Node fills `glibcVersionRuntime` by looking up `gnu_get_libc_version` in the running process (`src/node_report.cc` at
  v24.11.0), which reads the C library the addon will link against, where a file on disk describes the machine. A
  report otherwise resolves each open socket's peer synchronously (`src/node_report_utils.cc`), which could stall a
  server's first `open`.
- `npm ci` refuses a lock that lacks an entry for a dependency, even an optional one (npm 11.20.0, 2026-11-02), so a
  package naming unpublished targets needs those entries. With them, `npm install` and `npm ci` keep the lock and skip
  a package the registry does not hold.

## Consequences

- A host outside the support matrix gets no addon, and `open` throws there. Accepted.
- Reading the report costs one synchronous call on Linux, once per process, at the first `open`. Accepted.
- A pack ships whichever addon the last build left, a debug one included; the release builds it under `dist`
  ([ADR 4.55](/design-docs/adr/4.55-release-workflow.md)). Accepted.
- A lock regenerated from nothing loses the hand-written entries, and `npm ci` then fails naming them, until the
  version is on the registry. Accepted.
- CI runs one release of the floor's line and no newer line, so a break on Node 26 or on an early 24 release shows in no
  run. Accepted: the addon calls N-API alone, and the suite passed on both ends when the floor was set.
- Node 22 could run the package and `engines` refuses it. Accepted, see Rejected.

## Rejected

- **macOS and Linux with glibc alone** — the support matrix holds Linux musl and Windows for every channel (#120).
- **npm workspaces for the targets' packages** — they would make the lock's entries npm's own, but `npm ci` fails with
  `EBADPLATFORM` on a workspace of another platform.
- **`/usr/bin/ldd` for the libc** — it describes the machine, and the process may run on another C library.
- **`crt-static` off in a Cargo configuration** — it would reach every build in the checkout, the musl tests of
  [ADR 4.59](/design-docs/adr/4.59-ci-platform-coverage.md) included, which run the static link the target defaults to.
- **A release step that adds `optionalDependencies`** — it leaves a pack from a checkout unable to install its addon,
  and a step to keep the manifest apart from what ships.
- **Node 26** — it would drop a maintained line for nothing the package needs (#1052).
- **Node 22** — the suite passes there, but the line ends on 2027-04-30, and `.nvmrc` and `@types/node` move with the
  floor ([ADR 4.41](/design-docs/adr/4.41-node-toolchain.md)), so the whole toolchain would sit on a line that ends six
  months after this decision (#1052).

## Revisit if

N-API stops holding across Node majors, or npm stops skipping a package by `os`, `cpu` and `libc`, or Node 24 nears its
end of life. High confidence; the list of targets follows ADR 4.46.

## History

- 2026-11-02 — Dependencies: a pack from a checkout has to name the targets' packages for one to install, so the
  manifest holds them from the start, and a release only publishes (#132).
- 2026-11-02 — Engines: "the newest LTS line" went false when Node 26 entered LTS, so the rule states a floor (#1052).
- 2026-10-31 — Targets: the first release's support matrix adds Linux musl and Windows (#120).
