# Hold each extraction at its exact size

- **Status:** accepted
- **Date:** 2026-10-18
- **Updated:** 2026-10-18
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta/src/extracting.rs` (`Extracting::extract`, `encoding_buffers`)

An engine build holds every file's encoded extraction until resolution, and glibc keeps the memory a vector frees as it
grows resident in the arena of the thread that grew it. The walk's threads encode into buffers they reuse and the
build holds an exact-size copy of each, at the price of one copy per extraction.

## Decision

- The walk's threads take an encoding buffer from a pool the build keeps, encode an extraction into it, keep an
  exact-size copy of the encoding, and return the buffer to the pool.
- The pool holds at most as many buffers as threads extract at once, each as large as the largest encoding written into
  it, and it is dropped with the extraction state, before resolution starts.

## Why

The growth freed while each encoding doubled set about a quarter of the game-engine tree's resident peak under glibc:
with exact-size copies the median peak of a cold engine build fell to 1,087 MB from 1,480 MB, sixteen builds each, in a
glibc container limited to 4 CPUs (C++ game-engine tree, 2026-10-18).

## Consequences

- Resident memory after the build rose 9 MB at the medians on the game-engine tree, and 8 MB on the Go monorepo, whose
  peak did not move. Accepted.
- The peak now sits while the largest file is parsed: a 30 MB C source of numeric tables holds a 586 MB parse tree,
  which tree-sitter allocates through the C library.
  [ADR 3.31](./3.31-parse-a-c-or-c-plus-plus-table-without-its-numbers.md) takes it on.

## Rejected

- **Measure the encoding before writing it, and reserve its exact size** — a counting pass of the codec in
  `kartta-lang`: the same peak as the copy, each build about a second slower, and a change to a published crate's codec
  for what the engine does alone.
- **Reuse each thread's read buffer, keeping buffers of 1 MiB or less** — the peak did not move.
- **Pack the encodings into shared 1 MiB blocks** — no lower than the copy, and more code.
- **Trim after or before extracting each file of 1 MiB or more** — with the copy, a median 3% under the copy's peak,
  for a trim per large file on glibc alone.
- **Trim after each resolution batch** — the peak did not move.
- **Resolve batches while the walk runs** — resolution reads the finished index, the positions it inserts in, path order
  and the repository the resolvers ask, so it cannot start before the walk ends.
- **Reuse the parsers and their trees** — each language keeps one parser per thread already, and a tree is one file's.

## Revisit if

The build stops holding every encoding until resolution, so the growth of one no longer sits beside the others. High
confidence: resolution reads the finished index and cannot start before the walk ends.
