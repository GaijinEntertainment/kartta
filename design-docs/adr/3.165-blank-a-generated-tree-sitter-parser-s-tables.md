# Blank a generated tree-sitter parser's tables before the C parse

- **Status:** accepted
- **Date:** 2026-10-22
- **Updated:** 2026-10-22
- **Initiative:** `03-code-graph`
- **Governs:** `crates/kartta-lang-cpp/src/repair.rs` (`Tables`, `GENERATED_PARSER_MARKS`, `data_token_len`)
- **Pinned by:** `crates/kartta-lang-cpp/src/repair.rs`
  (`a_generated_parsers_tables_are_blanked_and_its_code_parsed_as_written`,
  `the_same_tables_are_parsed_as_written_in_a_file_that_is_no_generated_parser`,
  `a_generated_parser_keeps_its_definitions_and_what_its_code_calls_and_uses`),
  `crates/kartta-lang-cpp/tests/tree_memory.rs` (`a_generated_parsers_tables_take_no_parse_tree`)

The `parser.c` that tree-sitter generates for a grammar holds tables that spell macro calls and enumerators, so the
numeric rule of [ADR 3.31](./3.31-parse-a-c-or-c-plus-plus-table-without-its-numbers.md) passes them by, and their trees
reach twenty times the file's bytes. In such a file a table of names is blanked too, at the price of the names its
tables write at file scope, none a definition a graph holds.

## Decision

**A generated parser is told by its text before its first brace**, which includes `tree_sitter/parser.h` and defines
`LANGUAGE_VERSION`. A hand-written external scanner includes the same header and defines no `LANGUAGE_VERSION`, so it
is read as any other file. The test reads the bytes alone, never the file's name.

**In a generated parser, a brace group of 4 KiB or more is blanked when it holds names, macro calls, designators,
strings and character literals** beside the numeric data of ADR 3.31, under that ADR's scan, size and blanking. So the
parse tables, the symbol names, map and metadata, the field maps, the lexer modes, the parse actions, the reserved
words, the character sets and the grammar's enumerations are blanked.

**The lexers and the language function are read as written**, since they hold statements, with their uses of the
external scanner and of the tables the language function names. Every definition of the file, and every call and use
inside a definition, extracts as in the file parsed whole.

## Why

- The generated tables are a parser's mass: daslang's 30.2 MB `parser.c` parsed into 678 MB of trees, and blanked, no
  generated parser of the 68 on the macOS data volume holds more than 9.1 MB, the lexers' (2026-10-22).
- Every generated `parser.c` of the data volume, 68 of 25 grammars, opens with both marks, and no scanner does
  (2026-10-22).
- What the tables spell is the parser's macros, `ACTIONS`, `SHIFT`, `REDUCE`, `STATE` and their kin, the grammar's
  enumerators and `ts_builtin_sym_end`, none a definition a graph holds.
- A language extracts bytes alone, and the content cache keys an extraction by them
  ([ADR 2.1](./2.1-share-per-file-data-through-content-addressed-packs.md)), so a test by name could not reach it.

## Consequences

- The names the tables wrote at file scope leave the graph's file-scope uses and calls. The one a graph defines is
  `TSStateId`, which older generators cast to in the lexer modes, `(TSStateId)(-1)`, a cast the grammar reads as a
  call: `find_callers` lists no file-scope caller of it, as for every other cast. Accepted.
- Every C and C++ file pays a scan of its text before its first brace, 0.2% of the CPU its extraction takes on the data
  volume (2026-10-22). Accepted.

## Rejected

- **Blank a 4 KiB group of names, macro calls, designators, strings and numbers in every file** — 1,639 other files of
  the data volume extract otherwise, 40,293 calls inside definitions among the losses.
- **Blank every brace group of 4 KiB or more after `=` at file scope, whatever it holds** — the same extraction of the
  68, but the enumerations parsed and a scanner of its own needed for strings, characters and comments.
- **The same entries without strings and characters** — the symbol names and the character sets parsed, 216 MB of trees
  summed over the 68 against 182 MB.
- **Leave a generated parser unparsed** — all 1,831 definitions, 117,040 calls and 106,369 uses inside definitions
  lost, the language function other files call among them.
- **Leave unparsed a file of 4 MiB or more whose banner announces generated code** — 20 of the 68 come from generators
  that wrote no banner, cpp's 16.5 MB parser among them, and Perl's `charclass_invlists.h` loses its definitions.
- **Blank the lexers too** — the lexers make every call inside the files' definitions, `set_contains` of `parser.h`
  among them.
- **Tell a generated parser by its file name** — a language sees bytes, not the path.

## Revisit if

tree-sitter's generator writes a `parser.c` whose text before its first brace no longer includes `tree_sitter/parser.h`
and defines `LANGUAGE_VERSION`, or whose tables spell a definition a graph holds. High confidence: every generated
parser of the data volume opens so.
