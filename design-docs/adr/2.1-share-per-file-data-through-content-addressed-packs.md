# Share per-file data through content-addressed packs

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-18
- **Initiative:** `02-shared-cache`

Many processes index nearly identical trees at once: review containers on one build node check out one repository at
commits a few files apart, and each builds its index cold. On the game-engine checkout a content-index build takes
1.38–1.40s at a 4-CPU quota on Linux, and about 85% of it is extracting trigrams and writing their lists — work done
again for 169,188 text files when a hundred of them differ. The code graph that comes next repeats its per-file parsing
the same way. A cache that lets one process reuse what another computed for the same bytes, with no process ever
writing a file another one reads, is what `kartta-cache` provides.

**An entry is keyed by the content it was computed from and by what computed it, never by a path.** The content half
is the blake3 hash of the file's bytes, so identical contents share one entry wherever they sit and whichever tree holds
them; collision resistance matters, since the bytes come from repositories. The other half is a namespace derived from
the kind of data — `trigrams`, `graph/cpp` — and a fingerprint of the code that computed it, which the producer derives
from its rules, grammar and encoding. A new fingerprint is a new namespace, so an entry computed by older code is never
served to newer code, and two versions of a producer running against one store during a rollout keep their own entries
instead of overwriting each other's. Each producer and each language get their own namespace, so a grammar change drops
one language's entries and nothing else. The trigram index needs a fingerprint too: its case folding and its encoding
decide what it computes from the same bytes.

**Entries live in packs, not in a file each.** A store of one file per entry spends its lookups opening files, and on
macOS an open costs more than computing a small entry again. A process gathers what it computed in a
`PackWriter` and publishes one pack — payloads, then an index sorted by namespace and content hash, then a footer — and
a `Store` maps every pack in the directory and answers a lookup with a binary search over each mapped index, opening
nothing per entry and returning a borrow of the mapping. One file per entry was measured on both platforms, under three
directory fan-outs, and lost on every one:

| three million entries | `ab/<hash>` | `ab/cd/<hash>` | `abc/def/<hash>` | one pack |
| --- | --- | --- | --- | --- |
| directories | 257 | 65,793 | 2,750,194 | none |
| create, macOS | 171s | 164s | 282s | 0.035s for the index |
| look every entry up, macOS | 49.0–49.3s | 47.4–49.8s | 60.2–63.9s | 0.054–0.055s |
| create, Linux, 4 CPUs | 13.6s | 20.3s | 55.1s | 0.088s for the index |
| look every entry up, Linux | 1.47s | 1.20–1.57s | 2.22s | 0.19s |
| the same with the page cache dropped | 4.48s | 4.35s | 6.56s | 0.22s |

**A pack is published once and never written again.** The writer streams payloads into a temporary file in the store's
directory as entries arrive, holding only their index in memory, then writes the index and footer, syncs the file and
hard-links it under the hash of its index. A link creates a name only where none exists, on every platform, so a pack
appears whole or not at all and no file a reader mapped is ever replaced; a rename would replace one on unix and fail on
Windows while another process maps it. Two writers that publish the same index over the same payloads produce the same
name, and the second finds its pack already in place. A store maps the packs present when it opens and keeps them for
its life: a pack published later is seen by the next open, and a pack removed while a store maps it goes on answering
that store. Processes therefore read and publish in one directory with no lock and nothing shared but the files. The
directory has to allow hard links.

**Every lookup checks its entry.** Each index entry carries the first 64 bits of a blake3 hash over its namespace,
content hash and payload, verified before the payload is returned, so a changed payload byte, or an index entry
pointing at other bytes, escapes it only with a chance of 2^-64: the entry is passed over, another pack's sound copy
answers instead, and a lookup that finds no sound copy misses and is counted as damaged. A changed byte in an entry's
key makes the entry look absent, so its lookup misses and counts as a miss; telling that apart would take hashing every
index at every open. Either way nothing wrong is served, and a cache that served wrong data would turn into wrong
answers wherever the data is used. The check guards against damage, not against a writer: a process that can write the
directory can publish any pack it likes. A file with the pack extension that is not a readable pack is counted and
skipped. `Store::stats` reports packs, entries, rejected packs, hits, misses and damaged lookups.

**Revised 2026-10-16: past eight packs, all but the largest merge.** Each publish of entries adds a pack, unless the
same pack is already in place, and a lookup searches the packs largest first until one answers, so `Store::merge`
bounds how many there are: past eight, the packs other than the largest merge into one while together they hold fewer
entries than it, and every pack merges once they hold as many or more. A merge writes the entries of the packs the store
mapped through a writer, one entry per key and no damaged one, publishes the merged pack, then removes the packs it
merged; one it cannot remove stays in place, answering the same entries, and is counted. A store that mapped them keeps
answering from them, and two processes that merge the same packs waste one merge's work and lose nothing, since each
removes only what it merged. A store that opens while another process merges can list packs the merge then removes:
it lists the directory again when a listed pack has gone and finds the merged pack, which was published before anything
was removed, for up to four listings; a pack still vanishing after the fourth, which takes a merge finishing between
each two of them, is counted as rejected. A pack whose namespace ranges do not cover its index in order is refused when
it opens, so a merge never reads a damaged range as empty and removes the only copy of its entries. The caller decides
when to merge, because only it knows how many processes share the directory. Measured on the checkout's 149,697
entries:

| | macOS, 18 cores | Linux, 4 CPUs |
| --- | --- | --- |
| 169,188 lookups, one pack | 0.020s | 0.069–0.084s |
| the same, nine packs of one size | 0.022–0.039s | 0.073–0.076s |
| the same, one pack and eight small ones | 0.020–0.033s | 0.068–0.081s |
| merging the nine, 227 MB | 0.75–0.76s | 0.66–0.68s |
| merging the eight small ones, 2,379 entries | 0.024–0.031s | 0.019–0.022s |

**Revised 2026-10-18: entries expire.** Each index entry carries the second it was published, which a merge keeps, and
an entry older than the time to live a merge is given expires; ADR 2.3 records when an expired entry leaves its pack
and what that costs.

**Revised 2026-10-18: `Store::stats` reports packs and entries only.** Nothing read the counts of hits, misses, damaged
lookups and rejected packs, and the three lookup counts cost every lookup an atomic increment on one cache line that
every thread of a build shares. A damaged entry and a file that is not a readable pack are still passed over as above;
they are no longer counted.

## What it costs

Measured with each text file's distinct trigrams as the payload, delta-encoded, on the game-engine checkout:

| | macOS, 18 cores | Linux, 4 CPUs |
| --- | --- | --- |
| pack | 227 MB, 149,697 distinct contents for 169,188 text files | the same |
| publishing it | 0.047s | 0.12s |
| read, hash and look up every text file | 2.58–2.62s | 0.44–0.45s |
| the lookups and their checks alone | 0.019–0.024s | 0.068–0.071s |
| read and extract the trigrams again | 2.67–2.72s | 0.97–1.00s |
| read and hash only | 2.47–2.55s | 0.33–0.38s |
| one file per entry: read, hash and open it | 5.43–5.63s | 0.41–0.60s |

On Linux hashing the bytes is most of a hit's cost; the graph reads and hashes every file of its languages anyway —
144,946 of the checkout's 171,722 files, 1.45 of its 2.37 GB — so for those a producer that shares the hash pays only
the lookup. On macOS opening the files to read them is most of either path, so a hit saves
the extraction and nothing else. A build that finds nothing pays for writing: hashing, extracting and inserting every
entry took 2.53–2.60s against 2.51–2.54s without the inserts on macOS, and 1.37–1.48s against 1.27–1.35s on Linux,
where the threads queue on the writer's lock. The lock covers a copy into a 1 MiB buffer; with the 8 KiB default, a
write call every few entries, the same Linux build took 1.50–1.61s.

The Linux figures come from a container on a virtual machine whose disk is a file on the host, so even with the page
cache dropped its reads were served at about 3.8 GB/s; a real disk read cold is unmeasured, and so is Windows beyond its
test suite.

## Considered Options

- **One file per entry** — the table above; on macOS three million lookups spend 47–64s opening files, whichever
  fan-out holds them.
- **One index per tree, updated by each process** — a file that every process writes cannot be shared without locks,
  and an index keyed by its tree stores two identical trees twice.
- **One record per content holding every producer's data** — producers finish at different times, so the record would
  be completed after it was published, which is the in-place write packs exist to avoid; and one producer's new version
  would discard the others' data with its own.
- **The fingerprint as a check made after the lookup** — two versions of a producer then share each entry's key and
  overwrite each other's entries for as long as both run.
- **Publishing by rename** — replaces an existing file under its readers on unix and fails on Windows while one is
  mapped.
- **A portable blake3 build** — no C compiler needed, and hashing the checkout took 0.36s against 0.20s with the SIMD
  implementations at the same quota.
- **Write buffers sharded per thread** — would shorten the queue on the writer's lock, which costs a cold build
  0.1–0.2s on Linux; only a build that finds nothing pays it.

Revisit when the merges of many processes finishing at once cost more than a lock on merging would; when a store sits
on a filesystem without hard links; or when cold builds are frequent enough that the writer's lock matters. Entries for
contents no tree holds any more expire by age (ADR 2.3).
