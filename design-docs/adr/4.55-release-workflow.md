# Cut a release from a version tag

- **Date:** 2026-11-02
- **Governs:** `.github/workflows/release.yml`, `scripts/dist.sh`, `scripts/glibc-floor.sh`,
  `scripts/publish-crates.sh`, `RELEASING.md`
- **Pinned by:** `.github/workflows/release.yml` (jobs `versions`, `build` and `crates-dry-run`)

[ADR 4.46](/design-docs/adr/4.46-release-scope.md) names the artifacts and the matrix, and nothing built them. One
workflow builds every target from a tag, each Linux build inside a pinned image, and publishes the crates and the
release only on a tag push; the trade is a floor below which a glibc host gets no prebuilt artifact, and two library
names for one artifact.

## Decision

- **Runs.** A pushed tag `vX.Y.Z` builds and publishes. A manual run, on any ref, builds the same artifacts, packages
  and verifies every crate as the publish would, and publishes nothing, and so does a pull request that touches the
  workflow, a script its builds or its publish run, a Cargo manifest, `Cargo.lock`, the toolchain pin, or the Node
  package's manifests, lock, `.nvmrc`, build scripts or build configuration.
- **The version.** The `versions` job fails before any build when a site differs from the workspace version, and on a
  tag when `scripts/version.sh` would change a file to reach the tag's version.
- **Artifacts.** Each target of the matrix gets one gzipped tarball, `kartta-ffi-<version>-<target>.tar.gz`, on every
  platform. It holds one top directory of its own name, with `LICENSE` and `THIRD-PARTY-NOTICES.txt` beside the static
  library, `kartta.h` and `WIRE.md`. `scripts/dist.sh` builds it, under the commands of
  [ADR 4.49](/design-docs/adr/4.49-distribution-profile.md), and fails when it does not link as
  [ADR 4.58](/design-docs/adr/4.58-archive-symbols.md) states. `SHA256SUMS` covers every tarball. `kartta-mcp` ships as
  its crate alone ([ADR 4.46](/design-docs/adr/4.46-release-scope.md)).
- **Publishing.** Once every target has built, the `crates` job runs `scripts/publish-crates.sh`, which publishes each
  crate whose `publish` is unset with `cargo publish --workspace --locked`, in the order of their dependencies, and
  leaves out each crate whose version the crates.io sparse index already lists. The `publish` job follows it: it pushes
  `bindings/go/vX.Y.Z` to the tag's commit, then creates the release with every tarball and `SHA256SUMS`. It alone holds
  `contents: write`. The npm packages publish apart, under [ADR 4.65](/design-docs/adr/4.65-npm-publish.md).
- **Credential.** Of the two crates jobs, `crates` alone holds `id-token: write`; `rust-lang/crates-io-auth-action`
  trades the run's OIDC token for the crates.io token cargo reads from `CARGO_REGISTRY_TOKEN`. Each crate of the publish
  set holds a trusted publisher naming `GaijinEntertainment/kartta` and `release.yml` and no environment, which the
  maintainer configures (#1058). No job reads a stored registry token or names an environment.
- **A failed cut.** A re-run of the failed jobs finishes a cut whose tree is right. A fix that needs another commit is
  the next patch version of every artifact, whichever channels the failed version reached, and a version is yanked or
  deprecated only for a defect in it. `RELEASING.md` gives each failed or partial state its steps.
- **The dry run.** On every run that publishes nothing, once the `versions` job passes, the `crates-dry-run` job runs
  the same script with `--dry-run`, which leaves out no crate. It holds no `id-token: write`.
- **The Node addon.** Each `build` row of a target in the support matrix builds that target's addon after the archive,
  through `bindings/node/scripts/build.ts --profile dist`, with the Node of `.nvmrc`: on the runner for macOS and
  Windows, and in the row's image on Linux. The `x86_64-pc-windows-gnu` row builds none.
- **The glibc floor.** The Linux gnu artifacts and addons run on glibc 2.28 or newer. They build in the
  `manylinux_2_28` image of their architecture, pinned by digest, which holds glibc 2.28 and a current GCC; the Rust
  toolchain and Node come from the runner.
- **The floor's proof.** Each gnu build fails when the archive does not link a C program in the image, when
  `objdump -T` finds a glibc version past the floor on that program or on the addon, or when on `debian:10.13-slim`, a
  glibc 2.28 distribution that took no part in the build, the program does not run or the addon does not load in Node.
- **musl.** The musl artifacts build in `rust:1.100.0-alpine3.24`, pinned by digest, which brings the toolchain and the
  C compiler. The archive carries no musl and no unwinder: rustc leaves both to the consumer's link.
- **The Windows libraries.** The MSVC artifact ships `kartta_ffi.lib`, the name that target emits, and builds inside the
  Developer environment, because the link check runs `cl`. The `x86_64-pc-windows-gnu` artifact, which the Go module
  links ([ADR 4.60](/design-docs/adr/4.60-go-windows-link.md)), ships `libkartta_ffi.a` and builds on the runner with
  the MinGW-w64 the `go` job pins.

## Why

- A build inherits the floor of the glibc it links: on arm64 on 2026-11-03, the program linked from the archive built
  on Debian 12 needs 2.34, and `debian:10.13-slim` refuses it, while the one linked in the image runs there.
- 2.28 is the floor of the Node.js 24 the npm package requires (`BUILDING.md` of `v24.x`, read 2026-11-02), and one
  matrix promises one floor for every channel. A host below it cannot run Node at all.
- rustc states glibc 2.17 for both gnu targets (`src/doc/rustc/src/platform-support.md` at the pinned sources), so the
  image decides the floor and the toolchain from the runner can build in it.
- A digest pins every package an image holds, so the build installs nothing.
- For a musl `staticlib`, the pinned rustc's `--print native-static-libs` names `-lunwind -lc` and bundles neither
  (2026-11-03), so the C library and the unwinder come from the toolchain that links the program.
- `-lkartta_ffi` finds `kartta_ffi.lib` under GNU ld on Windows (the ld manual, section WIN32), and `link.exe` takes any
  name, so a rename would help neither linker. rustc sets the name
  (`compiler/rustc_target/src/spec/base/windows_msvc.rs:14-15`).
- Only the tag push publishes, so a manual run on a tag's ref cannot release by accident.
- `cargo publish --workspace` orders the crates itself and verifies each against the packages of the others; a publish
  of `kartta-mcp` alone verifies against the registry, and failed there against the `0.0.0` of `kartta` (2026-11-02,
  #137).
- A real `cargo publish` refuses the whole set, before any upload, when crates.io holds the version of one crate in it
  (`verify_unpublished` in `src/ops/registry/cargo_publish.rs` of the pinned toolchain's Cargo), and a version can never
  be overwritten (Cargo's `publishing.md`), so a re-run leaves out what the failed one uploaded. crates.io names the
  sparse index for a few crates' metadata, with no rate limit, and its API for what the index lacks, at one request a
  second (its `data-access` page, read 2026-11-06). An index file lists every published version, yanked ones included
  (Cargo's `registry-index.md`, "JSON schema").
- A dry run checks the tree, and the registry's copy of the same version need not be that tree: at `0.0.0` it is a
  placeholder that predates `Engine`, so leaving those crates out fails `kartta-mcp`.
- The maintainer chose "Trusted publishing. A credential per run and no stored secret." (#1058, 2026-11-24).
- crates.io configures a publisher only on a crate it holds: "initial publish requires an API token" (its
  trusted-publishing page, read 2026-11-25). A publisher binds the repository, its owner's id, the workflow's file name
  and, when one is entered, an environment; one exchange yields a 30-minute token of every crate whose publisher matches
  (`src/controllers/trustpub/tokens/exchange/mod.rs` of rust-lang/crates.io at `a6eb8106`).
- A re-run of the workflow after a failed release reaches `publish` again: a push of a tag to the commit it names
  changes nothing, and a different commit is refused. The steps likeliest to fail on a first run go first, the crates'
  upload and then the tag, before the GitHub release exists; the upload, which cannot be undone, waits for every
  target to build.
- No channel takes a version twice: the ruleset `protect-release-tags` refuses to delete, update or force-push a `v*`
  or `bindings/go/v*` tag and has no bypass actor (read 2026-11-06), crates.io never overwrites a version (Cargo's
  `publishing.md`), npm never reuses one, even unpublished (`npm-unpublish.md` of npm/cli), and a Go version is an
  immutable snapshot (the Go modules reference). One version names every artifact
  ([ADR 4.46](/design-docs/adr/4.46-release-scope.md)), so a fix moves all of them.
- A yank keeps a lockfile building and stops new resolutions (Cargo's `cargo-yank.md`), so on a version without a
  defect it only turns away an exact requirement.
- A failed cut surfaces late, so the changes likeliest to break a build run it on their pull request.
- The addon builds in the archive's row because the row already holds the image, the toolchain and the floor's proof.
  Node 24.22.0's Linux build ran in the arm64 `manylinux_2_28` image and on `debian:10.13-slim` (2026-11-06), and the
  arm64 gnu addon built there asks for glibc 2.28 at most, where one built on Debian 12 asks for 2.34 and fails to load
  there.

## Consequences

- A glibc host below 2.28 gets no gnu artifact and no Node addon. `cargo install` builds `kartta-mcp` against the
  host's own glibc, which rustc supports from 2.17, and no run has built it on such a host. Accepted.
- A pull request that bumps a dependency costs seven more builds on GitHub's runners, six of them with an addon after
  the archive, and the release jobs do not feed `ci-ok`, so they report and do not gate. The addon adds 2 min 32 s cold
  at 2 jobs on macOS arm64 (2026-11-06). Accepted.
- A source change under `crates/` runs none of these builds, because seven more on every pull request cost more than the
  rare break they find: a call past the floor, or code that only fails under fat LTO, shows at the next dependency bump
  or at the cut (#1096).
- The floor's images and the Alpine image follow no bot; a toolchain bump leaves the Alpine image behind until a hand
  edit, and rustup in it fetches the pinned toolchain on each run until then (#1097).
- A Windows user unpacks a `.tar.gz`, which the system's `tar` does. Accepted.
- A crate gets a publisher only once it is on crates.io, so a crate new to the publish set needs a version published by
  hand and its publisher before a cut, and without them its upload fails the job (#1058).
- The publisher takes any ref and event but `pull_request_target` and `workflow_run`: a writer's pull request that edits
  `release.yml` can take a token, as a writer can create a `v*` tag, which `protect-release-tags` allows. Accepted.
- The token lasts 30 minutes from the auth step, and a cut that outlasts it fails at its next upload; a re-run takes a
  new one. Packaging and verifying all 24 crates took 86 s at 3 jobs on macOS arm64 (2026-11-25). Accepted.
- Cargo waits for each upload to reach the index and may time out. A re-run that comes before the index lists the
  version tries that crate again and crates.io refuses it; a later re-run passes. Accepted.
- A pull request that touches the release inputs verifies every crate once more: 156 s at 2 jobs on macOS arm64
  (2026-11-06). Accepted.

## Rejected

- **A build on the runner** — the runner's glibc 2.39 sets the floor.
- **A lower floor, on `manylinux2014` and glibc 2.17** — Node.js 24 refuses such a host, so only a C consumer of the
  static library would gain, and one matrix promises one floor for every channel.
- **`libkartta_ffi.a` as the Windows file's name** — it renames an MSVC library for a linker that finds it either way.
- **Per-artifact `.sha256` files** — twelve more assets, where one file checks all of them.
- **One `cargo publish` per crate** — it verifies each crate against the registry, where `kartta-mcp` fails, and the
  order would be kept by hand.
- **`cargo publish`'s own refusal as the skip** — it refuses the whole set when crates.io holds one crate of it.
- **The crates.io API for the skip** — one request a second, where the index has no limit.
- **Moving the tag to the fixed commit** — the ruleset refuses it, and crates.io, npm and the Go proxy keep what they
  took.
- **Only the failed channel at the next patch version** — one version names every artifact.
- **A stored `CARGO_REGISTRY_TOKEN` secret** — it outlives the run, and #1058 chose trusted publishing.
- **A publisher bound to an environment** — a setting more per cut, which refuses no job without a protection rule.

## Revisit if

Node.js raises its floor, or a consumer needs a gnu artifact on an older host. High confidence in the floor, which ran
on both architectures in the pinned images; the Windows builds and the runners' toolchain mount wait for a first run.
