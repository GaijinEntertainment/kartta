# Report truncation from a listing, not from a ranked query

- **Status:** accepted
- **Date:** 2026-08-24
- **Initiative:** `01-kartta-fs-port`

Three query surfaces take a cap. `Index::glob_paths` and `Index::fuzzy_paths` return what fits and say nothing about
what did not; `Index::list_dir` returns a `ListOutcome` whose `truncated` reports whether the cap turned an entry away.
That reads as an inconsistency between neighbouring methods, and it is the point rather than an oversight.

**A cap announces itself exactly where the caller could read the capped answer as a complete description of something.**

A ranked query's cap *is* the request. "The ten best matches for `main`" is answered in full by ten paths, and no caller
ever believed the index held only ten — the ranking already says the rest scored lower. A flag there would be set on
nearly every call with a cap, which is how a flag stops being read.

A listing's cap is a resource guard on an answer about a place. "What is in `src`" answered with twenty entries asserts
that `src` holds twenty entries. If it holds two hundred, the caller has a wrong answer and nothing to detect it with,
because a listing carries no ordering that would hint at the omission.

This is the objection that removed the entry cap from `kartta-walk`, applied to a surface that can meet it. There, a
truncated tree could not be told apart from a complete one *and* the surviving subset depended on thread scheduling, so
the guard produced arbitrary wrong answers and was dropped in favour of failing the walk. A listing clears both halves:
`Index::entries` is depth-first and deterministic, so a cap takes a defined prefix rather than an arbitrary subset, and
the flag makes what it cut visible.

`truncated` is set by an actual rejection and never inferred from `entries.len() == limit`. A directory holding exactly
the cap is a complete answer and says so. Inferring would get the flag wrong in precisely the case where a caller most
needs it to be right.

The consequence is that this is a per-surface judgement, not a crate-wide convention to apply by reflex. A surface that
answers "what is at X" and takes a cap carries the flag; a surface that answers "the best N of X" does not. Content
search is the next case to decide, and it decides as a listing does: a cap on matches within one file bounds a
description of that file's content.

## Considered Options

- **Report truncation on every capped surface** — consistent to read, and the flag becomes noise on the ranked
  queries, where it is set whenever the index holds more matches than the caller asked for. That is the ordinary case,
  so the flag carries no information and trains the caller to ignore it on the one surface where it matters.
- **Report it nowhere, as the port arrived** — the cheapest surface, and it leaves a capped listing indistinguishable
  from a small directory. The upstream implementation did in fact carry a truncation flag on its listing; dropping it
  to match the other two queries would be trading a correct answer for a symmetrical one.
- **Return the total instead of a flag** — strictly more information, at the cost of the work the cap exists to avoid.
  A depth-limited listing skips a subtree by binary search precisely so it never touches what it is not returning, and
  a total would put that scan back on every call.
- **Leave the caller to ask for one more than it wants** — this works, and it is the caller reimplementing the flag
  with an off-by-one at each call site, then discarding the extra entry, against an index that already knows the
  answer.

Revisit if a caller needs the count of what was cut rather than the fact of it, which arrives as its own named thing
and never by widening `truncated` into a number.
