A family's resolver reads its configuration as it is built, a `go.mod`, a `tsconfig.json`, every `.sqconfig`, and what
it derives decides how every file of the family resolves. A followed engine keeps each family's resolver and what it
read, builds it again only when a refresh reaches that, and resolves the family's files again only when the rebuilt
resolver does not resolve as the kept one, at the cost of holding each resolver as long as the engine.

## Decision

- **What is kept.** An engine built with stamps keeps, for each family, the resolver its first language built
  ([ADR 3.122](/design-docs/adr/3.122-language-family-resolvers.md)) and what that
  resolver asked of the repository while it was built: the keys of its questions, a hash of every question and every
  answer, and the paths of the files it read. Both are kept from the build on, one for the family however many
  languages it holds. An engine without stamps keeps none.
- **When it is built again.** A refresh builds a family's resolver again when a key it reached is one of the
  resolver's questions, or when a file the resolver read, such as an edited `go.mod` a refresh names, lies inside a
  part the refresh walked, or when the family has a file to resolve and no resolver yet, because no file of it was
  there at the build. `RefreshOutcome::walked_over` finds the part that can hold a read file by a binary search of
  the walked parts ([ADR 1.44](/design-docs/adr/1.44-refresh-outcome-positions.md)), which are in
  tree order and none below another ([ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md)). A whole
  refresh walks the part that holds every read file, so it builds every kept resolver again. Any other refresh
  resolves through the kept resolver and reads none of the configuration.
- **When the family resolves again.** Only a family whose resolver was built again and that had a kept configuration is
  compared. When the hash of what it asked changed, and the rebuilt resolver does not answer
  `Resolver::resolves_as(kept)`, every file of the family is read and resolved again and `EngineRefresh::reconfigured`
  names the family. When it does answer yes, the configuration change resolves no file of the family again, a file a
  question of its own reaches still is, and `reconfigured` leaves the family out. The rebuilt resolver and its
  configuration replace the kept ones either way.
- **What a language compares.** The default `resolves_as` answers `false`, which keeps the hash rule for a language
  that states nothing. Five compare what they derived, leaving out the bytes they derive nothing from: Go its modules,
  each `module` line and replace onto a local directory, and which modules vendor; Blk its mount table from the files
  that state mounts; jsts the `tsconfig` aliases, the `package.json` `imports`, and each package's name, directory,
  `exports` and entry; Quirrel the mounts and base paths of each `.sqconfig`; and Rust the packages and the name and
  root of each library from the `Cargo.toml` files. A `require` bump, a dependency or version bump, a setting outside
  `mountPoints` and a comment then resolve no file of the family again.
- **What it reports.** `reconfigured` names families by `Language::family`, `go` for Go and `jsts` where TypeScript,
  TSX and JavaScript share one resolver, in the order of `Engine::graphs`; the C ABI's, Go's and Node's refresh
  answers and the MCP server's `refresh` carry those strings.

## Why

- A family's files resolve through one resolver, so one configuration a family is read, tested and compared once.
- Building a resolver reads the family's whole configuration: every `.sqconfig` for one Quirrel script, every Blk mount
  file for one `.blk`. A one-file refresh of a Quirrel script took 105.0 ms at the median on 16 copies of the C++
  game-engine tree, 2.92M entries, and 17.7 ms with the resolver kept (2026-10-22).
- A resolver derives only part of what it reads: in the 5,000 commits of the Go monorepo snapshot up to `8a0a07a58f`,
  49 of the 50 that touch a `go.mod` change only `require` lines, each of which resolved every Go file again.
- Both the read files and the parts a refresh walks grow with the tree: testing 2,800 read files against 97,448 parts
  one by one took 0.28 to 1.05 s of a refresh at the limit on the 16 copies (2026-10-21), and the search 0.66 to
  12.6 ms.

## Consequences

- The kept resolvers hold 1.3 MiB on the 16 copies, Quirrel's 0.90 and Blk's 0.35, for as long as the engine; accepted.
- A language that does not implement `resolves_as` resolves its whole family again on any change to a byte its
  resolver read; accepted, the language can state what it derives.

## Rejected

- **Build every family's resolver a refresh hands a file to** — reads the family's whole configuration on every refresh
  of one of its files.
- **Compare the hash of the bytes read alone** — a `require` bump or a comment resolves every file of the family to the
  same bindings.
- **One configuration for each language of a family** — tests and builds the jsts family's configuration three times
  where one resolver serves its languages.
- **A set of the walked parts, probed with each read file and every directory above it** — relies on no order, at a slot
  for each part built on every refresh that walks parts apart: 1.0 to 17.8 ms on the 16 copies against 0.66 to 12.6 ms
  for the search, which holds nothing.

## Revisit if

A language's configuration changes what its resolver derives on most edits to it, so the comparison stops saving the
family's resolution, or a kept resolver grows to a share of the heap; high confidence on the measured trees.
