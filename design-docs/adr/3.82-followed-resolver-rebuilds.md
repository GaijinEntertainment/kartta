# Build a followed family's resolver again only when a refresh reaches what it read

- **Date:** 2026-10-18
- **Governs:** `crates/kartta/src/following.rs` (`Following::plan`, `Following::reconfigure`, `reaches`),
  `crates/kartta/src/resolving.rs` (`Resolvers`), `crates/kartta/src/repository.rs` (`Configuration`,

- **Pinned by:** `crates/kartta-languages/tests/refresh.rs` (`a_changed_go_mod_resolves_every_go_file_again`,
  `a_go_mod_edit_that_only_bumps_a_requirement_resolves_no_go_file_again`,
  `a_local_replace_onto_an_imported_directory_resolves_every_go_file_again`,
  `a_settings_blk_edit_outside_its_mount_points_resolves_no_blk_file_again`,
  `a_package_json_version_bump_resolves_no_script_again`, `a_cargo_toml_dependency_bump_resolves_no_rust_file_again`,
  `a_sqconfig_comment_resolves_no_script_again`,

  `crates/kartta/tests/engine.rs` (`a_followed_family_with_no_file_at_the_build_builds_its_resolver_when_it_gains_one`,
  `a_configuration_rebuilt_to_resolve_as_the_kept_one_resolves_nothing_again`)

A family's resolver reads its configuration as it is built, a `go.mod`, a `tsconfig.json`, every `.sqconfig`, and what
it derives decides how every file of the family resolves. A followed engine keeps each family's resolver and what it
read, builds it again only when a refresh reaches that, and resolves the family's files again only when the rebuilt
resolver does not resolve as the kept one, at the cost of holding each resolver as long as the engine.

## Decision

- **What is kept.** An engine built with stamps keeps, for each family, the resolver its first language built
  ([ADR 3.122](/design-docs/adr/3.122-language-family-resolvers.md)) and what that resolver asked of the repository
  while it was built: the keys of its questions, a hash of every question and every answer, and the paths of the files
  it read. Both are kept from the build on, one for the family however many languages it holds. An engine without
  stamps keeps none.
- **When it is built again.** A refresh builds a family's resolver again when a key it reached is one of the
  resolver's questions, or when a file the resolver read, such as an edited `go.mod`, lies inside a part the refresh
  walked and its stamp changed, or when the family has a file to resolve and no resolver yet, because no file of it was
  there at the build. The engine stamps each file a resolver reads just before the read, by `kartta_fs::FileStamp`
  ([ADR 1.40](/design-docs/adr/1.40-unchanged-file-detection.md)), and a read file inside a walked part is stat'd again
  and counts as changed unless both stamps are there and equal. A file the resolver asked to read that the index did
  not hold is followed by its keys alone, since only its appearing changes it. `RefreshOutcome::walked_over` finds the
  part that can hold a read file by a binary search of the walked parts
  ([ADR 1.44](/design-docs/adr/1.44-refresh-outcome-positions.md)), which are in tree order and none below another
  ([ADR 1.16](/design-docs/adr/1.16-scoped-refresh.md)). So a whole refresh, or a named one of a directory, that changed
  no read file and reached none of a resolver's questions does not build that resolver again; any refresh that builds
  none resolves through the kept resolver and reads none of the configuration.
- **When the family resolves again.** Only a family whose resolver was built again and that had a kept configuration
  is compared. When the hash of what it asked changed, and the rebuilt resolver does not answer
  `Resolver::resolves_as(kept)`, every file of the family is read and resolved again and `EngineRefresh::reconfigured`
  names the family. When it does answer yes, the configuration change resolves no file of the family again, a file a
  question of its own reaches still is, and `reconfigured` leaves the family out. The rebuilt resolver and its
  configuration replace the kept ones either way.
- **What a language compares.** The default `resolves_as` answers `false`, which keeps the hash rule for a language
  that states nothing. Go, Blk, jsts, Quirrel and Rust compare what they derived, leaving out the bytes they derive
  nothing from: Go its modules, each `module` line and replace onto a local directory, and which modules vendor; Blk
  its mount table from the files that state mounts; jsts the `tsconfig` aliases, the `package.json` `imports`, and each
  package's name, directory, `exports` and entry; Quirrel the mounts and base paths of each `.sqconfig`; and Rust the
  packages and the name and root of each library from the `Cargo.toml` files. A `require` bump, a dependency or version
  bump, a setting outside `mountPoints` and a comment then resolve no file of the family again.
- **What it reports.** `reconfigured` names families by `Language::family`, `go` for Go and `jsts` where TypeScript,
  TSX and JavaScript share one resolver, in the order of `Engine::graphs`; the C ABI's, Go's and Node's refresh
  answers and the MCP server's `refresh` carry those strings.

## Why

- A family's files resolve through one resolver, so one configuration a family is read, tested and compared once.
- Building a resolver reads the family's whole configuration: every `.sqconfig` for one Quirrel script, every Blk mount
  file for one `.blk`. A one-file refresh of a Quirrel script took 105.0 ms at the median on 16 copies of the C++
  game-engine tree, 2.92M entries, and 17.7 ms with the resolver kept (2026-10-22, #336).
- A resolver derives only part of what it reads: in the 5,000 commits of the Go monorepo snapshot up to `8a0a07a58f`,
  49 of the 50 that touch a `go.mod` change only `require` lines, each of which resolved every Go file again (#362).
- Both the read files and the parts a refresh walks grow with the tree: testing 2,800 read files against 97,448 parts
  one by one took 0.28 to 1.05 s of a refresh at the limit on the 16 copies (2026-10-21, #158), and the search 0.66 to
  12.6 ms.
- A whole refresh of an unchanged tree built every kept resolver again: on the 16 copies it took 10.78 s at the median
  of 8, against 8.40 s with the read files stat'd instead (2026-10-24, #341).

## Consequences

- The kept resolvers hold 1.3 MiB on the 16 copies, Quirrel's 0.90 and Blk's 0.35, for as long as the engine; accepted.
- A refresh stats each read file inside the parts it walked, 2,304 on a whole refresh of the 16 copies, and keeps 24
  bytes of stamp beside each; accepted.
- Off unix, a same-size configuration edit whose modification time a tool set back keeps the stale resolver, as the
  index carries such an edit of any file over unread
  ([ADR 1.40](/design-docs/adr/1.40-unchanged-file-detection.md)); accepted.
- A language that does not implement `resolves_as` resolves its whole family again on any change to a byte its
  resolver read; accepted, the language can state what it derives.

## Rejected

- **Build every family's resolver a refresh hands a file to** — reads the family's whole configuration on every refresh
  of one of its files.
- **Compare the hash of the bytes read alone** — a `require` bump or a comment resolves every file of the family to the
  same bindings.
- **One configuration for each language of a family** — tests and builds the jsts family's configuration three times
  where one resolver serves its languages.
- **Name the files whose stamps changed in `RefreshOutcome`, and test the read files against that list** — the index
  stamps only the files it reads, so in an engine without a content index, the MCP server's default, a `go.mod`, a
  `tsconfig.json` or a `.sqconfig` has no stamp, and every whole refresh would still build every resolver again.
- **Build again every resolver whose read file lies in a walked part** — a whole refresh then builds every kept
  resolver again for nothing.
- **A set of the walked parts, probed with each read file and every directory above it** — relies on no order, at a slot
  for each part built on every refresh that walks parts apart: 1.0 to 17.8 ms on the 16 copies against 0.66 to 12.6 ms
  for the search, which holds nothing.

## Revisit if

A language's configuration changes what its resolver derives on most edits to it, so the comparison stops saving the
family's resolution, or a kept resolver grows to a share of the heap; high confidence on the measured trees.
