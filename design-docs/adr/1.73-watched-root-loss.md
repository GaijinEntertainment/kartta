# Tell a watched root that went from dropped changes

- **Date:** 2026-10-24
- **Governs:** `crates/kartta-fs/src/watch.rs` (`WatchError::RootGone`), `crates/kartta-fs/src/watch/notified.rs`
  (`root_went`), `crates/kartta-fs/src/watch/inotify.rs`, `crates/kartta/src/follow.rs`, `kartta_fs::WatchError`,
  `kartta::Follower`
- **Pinned by:** `crates/kartta-fs/src/watch/notified.rs` (`the_root_deleted_or_moved_is_told_as_the_root_gone`,
  `a_rename_from_the_root_is_told_as_the_root_gone_on_windows_alone`), `crates/kartta/src/follow.rs`
  (`a_follow_whose_root_was_deleted_or_moved_away_names_it_and_stops_once_no_restart_finds_the_root`,
  `a_follow_whose_root_was_replaced_restarts_over_the_tree_now_at_its_path`)

A watched root that is deleted or moved away leaves the caller a tree it may have to index again, and only the watcher
holds the notice that tells that apart from notifications the system dropped. A wait or a drain answers
`WatchError::RootGone` in place of its batch, and a follow names the root's loss as its restart's reason; the trade is a
watch of the root's parent on Windows, and a loss that an overflowed inotify queue still hides.

## Decision

- **The answer.** The root's deletion or move ends a wait or a drain with `WatchError::RootGone` in place of its batch,
  whatever else the batch gathered, so a caller tells it from dropped changes
  ([ADR 1.17](/design-docs/adr/1.17-change-notifications.md) states the lost batch).
- **The notice.** It is told from the notice the system raises for the root itself, never from a stat of the root, and
  on Windows a watch of the root's parent alone reports the root's move.
  [`WatchError::RootGone`](/crates/kartta-fs/src/watch.rs) documents the notice each system raises. A full macOS and
  Windows queue keeps the notice beside its overflow.
- **The follow.** `kartta::Follower` answers `WatchError::RootGone` with a new watcher over a refresh of the whole
  tree, which finds a tree moved into the root's place, and the reason it names is `the root was deleted or moved`. A
  restart that fails, as one does with nothing at the root's path, ends the follow with the reason in `Watch::off`.

## Why

- A root deleted or moved is a tree the caller may have to index again, not a burst of notifications, and only the
  watcher holds the notice that tells the two apart: a follow whose root went restarted with the reason
  `the notifications dropped changes`, from which an agent cannot tell a root it must index again (#469).

## Consequences

- An inotify queue that filled before the root's own deletion or move notice drops the notice with the rest, so that
  loss reads as dropped changes, and the follow's failed restart names the missing root directory instead. Accepted.
- A Windows watcher also hears each change to an entry of the root's parent, which it drops before the queue at a
  prefix test of each path it names, though an overflow of that watch loses the batch; a root whose parent cannot be
  watched cannot be watched either, with `WatchError::Start` naming the parent. Accepted.

## Rejected

- **Tell a root that went by a stat of the root at each lost batch** — a tree moved into the root's place before the
  stat reads as dropped changes, and the watcher already holds the notice.
- **Take a rename of the root's own path as its loss** — `FSEvents` carries the root's past flags on every later
  notification for it, so a `touch` of a root moved into place would still lose the batch, in 2 of 3 runs.
- **Watch no parent on Windows** — the root's watch follows the moved directory and names its changes by the root's
  path, so the follow would go on over a tree that left without a restart.

## Revisit if

An overflowed inotify queue hides a root's loss often enough that a stat of the root at each lost batch pays. Confidence
unknown: no figure records how often an overflow takes the root's notice.
