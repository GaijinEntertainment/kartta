Expiry ([ADR 2.3](./2.3-expire-cache-entries-by-the-time-each-was-published.md)) ages entries a store maps, but a cache
directory also gathers files no store maps: the temporary files of writers killed before they published, and packs of
an older format. Every merge removes them by the age of the file, with a floor of an hour that keeps a live writer's
file and a fresh pack, and a build reports the files its merge could not remove.

## Decision

- **Temporary files.** A merge removes a writer's temporary file once it has been unwritten for an hour and no writer
  holds its lock. A writer takes an exclusive lock on its file when it creates it, and a killed process drops its
  locks. Where the filesystem has no locks, the lock is not taken, and only the hour protects the file.
- **Packs the store did not map.** A merge removes a file with the pack extension that its store did not map, of format
  version 1, damaged, foreign, or published after the store opened, once the file is older than both the time to live
  and an hour. Every entry in it was published before its file was last written, so by then every entry has expired.
  The hour holds whatever the time to live, a zero included.
- **What the merge counts.** `Merged::orphans` and `Merged::unreadable` count the temporary files and unmapped packs it
  removed, and `orphans_left` and `unreadable_left` those it could not remove.
- **What a build reports.** The merge a build or a refresh ends with answers `Merged`, and the files it could not
  remove, merged packs left in place (`left_in_place`, holding their entries twice), temporary files and unmapped packs,
  are a `BuildError::Cache` naming each count, so they reach every consumer through the errors it already reads. What
  the merge expired and the expired entries it kept stay `Merged`'s own.

## Why

- A pack another process published after this store opened is one the store did not map; a merge given a time to live
  under an hour would otherwise remove it as it lands.
- Two versions that share a directory during a rollout each see the other's packs as unreadable, and the time-to-live
  floor keeps them from removing each other's fresh packs.
- A directory whose files the merge could not remove grows with nothing said unless the build reports it; the expiry
  counts are the store working as designed and give an agent nothing to act on.

## Consequences

- On a filesystem without locks, a build that leaves its temporary file unwritten for an hour can lose it to another
  process's merge, which costs that build's publish and nothing else. Accepted.
- Packs of an older format stay for a time to live after their last write. Accepted.

## Rejected

- **Removing packs of another format at once** — two versions sharing a directory during a rollout would remove each
  other's packs.
- **An hour of age alone for a temporary file** — a build that inserts little for an hour would lose its file to another
  process's merge, and its publish with it.
- **The time to live alone for a pack the store did not map** — a merge given a time to live under an hour would remove
  a pack another process published after the store opened, before any build read it.
- **The expiry counts on every build outcome** — they tell an agent nothing it acts on.

## Revisit if

A cache directory sits on a filesystem without file locks while its builds stay idle for an hour. Low evidence either
way: how long a build can go without inserting is not measured.
