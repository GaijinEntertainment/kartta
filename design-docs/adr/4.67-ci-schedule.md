# Run the whole of CI on `main` every week

- **Date:** 2026-11-06
- **Governs:** `.github/workflows/ci.yml` (`on.schedule`, `concurrency`)

The `deny`, `npm-audit` and `govulncheck` checks judge the dependencies against advisory databases that change with no
commit here, and CI ran only on a push or a pull request, so a quiet week hid a new advisory. CI runs on a weekly
schedule as well, every job of it; the trade is one more run of every job each week.

## Decision

- **Schedule.** `ci.yml` runs every Monday at 05:17 UTC, on the default branch, with every job it runs on a push.
- **Concurrency.** The run's group names its event, so a scheduled run and a push to `main` do not cancel each other.

## Why

- cargo-deny fetches the RustSec advisory database (its `advisories` configuration page), `npm audit` asks the registry
  for the known vulnerabilities of the dependencies (`npm-audit.md` of npm/cli), and govulncheck asks the Go
  vulnerability database (`cmd/govulncheck/doc.go` of golang.org/x/vuln at v1.9.0): each answer moves on its own.
- `fresh-resolve` builds the newest versions crates.io allows, so it moves with the registry too.
- govulncheck runs in the `go` job on each of its four runners, after that job's toolchain setup, so a run of the audits
  alone would copy that setup for every platform.
- One run of CI on `main` took 100 runner-minutes, its 39 jobs' durations summed (run 42269356753, 2026-11-06).
- A scheduled run runs on the last commit of the default branch, and the start of every hour is a high-load time that
  can delay or drop its jobs (GitHub's "Events that trigger workflows", `schedule`), so the minute is 17.
- One concurrency group with `cancel-in-progress` cancels the run in progress when another of the group starts
  (GitHub's workflow syntax, `concurrency`), and a scheduled run's ref is the push's.

## Consequences

- About 100 runner-minutes a week. Accepted.
- GitHub notifies one user of a failed scheduled run: the last to change its `cron` syntax, or the workflow's creator
  where no other user has (GitHub's "Notifications for workflow runs"). Accepted.
- In a public repository, GitHub disables a schedule after 60 days without activity (GitHub's "Events that trigger
  workflows"). Accepted.
- A scheduled failure gates no merge: it shows in the run list of `main` and in that notification. Accepted.

## Rejected

- **A workflow of the three audits** — it copies the `go` job's setup for each platform, and `fresh-resolve` stays
  unscheduled.
- **A schedule that skips every other job** — a condition on each of the other jobs, `fresh-resolve` included.

## Revisit if

CI's weekly runner time grows past what the week's pull requests spend, or the audits move to a service that alerts on
its own. High confidence in the schedule; the notification's single recipient waits on the first failure.
