# Say what a limited content search did not cover

- **Status:** accepted
- **Date:** 2026-10-14
- **Updated:** 2026-10-19
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/grep.rs` (`Planner`, `Fold`), `crates/kartta-fs/src/matches.rs`, `Matches`,
  `GrepOptions::limit`, `GrepOptions::count_all`
- **Pinned by:** `crates/kartta-fs/tests/grep.rs` (`the_limit_is_spent_in_index_order_and_an_exact_fit_is_whole`,
  `a_limit_that_fills_with_its_batch_reads_on_until_a_further_match_proves_the_cut`,
  `a_limited_search_answers_truncated_alike_whatever_shares_the_batch_that_fills_it`,
  `a_cut_proven_early_leaves_the_rest_unsearched`,
  `a_filter_selects_and_an_exclusion_removes_files_and_whole_directories`)

A capped answer announces its cap, and keeping `truncated` exact costs one item past the limit
([ADR 1.5](./1.5-announce-a-cap-unless-the-order-explains-it.md)). For content search that one match can lie anywhere in
the files not yet read. A limited search reads on until it finds it, and accounts for every candidate it did not
cover. The trade is that a limited search with no match past its limit costs a full search.

## Decision

- **`truncated` is exact.** It is set only by a match actually seen past the limit, never inferred, so an answer that
  holds exactly the limit can still be whole.
- **Read on until the cut is proven.** Files already being searched when the limit fills are folded in, and a further
  match in any of them proves the cut. When none holds one, the search reads on, each file stopping at its first match,
  until one does or the candidates run out.
- Once the cut is proven, `Matches::unsearched` counts the candidates the answer does not cover, a file already being
  read at that moment included.
- An answer is complete exactly when nothing is truncated, the search was not cancelled and no file failed to read.
- **Counting is the caller's to ask for.** `GrepOptions::count_all` searches every candidate past the limit. The answer
  still returns matching lines only up to the limit, and adds the matching lines and files the searched candidates hold
  in all. After a cancellation or an unreadable file the totals are lower bounds.
- **Every candidate is accounted for once.** A candidate is a regular file the filter selected and the exclusion kept.
  It lands in exactly one of: searched, binary, oversized, ruled out by the content index (ADR 1.14), failed to read,
  or unsearched.
- Beside those, the answer counts the files the exclusion removed and the symlinks the filter selected, which are never
  read through. An exclusion that matches a directory removes its subtree, as a listing's does (ADR 1.8).
- **One planning pass before any open.** The pass decides every entry from what the index already holds: kinds, paths,
  and the sizes and verdicts earlier queries kept. The number of candidates, and with it the number left unsearched, is
  therefore known without touching the filesystem.
- The pass runs in parallel. It keeps one `u32` per candidate it cannot settle unopened, in the run of entries that
  found it, never copied into one list. The runs are freed when the call returns.

## Why

- An agent reads a cut answer as complete unless the answer says what it cut (CLAUDE.md, `<answers>`). An inferred
  `truncated` would be wrong exactly when the answer is whole, the case ADR 1.5 exists to get right.
- Stopping with the batch that filled the limit made `truncated` depend on which candidates shared that batch. The
  content index keeps the files it rules out out of the batch, so the same search answered differently with and without
  it. Reading on gives one answer in every content-index storage and without one.
- `count_all` is the count of what the cap cut that ADR 1.5 calls for as its own named thing, not a widened flag.
- Reading on costs at worst one full search of the searchable candidates, which every search whose pattern matches
  fewer lines than its limit already pays. A limited search is therefore never dearer than a complete one.
- The planning pass makes the counts free: unfiltered, its runs hold at most about 10 MB for the 2.55M files of a
  3.03M-entry data volume (2026-10-14).

## Consequences

- A limited search whose limit equals the pattern's whole match count reads every remaining candidate. Accepted: it
  costs what a search without the limit costs.
- `count_all` reads the rest of the tree. Accepted: it is off by default.

## Rejected

- **Stop with the batch that filled the limit** — `truncated` then depends on what shares that batch, so the content
  index flips it, and an answer of exactly the limit with candidates unsearched cannot say whether it is whole.
- **Infer `truncated` when the limit fills** — cheap, and wrong precisely when the answer is whole.
- **Count unsearched positions instead of candidates** — no planning pass, and a number that mixes directories, files
  the filter never selected and files the binary rule would skip, which tells an agent nothing about its question.
- **Stream the candidates and plan lazily** — no candidate list, and a selective filter over a large tree then runs its
  globs serially on the calling thread, while the count of what the answer did not cover needs a pass over the rest.

## Revisit if

A content index can count matches without reading files, so that `count_all` is cheap enough to be the default. High
confidence the default holds until then: the trigram index (ADR 1.14) narrows by file and cannot count.
