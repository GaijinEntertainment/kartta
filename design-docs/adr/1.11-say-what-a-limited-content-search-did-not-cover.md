# Say what a limited content search did not cover

- **Status:** accepted
- **Date:** 2026-10-14
- **Revised:** 2026-10-19
- **Initiative:** `01-kartta-fs-port`

ADR 1.5 settles that a capped answer in index order announces the cap, and that keeping `truncated` exact costs one
item: the query looks for the one past the limit. Content search is the case that ADR left open, and the premise does
not hold there. The match past the limit may be anywhere in the files not yet read, so looking for it costs the rest of
the search — and when there is none, the whole of it. A limited search exists to avoid exactly that, so this revises
ADR 1.5's probe rule for content search.

**`truncated` keeps its meaning and is exact.** It is set only by a match actually seen past the limit, never inferred,
so an answer holding exactly the limit can still be whole. Files already being searched when the limit fills are folded
in, and any of them holding a further match proves the cut for free. When none does, the search reads on, each file
stopping at its first match, until one does or the candidates run out; the answer then says how many candidates it
**left unsearched** once the cut was proven, which includes a file already being read when it was. An answer is
complete exactly when nothing is truncated, the search was not cancelled and nothing failed to read.

Revised 2026-10-19. The search used to stop when the batch that filled the limit held no further match, leaving
`truncated` false and the rest unsearched. Which candidates share that batch depends on the content index, which keeps
the files it rules out out of the batch, so one search answered `truncated` with the index and not without it. And an
answer of exactly the limit with candidates unsearched never said whether more existed. The cost this decision first
avoided, measured on the 171,628-file checkout:

- **Realistic searches.** Of the 981 searches the parity plan asks across the checkout, every content-index storage
  and a Go monorepo, reading on changed one answer, which went from 10,427 candidates unsearched to `truncated` after
  708 more files and 16 ms. Total search time was within noise.
- **The worst case,** a limit equal to the pattern's whole match count with the last match early in the tree. The
  search then reads every remaining candidate: 2.58 s against 0.74 s without the content index, and 6.8 ms against
  3.0 ms with it.
- **At scale,** on the 8.68M-entry data volume, without a content index. Two alternating rounds, three runs each,
  under load averages of 17–46.
  - `TODO` with a limit of 100: 0.16–0.99 s, against 0.19–2.61 s for the previous rule.
  - `fn main` with a limit of 20: 5.09–7.03 s, against 4.95–13.88 s.
  - `unsafe impl Send` with a limit of 10: 9.45–9.72 s, against 10.37–21.62 s. The previous rule answered it with
    `truncated` false and 5.75M candidates unsearched in one round. Reading on answers `truncated` true every time.
  - A search with no limit, which bounds the worst case, read 4.97M–4.99M files in 1,385–2,279 s on both rules. A full
    scan runs the same code under both rules, and how long one takes on this volume depends on its network mounts and
    the machine's load. On a local 458k-entry tree, four alternating rounds of that search gave minimums of 16.84 s
    for the previous rule and 16.95 s for this one, and 16.01 s for a build of the previous rule's code that differs
    only in its package name.
  - Peak footprint was 1.41–1.51 GB under either rule.

That worst case is one full search of the searchable candidates, the ones not skipped as binary, oversized or ruled out,
which is what every search whose pattern matches fewer lines than its limit already costs. Reading on never makes a
limited search dearer than a complete one, and it turns an ambiguous answer into an exact one, the same in every
content-index storage.

**Counting what the cap cut is the caller's to ask for.** `count_all` searches every candidate past the limit without
keeping lines, and the answer then carries how many matching lines and files the searched candidates hold in all — the
count of what the cap cut that ADR 1.5 said would arrive as its own named thing rather than as a widened flag. A
cancellation or an unreadable file leaves candidates unread, and the totals are then lower bounds.

**Every candidate is accounted for once.** A candidate is a regular file the filter selected and the exclusion kept, and
it lands in exactly one of: searched, binary, oversized, ruled out, failed to read, or unsearched. Ruled out joined the
list on 2026-10-14 with the content index (ADR 1.14): a candidate missing a trigram every match must contain is never
read, and the answer counts it there. Beside those, the answer counts
the files the exclusion removed and the symlinks the filter selected, which are never read through. An exclusion that
matches a directory removes its subtree, as a listing's does (ADR 1.8).

These counts are free in the sense that matters. Before any file is opened, one pass over the index decides every
entry from what the index already holds — kinds, paths, and the sizes and verdicts earlier queries kept — so the number
of candidates, and with it the number left unsearched, is known without touching the filesystem. The pass runs in
parallel and keeps one `u32` per candidate it cannot settle unopened, left in the run of entries that found it rather
than copied into one list, which would hold every candidate twice at the moment of the copy. Unfiltered, that is at
most about 10 MB for the 2.55M files of a 3.03M-entry data volume, held for the call and freed when it returns. On a 171,628-file checkout a search for an
identifier that fills a limit of 100 reads 7,803 files in 120ms and reports 161,219 unsearched; asking it to count reads
every file in 2.6s and reports 28,286 matching lines in 4,529 files.

## Considered Options

- **Stop with the batch that filled the limit, as this decision first stood** — no read past that batch, and
  `truncated` then depends on which candidates share it, so the content index flips the answer, and an answer of
  exactly the limit with candidates unsearched cannot say whether it is whole.
- **Infer `truncated` when the limit fills** — cheap, and wrong precisely when the answer is whole, the case ADR 1.5
  exists to get right.
- **Count unsearched positions instead of candidates** — no planning pass, and a number that mixes directories, files
  the filter never selected and files the binary rule would have skipped, which tells an agent nothing about how much
  of its question went unanswered.
- **Stream the candidates and plan lazily** — no candidate list, and a selective filter over a large tree then runs its
  globs serially on the calling thread, while the count of what the answer did not cover needs a pass over the rest
  anyway.

Revisit if a content index lands that can count matches without reading files, in which case `count_all` may become
cheap enough to be the default.
