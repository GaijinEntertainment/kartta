# Watch on Linux each directory the index keeps, from the walk that keeps it

- **Status:** accepted
- **Date:** 2026-10-15
- **Updated:** 2026-10-21
- **Initiative:** `01-kartta-fs-port`
- **Governs:** `crates/kartta-fs/src/watch/inotify.rs`, `Index::refresh_paths_watched`, `WatchError::Limit`
- **Pinned by:** the tests of `crates/kartta-fs/src/watch/inotify.rs`, the Linux tests of
  `crates/kartta-fs/tests/watch.rs`

inotify watches one directory at a time, and every watch counts against `fs.inotify.max_user_watches`, which all of a
user's processes share. The Linux watcher of [ADR 1.17](/design-docs/adr/1.17-change-notifications.md)
watches only the directories the index keeps, each from the walk that keeps it, so ignored output takes no watch and
starting costs no second walk; the trade is a watch call for every directory each walk under the watcher keeps.

## Decision

- **What is watched.** Each directory a walk under the watcher keeps is watched as its visit keeps it, before the walk
  lists it: the walks of `Index::build_watched`, `Index::refresh_watched` and `Index::refresh_paths_watched`. A
  directory named `.git` or a pruned name, and one the ignore rules read for that walk hide, is not watched. A wait or
  a drain watches nothing, so a directory made after the start is watched by the refresh under the watcher that takes
  it in, and one a `.gitignore` edit shows by the refresh that edit asks for.
- **The mask** asks for creations, deletions, writes, closes after a write, moves, and the watched directory's own
  deletion and move, and for no access event and no change of attributes, so the reads of a refresh raise nothing.
- **A watch call each time.** A walk under the watcher makes a watch call for each directory it keeps, one already
  watched included; the kernel answers the watch the directory has.
- **A watch that fails.** A directory gone before its watch, or one the user cannot read, is not watched: the walk
  cannot list it either, and the build reports it. Any other refusal is held and reported as `WatchError::Start` when
  the walk ends.
- **The watch limit.** Once a watch call meets `fs.inotify.max_user_watches`, the walk finishes, makes no more watch
  calls, and counts each directory it keeps as unwatched. The walk's outcome comes back beside `WatchError::Limit`,
  which names how many directories were watched and how many were wanted. When the refresh returns an error of its
  own, the next `wait`, `drain` or `refresh_paths_watched` under that watcher reports the limit or the refusal. Either
  way the watcher no longer covers the tree.
- **A directory a refresh drops.** The refresh hands the watcher the directories it dropped from the index, the topmost
  of each run, and the watcher releases every watch at or below them in one pass over its map. That covers a directory
  an edit hides, and one deleted or moved away. A directory shown again is watched by the refresh that takes it in.
- **A moved directory.** A watch follows its directory wherever it moves and keeps the path it had, so the move of a
  watched directory, as it is read, drops its watches and those of every directory below it. The refresh of the name it
  went to watches it again wherever its walk keeps it, so a directory moved under an ignored or pruned one is no longer
  followed. A directory moved, before the move is read, from a path a refresh drops to one it keeps stays watched under
  its new path, since the walk's watches join the map before the release pass.
- **The notices read.** A watched directory's own notices name nothing, except that the root's own deletion or move
  loses the batch. The notice of a released watch, `IN_IGNORED`, removes that watch from the map alone.
- **Where the watches are kept.** The walk threads append each watch and its path to one buffer, and the caller's
  thread makes the map from it when the walk ends, and before each poll and release.
  [ADR 1.22](/design-docs/adr/1.22-inotify-watch-map.md) sizes the map.

## Why

- A directory watched before it is listed raises a notification for whatever is made in it after the listing, and
  whatever was made before is in the listing; a directory made after its parent was listed raises one in the parent's
  watch. So no directory is listed unwatched, and the start needs no second walk.
- Ignored and `.git` directories make up much of a tree: on `~/wrk` the index held 94,001 of the 150,237 directories on
  disk (2026-10-15). Build output in an ignored directory took a watch each from the shared limit, and each write
  inside it woke a refresh that changed nothing.
- The rules read for the walk decide each watch, so no rule kept from an earlier call does, and a directory a
  `.gitignore` edit shows is watched where a creation read by the watcher never was.
- A path allocated on a walk thread stays in that thread's glibc arena among the pages the walk freed, which the trim
  after the build cannot return: a map filled on the walk threads left 132–135 MiB resident after the build against
  64 MiB (2026-10-20).

## Consequences

- The kernel serves watch calls one at a time, so the walk threads queue on them: on 1.8 million entries and 111,001
  watches a watched build took about 0.2 s more than a build without a watch (2026-10-20), and the queue widens under
  load. Accepted.
- A whole refresh under the watcher pays a watch call for each directory it keeps, a median of 28 ms more on 111,061
  directories (2026-10-20). Accepted.
- inotify queues an `IN_IGNORED` notice for each watch released, so releasing more watches than the room
  `fs.inotify.max_queued_events` leaves in the queue overflows it, and the next wait hands over the whole tree: a
  distribution's limit of 16,384 lets a hide of some 16,000 directories through. Accepted.
- A refresh that drops directories pays the pass over the map and a removal call for each watch released. Accepted.

## Rejected

- **Watch each directory from the walk's `enter`, after its listing** — a change made between the listing and the
  watch raises nothing, so each directory would need a stat after its watch went on and a listing again when it moved.
- **fanotify's filesystem-wide marks** — one mark for the filesystem, but it needs `CAP_SYS_ADMIN`, which a consumer may
  not have; not prototyped.
- **Watch each directory as the wait reads its creation** — ignored build output takes a watch a directory, and a
  directory the rules hid at the start and an edit shows is never watched; dropping afterwards what the refresh did not
  keep still leaves the second.
- **Read the ignore rules in the watcher, and follow a directory again when its `.gitignore` changes** — a second reader
  of the rules, and a listing again on the caller's thread of every directory below a changed `.gitignore`: a root
  `.gitignore` edit took a median of 2.00 s to its refreshed index against 0.38 s (2026-10-20).
- **Re-point a moved directory's watches from the walk of the refresh that keeps it** — a directory moved where no
  refresh keeps it, under an ignored directory or out of the tree, would keep its watches under the path it had.
- **A map from each path to its watch, to skip the call for a directory already watched** — saves the 28 ms above for a
  second copy of every watched path; not prototyped.
- **Release the watches at and below each directory the walk's rules hide** — the walk meets a directory ignored from
  the start, such as `target/`, each time it walks the part that holds it, so the pass runs where nothing was watched.
- **Mark each watch a walk asks for again, and release the unmarked ones in the walked parts** — a pass over the
  watches at every refresh under the watcher, and a lock for each directory the walk keeps.
- **Read the queue between releases, so their notices cannot overflow it** — the changes read would wait in the watcher
  for the next wait, a second place a batch is gathered from; not prototyped.

## Revisit if

The trees consumers follow outrun `fs.inotify.max_user_watches` as a matter of course, or the walk threads' queue on the
watch calls costs a build more than a whole refresh. Medium confidence: no consumer has met the limit, and one inotify
instance per walk thread would take that queue apart.
