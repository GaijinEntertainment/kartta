# Judge code dead only where the graph sees it used

- **Status:** accepted
- **Date:** 2026-10-17
- **Revised:** 2026-10-19
- **Initiative:** `03-code-graph`

An agent that cleans up a tree asks which definitions nothing reaches. The graph resolves calls when a query asks (ADR
3.7), and much of what keeps code alive is not a call the extraction records: a runtime that starts `main`, an
annotation that registers a function, an operator an expression calls, a function passed as a value, a caller outside
the repository. A definition reported dead that something uses costs the agent a wrong deletion; a definition left out
costs it a candidate. The answer has to list the definitions it reports dead, and count those it found reached and,
under each reason, those it left unjudged.

**A definition is dead when no call and no use from another definition reaches it.** A call or a use counts from the
definition's own body only for something else: recursion alone, and for a type the members it owns, keep nothing
alive. A use counts beside a call, so a Go type that a declaration or a composite literal names is reached. A call
binds one definition, yet a build may link any other that the tier which bound it held equal, so it reaches every
definition of the bound one's qualified name: anywhere for a qualified call or a call through the receiver's type, in
the directory for a call bound through an import or a package, and in the file for a call bound in a file. A
declaration that several definitions implement links to none of them, so a call of it reaches each of them, and a call
of one of them reaches it. A type that another type names as a parent is reached.

**A call or a use at file scope keeps the name it spells.** It has no symbol to resolve from, so the graph used to drop
it; a script that calls its functions from its top level then had every one reported dead. Each file keeps the sorted
names of its file-scope calls and uses, and the graph indexes the files by those names, as it indexes includers (ADR
3.19). Such a name reaches every definition of it in its own file, in the files it includes, and where a package is a
directory, in its package.

**Only what the graph can see used is judged.** A function, a method and a macro are judged through their calls. A
type is judged only where the language records a use wherever code names one (`TypeUses::Every`), which Go states and
no other language does yet; elsewhere a type, a field, a value and a namespace are counted `unobservable`, as is any
definition local to a body, which its holder can pass or return where no use is recorded.

**What is not judged is counted under its reason, the first that holds:** a kind not asked for, test code, generated
code, an entry point, vendored code, and `unobservable`; then, for a definition no call reaches, `uncertain` and
`dispatched`. `uncertain` holds a definition that a call of its name may reach which binds no definition, binds one
only by proximity (below the unique tier), or binds its own caller through a value: a bare call any definition of the
name, and a call through a receiver a member, or a free definition that no member of the name could stand for or that
the call's file sees. `dispatched` holds a method that a call through another type may reach: one that an interface or
a trait declares a method of the name for, one that a parent of its owner declares too, and one of an owner with a
parent the graph does not hold.

**An entry point runs with no call that spells its name.** Each language marks its own: a program's `main`, a daslang
`def` that an annotation registers with what calls it, a Python special method or property of a class, which the
interpreter calls for an object it makes, a statement, an operator or an attribute read, and a C++ constructor,
destructor or operator, which the language calls for an object it makes or ends and for an expression. A minified
script beside its declaration file is generated code, since its renamed classes bind no call by name. These flags were
heuristics that only ranked answers; they now also decide what a dead-code answer leaves out, and it counts what they
left out.

**A query resolves each name once and judges every definition it covers.** A definition whose name no call and no use
spells is dead without a resolution, and the answer says so: `spelled` is false. Otherwise the call sites and uses of
the name are resolved once for the query, as `callers` resolves them, and every definition of the name is judged
against them. The query judges every definition in the files of its path prefix, so `total` and every count cover the
whole prefix, and `limit` bounds the list, not the work; a `limit` of 0 answers the counts alone.

**The answer** is `DeadCode`: `found`, at most `limit` dead definitions in path order and the order each file lists
them, each with its `Definition` and `spelled`; `total`, the dead before the limit; `live`, those judged and reached;
and `excluded`, the count under each reason above. A declaration and the definition it links to are one definition,
judged once.

**Revised 2026-10-18: a Go package's `func init()` is an entry point.** The runtime calls each one and no code can name
it, so every `init` judged read dead. On the Go monorepo 248 of the 1,716 dead Go definitions were an `init`; they and
1,307 vendored ones count under `entry`.

kartta reports a definition the reference does not in four cases, none of them a definition with a caller either side
resolves correctly:

- 416 on the C++ tree and 8 on the Go monorepo whose only caller in the reference is their own body, which kartta does
  not count: 253 C++, 111 Quirrel, 34 daslang, 10 Python and 8 JavaScript functions, and 2 C++ and 6 TypeScript.
- 411 DSHL macros, a language the reference does not read. 156 of them share a name with a macro that a library file
  defines through `define_macro_if_not_defined` and calls: a game that defines the macro first overrides the library's,
  so its own is used, while the graph binds the library's call to the library's definition. Those 156 are wrongly
  reported, and stay so until the extraction records a conditional definition as deferring to a namesake. Of the rest,
  the ones read are copies no file includes or macros no file calls.
- 2 C++ header declarations of functions that a stub and a real file both define, and so link to neither; both sides
  report both definitions, and the reference lists no unlinked declaration.
- 2 Python functions passed as a value, `parse_ecs_functions(..., is_es_name, ...)`, whose only caller in the
  reference is a call through a parameter of the same name, which kartta records as no call (ADR 3.12).

Of the edges, those read name real calls and uses, with one kind of exception: 12 JavaScript functions are reached
only by a call the cascade bound at the first-party tier, the one callable of the name outside vendored code, from an
unrelated project of the tree. Such a guess keeps its definition out of `found` as `live` rather than `uncertain`.

**A dead definition is a candidate, not a proof.** When this was decided no extraction recorded a function passed as a
value — a callback, an event handler, a script binding such as `.SquirrelFunc("calc_content_size", calc_content_size)`
— so such a function read dead. ADR 3.34 records it since for Go, Python, TypeScript and JavaScript; the other
languages still miss it, and the counts below are those of the decision. The dead functions whose own file names them
outside a call are 28,639 of 119,574 C++, 11,217 of 18,042 Quirrel, 614 of 2,785 daslang, 454 of 999 Python and 161 of
491 JavaScript on the C++ tree, and 2,100 of 4,114 TypeScript and JavaScript and 339 of 1,433 Go on the Go monorepo.
That count estimates the error and bounds it neither way: a name in a string or a key counts, and a function that
another file passes does not. Of the mentions read, most are callbacks and bindings. Recording such uses is an
extraction change in each language.

On the C++ tree the entry rules of Python and C++ moved 1,119 Python and 90,327 C++ definitions to `entry`, and the
dead count from 1,297 to 999 Python and from 173,138 to 119,574 C++: 10,544 destructors and 6,157 operators had been
reported dead, beside the constructors that no `new` names.

Cost, two runs of the reference's query sets at a load of 8 to 11: per graph the whole graph, and the ten top-level
directories that hold the most of its files. The reference stops at its default of 100 found and counts nothing; it
answers a whole graph in 7 to 13 µs.

- A whole graph: on the C++ tree, C++ 4.79–4.80 s, Quirrel 116–125 ms, daslang 62–63 ms, Python 17–18 ms and under 8
  ms each other graph; on the Go monorepo, Go 0.72–0.74 s, TypeScript 15–16 ms, Rust 6 ms and under 1 ms each other
  graph.
- A path prefix: p50 1.5 ms on the C++ tree and 0.14 ms on the Go monorepo; the slowest, C++ `prog/`, which holds most
  of the C++ graph, 4.36 s, and Go `.claude/` 0.68–0.74 s.
- The peak footprint of a process that builds and runs the whole set is 894 MB on the C++ tree and 552 MB on the Go
  monorepo, against 763–764 MB and 493–498 MB for the build alone: a whole-graph query holds the resolution of every
  name it judges until it answers.

Judging every definition is what the counts cost: a query that stops once it has listed 100 answers the whole C++
graph in 124 ms and the Go graph in 329 ms, and its counts cover only the files it read.

The build keeps the file-scope names, three interleaved runs against `main` at a load of 8 to 11: 3.77–3.79 s against
3.76–3.89 s on the C++ tree and 1.71–1.85 s against 1.79–1.81 s on the Go monorepo; the heap after the build 643.1 MB
against 634.1 MB and 298.5 MB against 296.9 MB, its peak 659.7 MB against 649.3 MB and 374.2–375.1 MB against
373.4–373.9 MB. The 9.0 MB on the C++ tree, 1.4% of the heap, keep out of the dead list the 21,521 definitions that a
file-scope call or use reaches and the reference reports dead.

## Considered Options

- **Count callers only, as the reference does** — a type, a field or a value that no call can reach reads dead: of
  the reference's 966,702 on the C++ tree, 506,478 are kinds no call reaches or locals.
- **Judge every kind** — where a language names types without recording a use, every type no call reaches reads dead.
- **Report what an uncertain call may reach as dead** — 127,300 definitions on the C++ tree that a call binding nothing
  certain may reach.
- **Mark Python special methods and C++ operators unobservable** — the same exclusion under a reason that says the
  graph cannot see them, where the runtime or the language calls them with no name; `entry` already carries that for
  `main` and for registered functions, and ranks them last among hotspots (ADR 3.22).
- **Stop once `limit` dead definitions are found** — 39 times faster on the C++ graph, but `total` and the exclusions
  would count only the files read, and a cut answer could not say how much it cut.
- **Resolve every call at the build and keep a reached flag** — ADR 3.7's trade: every build would pay for a query few
  ask.

Revisit when the language extractions record a function passed as a value, which removes most of the candidates the
dead list now holds in error, or when a consumer asks a whole large graph faster than the 4.8 s per-query resolution
takes on the C++ tree.
