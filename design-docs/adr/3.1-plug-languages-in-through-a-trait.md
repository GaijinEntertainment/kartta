# Plug languages in through a trait

- **Status:** accepted
- **Date:** 2026-10-16
- **Revised:** 2026-10-22
- **Initiative:** `03-code-graph`

The code graph is one language-agnostic structure — definitions, calls, references, includes — fed by many languages,
each with its own grammar and its own heuristics for what a name refers to. Where every language lives in one crate
behind one enum, adding a language means changing that crate, and the graph grows special cases for the languages it
was built around: what a Go package is, which extensions a TypeScript import may omit. kartta's graph is to know no
language, and a language kartta does not ship is to plug in without a change to kartta.

**A language is a value implementing `kartta_lang::Language`.** It names itself and its family — the languages whose
files resolve against each other in one graph, as TypeScript and JavaScript do — claims the files that are its, states
the fingerprint of what it extracts and the conventions its calls resolve under, extracts one file, and builds a
resolver for one build. The engine is handed the languages to build with; each of kartta's own is a crate of its own,
and anyone else's is one more crate against the same contract. `kartta-lang` holds the contract, the records it speaks
in, and the helpers that languages would otherwise each copy: path helpers, the scan of a generated-code banner, the
identity of a crate's source that its build script hands it, and behind a feature the tree-sitter walk helpers and the
fingerprint of a language that parses with a grammar; the contract names no parser.

**Extraction is split where a cache can share it.** `Language::extract` reads only the file's bytes and returns a
`RawExtraction`, so every file with the same content, in any tree, has the same one, and the per-file cache of ADR 2.2
computes it once under the language's fingerprint. Whatever depends on the path or the repository is recorded as a
directive and replayed by the `Resolver` the language builds over a read-only `Repository`: which file an import names,
whether the file is a test. A language that reads configuration — a `go.mod`, a `tsconfig.json` — reads it through the
repository when it builds its resolver.

**What the graph cannot infer is data the language states.** How a bare call reaches the members of the caller's own
type, whether a variable can be called, how an owner's chain of names is joined: these are `Conventions`, read by the
graph and never decided by a language's name. A concept only some languages have — a package whose files see each
other's names, a re-export, a declaration folded into its definition — is a channel of the extraction that a language
fills or leaves empty, so the graph implements it once for every language that uses it.

**Revised 2026-10-20: a graph hands out the conventions it was made with.** Which uses a language records is one of
them, and a consumer holding a graph says what its answers leave out from it rather than from a list of language names
of its own. `TypeUses::Nowhere` states that code names a type as one nowhere the language records a use, which Rust, C
and C++, TypeScript and JavaScript, PHP, Ruby, daslang and Puppet state, and `find_references` names such a language
on a type's match (ADR 4.1).

**Revised 2026-10-21: a language states its conventions as a `const`.** `Conventions` is `#[non_exhaustive]`, so a
field added to it breaks no language crate, and that rules out a struct literal and a `..` struct update outside
`kartta-lang`. `Conventions::DEFAULT` is the default as a `const`, and `Default` returns it. A language writes a `const`
block that copies it and assigns the fields it changes, which leaves a field added later at its default; each of
kartta's languages that changes one states them so. A `const fn` setter per field would do the same, but repeats every
public field as a method to keep in step with the struct, where the block assigns the fields themselves. Each
language's value is the one it built at run time, so the answers are identical on dagor and on the Go monorepo
snapshot, and nothing runs to build it.

**Revised 2026-10-22: a family resolves through one resolver.** The languages of one family build interchangeable
resolvers, so the engine asks only the first of a family's languages, in the order `Engine::build` was given them, for
the resolver every file of the family resolves through: the rule that already picks the conventions of the family's
graph. A family's first language builds it even when it claims no file the build read, as `typescript` does in a tree of
only `.tsx` files. Each of TypeScript, TSX and JavaScript read every `tsconfig.json` and `package.json` of the tree to
build its own; the family reads them once (ADR 3.4), and a followed engine keeps one configuration for it and names the
family when that changed (ADR 3.33). A language kartta does not ship still plugs in without a change to kartta: one that
names a family of its own is that family's first language, and one that joins a family states that it resolves that
family's files as its first language does.

**A language owns its fingerprint.** It has to change whenever what `extract` computes from the same bytes can change —
the grammar, the walk, the shape of the result — so a language derives it from those rather than keeping a version by
hand, and a cache keeps each fingerprint's extractions apart. The identity a crate's build script hands it digests the
crate's manifest, the versions a `Cargo.lock` above the crate resolves for its dependencies, and its sources, so an
update of the grammar crate or of tree-sitter changes it, whether the manifest's requirement or only the lock moved. A
build that sees no lock, such as one from a registry, follows the requirements alone. A grammar's own version metadata
does not suffice: in 2026-10 four of the fifteen grammars kartta ships (C++, Puppet, Ruby, TypeScript) carry none, and
Rust's said 0.24.1 in crate 0.24.2, so a bump that kept node types and table counts left the fingerprint, and every
cached extraction, as it was.

## Considered Options

- **A resolver for each language of a family, over a repository that reads each file once for all of them** — saves
  the reads, but still holds and compares a configuration for each language of the family, and needs a cache shared
  across their resolvers.
- **A resolver asked of the family through a method of its own** — every language crate would implement one more
  method, where the first of a family's languages already decides the family's conventions.

- **Every language in one crate behind an enum** — one place to change for a new language, and the graph's special
  cases grow from the languages it was built around.
- **Languages loaded at run time from shared libraries** — Rust has no stable binary interface, so the boundary would be
  a C one, unsafe on both sides and versioned by hand; only worth it if a host must take languages it was not built
  with.
- **Languages loaded at run time as WebAssembly modules** — safe and sandboxed, but every file's bytes are copied in and
  every extraction copied out, and a runtime comes with them.
- **Languages described by tree-sitter tag queries** — a grammar and a query file give a language its definitions and
  calls with no code, but not the resolution of its imports or the heuristics a receiver needs; it fits as one more
  language crate under this contract, not in place of it.

Revisit when a host needs languages it was not compiled with.
