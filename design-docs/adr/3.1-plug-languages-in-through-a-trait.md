# Plug languages in through a trait

- **Status:** accepted
- **Date:** 2026-10-16
- **Initiative:** `03-code-graph`

The code graph is one language-agnostic structure — definitions, calls, references, includes — fed by many languages,
each with its own grammar and its own heuristics for what a name refers to. Where every language lives in one crate
behind one enum, adding a language means changing that crate, and the graph grows special cases for the languages it
was built around: what a Go package is, which extensions a TypeScript import may omit. kartta's graph is to know no
language, and a language kartta does not ship is to plug in without a change to kartta.

**A language is a value implementing `kartta_lang::Language`.** It names itself and its family — the languages whose
files resolve against each other in one graph, as TypeScript and JavaScript do — claims the files that are its, states
the fingerprint of what it extracts and the conventions its calls resolve under, extracts one file, and builds a
resolver for one build. The engine is handed the languages to build with; each of kartta's own is a crate of its own,
and anyone else's is one more crate against the same contract. `kartta-lang` holds only the contract, the records it
speaks in, path helpers, and behind a feature the tree-sitter walk helpers; it names no parser.

**Extraction is split where a cache can share it.** `Language::extract` reads only the file's bytes and returns a
`RawExtraction`, so every file with the same content, in any tree, has the same one, and the per-file cache of ADR 2.2
computes it once under the language's fingerprint. Whatever depends on the path or the repository is recorded as a
directive and replayed by the `Resolver` the language builds over a read-only `Repository`: which file an import names,
whether the file is a test. A language that reads configuration — a `go.mod`, a `tsconfig.json` — reads it through the
repository when it builds its resolver.

**What the graph cannot infer is data the language states.** How a bare call reaches the members of the caller's own
type, whether a variable can be called, how an owner's chain of names is joined: these are `Conventions`, read by the
graph and never decided by a language's name. A concept only some languages have — a package whose files see each
other's names, a re-export, a declaration folded into its definition — is a channel of the extraction that a language
fills or leaves empty, so the graph implements it once for every language that uses it.

**A language owns its fingerprint.** It has to change whenever what `extract` computes from the same bytes can change —
the grammar, the walk, the shape of the result — so a language derives it from those rather than keeping a version by
hand, and a cache keeps each fingerprint's extractions apart.

## Considered Options

- **Every language in one crate behind an enum** — one place to change for a new language, and the graph's special
  cases grow from the languages it was built around.
- **Languages loaded at run time from shared libraries** — Rust has no stable binary interface, so the boundary would be
  a C one, unsafe on both sides and versioned by hand; only worth it if a host must take languages it was not built
  with.
- **Languages loaded at run time as WebAssembly modules** — safe and sandboxed, but every file's bytes are copied in and
  every extraction copied out, and a runtime comes with them.
- **Languages described by tree-sitter tag queries** — a grammar and a query file give a language its definitions and
  calls with no code, but not the resolution of its imports or the heuristics a receiver needs; it fits as one more
  language crate under this contract, not in place of it.

Revisit when a host needs languages it was not compiled with.
