# Judge code dead only where the graph sees it used

- **Date:** 2026-10-17
- **Governs:** `crates/kartta-graph/src/dead.rs`, `crates/kartta-graph/src/calls.rs` (`is_called_uncertainly`,
  `is_used_uncertainly`), `Graph::dead_code`, `DeadCode`, `Excluded`, `SymbolFlags::is_fallback`
- **Pinned by:** `crates/kartta-graph/tests/graph/dead_code.rs`, `crates/kartta-mcp/tests/graph.rs`
  (`find_unused_counts_a_method_a_library_interface_declares_as_dispatched`,
  `find_unused_reads_what_an_asserted_interface_may_hold_past_the_graph`)

An agent that cleans up a tree asks which definitions nothing reaches, and much of what keeps code alive is no call the
extraction records: a runtime that starts `main`, an operator an expression calls, a caller outside the repository. A
definition reported dead that something uses costs the agent a wrong deletion, one left out costs it a candidate, so
the query judges only what the graph can see used and counts what it leaves out under each reason.

## Decision

- **What reaches a definition.** A definition is dead when no call and no use from another definition reaches it; a
  use counts as a call does. These reach it besides:
  - A call or a use from its own body does not, and for a type, neither does one from a member it owns: recursion
    alone and a method's receiver keep nothing alive.
  - A call binds one definition, yet a build may link any other that the binding tier held equal, so it reaches every
    definition of the bound one's qualified name as far as that tier reaches: anywhere, in the bound one's directory,
    or in its file, by tier as [`Graph::dead_code`](/crates/kartta-graph/src/dead.rs) states. A call bound at the
    one-callable tier (60) or below reaches only what it bound.
  - A declaration that several definitions implement links to none of them, so a call of it reaches each definition
    whose file reaches the declaration's, and a call of one of them reaches the declaration.
  - A type that another type names as a parent is reached.
  - A call or a use made at file scope reaches what its name spells
    ([ADR 3.112](/design-docs/adr/3.112-file-scope-names.md)).
- **What is judged.** A function, a method and a macro are judged through their calls. A type is judged only where the
  language records a use wherever code names one (`TypeUses::Every`), and a field, a variable and a constant only where
  it records one wherever code reads or writes one ([ADR 3.110](/design-docs/adr/3.110-data-dead-code.md)). Elsewhere
  those kinds are `unobservable`, as are a namespace, an enum variant and any definition local to a body, which no use
  binds, so its holder can pass or return it unseen. A declaration and the definition it links to are one definition,
  judged once.
- **The reasons.** A definition is counted under the first reason that holds and is not judged: a kind not asked for,
  `test`, `generated`, `entry`, `vendored`, `unobservable`. A judged one that something reaches is `live`. One nothing
  reaches is then `reflected` ([ADR 3.187](/design-docs/adr/3.187-reflected-definitions.md)), `uncertain` or
  `dispatched`, in that order, and dead only where none holds. [ADR 3.111](/design-docs/adr/3.111-entry-points.md)
  states the entry marks.
  - **`uncertain`:** a call of the name may reach it that binds no definition, binds one only below the one-callable
    tier (60), binds a fallback, or binds its own caller through a value; the docs of
    [`Excluded`](/crates/kartta-graph/src/dead.rs) state which definitions a bare call and a call through a receiver
    may reach. [ADR 3.110](/design-docs/adr/3.110-data-dead-code.md) adds the uses that leave data uncertain. A use the
    tiers leave ambiguous among members of every kind, as one on a value whose type the graph cannot follow, may reach
    any member of the name, a method among them; one they leave ambiguous among fields alone, as a C++ member read
    without a call, reaches no method.
  - **A fallback** is a definition a build makes only where it holds none of the name (`SymbolFlags::is_fallback`);
    DSHL marks each `define_macro_if_not_defined`. A call bound to one stays an edge, so the fallback is live through
    it, and leaves its namesakes `uncertain`; `callers` of a namesake lists no caller.
  - **`dispatched`:** a method that a call through another type may reach: one whose name an interface or a trait
    other than its owner declares a method of, one whose owner's direct parent declares a method of the name, and one
    whose owner has a parent the graph does not hold. An interface's or a trait's own method is not `dispatched` by its
    own declaration: nothing reached, it is dead unless another interface or trait declares one of its name.
  - **`dispatched` in a directory package.** Go names a type per package and implements an interface by shape, so:
    - A method's owner is an interface only where the method's own file declares one of the name, because a Go
      interface spells its methods inside its declaration (`doc/go_spec.html`, Interface types).
    - A parent, and the interface an assertion names, is the type the writing file reaches
      ([ADR 3.20](/design-docs/adr/3.20-implementor-resolution.md)). A name that leaves the graph may declare any
      method, and so may a type that embeds another, an alias and a defined type, which may hold an interface's methods
      they do not spell (`doc/go_spec.html`, Embedded interfaces, Alias declarations, Type definitions).
    - A type's method whose name `Conventions::library_interface_methods` lists is `dispatched`: the standard library
      may call it. An interface's own method is not, since the library runs what implements its interface.
- **The query and its answer.** The call sites and uses of each name judged are resolved once for the query, as
  `callers` resolves them. The query judges every definition in the files of its path prefix, so `total` and every
  count cover the whole prefix, and `limit` bounds the list, not the work; a `limit` of 0 answers the counts alone. The
  answer is `DeadCode`, whose fields list at most `limit` dead definitions in path order and the order each file lists
  them, each with `spelled`, false where nothing the graph holds spells the name, and count the dead before the limit,
  the live and the excluded under each reason. [ADR 4.24](/design-docs/adr/4.24-mcp-omission-counts.md) renders it as
  `find_unused`.
- **A dead definition is a candidate, not a proof.** A call the graph cannot resolve, a function passed as a value
  where the language records no use ([ADR 3.34](/design-docs/adr/3.34-field-and-value-uses.md) lists where it records
  one), or a caller outside the repository reaches it unseen.

## Why

- A call bound by nearness or not at all names no definition the graph can trust, so a namesake it may reach is no
  candidate; one bound with certainty does, and its tier says how far the build could have linked another copy.
- A method that a call through an interface, a trait or a base may reach is called with no name the graph binds to it.
- The standard library is outside the graph, and Go lets a type implement its interfaces without naming them
  (`doc/go_spec.html`, Implementing an interface), some spelled only inside a function (`src/errors/wrap.go:15`). All 26
  methods the table takes off the lists of the Go monorepo snapshot, this repository and the game-engine tree implement
  a library interface, 12 of them `sort.Interface` (2026-11-01, #950).
- `spelled` tells an agent whether the graph saw any call or use of the name at all, before it reads the code.
- A fallback's call runs whatever the build defined first, which the repository does not record: 156 of 411 dead DSHL
  macros were a game's hook a library's fallback stands for (C++ game-engine tree, 2026-10-19).
- A field, a variable and a constant stay `unobservable` outside Go because too much of what a language's uses would
  call dead is used. Really dead, of 30 sampled per kind and tree set, on a scratch build that judges them
  (2026-10-31, #450):
  - C++ on the game-engine tree: 14 fields, 8 constants and 7 variables; in a second sample of 30 fields, from its own
    code outside its third-party libraries, 15.
  - TypeScript and JavaScript on the Go monorepo snapshot and SillyTavern: 2 fields, 0 constants and 2 variables.
  - Python, which extracts no constant, on the game-engine tree: 3 fields and 12 variables; on a build-tool tree,
    daScript and the small trees: 7 fields and 17 variables.

## Consequences

- The query resolves every call and use that spells a judged name, so a whole graph costs what resolving its calls
  costs, 4.8 s for the C++ graph of the C++ game-engine tree (2026-10-17, #59), and holds every judged name's
  resolution until it answers. Accepted.
- A call that a far tier guesses keeps its definition `live` rather than `uncertain`: a JavaScript function reached only
  by a first-party-tier guess from an unrelated project stays out of `found`. Accepted.
- A method that a use on an untyped value spells is `uncertain` even where the use means a namesake's member: 82% of
  105 sampled methods the rule takes out of `found` are used (game-engine tree and Go monorepo snapshot, 2026-10-23).
  Accepted.
- A Go type's unreached method named like a library interface's reads `dispatched` whatever its signature, as one of a
  type that lacks the interface's other methods does: none of the 26 methods the table moved on the three Go trees
  (2026-11-01, #950). Accepted.
- A Go method whose interface embeds, or is an alias or a defined type, reads `dispatched` though the tree may hold the
  whole interface: no definition on the three trees, whose assertions name no alias or defined type
  (2026-11-01, #950). Accepted.
- A Go method of a struct that embeds a type outside the graph reads `dispatched` though only an interface dispatches:
  one unused method of a struct over `http.Server`, the one wrong of 15 definitions leaving the lists (Go monorepo
  snapshot, 2026-11-01, #979).
- A function passed in a form its language records no use for reads dead. Before any extraction recorded a function
  taken as a value, 28,639 of 119,574 dead C++ functions on the C++ game-engine tree were named outside a call in their
  own file (2026-10-17, #59), an estimate that bounds the error neither way.

## Rejected

- **Count callers only** — a type, a field or a value that no call can reach reads dead.
- **Judge every kind** — where a language names types without recording a use, every type no call reaches reads dead.
- **Report what an uncertain call may reach as dead** — 127,300 definitions on the C++ game-engine tree that a call
  binding nothing certain may reach (2026-10-17).
- **Count every ambiguous use as reaching any member** — takes 1,144 C++ methods out of `found` on the C++ game-engine
  tree, most of them unused, for field reads that cannot name a method (2026-10-23).
- **Count an ambiguous use only for members its file reaches** — keeps 56 of 65 C++ methods taken as values listed,
  bound from files that include only their declaration (2026-10-23).
- **Stop once `limit` dead definitions are found** — answers the C++ graph in 124 ms against 4.8 s (2026-10-17), but
  `total` and the reasons would count only the files read, and a cut answer could not say how much it cut.
- **Resolve every call at build and keep a reached flag** — the trade of
  [ADR 3.7](/design-docs/adr/3.7-call-resolution.md): every build would pay for a query few ask.
- **A call edge from a fallback's call to each namesake** — which one runs depends on what the build defines first.
- **Match a library method's signature too** — the name alone moved no method wrongly on the three Go trees, so a
  comparison of written signatures with their spellings of imported types pays for nothing (2026-11-01, #950).
- **List the interfaces of `internal` and `vendor` packages** — 39 more names no other package can name, mostly
  `net/http`'s HTTP/2 adapters, which would take 2 `Span` methods off the game-engine tree's list (2026-11-01, #950).
- **List interfaces with an unexported method** — no other package's type declares it (`doc/go_spec.html`, Uniqueness
  of identifiers), and a struct that embeds one has a parent the graph does not hold.
- **Walk a Go type's embedded types, aliases and defined types to what they hold** — moved no definition on the three
  Go trees, for a loop and a list per read (2026-11-01, #950).

## Revisit if

A sample of the dead list finds most of it used through a form no extraction records, a name in a string or a table
key among them, so that the answer needs a new kind of use before it lists candidates worth deleting. Medium
confidence: [ADR 3.34](/design-docs/adr/3.34-field-and-value-uses.md) records a function taken as a value in most
shipped languages, and no sample of the dead list has been read since. A Go release that adds a library interface
reopens `library_interface_methods`, whose table states the release it was read from.
